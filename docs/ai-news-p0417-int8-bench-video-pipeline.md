## 1. 背景

### 1.1 int8 最適化とは

機械学習モデルの推論において、重みと活性化を fp16（16ビット浮動小数点）や fp32 から int8（8ビット整数）に精度を落とす量子化手法。主な効果:

| 指標 | fp16 | int8 | 削減率 |
|------|-----:|-----:|-------:|
| メモリ使用量（重み） | 2 bytes/param | 1 byte/param | **50%** |
| 推論速度（演算スループット） | 1x 基準 | 2〜4x | **200〜400%** |
| 品質劣化 | 基準 | 微減（0.1〜1%程度） | 許容範囲 |

### 1.2 なぜ今 int8 か

- **画像生成モデルの巨大化**: Genspark・Stable Diffusion・FLUX 等のモデルは数GB〜数十GBの重みを持ち、VRAM消費が課題
- **エッジ推論の需要**: ローカルGPU（RTX 3060 12GB / RTX 4060 Ti 16GB）でも高品質生成を可能にするには量子化が事実上の必須技術
- **Genspark の対応**: Genspark API は一部モデルで int8 最適化をサポートしており、`--precision int8` 相当のフラグで利用可能

### 1.3 現在の画像生成パイプライン

現在の生成経路（`tools/image-gen.mjs`）:

```
ユーザープロンプト → Genspark CLI (gsk) → 画像URL → ダウンロード
```

- 既定モデル: `nano-banana-2-flash-lite`
- Genspark は内部的に最適化を行っているが、int8 の明示的指定が可能か未検証
- 動画生成には未対応（静止画のみ）

## 3. ベンチマークツール設計

### 3.1 `tools/int8-bench.mjs`

```javascript
// 使用方法: node tools/int8-bench.mjs [--precision int8|fp16|auto] [--model <id>] [--prompt "<text>"] [--video] [--count <n>]
// 出力: benchmark-results-{date}.json（経過時間・VRAM・品質スコア）
```

### 3.2 実装方針

1. `tools/image-gen.mjs` をベースに精度指定オプションを追加
2. 各テストケースを n 回実行（n≥3）し、平均・中央値・標準偏差を記録
3. VRAM使用量は `nvidia-smi --query-gpu=memory.used --format=csv,noheader` で取得（Windows は `nvidia-smi`）
4. 品質評価は CLIP スコア（`clip-score` npm パッケージまたは API）と人間評価の両方
5. 結果は CSV と JSON の両方で出力

### 3.3 ファイル構成

| ファイル | 役割 |
|---------|------|
| `tools/int8-bench.mjs` | ベンチマーク本体 |

### 4.1 統合条件（効果確認の閾値）

int8 最適化を本番適用する条件:

| 条件 | 閾値 | 測定方法 |
|------|------|---------|
| 生成速度向上 | fp16 比 **1.5x以上** | 平均生成時間の比較 |

## 5. リスクと対策

| リスク | 影響 | 確率 | 対策 |
|-------|------|------|------|
| int8 で品質低下大 | 統合不可 | 低 | fp16 維持、他の最適化手法を検討 |
| Genspark が int8 未サポート | ベンチマーク不可 | 中 | OpenRouter の量子化モデルで代替 |
| VRAM 測定が不安定 | データ不正確 | 中 | 複数回測定 + 統計処理 |
| 動画生成モデルが未利用 | 動画パイプライン構築不可 | 高 | 静止画生成の最適化に限定して価値を出す |
