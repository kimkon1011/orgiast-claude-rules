# X-0012: AIコーディングの検証可能な再現ワークフロー — 5コンポーネント構成と実ブラウザ検証

観測日: 2026-11-09。出典: AIニュース提案 [X-0012]。
本稿は、AIによるコード生成・修正において「人間が確認しなくても正しく動くと確信できる」状態を得るための**検証可能な再現ワークフロー**を提案する。オージャストの展示会出展受付サイト（`expo-apply`）の予約フローを具体例として、ユニットテストだけでなく実ブラウザ検証を通して品質を担保する手順を定義する。

---

## 従来の課題

| 問題 | 説明 | 結果 |
|------|------|------|
| AIが生成したコードの動作確認が属人化している | 「目で見て大丈夫そう」で終わるか、カバレッジの低いユニットテストだけ | 本番で壊れていることに気づくのが遅れる |
| 修正のたびに同じ検証を手動で繰り返す | 再現手順が頭の中やローカル環境にしかない | 再発防止策が機能せず、同じバグが再び混入する |
| 検証の証拠が散逸する | 「試した」「動いた」という主張だけで客観的証拠がない | 複数人での品質判断ができず、都度フルリグレッションが必要 |
| AIの修正が予期せぬ副作用を生む | 直した箇所以外が壊れていても、テストが通れば気づかない | リリース後にユーザーから報告されて発覚する |

## 提案: 5コンポーネント検証可能再現ワークフロー

```
             ┌──────────────┐
             │   Planner    │  タスク分解・設計
             │ (プランナー) │
             └──────┬───────┘
                    │ 指示
                    ▼
             ┌──────────────┐
             │   Worker     │  実装実行
             │ (ワーカー)   │
             └──────┬───────┘
                    │ 成果物
                    ▼
             ┌──────────────┐
             │  Verifier    │  実ブラウザ検証
             │ (検証者)     │  （ユニットテスト＋α）
             └──────┬───────┘
                    │ 結果
                    ▼
   ┌────────────┐  ┌──────────────┐
   │Recovery    │←│  Evidence    │
   │Controller  │  │  Ledger     │
   │(リカバリー)│  │ (証拠台帳)   │
   └────────────┘  └──────────────┘
```

5つのコンポーネントが直列・並列に連携し、各フェーズの成果物と検証結果が証拠台帳に自動記録される。失敗時はリカバリーコントローラーが原因特定→再試行orエスカレーションを判断する。

### 1. Planner（プランナー）

**責務**: タスクの分解・設計・実装指示の生成。

| 項目 | 内容 |
|------|------|
| 入力 | 課題記述（例: 「予約フォームのバリデーションを追加」） |
| 出力 | ファイル単位の実装指示 + 検証シナリオ |
| 判断基準 | 既存コード構造・依存関係・影響範囲 |
| 使用AI | Opus / Fable（設計品質を優先） |

**設計原則**:
- 変更は最小単位に分解し、各単位で「実装→検証→記録」が完結する
- 副作用の可能性がある箇所を明示する（「この変更はXXXに影響する可能性がある」）
- 検証シナリオには**ユニットテストと実ブラウザ操作の両方**を含める
- 実装指示はコードだけではなく、「変更前後の状態」「ロールバック手順」を含む

### 2. Worker（ワーカー）

**責務**: Plannerの指示に従い、コードを実装する。

| 項目 | 内容 |
|------|------|
| 入力 | ファイル単位の実装指示 |
| 出力 | 変更されたコード + ユニットテスト |
| 使用AI | Codex / Sonnet（実装速度を優先） |
| 制約 | Plannerの指示範囲を超えない。副作用が発生したら停止して報告 |

**実行ルール**:
- 1指示につき1ファイルの変更を基本とする
- 変更前に`git diff --stat`で現状を記録する
- 変更後に`node --check`での構文チェックを必須とする
- 変更ファイルのみを`git add <pathspec>`する（`git add -A`禁止）
- ユニットテストを`node --test`で実行し、通過を確認する

### 3. Verifier（検証者）

**責務**: Workerの成果物を、ユニットテストと実ブラウザ検証の両方で確認する。

| 項目 | 内容 |
|------|------|
| 入力 | 変更されたコード + 検証シナリオ |
| 出力 | PASS/FAILの判定 + 証拠（スクリーンショット・コンソールログ） |
| 使用AI | コード検証は静的解析、UI検証はPlaywright/ヘッドレスブラウザ |

**検証の2層構造**:

#### Layer 1: ロジック検証（ユニットテスト）
- `node --test`の全テスト通過
- 既存テストとの退行がないこと
- 新規テストが意図した動作をカバーしていること

#### Layer 2: 実ブラウザ検証（Playwright / Puppeteer）
- 実際のブラウザで画面を描画し、DOM・CSS・フォントの実表示を確認
- フォーム入力→送信→完了画面の一連のユーザーフローを自動操作
- エラー状態（バリデーション・ネットワーク断・空データ）も網羅
- スクリーンショットを証拠として保存

**適用例: expo-applyの予約フロー検証シナリオ**:

| # | シナリオ | 操作 | 期待結果 | 検証方法 |
|---|---------|------|---------|---------|
| 1 | 正常入力→送信 | 全項目を正しく入力→送信ボタン | 受付番号表示・localStorageに保存 | Layer2: 実操作 + スクショ |
| 2 | 必須項目未入力 | 空欄で送信 | 該当項目直下にエラーメッセージ | Layer2: 実操作 + エラー表示確認 |
| 3 | メールアドレス形式誤り | `xxx` と入力→送信 | メール形式エラー表示 | Layer2: 実操作 |
| 4 | 最大文字数超過 | 会社名に1000文字入力→送信 | バリデーションエラー | Layer2: 実操作 |
| 5 | 言語切替 | 日本語⇔英語切替 | ラベル・エラーメッセージが切替わる | Layer1: DOM検証 / Layer2: 実操作 |
| 6 | localStorage保存確認 | 送信後→リロード | データが維持される | Layer1: Storage API検証 |
| 7 | CSVエクスポート | データ登録後→CSV出力 | 正しいCSV形式で出力される | Layer1: 出力検証 |
| 8 | 管理画面ステータス変更 | 新規→連絡済みに変更 | ステータスが更新される | Layer2: 実操作 |

### 4. Recovery Controller（リカバリーコントローラー）

**責務**: VerifierがFAILを報告した場合、原因を特定し、再試行 or エスカレーションを判断する。

| 状態 | 判断 | アクション |
|------|------|-----------|
| ユニットテスト失敗 | 再試行 | エラーメッセージをWorkerに渡して修正 |
| ブラウザ検証失敗（既知の環境問題） | 再試行 | 環境前提条件を確認して再実行 |
| ブラウザ検証失敗（ロジックバグ） | 再試行 | Verifierの証拠をWorkerに渡して修正 |
| 3回連続失敗 | エスカレーション | 人間の介入を依頼 + ここまでの証拠を台帳に保存 |
| 予期せぬ副作用（変更範囲外のテスト失敗） | 中断 | Plannerに戻して影響範囲の再評価 |

**リトライルール**:
- リトライには**理由と新しい証拠**が必須。同じ証拠で同じ修正を繰り返さない
- リトライ回数は最大3回。超過時は自動停止し、証拠台帳に記録して人間にエスカレーション
- リトライのたびに証拠台帳に追記し、何を変えたか・なぜ変わったかを記録する

### 5. Evidence Ledger（証拠台帳）

**責務**: ワークフローの全フェーズの入出力・検証結果・判断根拠を構造化して保存する。

**証拠台帳のスキーマ**:

```json
{
  "workflowId": "wf-20261109-x0012-001",
  "timestamp": "2026-11-09T13:00:00Z",
  "phase": "plan | implement | verify | recover",
  "component": "planner | worker | verifier | recovery",
  "input": { /* このフェーズへの入力 */ },
  "output": { /* このフェーズの成果物 */ },
  "evidence": [
    {
      "type": "screenshot | log | test_result | diff",
      "path": "evidence/xxx.png",
      "hash": "sha256:...",
      "description": "操作説明"
    }
  ],
  "verdict": "pass | fail | deferred",
  "cost": { "tokens": 1234, "duration_ms": 5678 }
}
```

**保存場所**: プロジェクトルートの `evidence/` ディレクトリに時系列で蓄積する。

**証拠台帳の役割**:
- 全フェーズの判断と結果が遡れる（「なぜこのコードになったか」の監査証跡）
- 再実行時に同じ条件で検証を再現できる
- 複数人でのレビューが可能（「このスクリーンショットは正常動作を確認したもの」と示せる）
- コスト計測（トークン消費・実行時間）と品質の相関を分析できる

## 適用例: expo-apply 予約フロー

### 現状の課題

展示会出展受付サイト（`apps/expo-apply/`）は以下の特徴を持つ:

- 保存先はlocalStorageのみ（外部API不使用）
- 多言語対応（英語⇔日本語）
- 1枚のHTML＋JSで完結するSPA
- テストはユニットテストのみ（`expo-apply.test.mjs`）で、ブラウザ検証は手動

この構成では以下のリスクがある:
1. ブラウザ固有の挙動（localStorageの容量制限・DOMレンダリングの差異）をテストで捕捉できない
2. 言語切替のUI表示が正しいか（ラベルが欠落していないか）を自動確認できない
3. CSSの崩れ・フォント表示の異常を検出できない
4. 修正のたびに人間がブラウザを開いて確認する必要がある

### 5コンポーネント適用の流れ

**シナリオ: 「予約フォームに電話番号入力欄を追加する」**

#### Phase 1: Plan（2ターン以内）

Plannerが以下を設計:
- 変更ファイル: `apps/expo-apply/expo-apply-core.mjs`（データモデル・バリデーション）, `apps/expo-apply/index.html`（UI）
- データモデル: `phone` フィールドを追加
- バリデーション: 日本/海外の電話番号形式に対応（国際番号許容）
- UI: フォームに「電話番号（任意）」欄を追加、言語切替対応
- 既存テストへの影響: テストデータに `phone: ""` を追加する必要あり
- 検証シナリオ:
  1. ユニットテスト: 電話番号バリデーションの正常系・異常系
  2. ブラウザ検証: フォーム表示→入力→送信→localStorage確認の一連フロー

#### Phase 2: Implement（Worker）

Workerが以下を実装:
1. `expo-apply-core.mjs` の `validateExpoApplication` に電話番号バリデーションを追加
2. `index.html` に電話番号入力フィールドを追加（日本語/英語両方のラベル）
3. `expo-apply.test.mjs` に電話番号テストケースを追加
4. `node --check` で構文チェック
5. 既存テスト全件通過を確認

#### Phase 3: Verify（Verifier）

**Layer 1: ユニットテスト**
```sh
node --test apps/expo-apply/test/expo-apply.test.mjs
```
期待: 既存テスト + 新規テストがすべてpass

**Layer 2: 実ブラウザ検証**

検証項目:
1. 電話番号フィールドがフォームに表示されること
2. 任意項目なので空欄で送信できること
3. 不正な電話番号形式（英字混入等）でエラーが出ること
4. 正しい電話番号（`03-1234-5678`, `+81-90-1234-5678`）が保存されること
5. 日本語表示で「電話番号（任意）」、英語表示で"Phone (optional)"と表示されること
6. localStorageに `phone` フィールドが正しく保存されること

検証コマンド（ヘッドレスブラウザ）:
```sh
node tools/browser-verify.mjs --url http://localhost:8000/apps/expo-apply/ \
  --scenario docs/evidence/scenarios/expo-apply-phone-field.json \
  --screenshot evidence/x0012-phone-field-001.png
```

#### Phase 4: Record（Evidence Ledger）

全フェーズの結果を証拠台帳に記録:
```json
{
  "workflowId": "wf-20261109-expo-apply-phone",
  "phases": [
    {
      "phase": "plan",
      "component": "planner",
      "output": "design doc (docs/plans/x0012-phone-field-plan.md)",
      "verdict": "pass"
    },
    {
      "phase": "implement",
      "component": "worker (codex)",
      "output": ["expo-apply-core.mjs", "index.html", "expo-apply.test.mjs"],
      "testResult": "15/15 pass",
      "verdict": "pass"
    },
    {
      "phase": "verify",
      "component": "verifier (browser)",
      "evidence": ["screenshot-001.png (フォーム表示)", "screenshot-002.png (入力後)", "screenshot-003.png (エラー表示)", "screenshot-004.png (送信完了)"],
      "verdict": "pass"
    }
  ],
  "totalCost": { "tokens": 45000, "duration_ms": 120000 }
}
```

#### Phase 5: Recover（必要な場合のみ）

Verifierで失敗した場合:
- 1回目: エラーメッセージ付きでWorkerに修正指示 → 例: 「電話番号バリデーションが国際番号の`+`記号を許容していない」
- 2回目: 同じ検証を再実行 → 改善を確認または異なる原因を特定
- 3回目: 人間にエスカレーション → 証拠台帳の全記録を添付

## 既存の関連ワークフローとの比較

| 特徴 | 従来のCI/CD | 提案ワークフロー |
|------|-----------|----------------|
| テスト | ユニットテスト + E2E（CI上） | ユニットテスト + 実ブラウザ（手元 or CI） |
| 証拠 | テスト結果のログのみ | スクリーンショット + 操作ログ + 構造化台帳 |
| 失敗時 | CI通知 + 手動デバッグ | Recovery Controllerが自動原因特定 + 再試行判断 |
| 再現性 | CI環境が不定 | 証拠台帳により同じ条件で再実行可能 |
| コスト計測 | なし | フェーズごとのトークン・時間を記録 |
| 多人数判断 | ログを見て各自判断 | 証拠台帳で統一的な判断基準 |

## 課題と対策

| 課題 | 対策 |
|------|------|
| ブラウザ検証の実行時間（1シナリオ10〜30秒） | 変更範囲に応じて検証シナリオを選択実行する。全件実行は夜間バッチに回す |
| ヘッドレスブラウザの環境依存（フォント・OS差） | Dockerで統一環境を用意。フォールバックとしてスクリーンショット目視確認手順を文書化 |
| 証拠台帳の容量肥大化 | スクリーンショットは7日で自動圧縮、台帳は月次ローテーション |
| リカバリーコントローラーの誤判断（無駄な再試行） | コスト上限を設定（例: 1ワークフローあたり$5上限）。超過時は自動停止 |

## 結論

AIコーディングの検証可能な再現ワークフロー（5コンポーネント構成）は、以下の3点を同時に達成する:

1. **検証の自動化**: ユニットテスト＋実ブラウザ検証の2層で、人間の目視確認を不要にする
2. **証拠の構造化**: 全フェーズの判断と結果を証拠台帳に記録し、監査と再現を可能にする
3. **失敗からの学習**: リカバリーコントローラーが失敗原因を特定し、同じ過ちを繰り返さない仕組みを作る

オージャストの`expo-apply`予約フローへの適用を通じて、このワークフローの有効性を実証し、他の案件（ラハイナ宿泊予約、212coffee貸しスペース予約、Makuake納品フロー）へ横展開する。
