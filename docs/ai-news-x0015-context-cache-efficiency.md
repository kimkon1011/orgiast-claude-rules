# X-0015: コンテキストキャッシュ効率化で消費を何分の1に削減

> 2026-11-10 包括版。静的配置・長期記憶隔離・Daily.md自動化・Idle compaction制御・
> 人間AI役割分担・Worktree制限の6軸でキャッシュ消費を**1/5〜1/10**に削減する設計。
> オージャストのブース提案フローへの適用手順と実測計画を含む。

## 1. 概要: 「キャッシュ効率化」の全体像

プロンプトキャッシュのコスト削減は「1つのテクニックで完了」ではなく、
**複数の独立した軸の積み上げ**で初めて1/5〜1/10の削減が現実的になる。

```
削減の6軸:
  ① 静的先頭配置（P=〜300トークン）     → −60〜68%
  ② 長期記憶フォルダ隔離（検索のみ）     → コンテキスト0消費
  ③ Daily.md 自動日報（参照設定）         → 繰り返し説明ゼロ
  ④ Idle compaction=false                 → 無駄な再計算防止
  ⑤ 人間/AI役割分担（5:3:1+確認項目）    → AI消費量 〜1/2
  ⑥ Worktree最大3制限                     → 並列コンテキスト分散防止
```

各軸は独立して効くため、**積み上げ式に効果が乗算される**。
本稿は①を除く②〜⑥を詳述する（①は姉妹記事 `docs/ai-news-x0015-static-prefix-placement.md` 参照）。

## 2. 長期記憶フォルダ隔離 — 能動読込禁止で検索のみ

### 原理

Claude Code の `--memory` ディレクトリやプロジェクトフォルダに過去完了案件を保存すると、
セッション起動時にその内容が自動ロードされてコンテキストを消費する。

**対策:** 長期記憶フォルダは「AI能動読込禁止」に設定し、人間が明示的に参照指示したときだけ
Grep/検索（`Grep` ツールや `WebSearch`）で必要な情報を取り出す方式にする。

### 実装

```
~/.claude/memory/archived/        ← このフォルダは AI 自動読込対象外
  ├── case-C0056-booth-proposal/  ← 案件ごとにサブフォルダ
  │   ├── spec.md                  ← 仕様書（構造化）
  │   ├── design.md                ← デザイン決定事項
  │   ├── materials.md             ← 使用部材・コスト
  │   └── lessons.md               ← 教訓（次の案件に活かす）
  └── ...
```

- Claude Code は `~/.claude/memory/` 全体を自動読込するが、`archived/` 下は **スキップ**
- 検索専用: 人間が「過去のC0056案件の教訓を参照して」と指示したときのみ `Grep` で読む
- `CLAUDE.md` や `rules/` に「長期記憶フォルダは検索のみ・自動読込禁止」と明記

### 効果

| 項目 | 効果 |
|---|---|
| 起動時コンテキスト | 完了案件分のトークン消費ゼロ（案件5件で〜5,000トークン節約） |
| 参照品質 | 必要なときだけGrep検索 → 取得精度は低下せず |
| メンテナンス | 完了案件を `archived/` に移動するだけ |

### オージャスト適用: ブース設計過去案件

```
~/.claude/memory/archived/booth/
  ├── C0056-re-booth/         ← Re:ブース提案の全資料
  ├── C0057-sankyo-seiki/     ← 三共精機ブース提案
  ├── specs-common.md         ← 共通仕様（小間・パネル・照明・安全基準）
  └── equipment-inventory.md  ← 保有機材一覧
```

新規イベント企画時に：
```
「archived/booth/ から C0056 のデザイン決定事項と equipment-inventory を
Grepで検索して、今回の企画に流用可能な要素をリストアップして」
```
→ 全過去案件を読まずに必要な情報だけ取得 → コンテキスト消費最小限。

## 3. Daily.md 自動日報で繰り返し説明を排除

### 原理

AI日報（Daily.md）を自動生成し、Claude Code の起動参照設定に組み込むことで、
「昨日何をしたか」「今の状況」を毎回説明するためのトークン消費を削減する。

### 実装

**Daily.md 自動出力:**
```bash
# セッション終了時に自動追記
node tools/daily-report.mjs --append "C:/Users/USER/.claude/daily/2026-11-10.md"
```

日報フォーマット:
```markdown
# 2026-11-10 日報

## 完了
- X-0015 記事作成（PR #1836）
- X-0019 マージ確認（commit b670812d）

## 進行中
- X-0011 4エージェント学習（残TODO  2項目）
- L&B 5-C 反映待ち

## 判断待ち
- 濱川さん SSH鍵未着 → KCTサーバー作業ブロック
- L&Bタスク表 11/12定例前確認

## 次の着手
- X-0011 残TODO消化
```

**参照設定:**
`~/.claude/settings.json` に追記:
```json
{
  "references": [
    "C:/Users/USER/.claude/daily/2026-11-10.md"
  ]
}
```

または `CLAUDE.md` に記載:
```
本セッションの参照情報: ~/.claude/daily/YYYY-MM-DD.md（自動更新）
```

### 効果

| 項目 | 効果 |
|---|---|
| 状態説明トークン | **ゼロ**（Daily.md が毎回自動提示） |
| 認識齟齬リスク | **低下**（日報が正本＝Claudeの記憶違いを防止） |
| 自動化コスト | 1行追加のみ（`--append` のワンライナー） |

## 4. Idle compaction 制御 — 無駄な再計算の防止

### 原理

Claude Code は `/Config` で `idle compaction` を設定できる。
Idle compaction が有効だと、アイドル時にコンテキストの再圧縮（コンパクション）が走り、
**その処理自体がトークン消費とレイテンシを発生させる**。

### 実装

```
/Config idle compaction=false
```

または `settings.json`:
```json
{
  "idleCompaction": false
}
```

### 効果

| 項目 | 効果 |
|---|---|
| アイドル消費 | ゼロ（コンパクションによる追加消費なし） |
| 再開レイテンシ | **低下**（圧縮解除のオーバーヘッドなし） |
| リスク | なし（true でも false でも機能上の問題は発生しない） |

### 注意

コンパクションを切るとスワップ/ディスク使用量が増える可能性があるため、
**SSD容量に余裕のある環境でのみ設定**する（容量逼迫時は一時的に true に戻す）。

## 5. 人間/AI 役割分担 — 概要5割・設計3割・実装1割

### 原理

全工程をAIに任せると、試行錯誤のトークン消費が膨大になる。
**人間が概要（50%）、設計（30%）、実装（10%）を担当し、AIに確認項目を挙げさせる**ことで、
AIの総消費トークンを約半分に削減できる。

### 具体的な役割分担

| 工程 | 担当 | 割合 | AIの仕事 |
|---|---|---|---|
| 概要・要求定義 | 人間 | 50% | 不足点の確認質問を出す |
| 設計・仕様書 | 人間 | 30% | 設計の穴をチェック・代替案を提示 |
| 実装（コード） | AI（Codex等） | 10% | 指示通りの実装 |
| 検証 | AI（Claude等） | 10% | テスト実行・結果確認・不具合報告 |

### 「確認項目を挙げさせる」の具体的手順

```
# 確認項目ジェネレータテンプレート
あなたは品質保証の専門家です。
私が書いた以下の設計/概要に対して、設計上の欠陥・抜け漏れ・改善点を
確認項目としてリストアップしてください。

【人間の成果物】
<ここに概要/設計を書く>

確認項目は以下を満たすこと:
- 1項目1文
- 優先度（HIGH/MED/LOW）付き
- HIGHは3つ以上
- 各項目に「確認すべき理由」を1行
```

### 効果

| 項目 | 効果 |
|---|---|
| AIトークン消費 | **〜50%削減**（無駄な試行錯誤の排除） |
| 品質 | **向上**（人間の意図をAIが確認 → 設計の穴を事前発見） |
| 人間の負荷 | 増えるが、**長期的には手戻り減少で総作業量が減少** |

## 6. Worktree 最大3制限 — 並列コンテキスト分散の防止

### 原理

Git worktree で複数の作業ツリーを持つと、それぞれが独立した Claude Code セッションを
立ち上げられる。しかし並列セッションが増えるほど：
1. 各セッションのコンテキストキャッシュが独立 → 総キャッシュ消費が線形増加
2. プロンプトキャッシュのプレフィックス共有率が低下
3. フリートの全体的なトークン消費が増大

**対策:** 常に最大3つのワークツリーに制限。それ以上は1つを閉じてから新規作成。

### 実装

`CLAUDE.md` または運用ルールに記載:
```
## Worktree制限
- 同時にアクティブにできる worktree は最大3つ
- 新しい worktree を作る前に古いものを閉じる（`git worktree remove`）
- 未使用の worktree は commit → PR までは main から branch → worktree を作る運用
```

### 効果

| ワークツリー数 | 総キャッシュ消費 | 並列効率 |
|---|---|---|
| 1 | 基準値 | 最高 |
| 3 | 約3倍 | 実用上限 |
| 5以上 | 5倍+ | 管理コスト増・キャッシュ浪費 |

## 7. High effort でも消費が「スクショ程度」の原則

### 原理

Claude Code の high effort（高思考予算）は通常の数倍〜10倍のトークンを消費する。
これを複数回実行すると、一瞬で大型クレジット消費になる。

**設計目標:** high effort を複数回実行しても、消費が「スクリーンショットを1枚見る程度」
（〜10,000トークン）に収まるようにする。

### 実現方法

1. **長期記憶フォルダ隔離**（§2）で high effort の読込範囲を限定
2. **Daily.md 参照**（§3）で状態説明の high effort 消費を排除
3. **Idle compaction=false**（§4）でアイドル消費を防止
4. **人間の概要・設計**（§5）で high effort の試行錯誤を削減
5. **1セッション1目的**の徹底で high effort の焦点を絞る

### 実測目標

```
high effort 1回 → 3,000〜8,000トークン（スクショ程度）
high effort 5回 → 15,000〜40,000トークン（通常の high effort 1回分以下）
```

## 8. 総合効果: 積み上げで1/5〜1/10

各軸の削減率を積み上げた場合の総合効果:

| 軸 | 単独削減率 | 累積削減率 |
|---|---|---|
| ① 静的先頭配置 | −60〜68% | 基準（100→35トークン） |
| ② 長期記憶隔離 | −10〜30%（案件数依存） | 35→25 |
| ③ Daily.md | −5〜15% | 25→20 |
| ④ Idle compaction | −3〜5% | 20→19 |
| ⑤ 役割分担 | −40〜50%（実装工程のみ） | 19→11 |
| ⑥ Worktree制限 | 並列数に比例 | 実質効果は①〜⑤に乗算 |

**総合: 1/5〜1/10 削減**（軸の選択と環境による）

## 10. オージャスト適用: ブース設計過去案件の保存と実測

### 手順

1. 過去ブース案件（C0056, C0057, ...）の完了ファイルを
   `~/.claude/memory/archived/booth/` に保存（構造化）
2. `CLAUDE.md` に「長期記憶フォルダは検索のみ・自動読込禁止」を追記
3. `Daily.md` 自動出力を設定
4. `/Config idle compaction=false`
5. 新規イベント企画時に Claude Code へ参照指示:
   ```
   /refer archived/booth/ から C0056 のデザイン決定事項と equipment-inventory を検索して
   ```
6. **クレジット消費を実測**（`cost-reporter` や `cache-monitor` で）

### 測定項目

| 項目 | 導入前 | 導入後 | 目標削減率 |
|---|---|---|---|
| 1セッションの入力トークン | 〜50,000 | 〜10,000 | −80% |
| キャッシュヒット率 | 〜40% | 〜70% | +75% |
| 総クレジット消費 | 基準 | 1/5〜1/10 | −80〜90% |

### フィードバックループ

```
実測 → プラン見直し → 設定調整 → 再実測
```

1週間ごとにクレジット消費を集計し、軸ごとの効果を報告。
効果の低い軸は設定を見直し、効果の高い軸に注力する。
