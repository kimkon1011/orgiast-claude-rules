## 概要

LLM の KV キャッシュは計算済み Key/Value を保持するため、シーケンス長に比例してメモリを消費する。
元ニュースの構成例（**32層GQA・ヘッド次元128・BF16**）では:

- **8192トークン1シーケンス = 1GiB**
- **独立した16シーケンス = 16GiB**

プレフィックスキャッシュ（radix / prompt cache）は**一致するプレフィックス部分の KV を1部に共有**するため、
「共通部分を先頭に固定して使う」だけでメモリ・コストを大幅に減らせる。オージャストでは
**類似ブース提案で共通プレフィックスを使い、メモリ効率を意識した生成**を試すのが本提案のアクション。

## 1. 数値の検算（h_kv = 8 で一致）

```
KV bytes = L × h_kv × d × 2(K,V) × 2(BF16) × T
         = 32 × 8 × 128 × 4 × 8192
         = 1,073,741,824 bytes = 1 GiB   ✓
```

- h_kv（KVヘッド）= 8 は GQA の代表構成（Llama-3 8B 級）で、新聞の数値と整合。
- 16シーケンス独立 = 16 GiB ✓。詳細の表は `outputs/X-0016/memory-metric-analysis.md`。

## 2. 共有プレフィックスPトークンでのメモリ

`total[GiB] = P/8192 + 16 × (8192−P)/8192`

| P | 合計 | 16GiB比 |
|---|---:|---:|
| 0（独立） | 16.00 GiB | 基準 |
| 2,048 | 12.25 GiB | −23.4% |
| 4,096 | 8.50 GiB | −46.9% |
| 8,192（全一致） | 1.00 GiB | **−93.75%** |

## 3. オージャスト適用（類似ブース提案の共通プレフィックス）

X-0009 の `tools/kv-cache-prefix-gateway.mjs` はすでに「共通プレフィックス抽出 → 順次実行 → TTFT/コスト計測」を実装済み。
これにメモリ定量を接続する運用プラン:

1. **共通プレフィックスを固定**: 小間規格（2.7m×6m）、標準構造材・照明・床材スペック、安全・搬入出ルール、
   会社プロフィールをシステムプロンプト先頭に固定（バイト単位で一致させる。X-0015 の「静的先頭配置」と同趣旨）。
2. **類似案件を連続生成**: 同じ展示会の複数出展者・類似ブースの提案をゲートウェイ経由で順次実行
   （キャッシュTTL=5分以内にまとめる）。
3. **測定**: 2件目以降の `cache_read_input_tokens` / `cached_tokens` が 0 でないこと・TTFT短縮を確認。

## 4. 実運用上の注意

- API プロンプトキャッシュ（Anthropic / OpenRouter）はプロバイダー側キャッシュで、
  **メモリ共有そのものはサーバーサイド（vLLM/SGLang の RadixAttention 型）の話**。
  API 経由のオージャストには TTFT とコストの効果で現れる（メモリはプロバイダー側で集約される）。
- キャッシュは**プレフィックス完全一致が前提**。末尾の1バイト違いは許容されるが、先頭がずれると効かない。
- プロンプトの動的部分（案件名・出展企業・要件）は**必ず末尾側**に置く（X-0015 と同じ配置原理）。
