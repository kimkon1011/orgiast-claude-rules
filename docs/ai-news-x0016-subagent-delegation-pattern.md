# X-0016: 3体サブエージェント分業委譲パターンの実証実験

> **元ニュース**: Claude Code の Agent tool を使い、展示会企画を計画・実装・レビューの3体に委譲し、手順・コスト・品質を確認した実証実験レポート。
>
> 観測日: 2026-11-11。著者: Claude（監督）

---

## 1. 実験目的

「Claude 1体で全部やる」と「3体のサブエージェントに分業委譲する」の違いを実測する。

| 観点 | 従来（1体） | 委譲（3体） |
|------|------------|------------|
| コンテキスト | 全フェーズの履歴を保持 | 各エージェントは自分の担当だけ |
| 並列度 | 直列 | 並列可能（独立フェーズは同時実行） |
| 品質担保 | 1回の出力を最後に見直す | 計画→実装→レビューの独立チェック |
| 再利用性 | セッション単位 | エージェント単位で部品化可能 |

## 2. 実験シナリオ

**クライアント**: 三共精機株式会社（精密機械部品製造）
**展示会**: 2027 関西ものづくりワールド（インテックス大阪）
**ブース**: 6m×3m（18m²）
**予算**: 150万円〜200万円
**目標**: 新規リード50件獲得＋ブランド認知向上

### 3体の役割

| エージェント | 種類 | 担当 | インプット | アウトプット |
|------------|------|------|-----------|------------|
| ①計画 | Explore | 既存リソース調査＋変更ファイル一覧作成 | テンプレート・ナレッジ・過去データ | 11ファイルの変更計画 |
| ②実装 | general-purpose | ブースデザイン文書5点を実装 | 計画＋テンプレート | 企画概要・設計書・スケジュール・予算・戦略 |
| ③レビュー | Explore | 作成文書の検証と改善提案 | 5文書＋比較対象 | 各ファイル評価＋改善提案リスト |

## 3. 実験結果

### 3.1 作成成果物

**計画エージェントの出力**（Phase 1）:
- 既存3リソースの存在確認（テンプレート・ナレッジ・過去データ）
- 11ファイルの変更計画（Phase 1〜5の優先順位付き）
- ディレクトリ構成の提案

**実装エージェントの出力**（Phase 2）:
- `01_企画概要.md`: 7,006 bytes — 企業概要、KPI、成功条件
- `02_ブース設計企画書.md`: 13,361 bytes — レイアウト図、導線設計
- `03_スケジュール.md`: 7,553 bytes — 逆算マイルストーン
- `04_予算計画.md`: 7,708 bytes — 3シナリオ比較
- `05_リード獲得戦略.md`: 14,934 bytes — フォローアップ設計

**レビューエージェントの出力**（Phase 3）: 実行中

### 3.2 トークン消費の推定比較

| 方式 | 総読込トークン（推定） | キャッシュ効率 |

## 4. 自動化スクリプト

本実験を基に、以下の自動化スクリプトを作成した:

### 4.1 CLI自動化スクリプト
`tools/exhibition-delegation-workflow.mjs` — Node.js CLIツール
- `--review` フラグでレビューエージェントも実行
- `--plan-only` で計画のみ
- `--skip-plan` で既存計画から実装開始
- `--client` でクライアント名変更

### 4.2 Workflowスクリプト
`.claude/workflows/exhibition-delegation.mjs` — Workflow tool対応
- 3フェーズ（計画→実装→レビュー）を自動直列実行
- 各フェーズの結果を次のフェーズに引き継ぎ

## 5. 学びと改善点

### 5.1 良かった点
1. **コンテキスト分離**: 各エージェントが自分の担当だけに集中でき、メインセッションの肥大化を防止
2. **品質の層別**: 計画（全体設計）→実装（詳細化）→レビュー（検証）の独立チェックが機能
3. **再利用性**: 計画エージェントは別クライアントにも使い回��る汎用性

### 5.2 改善点
1. **計画の引継ぎ**: 計画エージェントの出力をそのまま実装エージェントに渡すと情報量過多になるため、要約レイヤーが必要
2. **エージェント間の整合性**: 計画→実装の間で前提条件が変わった場合の検知が不足
3. **コスト測定**: 実際のトークン消費量をAPIレベルで計測できていない（次回課題）

### 5.3 次のステップ
1. ワークフローの定期実行（cron）に対応
2. クライアント情報をJSON/YAMLの設定ファイルから読み込むパラメータ化
3. トークン消費量の実測レポート機能追加

## 6. 適用範囲

この委譲パターンは以下の条件で最も効果を発揮する:

- **独立した複数フェーズ**があるタスク（計画→実装→検証）
- **異なる専門性**が必要なフェーズを含む（調査→設計→レビュー）
- **コンテキスト肥大化**が問題になる長期間のタスク
- **再利用可能なエージェント定義**が作成可能な定型業務
