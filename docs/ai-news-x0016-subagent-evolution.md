# X-0016: サブエージェント進化でトークン消費99%カット

> **元ニュース**: Claude Code のエージェント機能（Agent tool）が進化。従来は全コンテキストを毎ターン再読込していた複数タスクを、独立したサブエージェントに委譲することで、メインセッションのコンテキスト肥大を抑制しトークン消費を最大99%削減できる。
>
> 観測日: 2026-11-10。著者: Claude（監督）

---

## 1. 問題: コンテキスト再読込のコスト

従来の Claude Code の典型的なワークフロー:

| ターン | セッション合計トークン（累積） | 操作 |
|-------|------------------------------|------|
| 1 | ~15K | 初期コンテキスト読込 + 指示 |
| 2 | ~30K | 1ターン目の結果読込 + 次の指示 |
| 3 | ~50K | 2ターン目まで読込 + 調査指示 |
| 4 | ~75K | 3ターン目まで読込 + 別調査指示 |
| 5 | ~100K | 全履歴読込 + 統合指示 |

**累積コンテキストが直線的に増え、毎ターンその全量を再読込する**。特に調査・設計・分類など独立した複数作業を直列で行うと、不要な過去履歴が常に再読込される。

---

## 2. 解決: サブエージェント委譲

Agent tool（サブエージェント）を使うと、独立タスクを**別コンテキストで実行**し、結果だけをメインセッションに返す。

```
【従来】メインセッションに全履歴を保持しながら複数タスク
  ターン1: Context 15K → ターン2: Context 30K → ターン3: Context 50K
  毎ターン、過去の全履歴をプロンプトキャッシュに載せ直す

【改善】サブエージェントに独立タスクを委譲
  メイン: Context 10K（最小限の指示＋サブエージェント結果だけ）
    ├── Agent A（調査）: Context 5K → 結果500Bで返す
    ├── Agent B（設計）: Context 5K → 結果500Bで返す
    └── Agent C（見積）: Context 5K → 結果500Bで返す
  メインセッションのコンテキストは10Kで維持される
```

**サブエージェントのコンテキストは各タスクに必要な最小限だけ**。メインセッションに戻るのは数百トークンの結果のみ。

---

## 3. 定量的効果予測

### 3.1 3タスク直列 vs サブエージェント委譲

| 方式 | 総読込トークン | キャッシュヒット率 | 備考 |
|------|--------------|-----------------|------|
| 従来（直列3ターン） | 15K+30K+50K = **95K** | 低（毎ターン過去履歴を再計算） | 毎ターンコンテキスト肥大化 |
| サブエージェント委譲 | 10K+(5K+5K+5K) = **25K** | 高（各サブエージェントは最小コンテキスト） | メインコンテキスト安定 |

**削減率: (95K - 25K) / 95K = 73.7%**

### 3.2 5タスク（並列可能）の場合

| 方式 | 総読込トークン | 備考 |
|------|--------------|------|
| 従来（5ターン直列） | 15K+30K+50K+75K+100K = **270K** | コンテキストが直線増加 |
| サブエージェント（並列委譲） | 10K + 5×5K = **35K** | 並列可能なタスクは同時実行 |

**削減率: (270K - 35K) / 270K = 87.0%**

### 3.3 10タスク（中規模調査案件）

| 方式 | 総読込トークン | 備考 |
|------|--------------|------|
| 従来（10ターン直列） | 累積等差数列: (15K+150K)×10/2 = **825K** | 15ターンで150K、等差 |
| サブエージェント（並列委譲） | 10K + 10×5K = **60K** | 並列度に依存 |

**削減率: (825K - 60K) / 825K = 92.7%**

### 3.4 99%カットの条件

99%削減は以下の複合効果で達成される:

1. **コンテキスト維持**: メインセッションが肥大化しない（10ターン後も15K〜20Kで安定）
2. **並列実行**: 独立タスクを同時実行し、直列累積が発生しない
3. **プロンプトキャッシュ効率**: メインセッションの静的プレフィックス（システムプロンプト等）がキャッシュに留まり続ける（TTL=5分以内）
4. **不要履歴を除外**: サブエージェントごとに必要なコンテキストだけを渡すため、ノイズトークンが入らない

**実測見込み**: 10タスク以上 + 並列度4以上で 92〜95%。**99%到達には**:
- 最小限のメインコンテキスト（〜5K）を徹底
- 20タスク以上の中規模案件
- キャッシュTTL内（5分）に全実行
- Agent tool の isolation モード（worktree 分離）併用でメインセッションへの副作用ゼロ

```
20タスクの試算: (15K+300K)×20/2 = 3,150K（従来）
→ サブエージェント: 5K + 20×5K = 105K（全並列不要、4バッチ=5並列×4）
→ 削減率: (3,150K-105K)/3,150K = 96.7%（99%にはプレフィックスキャッシュ重複効果＋）
プレフィックスキャッシュで各サブエージェント間の共通部がキャッシュされると:
→ 実質読込: 5K + 5K(先頭1エージェントだけ新規) + 19×0.5K(残りはキャッシュヒット)
→ 削減率: (3,150K-14.5K)/3,150K = 99.5% ✅
```

## 4. 株式会社オージャストへの適用

### ブース制作リサーチ + デザイン案 + 見積もり

従来の1件対応:

| ターン | 内容 | コンテキスト |
|-------|------|------------|
| 1 | 出展企業の業界リサーチ | 15K |
| 2 | 競合ブース調査 | 30K |
| 3 | デザイン案A作成 | 50K |
| 4 | デザイン案B作成 | 75K |
| 5 | 構造検討 | 100K |
| 6 | 見積もり | 130K |
| **合計** | **6ターン** | **400K読込** |

サブエージェント委譲版:

```
メインセッション（最小指示のみ）: Context 8K（案件概要＋指示）
  ├── Agent 1: 業界リサーチ（context 3K + tools）→ 結果1K
  ├── Agent 2: 競合調査（context 3K + tools）→ 結果1K
  ├── Agent 3: デザイン案A（context 5K + 業界・競合データ）→ 結果2K
  ├── Agent 4: デザイン案B（context 5K + 業界・競合データ）→ 結果2K
  ├── Agent 5: 構造検討（context 4K + 規格データ）→ 結果1K
  └── Agent 6: 見積もり（context 4K + デザイン案結果）→ 結果1K
メインセッションの最終コンテキスト: 8K + (1K+1K+2K+2K+1K+1K) = 16K
サブエージェント総読込: 3K+3K+5K+5K+4K+4K = 24K
総読込トークン: 16K(メイン) + 24K(サブ) = **40K**
```

**削減率: (400K - 40K) / 400K = 90.0%**

並列度が上がれば上がるほど効果が増す。デザイン案A/B は同時実行可能。

### 並列度を最大化した実測プラン

展示会同時期の複数案件を一括処理:

```
メイン（案件概要のみ）: 5K
  ├── 案件A 業界リサーチ → 案件A デザイン案
  ├── 案件B 業界リサーチ → 案件B デザイン案
  ├── 案件C 業界リサーチ → 案件C デザイン案
  └── 案件D 業界リサーチ → 案件D デザイン案
期待削減率: 95〜99%（並列度4×4案件の効果）
```

## 5. 実装と検証

### 前提条件

- Claude Code の Agent tool が利用可能であること（`subagent_type` 指定可）
- isolation モード（worktree）で副作用を分離
- サブエージェントへの指示はファイルベースで渡す（§1.17）

### 検証手順

1. **サブエージェント無し**: 3タスクを従来の直列ターンで実行 → 総トークン消費を測定
2. **サブエージェント有り**: 同一3タスクを Agent tool 委譲で実行 → 総トークン消費を測定
3. **比較**: 削減率を算出
4. **複合**: 並列度・タスク数を変えて再測定し、99%近傍を確認

### 測定項目

- メインセッションの `input_tokens` + `output_tokens`（Anthropic API usage）
- 各サブエージェントの `input_tokens` / `output_tokens`
- プロンプトキャッシュヒット率（`cache_read_input_tokens` / `cache_creation_input_tokens`）
- 壁面実時間（並列実行の高速化効果）

## 6. リスクと注意点

| リスク | 影響 | 対策 |
|-------|------|------|
| サブエージェントへの指示不足で結果が不十分 | 再委譲でコスト増 | 指示は詳細なファイルで渡す（§1.17の原則） |
| isolation モードのオーバーヘッド | 起動コストが小タスクの利益を上回る可能性 | 1タスクあたり最低5K読込以上のタスクに限定 |
| サブエージェントの利用上限 | 同時実行制限に抵触 | キューイング＋逐次実行へのフォールバック |
| プロンプトキャッシュTTL切れ | 共通プレフィックスの再計算 | 全サブエージェントを5分以内に実行完了 |
