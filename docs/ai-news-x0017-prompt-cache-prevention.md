# X-0017: プロンプトキャッシュ漏れ防止ガイドライン

> **元ニュース**: Anthropic Claude のプロンプトキャッシュは同一セッション内でモデル・会話IDを維持することで最大90%のコスト削減が可能。モデル切替や長時間中断がキャッシュを無効化する。2026年11月観測。
>
> 観測日: 2026-11-09。著者: Claude（監督）
> 実装日: 2026-11-14。著者: Claude（監督）→ Codex（実装）

---

## 1. プロンプトキャッシュの仕組み

Claude API（anthropic-sdk）は**会話ID（conversation_id）単位**でシステムプロンプト・会話履歴・ツール定義をキャッシュする。同一セッション内で以下が維持される間、2回目以降のリクエストは入力トークンの最大90%がキャッシュヒットし、課金対象外になる。

| 要素 | キャッシュキー | 無効化条件 |
|------|--------------|-----------|
| システムプロンプト | 会話ID | モデル変更・セッション破棄 |
| 会話履歴（過去20ターン程度） | 会話ID | 長時間経過（約1時間）・設定変更 |
| ツール定義・MCP設定 | 会話ID + モデル | モデル切替・ツール定義変更 |

## 2. キャッシュが漏れる4つの原因

### 2.1 モデル切替（最大の原因）

`/config` または `--model` でモデルを変更すると**会話IDが再生成**され、蓄積されたキャッシュが全て消える。

**影響**: 初回リクエスト相当のフル課金が再発生。切替1回あたり数千〜数万トークンの再送。

**対策**:
- セッション開始時にモデルを選び、作業中は切り替えない
- どうしても別モデルが必要なら `/compact` で会話を要約してから `/config` で切り替える
- 高負荷タスク（設計・調査）は Opus/Fable、実装は Codex と**別セッション**で行う

### 2.2 長時間中断（約1時間）

Anthropic のキャッシュTTLは約5分（プロンプトキャッシュ）〜1時間（会話履歴の暗黙的キャッシュ）。1時間以上操作がないとキャッシュが期限切れになる。

**影響**: 再開時に全コンテキストの再送。

**対策**:
- 1時間以上の休憩は避ける
- やむを得ず中断する場合は `/compact` で現在の状態を要約ファイルに保存してから終了する
- 定期監視タスクは `ScheduleWakeup` や cron の間隔を60分以内に設定する

### 2.3 コンパクトの過剰実行

`/compact` は会話履歴を要約して短縮するが、この処理自体が「会話履歴」の変更であり、最適化の仕方によってはキャッシュを部分的に無効化する。

**影響**: 可変。会話履歴キャッシュが失われる。

**対策**:
- コンパクトは**作業中の自然な区切り**（PR作成後・大きなタスク完了後）でのみ実行
- 「とりあえずコンパクト」はしない。必要なのは会話が長くなりすぎてコンテキストウィンドウ圧迫が起きたときだけ
- コンパクト後はシステムプロンプトとツール定義のキャッシュは維持されるため、影響は限定的

### 2.4 セッションの再利用と新規作成

`/session-close` 後に新しいセッションを開くと**会話IDが完全に変わる**。

**影響**: キャッシュゼロからのスタート。

**対策**:
- 1つの目的は1セッションで完結させる
- 引き継ぎ時は `next-session.md` に必要なコンテキストのみを保存し、新しいセッションでは最小限の再説明で済ませる
- CLAUDE.md と memory に恒久設定を移して、毎回の再説明を減らす

## 3. キャッシュヒット率の確認方法

Claude Code のセッション内で `/usage` を実行すると以下の指標が表示される：

```
Total Input: 1,234,567 tokens (Cache Hit: 1,000,000 tokens, 81%)
Total Output: 123,456 tokens
```

**目標値**:
- **80%以上**: 理想的なキャッシュ利用状態
- **50〜80%**: 改善余地あり（モデル切替・中断の確認）
- **50%未満**: キャッシュが機能していない。即座に見直し

**確認タイミング**:
- セッション開始直後（基準値として）
- 2時間ごと（定期監視）
- モデル切替後（切替の影響を定量化）

## 4. 展示会ブースデザイン生成での実践

### 4.1 現状の問題

ブースデザインの反復生成（デザイン案→フィードバック→修正）において、以下のキャッシュ漏れが観測されている：

1. 生成と評価を同じセッションで行うため、モデル切替が頻発（Opus→Sonnet→Opus）
2. フィードバックの待機時間が1時間を超え、キャッシュ失効
3. 毎回のプロンプト冒頭に同じ前提（会社情報・ブースサイズ等）を書き、システムプロンプトに移せていない

### 4.2 改善策

**Step 1: 恒久設定の CLAUDE.md への移行**
```
# 恒久設定（既に CLAUDE.md に記載済み）
- 会社: 株式会社オージャスト（展示会ブース制作・イベントプロデュース）
- 既定のブースデザイン出力形式: outputs/booth-design-format.md 参照
- 色使いの制約: コーポレートカラーは#D42139（赤）と#1E1E1E（黒）
```

**Step 2: 別セッション戦略**
- 設計（Opus/Fable）= 専用セッションで行い、完了後に必要な仕様だけ `next-session.md` に書く
- 実装（Codex）= 別のセッション（または worktree）で行う
- レビュー/検証（Claude）= さらに別のセッションで行う
- **同一セッション内でのモデル切替は禁止**

**Step 3: ブースデザイン反復プロンプトのキャッシュ最適化**
```markdown
❌ 悪い例（毎回モデル切替・前提再説明）:
「前回のデザイン案Aの修正です。
株式会社オージャストの展示会ブース提案です。
ブースサイズは6m×4mです。
予算は200万円です。
…」
→ 毎回システムプロンプトのキャッシュが効かない

✅ 良い例（同一モデル・システムプロンプトに前提）:
（システムプロンプトに恒久設定）
（毎回のプロンプトは差分だけ）
「デザイン案B: 高さ制限を3.5mから4.0mに変更。
照明を間接照明からダウンライトに変更。
全体のトーンは落ち着いた雰囲気に。」
→ システムプロンプトのキャッシュが効き、差分のみ課金
```

### 4.3 費用対効果の試算

| 項目 | キャッシュなし | キャッシュあり（80%ヒット） |
|------|---------------|------------------------|
| 1セッションの平均入力 | 200,000 tokens | 40,000 new + 160,000 cached |
| 1セッションの費用（Opus） | ~$3.00 | ~$0.60 |
| 週5セッションの月間費用 | ~$60.00 | ~$12.00 |
| **年間削減額** | - | **~$576** |

## 5. チェックツール

`tools/x0017-prompt-cache-usage.mjs` を提供する。このツールは：

1. 現在のセッションのキャッシュ状態を推測するチェックリストを出力
2. 改善のための具体的なアクションを提案
3. /.usage で得たヒット率を記録・推移を管理

### 使用方法

```bash
node tools/x0017-prompt-cache-usage.mjs --check
# → キャッシュ状態のチェックリストを表示

node tools/x0017-prompt-cache-usage.mjs --record --hit-rate 81 --session "セッションID"
# → ヒット率を記録

node tools/x0017-prompt-cache-usage.mjs --report
# → これまでの記録からレポートを生成
```

## 7. セッション開始時にやること

1. `tools/x0017-prompt-cache-usage.mjs --check` を実行 → 前回のヒット率と改善点を確認
2. モデルを選択し、作業中は切り替えないことを宣言
3. 1時間以上の休憩が予想される場合は `/compact` してから離脱
4. 終了時に `--record` でヒット率を保存
