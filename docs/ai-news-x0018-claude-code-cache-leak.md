# X-0018: Claude Code プロンプトキャッシュ漏れ9パターン — 実践的対策とコスト削減

**AIニュース提案 X-0018**: Claude Codeのプロンプトキャッシュは1時間で失効（TTL）、ヒットでリセット。100K Opusチャットでキャッシュヒット時$0.02が、1回のキャッシュ破壊で$0.80へ急増（40倍差）。モデル切替・長時間離席・`/compact`・Fastモード切替・冷たい起動の9パターンを特定し、各々の対策とコストインパクトを定量評価する。

観測日: 2026-11-10

---

## 1. 概要

Claude CodeはAnthropicのプロンプトキャッシュ機能を活用し、同一プレフィックスのKV計算をスキップすることで入力を最大90%削減する。しかし、以下の理由によりキャッシュが意図せず破棄され、コストが急増するケースが多発している:

```
正常時: [固定Prefix + 会話履歴] → キャッシュヒット → $0.02/呼出
漏洩時: [固定Prefix + 会話履歴] → キャッシュミス → $0.80/呼出（40倍）
```

本稿では、Claude Codeセッションで観測された**9つのキャッシュ漏洩パターン**を分類し、各パターンの発生条件・コストインパクト・対策を定義する。

### キャッシュの基本仕様

Anthropic Claude APIのプロンプトキャッシュは以下の特性を持つ:

| 項目 | 値 |
|------|-----|
| キャッシュTTL | 5分（アイドル時）〜1時間（アクティブ時） |
| キャッシュキー | 先頭からのバイト完全一致 |
| キャッシュヒット時のコスト | 入力トークン単価の10%（書込済み部分） |
| 書込コスト | 入力トークン単価の125%（5分以内）/ 200%（1時間以内） |
| 最大キャッシュサイズ | モデルにより異なる（Opus: 200K tokensまで） |

キャッシュ書込（書き込み）は読み取りより高コストであり、短時間での書込更新（追記）が頻発すると総コストが上昇する。**キャッシュヒット率の最大化と書込頻度の最小化が、実効コスト削減の両輪となる。**

## 2. 9つのキャッシュ漏洩パターン

### パターン1: モデル切替（Model Switching）

**発生条件**: セッション中に `/opus` → `/sonnet` などモデルを切り替える。

**原因**: モデルごとにキャッシュ空間が独立している。OpusのキャッシュにSonnetのリクエストはヒットせず、逆も同様。

**コストインパクト**: 切替直後の1呼出しがフルコスト（100Kトークン: $0.80 vs $0.02）。

**対策**: セッション開始時に使用するモデルを固定する。複数モデルを使い分ける場合は別セッションで行い、APIレベルでキャッシュを分離する。

### パターン2: Fastモードの切替（Fast Mode Toggle）

**発生条件**: `/fast` でFastモードをオン/オフ切り替える。

**原因**: FastモードではOpusが高速出力モードになるが、システムプロンプトが通常モードと異なる。先頭バイトが一致せず、キャッシュ全体が無効化される。

**コストインパクト**: 切替ごとに全キャッシュが破棄。Opus 100Kトークン想定で約$0.80の追加コスト。

**対策**: セッション開始時にFastモードのON/OFFを決め、途中で変更しない。長期間のバッチ処理ではFastモード固定、品質重視の対話セッションでは通常モード固定。

### パターン3: `/compact` の実行

**発生条件**: `/compact` コマンドで会話履歴を圧縮する。

**原因**: `/compact` は会話を要約して再構成する。要約文は元の会話とバイト単位で一致しないため、キャッシュプレフィックスが完全に置き換わる。

**コストインパクト**: 圧縮直後の呼出しが全キャッシュミス。100K Opusで約$0.80。加えて圧縮用のモデル呼出しが別途発生。

**対策**: 
- `/compact` はキャッシュが自然失効する直前（アイドル45分経過時など）に計画的に実行する
- 会話が長くなりすぎる前に定期的に `/compact` を実行し、1回あたりのキャッシュ破棄コストを小さくする
- `/compact` 後はすぐに次のタスクを開始し、キャッシュを温める

### パターン4: 長時間離席・アイドル（Idle Timeout）

**発生条件**: 5分以上の操作なし（アイドル）。

**原因**: Anthropicのプロンプトキャッシュは5分間のアイドルでTTL切れとなり失効する。キャッシュが完全にクリアされ、次回呼出しはフルコスト。

**コストインパクト**: 復帰後の初回呼出しがフルコスト。頻繁な離席（10回/日）で1日あたり約$8.00の追加コスト。

**対策**:
- 自然な休憩（トイレ・会議・昼食）の前に `/compact` を実行し、キャッシュを温かい状態で保存
- キャッシュが温かいまま短時間（1分以内）のタスクを1件実行し、TTLをリセット
- 離席前に意味のない軽量クエリを投げてキャッシュを維持する（probe）

### パターン5: 冷たい起動（Cold Start）

**発生条件**: セッション開始直後 / 新規セッションの初回呼出し。

**原因**: キャッシュが存在しない状態からの起動。システムプロンプト全体のKV計算が必要。

**コストインパクト**: 初回呼出しは必ずフルコスト（$0.80/100K）。書込コスト（125%）も加算される。

**対策**:
- セッション開始時にウォームアップクエリを実行し、キャッシュを書き込んでから本番タスクを開始する
- 同じ種類のタスクを連続実行する場合、最初のタスクでキャッシュを温めておく
- システムプロンプトに静的先頭配置（X-0015）を適用し、セッション間で共通のPrefixを再利用する

### パターン6: システムプロンプトの動的変更（Dynamic System Prompt）

**発生条件**: セッション中にシステムプロンプトを変更する（カスタム指示の追加・削除）。

**原因**: システムプロンプトの内容が変わると先頭バイトが一致しなくなり、全キャッシュが無効化される。

**コストインパクト**: 変更後の初回呼出しがフルコスト。カスタム指示の更新頻度が高いほどコストが増加。

**対策**: 
- 変更が必要な部分は末尾に追加する形式をとり、固定Prefixを維持する
- カスタム指示はプリセット化し、セッション間で統一する
- どうしても変更が必要な場合は、変更をまとめて1回で行う

### パターン7: マルチターンでの動的部分の先頭混入（Dynamic Prefix Contamination）

**発生条件**: 会話の進行に伴い、ユーザー入力がプロンプト先頭に近づく。

**原因**: ターンが進むと新しいユーザーメッセージが末尾に追加される。Anthropicのキャッシュはmessages配列の先頭から一致を確認するため、**会話の順序は変えてもキャッシュ範囲は変わらない**が、新規ターンのたびにシステムプロンプト＋過去の全ターンがキャッシュの対象となる。ターンが進むほど過去ターンがキャッシュから溢れ、後半部分でミスが発生する。

**コストインパクト**: ターン数に比例してキャッシュ範囲を超えた部分のトークンがミスになる（段階的増加）。

**対策**:
- 定期的に `/compact` で過去ターンを圧縮し、キャッシュ範囲をリセット
- システムプロンプトに固定Prefixを配置し、動的部分を末尾に集約（X-0015）
- 会話の文脈を必要最小限に保つ

### パターン8: 書込コストの累積（Write Cost Accumulation）

**発生条件**: 短時間（5分以内）に連続してキャッシュ書込が発生する。

**原因**: キャッシュ書込（新規トークンのキャッシュ保存）は読み取りの125%（5分以内）〜200%（1時間以内）のコストがかかる。短時間での連続書込は、従来の入力コストより高くなる。

**コストインパクト**:

| シナリオ | 入力トークン | 従来コスト | キャッシュ書込コスト | 差 |
|---------|------------|-----------|-------------------|----|
| 5分以内の連続書込 | 100K×5回 | $3.20 | $4.00 | +25% |
| 1時間以内の連続書込 | 100K×10回 | $6.40 | $12.80 | +100% |
| キャッシュヒット継続 | 100K×10回 | $6.40 | $0.20（読込のみ） | −97% |

**対策**:
- タスクをバッチ処理し、キャッシュ書込回数を最小化する
- 同じプレフィックスを使い回し、新規書込を減らす
- 長時間の一括処理では、書込コストよりヒット率向上の効果が上回ることを確認する

### パターン9: 外部API経由でのキャッシュ分断（API Route Cache Fragmentation）

**発生条件**: Claude Codeの内部API呼出しと、カスタムスクリプトからの直接API呼出しが混在する。

**原因**: Claude Code CLIが使うAPIエンドポイントと、ユーザーが直接呼ぶAPIエンドポイントでキャッシュ空間が分断される（異なるAPIキー・異なるリージョン・異なる認証方式）。片方で温めたキャッシュがもう片方で使えない。

**コストインパクト**: 分断された経路ごとに独立したキャッシュが必要。2経路で2倍、3経路で3倍のキャッシュ書込コスト。

**対策**:
- Claude CodeのAPI呼出しとカスタムスクリプトのAPI呼出しで、同一のAPIキー・リージョンを使用する
- 可能であればClaude Code CLIの内部API呼出しに統一する
- APIキーを用途別に分ける場合は、キャッシュが独立することを認識して運用する

## 4. 株式会社オージャストへの適用

### ユースケース: ブースデザイン生成・イベント企画の長セッション

オージャストでは展示会ブースのデザイン生成やイベント企画で、長時間のClaude Codeセッションが頻繁に発生する。1セッションあたりの平均的なキャッシュ損失を試算する:

**現状（対策前）**:
- 1セッション: 200K Input Tokens、モデル呼出し50回
- キャッシュヒット率: 約40%（モデル切替・離席・`/compact`による断片化）
- コスト: 約$24.00/セッション（50回のうち20回がヒット($0.02)、30回がミス($0.80)）

**改善後（9対策適用）**:
- キャッシュヒット率: 約85%
- コスト: 約$8.60/セッション（43回ヒット($0.02)、7回ミス($0.80)）
- **削減率: 約64%**

### 実装手順

1. **セッション開始時の固定設定**:
   - 使用するモデル（Opus/Sonnet）を決め、セッション中に変更しない
   - FastモードのON/OFFを決め、途中で切り替えない
   - システムプロンプトに静的先頭配置（X-0015）を適用

2. **休憩時のキャッシュ維持**:
   - 自然な休憩（トイレ・会議）の前に短いクエリ（例: `「続けて」`）を実行し、キャッシュTTLをリセット
   - `/compact` はキャッシュが古くなったタイミング（アイドル45分後など）に計画的に実行
   - 昼食など長時間離席の前は、会話を保存してセッションを閉じる

3. **繰り返し使うテンプレートの先頭配置**:
   - 展示会の基本情報・ブース規格データ・デザインガイドラインをシステムプロンプト先頭に固定（X-0015）
   - 案件ごとに変わる部分（企業名・出展ブース番号）は末尾に配置
   - これにより、セッション間でも共通Prefixのキャッシュが効く

4. **ヒット率の監視**:
   - `/usage` コマンドで `cache_read_input_tokens` / `input_tokens` の比率を確認
   - 目標: ヒット率85%以上
   - ヒット率が60%を下回ったら、どの漏洩パターンが発生しているか診断

### 期待効果

| 軸 | 対策前 | 対策後 | 改善 |
|----|-------|-------|------|
| キャッシュヒット率 | 40% | 85% | +45pt |
| 1セッションコスト（50呼出） | $24.00 | $8.60 | −64% |
| モデル切替による損失 | 毎回$0.80 | $0 | ゼロ |
| `/compact` による損失 | 毎回$0.40〜0.80 | 計画的実行で$0.20 | −50〜75% |
| 離席による損失（10回/日） | $8.00/日 | $1.60/日（probe活用） | −80% |
