# X-0018: 構築エージェントと評価エージェントを分離したUI改善ループ

## 概要

ブースデザインのWeb UIやイベントサイトのフロントエンド開発において、**構築（Build）** と **評価（Evaluate）** の責任を分離した改善ループを導入する。評価エージェントが視覚的一貫性と独創性を基準にチェックし、不合格であれば改訂要求をフィードバックする。承認前に改訂を必須化することで再現性を確保する。

## 問題

- 従来のAI開発では、同じAIが生成と自己チェックを兼ねるため、同じ見落としを繰り返す（AI運用プレイブック §原則）
- 視覚的品質の評価基準が属人化しており、再現性が低い
- 「OK」「もう少し」などの曖昧なフィードバックでは修正に反映できない

## 提案

**Build Agent**（UIを構築する）と **Evaluate Agent**（視覚的基準で評価する）を分離し、評価不合格→フィードバック→改訂のサイクルを必須化する。

```
┌─────────────┐    要件/仕様    ┌─────────────┐
│  Build Agent │ ──────────────│ Evaluate Agent│
│  (構築)      │ ← フィードバック │  (評価)      │
│              │                │              │
│  UIを生成    │ ──────────────→│ 基準と照合    │
│  修正を適用  │                │  合格/不合格  │
│              │                │  判定理由     │
└─────────────┘                └─────────────┘
                                        │
                                 不合格 │ 合格
                                        ▼
                                 ┌─────────────┐
                                 │  承認/デプロイ│
                                 └─────────────┘
```

## 評価基準

### 1. 視覚的一貫性（Visual Consistency）

| # | 基準 | 説明 | 判定方法 |
|---|------|------|---------|
| V1 | カラーパレット統一 | 既定のカラートークン（プライマリ/セカンダリ/アクセント/背景/テキスト）を守っているか | 全スタイルシートの色値がトークン範囲内か検査 |
| V2 | タイポグラフィ統一 | 見出し/本文/ラベルでフォントサイズ・行間・ウェイトの一貫性があるか | 全テキスト要素の CSS プロパティ検査 |
| V3 | スペーシング統一 | マージン・パディングが既定のスペーシング単位の倍数になっているか | 全要素の box model 検査 |
| V4 | コンポーネント統一 | 同じ意味の要素（ボタン/カード/入力欄）に同じスタイルが適用されているか | 同一コンポーネント間の差分検査 |
| V5 | 状態の一貫性 | hover/focus/active/disabled のスタイルが全対話要素に実装されているか | 疑似クラス付きスタイルの網羅検査 |

### 2. 独創性（Originality）

| # | 基準 | 説明 | 判定方法 |
|---|------|------|---------|
| O1 | テンプレート回避 | 既存テンプレートや一般的な配色パターンの完全コピーでないか | 既存デザインとの類似度スコア |
| O2 | レイアウトバリエーション | 全画面が同一レイアウトではなく、コンテンツに合わせた変化があるか | 画面間の構造的差異の分析 |
| O3 | ビジュアル階層 | 情報の重要度に応じた視覚的重み付け（サイズ/色/位置）が適切か | 主要要素の視覚的強調度の評価 |

### 3. ユーザビリティ（Usability）

| # | 基準 | 説明 | 判定方法 |
|---|------|------|---------|
| U1 | 応答性 | 320px〜1920pxの全幅でレイアウトが崩れないか | 複数ビューポートでのレイアウト整合性検査 |
| U2 | アクセシビリティ | WCAG 2.1 AA の色コントラスト/フォーカス可視性/ラベル付けを満たすか | 自動アクセシビリティ検査 |
| U3 | 読込みパフォーマンス | 画像の遅延読込・CSS/JSの最小化などの基本最適化が施されているか | Lighthouse 類似の静的検査 |

## 実装（Claude Code スキル）

### スキル構成

```
skilly/booth-ui-eval-loop/
├── SKILL.md                  # スキル定義
├── visual-criteria.md        # 評価基準の詳細定義
├── evaluate.mjs              # 評価エンジン（独立した評価エージェント）
├── build.mjs                 # 構築エージェント（評価結果に基づく修正）
├── loop.mjs                  # ループ制御
└── test/
    └── eval-loop.test.mjs    # テスト
```

### 評価エンジン（evaluate.mjs）

- 入力: UI の HTML+CSS（ファイルパスまたは文字列）
- 評価基準の各項目をスコア化（1〜5）
- 不合格項目ごとに具体的なフィードバック文を生成
- 総合スコアが閾値未満なら「不合格＋改訂要求」
- 出力: `{ scores, feedback, verdict: 'pass'|'revision' }`

### 構築エージェント（build.mjs）

- 入力: 要件/仕様 + 評価結果からのフィードバック
- フィードバックを反映した修正を適用
- 修正内容の変更差分を記録
- 再評価のために評価エンジンを呼び出す

### ループ制御（loop.mjs）

- 最大試行回数（既定3回）を設定
- 各試行の評価スコアと修正内容を履歴として保存
- 合格または最大試行到達でループ終了
- ループ終了後に承認者へのレポートを生成

## 適用シナリオ

### ブースデザインWeb UI

制作アプリ（booth-app）のUI変更時に、評価エージェントが変更前後の画面を比較し、視覚的一貫性を保証する。

### イベントサイト

年会費/イベント申込フォームやランディングページの新規作成時に、ブランドの視覚基準を自動評価する。

## 成功条件

1. 評価エージェントが不合格と判定したUIの80%以上が、1回の改訂サイクルで合格に達する
2. 承認者が「視覚的に違和感がある」と指摘するケースが従来比50%以上減少する
3. 評価からフィードバックまでの所要時間が5分以内（従来のレビュー依頼の数時間から改善）
