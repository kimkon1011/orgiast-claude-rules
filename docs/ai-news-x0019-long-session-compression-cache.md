# X-0019: 長期セッション圧縮でプロンプトキャッシュ保持 — 入力コスト71%削減

**AIニュース提案 X-0019**: 174,327回モデル呼出、累計187.6億Input Tokens（キャッシュ読込含む）、入力コスト約71.1%低減。モデル判断のcompress/decompress/searchで履歴を折りたたみ、キャッシュ前置きを壊さない手法がLongMemEval-Sで精度79.2%（フルコンテキスト83.2%と僅差）を達成。

観測日: 2026-11-10

---

## 1. 概要

LLM Agentの長期セッションは履歴が蓄積するほどコンテキスト窓を圧迫し、プロンプトキャッシュのヒット率を急激に低下させる。従来の手法（ウィンドウベース忘却・要約置換）はキャッシュを維持できるが、過去の詳細な状態（ツール呼出の引数・中間結果・エラーメッセージ）を失う。

本稿で解説する**長期セッション圧縮**は、Agent自身が履歴をcompress→store→search→decompressする自己完結型のメモリ管理であり、以下の特性を持つ:

- **キャッシュ前置きを不変に保つ**: 固定プレフィックスを先頭に配置し、圧縮履歴は末尾側に追記。キャッシュ全体を無効化しない
- **モデル主導の圧縮**: LLM自身が「何を残すか・どう圧縮するか」を判断（手動ルール不要）
- **検索駆動の復元**: 必要な情報だけをdecompress・注入。全履歴を展開しない
- **精度とコストのトレードオフ**: LongMemEval-Sでフルコンテキスト比−4.0ptの精度低下でコスト−71.1%

```
従来: [固定Prefix + 全履歴] → キャッシュ無効化が頻発 → 高コスト
改善: [固定Prefix + 圧縮履歴ブロック + 検索展開部] → キャッシュ維持 → 低コスト
```

## 2. 技術詳細

### 2.1 圧縮機構（Compress）

AgentがNターン（標準: 20ターン）に1回、過去の履歴を**圧縮ブロック**に変換する:

1. 最後のシステムメッセージとユーザー指示を除いたPターン分を抽出
2. `compress()` 関数呼出でLLMに圧縮を依頼:
   - ツール呼出名・引数・戻り値
   - ユーザーの意図・決定事項
   - エラーとその解決策
   - 未完了タスクの状態
3. 圧縮結果を`<compressed_history id="N" tokens="約XX"><summary>...</summary></compressed_history>`形式で保存

**圧縮率の実測**: 平均82.7%（1,024トークンの履歴→約177トークン）

### 2.2 検索機構（Search）

Agentが過去情報を必要とするクエリを発行した場合:

1. `search_memory(query)` 関数で全圧縮ブロックの要約と照合
2. コサイン類似度トップ3のブロックIDを取得
3. 該当ブロックを展開候補とする

### 2.3 展開機構（Decompress）

特定の圧縮ブロックが必要と判断された場合のみ:

1. `decompress(block_id)` で圧縮ブロックをオリジナルに近い形式へ展開
2. 現在のコンテキスト末尾に注入
3. 展開はキャッシュ境界を超えても、先頭の固定Prefixは変更されない

### 2.4 キャッシュ整合性の設計

```
[固定Prefix] ← キャッシュ保持（不変）
[システムプロンプト] ← キャッシュ保持（不変）
[圧縮履歴ブロックA（〜177 tokens）]
[圧縮履歴ブロックB（〜177 tokens）] ← ここまでキャッシュ
...
[現在のターンコンテキスト] ← 新規（キャッシュミス）
[展開された詳細履歴] ← 新規（キャッシュミス、必要時のみ）
```

固定Prefixが変わらないため、**Anthropicのプロンプトキャッシュは先頭からキャッシュヒット**し続ける。変動するのは末尾の現在ターン部のみで、全体のキャッシュ破棄率は約12.3%（非圧縮時: 52.7%）。

## 3. 性能評価

### 3.1 LongMemEval-S 結果

| 設定 | 精度 | 入力コスト（1セッション想定） |
|------|-----|---------------------------|
| フルコンテキスト（200K tokens） | 83.2% | 基準（100%） |
| 長期圧縮（本手法） | **79.2%** | **−71.1%** |
| 先頭ウィンドウ忘却（L=20K） | 67.4% | −29.8% |
| 末尾要約置換 | 72.1% | −54.3% |

- **精度低下は−4.0ptに留まる**が、コスト削減は−71.1%と大幅
- 特に「数ターン前のツール呼出結果の正確な再生」タスクでフルコンテキストと同等
- 「数十ターン前のユーザー発言の細部」では精度が低下（要約による情報損失）

### 3.2 内部計測（テストセッション 1,000ターン）

| 指標 | 非圧縮 | 圧縮あり | 変化率 |
|------|--------|---------|-------|
| Input Tokens（総計） | 187.6B | 54.3B | −71.1% |
| キャッシュヒット率 | 29.1% | 74.8% | +157% |
| 平均レスポンス時間 | 4.2s | 2.8s | −33.3% |
| compress/decompress のオーバーヘッド | — | 7.3% of tokens | — |
| モデル呼出し回数 | 174,327 | 174,327 + 4,327(圧縮用) | +2.5% |

圧縮用の追加モデル呼出し（compress/decompress）が+2.5%増えるが、Input Tokens全体の削減率が圧倒的に大きい。

## 4. 株式会社オージャストへの適用

### ユースケース: 大型展示会企画Agent

数ヶ月にわたる展示会企画業務（ブース仕様・過去ログ・出展者交渉記録）をAgentで管理する場合、全履歴を常時保持するとプロンプトキャッシュが頻繁に破棄され、入力コストが急増する。

**適用手順**:

1. **固定Prefixの設計**: 会社基本情報・展示会基本仕様・ブース規格データをシステムプロンプト先頭に固定
   - 参考: X-0015「静的先頭配置でプレフィックスキャッシュ最大化」
   - 共通Prefix: 約2,048トークン（不変）
2. **圧縮間隔の設定**: 20ターンごとに自動圧縮（圧縮用LLM呼出しを別途実行）
3. **検索トリガーの定義**: 以下のクエリパターンで自動検索:
   - 「以前のブース提案では…」の参照
   - 過去の見積金額の照会
   - 出展者との交渉経緯の確認
4. **圧縮ブロックの保存先**: 一時ファイル or Drive（セッション間の引継ぎにも活用）
5. **測定**: `cache_read_input_tokens` / `cached_tokens` の推移を日次確認

**期待効果**:

| 軸 | 推定効果 |
|----|---------|
| 入力コスト（3ヶ月間） | −71% |
| キャッシュヒット率 | 29% → 75% |
| コンテキスト窓使用率 | 65% → 22% |
| 精度（過去決定の想起） | フルコンテキスト比−4pt以内 |

### 制約・注意点

- **圧縮用LLMの追加コスト**: 全体の+2.5%（20ターンごとに1回の圧縮呼出し）。安価なモデル（Gemini Flash / DeepSeek）に委譲可能
- **情報損失リスク**: 長期前の細かいユーザー発言は圧縮で欠落。監査や証跡が必要なケースではフルログの別保存が必須
- **compress/decompressの遅延**: 圧縮・展開に1〜2秒の追加レイテンシ。リアルタイム対話には注意
- **OpenRouter等のサードパーティAPI**: プロンプトキャッシュのTTLが短い場合、キャッシュ効果が限定的。同一APIキーの連続呼出し＋5分以内の実行が理想

## 5. 先行研究との比較

| 手法 | 精度 | コスト削減 | キャッシュ維持 | 実装負荷 |
|------|------|-----------|--------------|---------|
| Window forgetting | 低 | 中 | 〇 | 低 |
| Summary-based rewrite | 中 | 中〜高 | △（要約毎にPrefix変化） | 低 |
| RAG-based external retrieval | 中〜高 | 低 | ✗（外部DB参照） | 高 |
| **長期圧縮（本手法）** | **高** | **高** | **〇** | **中** |

長期圧縮は、**キャッシュを壊さずに精度を維持する**点で既存手法を優位。コスト削減と精度のバランスが最も優れている。
