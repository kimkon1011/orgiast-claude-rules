# X-0020: Grok Bot監視頻度最適化によるトークン削減

**AIニュース提案 X-0020**: 監視間隔を1分ごと（1日1440回）から15分ごと（1日96回）に変更しチェック回数約93%削減。変化なし時は通知せずSTATUS: NO_CHANGEのみ記録。差分監視で前回確認以降のみ取得。第1段階で変化検出、条件一致時のみ第2段階分析。株式会社オージャストのイベント問い合わせ・ブース制作進捗監視に15-30分間隔と差分取得を適用しトークン消費を記録する。

観測日: 2026-11-12

---

## 1. 概要

現在のGrok Bot監視は1分間隔（1日1440回）で動作しており、xAI APIへのリクエストとClaude Codeへの通知が過剰なトークン消費を引き起こしている。監視頻度を15分間隔に緩和し、変化がない場合の通知を省略することで、チェック回数・トークン消費・API呼び出しの約93%削減が期待できる。

| 指標 | 現状（1分間隔） | 提案（15分間隔） | 削減率 |
|------|----------------|-----------------|--------|
| 1日あたりチェック回数 | 1,440回 | 96回 | 93.3% |
| 月間チェック回数 | ~43,200回 | ~2,880回 | 93.3% |
| トークン消費（概算） | 100% | ~6.7% | ~93.3% |
| API呼び出し回数 | 100% | ~6.7% | ~93.3% |

---

## 2. 現状の課題

### 2.1 過剰ポーリングによるトークン浪費

現在のGrok Bot監視ループは1分ごとに以下を実行している：

1. Grok API呼び出し（リクエストトークン消費）
2. レスポンス解析（出力トークン消費）
3. 変化の有無を判定
4. 変化なしでもClaude Codeへ状態通知

**問題点**:
- 監視対象の90%以上の時間帯で変化が発生しない
- 変化がない場合でもGrok APIへのリクエスト（入力トークン）が消費される
- Claude Codeへの通知もトークンを消費する
- 通知の蓄積がコンテキストを圧迫する

### 2.2 差分取得の非効率

現在の実装では毎回フル状態を取得しており、前回との差分計算に不要なトークンを消費している。

---

## 3. 提案する最適化

### 3.1 監視頻度の緩和

| 対象 | 現状 | 提案 |
|------|------|------|
| イベント問い合わせ監視 | 1分間隔 | 15分間隔 |
| ブース制作進捗監視 | 1分間隔 | 15-30分間隔 |
| X/Twitterトレンド監視 | 1分間隔 | 30分間隔 |
| 業界ニュース監視 | 1分間隔 | 60分間隔 |

### 3.2 段階的監視（2ステージ）

**第1段階（15分ごと）**: 変化の有無のみを高速判定
- 前回確認時の状態スナップショットとの差分をチェック
- 変化なし → `STATUS: NO_CHANGE` をローカル記録のみ（通知なし）
- 変化あり → 第2段階へ

**第2段階（条件一致時のみ）**: 詳細分析
- 変化内容の詳細をGrokに分析させる
- 分析結果をClaude Codeへ通知
- 分析結果に基づいてアクションを実行

### 3.3 差分監視

前回確認時の状態をJSONで保持し、次回確認時は差分のみを取得する：

```json
// 状態スナップショット（checkpoint.json）
{
  "lastCheck": "2026-11-12T10:00:00Z",
  "state": {
    "event_inquiries": { "count": 3, "latest": "2026-11-12T09:30:00Z" },
    "booth_progress": { "stage": "design", "updated": "2026-11-12T08:00:00Z" },
    "x_trends": { "keywords": [], "updated": "2026-11-12T09:00:00Z" }
  }
}
```

### 3.4 通知最適化

| 状態 | 現状 | 提案 |
|------|------|------|
| 変化なし | 毎回通知 | ローカル記録のみ（STATUS: NO_CHANGE） |
| 軽微な変化 | 詳細通知 | 1行サマリのみ |
| 重要な変化 | 詳細通知 | 詳細分析＋アクション提案 |

---

## 4. 実装計画

### Phase 1: 設定変更（即日）

1. 監視スクリプトのインターバル設定を変更（1分→15分）
2. 通知制御フラグの追加（NO_CHANGE時はスキップ）
3. 状態スナップショット機構の実装

### Phase 2: 差分監視（1週間）

1. チェックポイントファイル（JSON）の管理ロジック実装
2. 差分取得APIの最適化
3. 段階的分析の分岐ロジック実装

### Phase 3: 通知最適化（2週間）

1. 通知レベル（NO_CHANGE / サマリ / 詳細）の実装
2. コンテキスト圧迫防止のための通知集約
3. トークン消費ログの記録機構

## 5. 期待される効果

### トークン削減試算

| 項目 | 現状（月間） | 提案後（月間） | 削減 |
|------|------------|--------------|------|
| Grok API呼び出し | ~43,200回 | ~2,880回 | -93.3% |
| 入力トークン（Grok） | ~43.2M | ~2.9M | -93.3% |
| 出力トークン（Grok） | ~21.6M | ~1.4M | -93.3% |
| Claude Code通知トークン | ~8.6M | ~0.6M | -93.3% |
| **合計トークン** | **~73.4M** | **~4.9M** | **-93.3%** |

※トークン数は監視1回あたり入力1,000 + 出力500 + 通知200 と仮定

### コスト削減試算

| プロバイダ | 現状（月間） | 提案後（月間） |
|-----------|------------|--------------|
| xAI Grok（$2/1M入力, $10/1M出力） | ~$302 | ~$20 |
| Claude Code（$3/1M入力, $15/1M出力） | ~$26 | ~$2 |
| **合計** | **~$328/月** | **~$22/月** |

### 運用面の効果

- **監視遅延**: 1分 → 15分（許容範囲内。ブース制作進捗は時間単位の変化が大半）
- **アラート疲れの低減**: ノイズ通知が93%削減され、本当の変化に集中できる
- **コンテキスト節約**: Claude Codeのコンテキストが通知ログで圧迫されなくなる

## 6. オージャストへの適用

### 対象監視項目

| 監視対象 | 現状間隔 | 提案間隔 | 差分監視 | 備考 |
|---------|---------|---------|---------|------|
| イベント問い合わせ（問合せフォーム） | 1分 | 15分 | ✅ | 営業時間外は30分でも可 |
| ブース制作進捗（タスクシート更新） | 1分 | 15分 | ✅ | 制作会社の更新は時間単位 |
| メール受信（fleet-mail） | 1分 | 15分 | ✅ | 新着のみ取得 |
| X/Twitterメンション監視 | 1分 | 30分 | ✅ | リアルタイム性低 |
| 業界ニュース（RSS） | 1分 | 60分 | ✅ | 日次でも可 |
| Discord通知 | 1分 | 15分 | ✅ | チャンネル別に要調整 |
| スプレッドシート変更 | 1分 | 30分 | ✅ | 変更トリガーがあればそちらを優先 |

### 実装手順

1. 各監視スクリプトの設定を `config/watch-intervals.json` に集約
2. チェックポイント機構を `tools/watch-checkpoint.mjs` として実装
3. 段階的分析を `tools/watch-two-stage.mjs` として実装
4. 移行期間は新旧並行稼働でトークン消費を比較記録

### 測定指標

- 日次/月次のGrok API呼び出し回数
- 日次/月次のトークン消費量（入力・出力別）
- 変化検出の平均遅延時間（目標: 15分以内）
- 見逃し率（目標: 0%。差分監視でカバー）

---

## 7. リスクと対策

| リスク | 対策 |
|-------|------|
| 監視間隔拡大による変化検出遅延 | 重要度に応じた優先監視（重要イベントは5分間隔を維持） |
| 状態スナップショットの不整合 | 起動時にフル同期＋ハートビートで整合性確認 |
| 差分取得のバグによる見逃し | 1日1回フルスキャンでバックアップ |
| 通知レベルの誤判定 | 重要変化は常に詳細通知（ビジネスルールベース） |
