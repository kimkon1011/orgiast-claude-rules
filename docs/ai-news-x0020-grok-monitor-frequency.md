# X-0020: 監視頻度3段階化と差分処理でGrokコスト削減

> AIニュース提案 2026-11-12
> 対象: Grok Bot の監視頻度最適化（3段階頻度 / 差分処理 / 時間帯別制御）

## 概要

Grok Bot を使った情報監視（競合監視・SNS反応・顧客問い合わせ）のチェック頻度を、全対象一律ではなく**緊急・通常・収集の3段階**に分類する。1分間隔（1日1,440回）から15分間隔（1日96回）へ変更することでチェック回数を約93%削減する。さらに変化がない場合の通知停止・差分のみの取得・時間帯別頻度変更により、Grok API の呼び出しコストを最大 **99%削減**できる。

```
[変更前] 全対象を1分間隔で監視 → 1日1,440回 の Grok API 呼び出し
[変更後] 対象ごとに頻度を3段階に設定 → 1日約96回（▲93%）

さらに:
  - 変化なし時は STATUS:NO_CHANGE のみ記録（AI分析をスキップ）
  - 前回からの差分だけ取得（全件再読込を回避）
  - 時間帯別に頻度変更（営業中15分 / 時間外60分）
  - 1回の処理上限を設定（新着10件まで）
```

## 1. 現状の問題

| 問題 | 影響 |
|------|------|
| 全監視対象を同じ頻度（1分間隔）でチェック | Grok API 呼び出しが1日1,440回に膨らむ |
| 変化がなくても毎回AI分析を実行 | 無駄なトークン消費（90%以上が"変化なし"） |
| 毎回全件を再読込 | 重複データの転送・処理 |
| 24時間同じ頻度 | 深夜・早朝のチェックはほぼ無意味 |
| 監視対象が増えても頻度を調整しない | 対象が増えるほどコストが線形に増加 |

## 2. 3段階頻度モデル

監視対象を重要度に応じて3つのティアに分類する:

| ティア | 頻度 | 1日あたり回数 | 対象例（オージャスト） | 備考 |
|-------|------|-------------|---------------------|------|
| **緊急 (emergency)** | 5〜15分 | 96〜288回 | イベント期間中の顧客問い合わせ、障害通知、発注関連 | イベント期間のみ、それ以外は通常にダウングレード |
| **通常 (normal)** | 15〜60分 | 24〜96回 | 通常時の顧客問い合わせ、SNS反応、メディア言及 | デフォルト。ビジネスアワーは15分、時間外は60分 |
| **収集 (collect)** | 6〜12時間 | 2〜4回 | 競合情報、業界ニュース、市場トレンド | 更新を確認するだけで即時性不要。1日2回で十分 |

**デフォルト推奨**: 15分間隔（1日96回）に統一。緊急時のみ5分、収集系は6-12時間。

### コスト比較

| 方式 | 1日あたりGrok呼出し | 月間呼出し(概算) | コスト(月間概算) |
|------|-------------------|----------------|----------------|
| 現状: 1分間隔 全対象 | 1,440回 | 43,200回 | **基準額** |
| 3段階: 5〜60分＋時間帯別 | 〜96回 | 〜2,880回 | **約6.7%** (▲93.3%) |
| 3段階＋変化時のみAI分析 | 変化検出のみ | 〜1/10以下 | **約0.2〜1%** (▲99%) |

※正確な削減率は監視対象の数・変化頻度に依存する。変化が1日1回だけの対象では、チェック回数1,440→96（▲93%）に加え、AI分析が不要なためさらに約90%削減。

## 3. 省コスト機構

### 3.1 変化なしは通知しない（STATUS:NO_CHANGE）

変化がないチェック結果は通知を生成せず、`STATUS:NO_CHANGE` としてログにだけ記録する。AI分析（Grok API 呼び出し）自体をスキップする。

**フロー**:
```
1. 前回のスナップショット（ハッシュ値）と比較
2. 変化なし → STATUS:NO_CHANGE を記録して終了（API呼出し不要）
3. 変化あり → 差分のみをGrok APIに渡して分析
```

### 3.2 差分取得（全件再読込の回避）

監視対象の全データを毎回取得する代わりに、前回確認時のチェックポイント以降の差分だけを取得する。

```
[従来]  全データを取得 → Grok API に丸ごと送信 → 分析
[改善]  差分（新着のみ）を取得 → 差分だけ Grok API に送信 → 分析
```

### 3.3 2段階処理（軽処理→AI分析）

第1段階で軽量な変化検出（HTTPステータス確認・ハッシュ比較・タイムスタンプ照合）を行い、変化があった時だけ第2段階で Grok API を使ったAI分析に進む。

```
          ┌──────────────┐
          │ 監視対象チェック │ ← ここはHTTPヘッダーレベル等の軽処理
          └──────┬───────┘
                  │
           変化あり？──┼──→ No → STATUS:NO_CHANGE（Grok API不使用）
                  │
                 Yes
                  ▼
          ┌──────────────┐
          │ Grok API分析  │ ← ここだけ従量課金
          └──────────────┘
```

### 3.4 時間帯別頻度制御

営業時間（9:00-18:00）と時間外（18:00-9:00）で頻度を変更する。

| 時間帯 | 頻度 | 1日あたり回数 | 節減効果 |
|-------|------|-------------|---------|
| 営業中 (9:00-18:00) | 15分 | 36回 | — |
| 時間外 (18:00-9:00) | 60分 | 15回 | 時間外を60分にすると50%減（全体で約58%減） |
| 深夜 (0:00-6:00) | チェック停止 | 0回 | 対象による（完全停止で約25%減） |

### 3.5 1回の処理上限設定

1回の監視サイクルで処理する新着上限を設定する（例: 最大10件）。上限を超えた新着は次回に持ち越す。これにより1回のAPI呼び出しのトークン消費を予測可能にする。

### 3.6 対象数制限（7日間で3つ以内）

7日間のアクティブ監視対象を3つ以内に絞り、頻度を対象ごとに見直す。一時的に監視を休止する対象は `STATUS:SLEEPING` として保存し、週次レビューで再開判断する。

## 4. 検証可能なコストモデル

`tools/grok-monitor-cost-model.mjs` が上記コストモデルを実装し、`tools/grok-monitor-cost-model.test.mjs` が node:test で検証する。

```
node --test tools/grok-monitor-cost-model.test.mjs   # 全テスト green を確認
node tools/grok-monitor-cost-model.mjs                # 削減率一覧を表示
```

### モデルの計算式

```
削減率 = 1 - (改善後のコスト / 改善前のコスト)

改善前コスト = 監視対象数 × チェック間隔(回数) × API単価
改善後コスト = Σ(ティア別チェック回数 × API単価) + Σ(変化時AI分析回数 × AI単価)
```

### テストで固定する値

| 入力 | 期待する削減率 |
|------|-------------|
| 1分間隔(1,440回/日) → 15分(96回/日) | 約93.3% |
| 1分間隔 + AI分析毎回 → 15分 + 変化時のみAI | 約99.0%以上 |
| 時間帯別(営業15分/時間外60分) + 変化時のみAI | 約99.5%以上 |
| 緊急5分/通常15分/収集12時間 (変化率10%想定) | 約90%以上 |

## 5. オージャスト適用シナリオ

株式会社オージャストの展示会ブース業務に当てはめた具体的な設定:

| 監視対象 | ティア | 頻度 | 時間帯別 | 備考 |
|---------|-------|------|---------|------|
| 展示会ブースの顧客問い合わせ | 通常 | 15-30分 | 営業中15分 / 時間外60分 | イベント期間のみ緊急に昇格 |
| 競合情報（他社ブース関連） | 収集 | 6-12時間 | 1日2回固定 | 毎朝・夕にチェック |
| SNS反応（X/Twitterでの言及） | 通常 | 1-3時間 | 日中1時間 / 夜間3時間 | キャンペーン期間のみ通常に |
| 展示会スケジュール・締切 | 収集 | 12時間 | 1日2回 | 新着チェックのみでOK |
| 発注・入札情報（イベント期間） | 緊急 | 5-10分 | 24時間 | 期間終了後は通常に戻す |

**期待効果**:
- チェック回数: 1日1,440回 → 約96回（▲93%）
- AI分析回数: 変化がない限りゼロ（ほぼ全停止）
- 月間コスト: 現行比 **約1-5%** に低減
- 通知の質: 変化ありのときだけ届くので見落とし防止

## 6. 実装手順

1. **現状の監視スクリプト棚卸し**: 現在の Grok Bot が何を・どの頻度でチェックしているかリスト化
2. **監視対象の3段階分類**: ティア割り当て（緊急/通常/収集）
3. **差分取得機構の実装**: チェックポイントファイル（JSON）の管理
4. **時間帯別頻度制御の実装**: cron式のスケジュール定義
5. **変化検出（第1段階）の実装**: ハッシュ比較・HTTPヘッダー確認
6. **STATUS:NO_CHANGE の通知制御**: 記録のみでSlack/Grok通知を抑制
7. **上限設定**: 1処理あたりの最大新着数を config 化
8. **週次レビュー機構の追加**: 監視対象の休眠/再開判断を自動化

## 7. 制約・注意点

- **変化を見逃すリスク**: 頻度を下げると変化を検出するまでのタイムラグが生じる。緊急ティアはイベント期間のみに限定する
- **差分取得の正確性**: チェックポイントの永続化（停電・障害時）を考慮した設計が必要
- **時間帯別制御の過信**: 深夜にも顧客からの問い合わせ（LINE等）が届く可能性がある。完全停止は推奨せず「60分間隔＋差分のみ」を下限とする
- **コスト削減率は対象の性質に依存**: 変化が頻繁な対象には効果が薄い。実測値でティア割り当てを調整する
