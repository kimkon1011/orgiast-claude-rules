# X-0021: Claude effort調整とHaikuサブエージェントでコスト4割減

> AIニュース提案 2026-11-12
> 対象: Claude Code のタスク分担（effort 調整 / Haiku・Sonnet・Opus のモデルルーティング）

## 概要

タスクのコストを下げるために「モデルを替える前に effort を変える」。Opus 5.5 を effort medium で使い、分類・抽出・ログ読みは Haiku サブエージェント、範囲が明確なバグ修正・実装は Sonnet、全体企画のみ Opus（effort medium）で実行する。さらに「全部 low で回して失敗した分だけ high で再実行する」方式（失敗時リトライ方式）により、正解率 97% の前提で全部 high にして回すよりコストを約 4 割減らせる。

```
[タスク投入]
   ├─ 分類・抽出・ログ読み     → Haiku サブエージェント（model: haiku）
   ├─ 範囲明確なバグ修正・実装 → Sonnet
   └─ 全体企画・方針判断        → Opus 5.5（effort medium）
         │
         ▼
   [失敗時リトライ方式]
     ├─ 全タスクを effort low で実行
     └─ 失敗（検証 NG）した分だけ effort high で再実行
         → 正解率 97% なら全部 high より約 4 割コスト減
```

## 1. モデルを替える前に effort を変える

モデルを切り替えるとプロンプトキャッシュが失われ、同じ文脈を最初から送り直すことになる。同モデル内で effort を下げる方が、キャッシュを温かいまま保てる。

| 変更手段 | キャッシュ | 品質への影響 | コスト |
|---|---|---|---|
| effort を high → medium / low | 維持 | 少し下がる（失敗分は high 再実行で回収） | 数割減 |
| Opus → Sonnet / Haiku | 失われる | タスク次第で大きく下がる | 数分の1 |

そのため、**まず effort 調整を試し、それでも足りない部分だけ上位モデルへ**回す。

## 2. タスク種別ごとのモデル分担

株式会社オージャストの展示会ブース提案ワークフローに当てはめると:

| タスク | モデル | effort | 例 |
|---|---|---|---|
| 顧客要望の分類・抽出 | Haiku | low–medium | 顧客ヒアリングの要望項目分類、提案要件の抽出 |
| ログ読み・状態確認 | Haiku | low | CI ログの失敗原因読み取り、入札状態の確認 |
| デザイン実装・修正（範囲明確） | Sonnet | medium | 既存パースの修正、ページ差分実装 |
| 全体企画・構成判断 | Opus 5.5 | medium | 提案書の全体構成、予算と要望の整合判断 |
| 失敗した部分の再実行 | Opus 5.5 | high | low で落ちた検証項目の再トライ |

ログ読みサブエージェントは `model: haiku` を明示し、健康診断・CI 失敗解析のような「安価で何度も呼ぶ」処理に使う。

## 3. コストモデルと「約4割減」の根拠

失敗時リトライ方式（全部 low ＋ 失敗分だけ high）:

```
全部 high のコスト:        n × H
low → 失敗分 high のコスト: n × L + (1 - p) × n × H

p = 正解率（low で通る割合）
L = low 1タスクあたりコスト
H = high 1タスクあたりコスト
```

例（Opus 5.5、タスクあたり low $0.17 / high $0.29、正解率 97%）:

```
全部 high: 100 × $0.29            = $29.00
low→再実行: 100×$0.17 + 3×$0.29   = $17.87
削減率:     1 - 17.87/29.0        ≈ 38.4%（約4割減）
```

- 正解率が 1.0 なら削減率は `1 - L/H` = 約41%
- 正解率が 50% まで落ちると `1 - (0.17+0.145)/0.29` = 約マイナス（逆に高くなる）
- つまり「正解率が低いタスク種別は最初から high」「正解率が高いタスク種別は低 effort ＋ failing 高速再試行」が最適

## 4. 検証可能なテスト手段

`tools/effort-cost-model.mjs` が上記コストモデルを実装し、`tools/effort-cost-model.test.mjs` が node:test で検証する。

```
node --test tools/effort-cost-model.test.mjs   # 全テスト green を確認
node tools/effort-cost-model.mjs --pass-rate 0.97 --low-cost 0.17 --high-cost 0.29 --count 100
# → NbLowFirst=117円相当の事例として、削減率38.4%を出力
```

テストで固定する値:

| 入力（p, L, H, n） | 期待する削減率 |
|---|---|
| 0.97, $0.17, $0.29, 100 | ≈ 38.4%（35%以上） |
| 1.00, $0.17, $0.29, 100 | ≈ 41.4% |
| 0.50, $0.17, $0.29, 100 | コスト増（削減率マイナス） |

## 5. Orgiast への適用（展示会提案コストの抑制）

1. ブース制作の顧客要望分類・抽出 → **Haiku サブエージェント**で実施
2. デザイン実装・修正 → **Sonnet**（範囲が明確なもの）に限定
3. 全体企画・提案書の構成 → **Opus 5.5 effort medium**
4. 検証に落ちた項目だけ **effort high で再実行**
5. 1〜4 の「cost per finished task」を `tools/effort-cost-model.mjs` の実測値で比較し、削減率を毎回記録する

## 6. 制約・注意点

- **正解率の計測が前提**: 低 effort の正解率が低いタスクに適用すると逆効果。サンプル計測で p ≥ 0.85 程度を確認してから本適用する
- **検証手段が必須**: 「失敗」を機械的に判定できるテストを渡し、high 再実行の対象を自動抽出する
- **モデル切替は自然ブレイクで**: プロンプトキャッシュを引き継がないため、同一目的のセッション内ではモデルを乱発しない
- **Fable は監督用途のみ**: Fable 5.2 は実装・量産・分類に使わず、企画判断の監督だけに保持する
