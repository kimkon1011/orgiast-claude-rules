# X-0023: 7つのOSSリポでAIワークフローインフラを再利用

**AIニュース提案 X-0023**: LangGraph（状態チェックポイントワークフロー）・n8n（ビジュアル接続）・LiteLLM（モデルゲートウェイ）・Pydantic AI・promptfoo・Phoenix（Arize）・FastMCPの7つのOSSリポジトリを評価し、株式会社オージャストのサイトSEO最適化ワークフローとブース予約UI自動化ワークフローへの適用を検討する。

観測日: 2026-11-11

---

## 1. 概要

AIワークフローインフラをスクラッチで構築する代わりに、成熟したOSSを組み合わせて再利用するアプローチを評価する。7つのリポジトリは以下の4層に分類できる：

| 層 | リポジトリ | 役割 |
|---|---|---|
| **オーケストレーション** | LangGraph, n8n | ワークフロー定義・状態管理・分岐 |
| **モデルアクセス** | LiteLLM | 複数LLMプロバイダへの統一ゲートウェイ |
| **エージェントフレームワーク** | Pydantic AI | 型安全なAIエージェント構築 |
| **評価・観測** | promptfoo, Phoenix | LLM評価・レッドチーミング・トレーシング |
| **MCP接続** | FastMCP | ツール・リソースのMCPサーバー化 |

---

## 2. リポジトリ別評価

### 2.1 LangGraph — 状態チェックポイントワークフロー

**GitHub**: [langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)

**特徴**:
- 長期実行・ステートフルなAIエージェントのための低レベルオーケストレーションフレームワーク
- グラフ（ノード＋エッジ）でワークフローを定義、LLM駆動ステップと決定論的ステップを混在
- **チェックポインター**: 各スーパーステップごとに状態をスナップショット保存
  - 永続性・フォールトトレランス: 障害から再開可能
  - Human-in-the-Loop: `interrupt()` で一時停止→状態検査→再開
  - タイムトラベル: 過去の実行をリプレイ、分岐探索
  - メモリ: スレッド内状態＋セッション間長期記憶
- スレッドベース状態管理: `thread_id` でチェックポイント所属管理

**オージャストへの適用判断**: **推奨（ブース予約UI自動化）**
- ブース予約フローは複数ステップ（日程選択→オプション選択→見積→承認→確定）で構成され、各ステップでHuman-in-the-Loopが必要
- 予約途中での中断・再開、状態の永続化にチェックポイント機構が最適
- ただし学習コストが高い（グラフ定義の理解が必要）

### 2.2 n8n — ビジュアルAIワークフロー自動化

**GitHub**: [n8n-io/n8n](https://github.com/n8n-io/n8n)

**特徴**:
- ノーコード/ローコードのビジュアルワークフロー自動化プラットフォーム
- **LangChain深層統合**: AIノードはLangChain JSフレームワーク上に構築
- AI Agent（Tools Agent）: MCPサーバー接続・Human-in-the-Loopツール承認対応
- 400+ ノード: Gmail, Slack, Google Sheets, HTTP等の既製コネクタ
- セルフホスト可能（Docker）, クラウド版もあり
- LangSmithトレーシング連携、ストリーミング対応

**オージャストへの適用判断**: **推奨（サイトSEO最適化ワークフロー）**
- SEO関連の定期処理（キーワード収集→コンテンツ生成→GSCデータ確認→レポート）をビジュアル編集で構築可能
- Gmail・Google Sheets・HTTPノードでGoogle系サービスと直接連携
- 非エンジニアでもメンテナンス可能なメリット大
- ただしブース予約UIのような複雑な状態遷移には不向き

### 2.3 LiteLLM — モデルゲートウェイ

**GitHub**: [BerriAI/litellm](https://github.com/BerriAI/litellm)

**特徴**:
- セルフホスト型AIゲートウェイ。単一のOpenAI互換エンドポイントで140+プロバイダ・1,800+モデルにルーティング
- **仮想キー**: キー単位・チーム単位・ユーザー単位の予算・レート制限
- **コスト管理**: リクエスト単位の費用追跡、キー/チーム/ユーザーへの按分
- **信頼性**: ロードバランシング、フォールバック、リトライ
- **ガードレール**: コンテンツフィルター、PIIマスキング
- **自動ルーティング**: 簡単なプロンプトは安価なモデルへ、難しいものは強力なモデルへ
- **キャッシング**: レスポンスキャッシュ・セマンティックキャッシュ（Redis, S3, GCS）
- 管理UI: ブラウザからモデル・キー・コスト・ログ管理
- デプロイ: Docker / Helm (Kubernetes) / Terraform、Postgres必須

**オージャストへの適用判断**: **推奨（全ワークフロー共通基盤）**
- SEO最適化とブース予約の両方で複数LLM（SEO用のGemini、予約用のClaudeなど）を使い分ける場合、単一エンドポイントで統制可能
- コスト管理・利用制限を一元的に実施できる
- 導入コストは低い（Dockerで即起動）

### 2.4 Pydantic AI — 型安全エージェントフレームワーク

**GitHub**: [pydantic/pydantic-ai](https://github.com/pydantic/pydantic-ai)

**特徴**:
- プロダクション向けGenAI SDK。Pydantic v2の型安全性をAIエージェントに適用
- **v2（2026-06リリース）**: 「capability」概念を中心にエージェント動作を構成
- **構造化出力**: `output_type` パラメータでスカラー・リスト・dict・TypedDict・Pydanticモデルを型安全に出力
- **3つの出力モード**: Tool Output / Native Output / Prompted Output
- **Human-in-the-Loopツール承認**: 高コストアクション実行前にユーザー確認
- **Durable Execution（Temporal連携）**: クラッシュから復旧
- **依存性注入**: ツールへのDI、エージェントの公開性維持
- **モデル非依存**: プロバイダを文字列で切り替え、障害時フォールバック
- **Pydantic Graph**: 型付きグラフベースワークフロー（LangGraphの軽量代替）

**オージャストへの適用判断**: **推奨（ブース予約UIのエージェント基盤）**
- 予約データのスキーマ定義（顧客情報・オプション・金額）をPydanticモデルで型安全に定義可能
- 構造化出力により予約確定データの信頼性が向上
- v2のcapability設計でSEO用・予約用の機能を分離して構成可能
- LangGraphより軽量で学習コストが低い

### 2.5 promptfoo — LLM評価・レッドチーミング

**GitHub**: [promptfoo/promptfoo](https://github.com/promptfoo/promptfoo)

**特徴**:
- ローカル実行のLLM評価・レッドチーミングCLI/ライブラリ
- **自動敵対的テスト生成**: カスタム攻撃を対象アプリに合わせて生成
- **157+ プラグイン**: ブランド/コンプライアンス/セキュリティ/信頼性など6カテゴリ
- **脆弱性カバレッジ**: プロンプトインジェクション、ジェイルブレイク、PII漏洩、SQLインジェクション、SSRF、BOLA/BFLA、ASCIIスマグリング、過剰なエージェンシー、ハルシネーション等
- **リスク管理フレームワーク**: OWASP Top 10 for LLMs、NIST AI RMF、MITRE ATLAS対応
- **モデル比較**: サイドバイサイドで複数モデル比較（OpenAI, Anthropic, Ollama等）
- **宣言的YAMLテストケース**: テスト駆動LLM開発
- CI/CD統合、Web UI

**オージャストへの適用判断**: **推奨（品質保証基盤）**
- ブース予約UIのフォーム入力が意図通りにLLM処理されるかのテストに最適
- SEOコンテンツ生成の品質評価（ハルシネーション検出、一貫性チェック）
- 導入は軽量（npm install / pip install で即使用可能）
- CIに組み込んで継続的評価が可能

### 2.6 Phoenix (Arize) — AI可観測性

**GitHub**: [Arize-AI/phoenix](https://github.com/Arize-AI/phoenix)

**特徴**:
- オープンソースのAI可観測性プラットフォーム
- **OpenTelemetry (OTLP) / OpenInference** ベースのトレーシング
- **自動インストルメンテーション**: LlamaIndex, LangChain, DSPy, Mastra, Vercel AI SDK
- **LLM-as-a-judge評価**: 構造化出力による評価、コードベース評価（exact match, regex）
- **プロンプト管理**: バージョン管理・デプロイ、Playgroundで比較実験
- **データセット＆実験**: トレースをデータセットにグループ化、実験実行
- 言語: Python, TypeScript, Java

**オージャストへの適用判断**: **条件付き推奨（監視基盤）**
- SEOワークフローとブース予約の両方のLLM呼び出しをトレースし、レイテンシ・トークン消費・エラー率を監視可能
- ただし既存のログ基盤（Grafana等）がある場合、追加導入の優先度は中
- 本番運用開始後に導入を検討

### 2.7 FastMCP — MCPサーバー構築フレームワーク

**GitHub**: [jlowin/fastmcp](https://github.com/jlowin/fastmcp)

**特徴**:
- MCP（Model Context Protocol）サーバーとクライアントを構築するPythonフレームワーク（v4.1.7）
- **多彩なプロバイダ**: FileSystemProvider（ホットリロード自動検出）、OpenAPIProvider（REST APIラップ）、リモートMCPサーバープロキシ
- **CLIツール**: `fastmcp install` でClaude Desktop/Cursor/Gooseにワンコマンド登録
- **プロトコル互換**: レガシーhandshake型とモダンsessionless型を1デプロイで両対応
- **インタラクティブツール**: 多ターン会話（予約フロー等）を `ctx.input_responses` で実現
- **エンタープライズID**: エージェント代理シナリオのID表明、ロールベース認可
- **OpenTelemetryトレーシング**: 組み込み
- **MCP Apps（3.1 preview）**: Python DSLで生成UI（JavaScript不要）

**オージャストへの適用判断**: **推奨（ツールのMCPラップ）**
- 既存の社内ツール（在庫照会・見積生成・顧客DB）をMCPサーバー化し、Claude等のAIから直接呼び出せるようにする
- ブース予約UIの外部サービス連携（カレンダー照会・在庫確認・決済）をMCP経由で統一
- FastMCPを使えばPythonの関数をデコレーションするだけでMCPサーバーになる

## 3. オージャスト用途別リポジトリ比較

### 3.1 サイトSEO最適化ワークフロー

```
[キーワード調査] → [コンテンツ生成] → [内部SEO設定] → [GSC確認] → [改善ループ]
```

| リポジトリ | 役割 | 優先度 |
|---|---|---|
| **n8n** | ワークフロー全体のビジュアルオーケストレーション。Gmail・Google Sheets・HTTPノードでSEOツールと連携 | ★★★ 最優先 |
| **LiteLLM** | コンテンツ生成用LLM（Gemini/Claude）の一元管理・コスト統制 | ★★★ 必須 |
| **promptfoo** | 生成コンテンツの品質評価・ハルシネーション検出 | ★★ 有用 |
| **Phoenix** | ワークフローのトレーシング・性能監視 | ★ 本番後 |
| **LangGraph** | 複雑な条件分岐が必要な高度なSEO判断フロー | ★ 将来 |

**推奨構成**: n8n（オーケストレーション）→ LiteLLM（LLMゲートウェイ）→ promptfoo（評価）

### 3.2 ブース予約UI自動化ワークフロー

```
[日程選択] → [ブース種別選択] → [オプション設定] → [見積生成] → [承認] → [確定・通知]
```

| リポジトリ | 役割 | 優先度 |
|---|---|---|
| **Pydantic AI** | 予約データの型安全なスキーマ定義・エージェントロジック | ★★★ 最優先 |
| **LangGraph** | 複数ステップの状態管理・中断/再開・Human-in-the-Loop | ★★★ 必須 |
| **FastMCP** | 既存システム（在庫・カレンダー・顧客DB）のMCPサーバー化 | ★★★ 必須 |
| **LiteLLM** | 見積提案用LLMの一元管理 | ★★ 有用 |
| **promptfoo** | 予約フローのテスト自動化 | ★★ 有用 |
| **n8n** | 通知・メール送信等の後処理自動化 | ★ 周辺 |
| **Phoenix** | トランザクションのトレーシング | ★ 本番後 |

**推奨構成**: Pydantic AI（エージェント）+ LangGraph（状態管理）+ FastMCP（外部連携）

## 5. 導入優先順位と推奨アクション

### Phase 1（即日〜1週間）: 基盤構築
1. **LiteLLM** をDockerで導入 → SEO用・予約用のLLMルーティング一元化
2. **n8n** をDockerで導入 → 既存のSEO手動タスクのワークフロー化開始
3. **promptfoo** を導入 → 現状のSEOコンテンツ品質のベースライン測定

### Phase 2（1〜2週間）: SEO最適化パイプライン
1. n8nでキーワード調査→コンテンツ生成→GSC確認のパイプライン構築
2. promptfooで生成コンテンツの自動評価CIパイプライン

### Phase 3（2〜4週間）: ブース予約UI自動化
1. Pydantic AIで予約エージェントのプロトタイプ
2. LangGraphで予約フローの状態管理・中断/再開
3. FastMCPで既存システム（在庫・カレンダー）のMCPサーバー化

### Phase 4（本番運用）: 監視・改善

2. パフォーマンス最適化とコスト削減
3. 継続的なプロンプト評価と改善ループ

## 6. 注意点・リスク

- **LiteLLM**: Postgresが必要（運用コスト増）。小規模ならOpenRouterで代替可能
- **n8n**: ノーコードの柔軟性と引き換えに、複雑な状態遷移は実装困難。予約UIのコアロジックには不向き
- **LangGraph**: 学習曲線が急。小規模チームではPydantic AI Graphからの移行を検討
- **FastMCP**: Python環境が必要。既存のNode.js/TypeScriptスタックと二重運用になる可能性
- **promptfoo**: テストケースのメンテナンス工数が増大するリスク
- **Phoenix**: 導入効果が可視化されにくいため、優先度は本番運用後で十分
- **全体**: 7つのOSSすべてを導入すると運用負荷が高い。最小構成（LiteLLM + n8n or Pydantic AI）から開始し、必要に応じて追加することを推奨

## 7. 結論

| 用途 | 推奨OSS構成 | 開始方法 |
|---|---|---|
| サイトSEO最適化 | **n8n + LiteLLM + promptfoo** | `docker compose up` でn8n/LiteLLM起動 |
| ブース予約UI自動化 | **Pydantic AI + LangGraph + FastMCP** | `pip install pydantic-ai fastmcp langgraph` |
| 共通基盤 | LiteLLM（全LLM統制）+ Phoenix（本番監視） | Docker Compose |

両方の用途に共通するのは **LiteLLM**（LLMゲートウェイ）で、まずここから導入することで即座にコスト統制とモデル比較が可能になる。その上で、ビジュアル志向ならn8n、コード志向ならPydantic AIから着手するのが現実的なロードマップ。
