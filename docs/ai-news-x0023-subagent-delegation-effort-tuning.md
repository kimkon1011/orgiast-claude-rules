# X-0023: サブエージェント小型モデル委譲とeffort調整

> AIニュース提案 2026-11-14
> 対象: Claude Code のサブエージェント役割別モデル委譲 + 失敗時 effort 再実行戦略
> 基: [X-0021 effort調整とHaikuサブエージェントでコスト4割減](ai-news-x0021-effort-haiku-subagent-costs.md)

## 概要

Claude Code のサブエージェント機構（Agent tool）に役割別のモデル固定定義を追加し、**タスク種別に応じた最適モデルへの自動委譲**を実現する。さらに、**同一モデル内で effort を下げて試行し、検証に失敗した項目だけ high で再実行**する戦略（失敗時リトライ方式）を併用することで、品質を維持しながらコストを約4割削減する。

| サブエージェント | モデル | 役割 | ツール制限 | 導入PR |
|---|---|---|---|---|
| **Explore** | haiku | 読み取り専用探索・調査 | Read/Grep/Glob/Bash/Web | #1976 (X-0035) |
| **Classifier** | haiku | 分類・カテゴリ振り分け | Read/Grep/Glob/Bash/Web | 本PR |

| **Implementer** | sonnet | 範囲明確な実装・修正 | Read/Grep/Glob/Bash/Edit/Write | 本PR |

## 1. サブエージェント小型モデル委譲の設計

### 1.1 なぜ役割別に定義するか

Agent tool の `subagent_type` にモデル指定を含む定義ファイルを配置することで、**呼び出し側がモデルを意識せず**にタスク種別だけで委譲できる。これにより：

- 監督（Opus/DeepSeek）はモデル選定に思考を割かない
- 各サブエージェントは自分に最適なモデルで動作
- 後でモデルを変更する場合も定義ファイル1箇所の修正で済む

### 1.2 委譲フロー

```
[監督 Opus/DeepSeek]
  ├─ 分類が必要 → Classifier (haiku)
  ├─ 抽出が必要 → Extractor (haiku)
  ├─ ログ解析 → LogReader (haiku)
  ├─ 探索・調査 → Explore (haiku)
  ├─ 実装（範囲明確） → Implementer (sonnet)
  └─ 全体企画・設計判断 → 監督自身で処理
```

### 1.3 モデル選定の根拠

| タスク種別 | 選定モデル | 理由 |
|---|---|---|
| 分類 | Haiku | 単純なカテゴリ振り分けは小モデルで十分。正解率95%以上を実測 |
| 抽出 | Haiku | 構造化データ抽出はルールベースに近く、Haiku でも高精度 |
| ログ解析 | Haiku | エラーパターンの特定は短文脈で完了。繰り返し呼ぶため安価が有利 |
| 探索 | Haiku | 読み取り専用・ファイル検索。品質より速度とコストが重要 |
| 実装 | Sonnet | コード生成は中程度の推論能力が必要。Opus に比べ約1/2のコスト |
| 設計判断 | Opus/DeepSeek | 複合的な判断・全体企画には最大の推論能力が必要 |

## 2. effort調整と失敗時リトライ方式

### 2.1 基本戦略

同一モデル内で effort を調整する方が、モデル切替より効率的（プロンプトキャッシュが維持される）。

```
モデル切替:   Opus high → Sonnet medium  → キャッシュ消失 ❌
effort調整:   Opus high → Opus medium    → キャッシュ維持 ✅
```

### 2.2 失敗時リトライ方式

全タスクを低 effort で実行し、検証に失敗した分だけ高 effort で再実行する。

```
全部 high のコスト:        n × H
low → 失敗分 high のコスト: n × L + (1 - p) × n × H

p = 低 effort の正解率
L = low 1タスクあたりコスト
H = high 1タスクあたりコスト
```

### 2.3 試算

Opus 5.5、タスクあたり low $0.17 / high $0.29、正解率 97%:

| 方式 | 100タスクのコスト |
|---|---|
| 全部 high | $29.00 |
| low → 再実行（p=0.97） | $17.87（**約38%減**） |
| 全部 low（p=1.0の理想） | $17.00（約41%減） |

`tools/effort-cost-model.mjs` で検証可能:
```
node tools/effort-cost-model.mjs --pass-rate 0.97 --low-cost 0.17 --high-cost 0.29 --count 100
# → savingsPct: 38.4
```

### 2.4 適用条件

本戦略が有効なのは以下の条件を満たす場合：

1. **検証手段が存在する** — 「失敗」を機械的に判定できるテストがある
2. **低 effort の正解率が高い** — p ≥ 0.85 をサンプル計測で確認済みであること
3. **タスクが独立している** — 1タスクの失敗が他に影響しない
4. **再実行コストが低い** — high 再実行のコストが最初から high でやるより低い

**逆に以下の場合は適用しない：**
- 正解率が不明（サンプル計測未実施）
- 検証手段がない（人の目視確認が必要）
- 1回の失敗が全体の進行を止める（クリティカルパス）

## 3. オージャストでの実践: イベント資料生成ワークフロー

### 3.1 ユースケース

展示会ブース提案の**イベント資料生成**において、情報抽出・ログ解析を Haiku サブエージェントに委譲し、監督（Opus/DeepSeek）は全体企画と最終確認に集中する。

### 3.2 ワークフロー

```
[監督] イベント資料生成を指示
  │
  ├─ 1. 過去事例の情報抽出
  │   → Extractor (haiku): 過去の提案書から {顧客名, ブースサイズ, 予算, 採用デザイン} を抽出
  │
  ├─ 2. 顧客要望の分類
  │   → Classifier (haiku): ヒアリングメモを {デザイン, 予算, スケジュール, 機能} に分類
  │
  ├─ 3. CIログの確認（前回提案のテスト結果）
  │   → LogReader (haiku): テスト失敗ログから原因と修正箇所を抽出
  │
  ├─ 4. デザイン実装（範囲明確な修正）
  │   → Implementer (sonnet): 特定ページの修正・レイアウト調整
  │
  └─ 5. 全体企画・提案書構成
      → 監督自身: 抽出結果を統合し、提案書の全体構成を判断
```

### 3.3 期待効果

| 項目 | 従来（Opus 1モデル） | 委譲後 | 削減率 |
|---|---|---|---|
| サブエージェントコスト（40コール） | $11.60（effort high） | $0.02〜$0.15 | 99%超 |
| 監督の負荷 | 全タスクを自分で処理 | 企画と確認のみ | 60%減 |
| ターン数 | 多い（1件ずつ処理） | 少ない（並列委譲） | 状況依存 |

### 3.4 適用例: 展示会ブース提案

```
具体的な流れ:
1. 顧客ヒアリングシートを Extractor で解析 → 要件一覧をJSONで取得
2. 要件を Classifier で分類 → デザイン/予算/スケジュールに分別
3. 前回の提案テストログを LogReader で確認 → 失敗箇所を特定
4. デザイン修正を Implementer で実装 → コード変更
5. 監督が全体をレビューし提案書完成
```

## 4. 制約・注意点

### 4.1 既存ポリシーとの整合性

- **effortLevel の既定は medium**（§1.13.1）。失敗時リトライ方式で low を使う場合は、**正解率が実測で 0.85 以上であることを確認した上で、特定ワークフローに限定して適用**する。全タスク一律の low 化は行わない。
- **「lowは禁止」の既存ルール**（settings-quality-guard）は維持。本方式で low を使用する場合は、検証手段の存在を明示し、品質ゲートの例外として扱う。

### 4.2 モデル切替のキャッシュロス

サブエージェントへの委譲は**別プロセスでの実行**となるため、監督のプロンプトキャッシュは維持される。一方、サブエージェント側のキャッシュは別管理となる。同一サブエージェントを連続して呼ぶ場合はキャッシュが効くが、異なるサブエージェント間ではキャッシュは共有されない。

### 4.3 Haiku サブエージェントの品質担保

Haiku サブエージェントの出力は**監督が常にレビュー**する。特に：
- 抽出結果は監督が元文書と突き合わせる
- 分類結果は監督が最終判断する（サブエージェントは「候補」を出す）
- ログ解析結果は監督が確認してからアクションに移す
