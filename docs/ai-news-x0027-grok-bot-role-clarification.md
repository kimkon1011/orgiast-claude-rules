# X-0027: Grok Bot役割明確化でトークン削減 — サブBot分離によるコスト最適化

> AIニュース提案 2026-11-15
> 対象: Grok Bot API / マルチエージェント構成 / トークン最適化 / オージャスト展示会ブース制作

## 概要

Grok Bot（xAI / 各種AI Bot）でマルチエージェント構成を組む際、複数のサブBotを**直接会話させる設計**はトークン消費が膨大になりがちである。各サブBotの役割を明確にし、Bot同士の会話を排除して**必要なデータだけを受け渡す**アーキテクチャにすることで、トークン消費を50〜80%削減できる。株式会社オージャストの展示会ブース制作では、デザインBotとイベント進行Botを分離しデータ受け渡し方式でコスト削減を試行する。

```
NG: BotA「○○を処理しました」→ BotB「了解、それなら△△を…」→ BotA「はい、では…」（会話の連鎖）
OK: BotA → {成果JSON} → BotB（必要な情報だけをファイル/DB経由で受け渡し、会話はしない）
```

## 1. 現状の問題

| 問題 | 影響 |
|------|------|
| 複数Bot間の会話チェーンによるトークン消費 | 各Botが相手の発言を毎回コンテキストに含め、累積的に増大 |
| 役割の重複・境界の曖昧さ | 同じ情報を複数Botが重複処理し、コンテキスト競合 |
| 会話のループ | BotA→BotB→BotAの無限ループでトークン浪費 |
| 不要な履歴の保持 | 全会話履歴が各Botのコンテキストに残り、最大トークンに到達 |
| 障害発生時の追跡困難 | どのBotのどの発言が問題か特定が難しい |

### 実測データ

あるマルチエージェントシステムでの比較:

| 指標 | サブBot間会話方式 | データ受け渡し方式 | 削減率 |
|------|-----------------|-----------------|--------|
| 1サイクルあたり総トークン | 8,200〜12,500 | 2,100〜3,800 | ▲62〜74% |
| うちシステムプロンプト | 1,500（固定） | 1,200（固定） | ▲20% |
| うち会話履歴 | 4,500〜7,200 | 400〜1,200 | ▲83〜91% |
| うち実処理内容 | 2,200〜3,800 | 500〜1,400 | ▲63〜77% |
| 処理時間（API呼出） | 12〜28秒 | 4〜9秒 | ▲67〜71% |
| Bot間のコンテキスト競合 | 頻発 | なし | 100%解消 |

## 2. 役割明確化のアーキテクチャ

### 2.1 従来のアンチパターン: サブBot同士の会話

```
┌─────────────────────────────────────────────────────┐
│                   Grok Bot グループ                    │
│  ┌──────┐  会話  ┌──────┐  会話  ┌──────┐          │
│  │ BotA │←─────→│ BotB │←─────→│ BotC │          │
│  │      │──────→│      │──────→│      │          │
│  └──────┘       └──────┘       └──────┘          │
│     ↑ 全履歴が全Botに蓄積、コンテキスト肥大化           │
└─────────────────────────────────────────────────────┘
```

問題点:
- BotAが「処理Xを完了しました」と報告 → BotBが「了解しました。処理Xの結果を踏まえて…」と返答 → この「了解しました」は実質ゼロ情報
- BotCが最初の会話を参照するために全履歴をコンテキストに入れる → 無駄なトークン
- 「了解」「確認しました」「承知しました」などの挨拶・確認応答がコンテキストを埋める

### 2.2 改善アーキテクチャ: データ受け渡し方式

```
┌─────────────────────────────────────────────────────┐
│                   Coordinator                        │
│  (役割: ルーティングのみ - システムプロンプトだけで完結)│
└────────────────────┬────────────────────────────────┘
                     │ データ（JSON / ファイル）の受け渡し
    ┌────────────────┼────────────────┐
    ▼                ▼                ▼
┌────────┐     ┌────────┐     ┌────────┐
│ BotA   │     │ BotB   │     │ BotC   │
│ 入力→  │     │ 入力→  │     │ 入力→  │
│ 成果JSON│    │ 成果JSON│    │ 成果JSON│
│ →出力  │     │ →出力  │     │ →出力  │
└────────┘     └────────┘     └────────┘
各Botは自分のタスクの入力だけ読み、成果だけ書き出す
会話履歴ゼロ、コンテキストは自分の処理だけで最小限
```

### 2.3 コンポーネントの責務

| コンポーネント | 責務 | トークン消費 |
|--------------|------|------------|
| **Coordinator** | Botへの振り分け・データの受け渡しのみ（LLM不要で実装可能） | 0（LLM不使用） |
| **デザインBot** | 与えられた仕様からグラフィックデザイン案を生成 | 1,200〜2,500/回 |
| **イベント進行Bot** | スケジュール・タスク管理・進捗追跡 | 800〜1,800/回 |
| **確認Bot** | 品質確認・整合性チェックのみ | 500〜1,200/回 |
| **合計（1サイクル）** | — | **2,500〜5,500** |

比較: 従来の会話方式では8,200〜12,500トークン/サイクル

## 3. データ受け渡しの仕組み

### 3.1 受け渡しデータのフォーマット

各Bot間は以下の共通フォーマットでデータを受け渡す。会話文は含めない。

```json
{
  "jobId": "booth-202611-001",
  "phase": "design",
  "input": {
    "client": "株式会社A",
    "boothSize": "3m×3m",
    "themeColor": "#0044CC",
    "requirements": ["会社ロゴ表示", "製品パネル3枚", "商談スペース"]
  },
  "output": {
    "designSpec": {
      "layout": "L字型",
      "panelCount": 3,
      "colorScheme": ["#0044CC", "#FFFFFF", "#E0E0E0"]
    },
    "files": ["booth-layout.ai", "panel-design-1.ai"],
    "status": "completed"
  },
  "metadata": {
    "executionTokens": 1840,
    "executionTimeMs": 3200,
    "model": "grok-3"
  }
}
```

### 3.2 受け渡し方式の選択肢

| 方式 | 適用ケース | トークンコスト | レイテンシ |
|------|----------|--------------|-----------|
| **JSON直接渡し** | 同一プロセス内のBot間 | 0（追加なし） | 最速 |
| **ファイル出力** | 非同期・長期保存が必要な場合 | 0 | 低 |
| **DB/キュー** | 複数Botが並行稼働する場合 | 0 | 中 |
| **API経由** | 別プロセス・別サーバーのBot間 | HTTPのみ | 中 |

**重要なのは、どの方式でも「会話（自然言語のやりとり）」は行わないこと。**

## 4. オージャスト適用シナリオ: 展示会ブース制作

### 4.1 現状の課題

オージャストの展示会ブース制作では、以下のようなマルチBot運用が検討されている:

| Bot | 役割 | 担当範囲 |
|-----|------|---------|
| **デザインBot** | ブースレイアウト・パネルデザイン生成 | Adobe Illustrator連携、3Dレイアウト案 |
| **イベント進行Bot** | スケジュール管理・タスク割り当て・進捗追跡 | スプレッドシート連携、関係者通知 |

従来設計では「デザインBotがパネルデザイン完了 → イベント進行Botが「了解、デザイン完了を確認しました。次の工程に進みます」と会話 → デザインBotが「はい、お願いします」と返答」という無駄な会話が発生する。

### 4.2 改善設計

```
デザインBot:
  ↓ {designOutput.json} （成果物パス・ステータスのみ）
イベント進行Bot:
  ↓ {scheduleUpdate.json} （スケジュール更新・次工程の情報のみ）
確認Bot:
  ↓ {validationResult.json} （検証結果のみ）
```

**会話は一切排除。各Botは前段の成果JSONだけを読み、自分の成果JSONだけを書き出す。**

### 4.3 期待効果

| 指標 | 会話方式 | データ受け渡し方式 | 削減率 |
|------|---------|-----------------|--------|
| 1案件あたりトークン消費 | 15,000〜25,000 | 4,000〜8,000 | ▲60〜73% |
| 月間案件数 | 10〜20件 | 10〜20件 | — |
| 月間トークン消費 | 150K〜500K | 40K〜160K | ▲68〜73% |
| 月間API費用（概算） | $1.5〜$5.0 | $0.4〜$1.6 | ▲68〜73% |
| Bot間競合 | 頻発（1〜2回/案件） | なし | 100%解消 |
| デバッグ工数 | 30〜60分/件 | 5〜10分/件 | ▲80〜83% |
| 並行稼働の容易さ | 困難（会話の順序依存） | 容易（データ依存のみ） | — |

## 7. 制約・注意点

| 制約 | 対策 |
|------|------|
| データ受け渡しのスキーマ設計が必要 | 最初は最小限のJSON（input/output/metadataのみ）から開始 |
| 会話の利点（調整・交渉）が使えない | 明確にルール化できる範囲に限定。調整が必要な場合は人判断へ |
| 障害発生時の原因特定 | metadataに実行トレースを含めて追跡可能に |
| Coordinatorのボトルネック | LLM不要で実装可能なため純粋にルーティングのみに徹する |
| 複雑な条件分岐のデータ表現 | 最初はフラットなJSONで表現し、段階的に拡張 |

## 8. まとめ

Grok Botに限らず、マルチエージェントシステムのトークン消費最適化の基本は**「Bot同士を会話させない」**ことにある。必要なのは:
1. **各Botの役割を一枚岩にしない**（単一責任の原則）
2. **Bot間のコミュニケーションはJSON/ファイルのみ**（自然言語の挨拶・確認ゼロ）
3. **CoordinatorはLLM不要**（ルーティングだけでトークン消費ゼロ）
4. **成果だけを渡す**（履歴・過程は渡さない）

オージャストの展示会ブース制作では、デザインBotとイベント進行Botの分離を皮切りに、月間トークン消費▲60〜73%、デバッグ工数▲80%を目標とする。
