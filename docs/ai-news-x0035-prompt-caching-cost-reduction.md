# X-0035: プロンプトキャッシングで繰り返し入力コストを最大90%削減

**AIニュース提案 X-0035**: LLM APIの入力トークンコストはプロンプトキャッシングの適切な活用で最大90%削減可能。Claude APIはキャッシュ書き込み1.25x（5分TTL）〜2x（1時間）、キャッシュ読み取りは75%オフ。OpenAIはシステムプロンプト・ツール定義を自動キャッシュ。xAI Grokは同一conv-idでプロンプトキャッシュを再利用。適切なプレフィックス設計・履歴管理・モデルルーティングの組み合わせで効果が最大化する。

観測日: 2026-11-12

## 1. 概要

LLM APIのコスト構造において、**入力トークンが出力トークンを大幅に上回る**のが一般的である（エージェント型ワークロードでは入力:出力 = 5:1〜10:1）。プロンプトキャッシングは、同一または類似のプロンプト前置き（システムプロンプト・ツール定義・固定指示）をAPIプロバイダ側で再利用することで、入力トークンの実質コストを大幅に低減する。

**主要な発見**:
- Claude API: `cache_control: {"type": "ephemeral"}` で明示的キャッシュ制御 → 読み取り75%オフ
- OpenAI API: システムプロンプト・ツール定義を自動キャッシュ（~1,024トークンブレークポイント）
- xAI Grok: `prompt_cache_key` または `x-grok-conv-id` の再利用でキャッシュヒット
- 3社とも5分〜1時間のTTLが標準（キャッシュ書き込みから有効期限）
- 適切な設計で**入力コストの70〜90%削減が現実的**

```
削減の3層:
  ① プロバイダ別キャッシュ機構の活用（Claude/OpenAI/Grok）→ −60〜75%
  ② エージェント履歴管理（/clear・/compact・ファイル保存）  → −10〜30%
  ③ モデルルーティング（複雑→高コスト／単純→低コスト）     → −20〜50%
  ─────────────────────────────────────────────
  統合効果: −70〜90%
```

## 3. Claude API: 明示的キャッシュ制御

### 3.1 基本機構

Anthropicのプロンプトキャッシングは、リクエスト内の各ブロックに`cache_control: {"type": "ephemeral"}`を付与することで動作する。キャッシュは以下の特性を持つ:

- **エフェメラルキャッシュ**: 5分間のTTL。キャッシュ書き込み後、同一プレフィックスで5分以内のリクエストはキャッシュ読み取り（75%オフ）が適用される
- **長期間キャッシュ**: 1時間のTTL（2x書き込みコスト）。長時間のバッチ生成や連続セッション向け
- **プレフィックス一致**: キャッシュは先頭からの一致でヒットする。先頭のブロックを変更すると、それより後方のキャッシュはすべて無効化される

### 3.2 推奨配置順序

```
最適なブロック配置:
  [tools定義（不変）]            ← 最も安定。先頭に置く
  [systemプロンプト（不変）]     ← ツール定義変更より低頻度
  [固定指示・コンテキスト（不変）] ← 案件固有の固定情報
  [可変部分（ユーザーメッセージ）]  ← キャッシュ対象外
```

**理由**: tools定義はセッション間で最も変化しにくい（追加は末尾appendで対応）。systemプロンプトはプロジェクトごとに固定。固定指示（会社概要・過去事例）はバッチ生成時に不変。

### 3.3 実装例

```
// キャッシュ書き込み（初回）
{
  "model": "claude-sonnet-5-5",
  "tools": [/* 定義 */],           // ← 先頭。キャッシュ対象
  "system": "あなたはブース設計者...", // ← キャッシュ対象
  "messages": [
    {"role": "user", "content": [
      {"type": "text", "text": "会社概要: ...", "cache_control": {"type": "ephemeral"}},
      {"type": "text", "text": "今回の指示: ..."}  // ← キャッシュ対象外
    ]}
  ]
}

// キャッシュ読み取り（2回目以降、5分以内）
// 先頭（tools + system + 会社概要）が自動キャッシュヒット
// → これら部分のトークンが75%オフ
```

### 3.4 キャッシュモニタリング

Claude APIのレスポンスには以下のキャッシュ関連フィールドが含まれる:

| フィールド | 意味 | 活用方法 |
|-----------|------|---------|
| `usage.cache_creation_input_tokens` | キャッシュ書き込みトークン数 | 初期セットアップコストの把握 |
| `usage.cache_read_input_tokens` | キャッシュ読み取りトークン数 | 削減効果の実測 |
| `usage.input_tokens` | 総入力トークン数 | 非キャッシュ部の把握 |

**日次モニタリングの推奨**: `cache_read_input_tokens / input_tokens` の比率を日次で確認。目標: 70%以上がキャッシュ読み取り。

## 4. OpenAI API: 自動キャッシング

### 4.1 基本機構

OpenAIのプロンプトキャッシングは、API利用者が特別なパラメータを指定しなくても**自動的**に動作する:

- **自動プレフィックス検出**: リクエストの先頭部分が以前のリクエストと同一か自動判定
- **~1,024トークンブレークポイント**: キャッシュはおおよそ1,024トークン単位で管理される
- **システムプロンプト・ツール定義は自動キャッシュ対象**: これらの固定部分が変わらなければ自動ヒット
- **レスポンスヘッダでの確認**: `x-cache-hit` や `prompt-cache-hit` でヒット状況を確認可能

### 4.2 注意点

| 項目 | 内容 |
|------|------|
| プレフィックス一致が必須 | 先頭1トークンでも異なるとキャッシュミス |
| 動的変数は末尾に配置 | 先頭に日付・時刻・セッションID等を入れない |
| ツール定義は不変に | ツールを追加する場合は末尾append（前方一致を維持） |
| キャッシュヒットの確認方法 | レスポンスヘッダ（SDK経由でも取得可能） |

### 4.3 最適化パターン

```
最適: [システムプロンプト（不変）] + [ツール定義（不変）] + [固定コンテキスト] + [動的指示]
非推奨: [動的指示] + [システムプロンプト]  ← 最初の1トークンが異なり全キャッシュミス
```

OpenAIの自動キャッシングは「何もしなくても効く」が「崩れやすい」。プレフィックスに動的部分を含めない運用が最も重要。

## 5. xAI Grok API: 明示的キー管理

### 5.1 基本機構

xAI GrokのAPIは、以下の2つの方法でプロンプトキャッシングを制御する:

1. **`x-grok-conv-id` の再利用**: 同一の会話IDをリクエストヘッダに指定すると、サーバ側でプロンプトの前方部分がキャッシュされる
2. **`prompt_cache_key` の指定**: リクエストボディに明示的なキャッシュキーを指定可能

### 5.2 最適化パターン

```
// 初回リクエスト（キャッシュ書き込み）
POST https://api.x.ai/v1/chat/completions
x-grok-conv-id: conv_booth_design_202611

{
  "model": "grok-4-turbo",
  "prompt_cache_key": "booth-design-v1",
  "messages": [
    {"role": "system", "content": "あなたはブース設計AI..."},
    {"role": "user", "content": "3m x 3mの小間..."}
  ]
}

// 2回目以降（同一conv-id / cache_key → キャッシュヒット）
// messages配列の先頭（システムプロンプト以降）がキャッシュから読み取り
```

### 5.3 重要な制約

| 制約 | 対策 |
|------|------|
| `messages`配列の先頭を変更しない | 動的部分は末尾に追加 |
| conv-idは期限内（5〜10分）に再利用 | バッチ生成は連続実行 |
| キャッシュキーは衝突を避ける | `{プロジェクト}-{バージョン}`形式で一意に |
| キャッシュヒット率の確認 | レスポンスの`usage`フィールドで確認 |

## 6. エージェント戦略: キャッシュ効率を最大化する運用

### 6.1 実践的テクニック

| テクニック | 効果 | 実装方法 |
|-----------|------|---------|
| `/clear` で無関係タスク間をリセット | 履歴増加によるキャッシュ破棄防止 | タスク完了後に/clear |
| `/compact` で長セッションを圧縮 | コンテキスト窓の逼迫防止 | 20ターンごとに実行 / または自動フック |
| CLAUDE.md / システムプロンプトをリーンに | キャッシュ書き込みサイズ最小化 | 不変部のみ維持、動的参照は最小限 |
| 未使用MCP / ツールの無効化 | ツール定義サイズ削減 | settings.json で不要ツールを除外 |
| 大きなツール出力をファイル保存 | 履歴の肥大化防止 | 10KB超の出力はファイル参照に置換 |
| 同一プレフィックスの再利用 | キャッシュヒット率最大化 | 会社概要・過去事例を固定配置 |

### 6.2 プレフィックス設計の黄金則

```
キャッシュ効率 = プレフィックス一致率 × TTL内再利用頻度

最大化の条件:
  ① 不変部分を前方に集める（キャッシュ対象）
  ② 変動部分を後方に置く（キャッシュ対象外）
  ③ 同一プレフィックスを短時間で繰り返し利用（TTL内）
  ④ プレフィックスサイズは必要最小限に（書き込みコスト削減）
```

### 6.3 セッション管理とキャッシュの関係

| シナリオ | キャッシュ効率 | 推奨運用 |
|---------|-------------|---------|
| 単一タスク完了後 → 新規タスク | 低（全キャッシュ破棄） | `/clear` でリセット後、新しい固定Prefixで開始 |
| 関連タスクの連続実行 | 高（プレフィックス共有） | 同一conv-id / sessionで継続 |
| バッチ生成（同一フォーマット） | 最高（全プレフィックス一致） | 固定Prefixを先頭に、可変部のみ変更 |
| モデル切替 | 低（キャッシュはモデル単位） | 切替前に`/compact`、切替後は新規キャッシュ書込 |

## 7. モデルルーティング: 複雑/単純の出し分け

### 7.1 基本戦略

すべてのタスクを高コストモデル（Claude Opus / GPT-6 等）で実行すると、キャッシュ効率が良くてもコストが嵩む。タスクの難易度に応じてモデルを出し分けることで、総コストをさらに削減できる。

| タスク種別 | 適性モデル例 | コスト比（高コスト=1.0） |
|-----------|-------------|----------------------|
| 設計・アーキテクチャ決定 | Claude Opus 5, GPT-6 Luna | 1.0（基準） |
| コード実装・修正 | Claude Sonnet 5.5, GPT-6 | 0.6〜0.8 |
| 抽出・分類・フォーマット | Claude Haiku, GPT-6 mini | 0.1〜0.2 |
| ファイル検索・grep | Grok Fast, Gemini Flash | 0.05〜0.1 |
| エラーメッセージ解析 | DeepSeek, Claude Haiku | 0.1〜0.15 |

### 7.2 ルーティングとキャッシュの関係

ルーティング戦略はキャッシュ効率とトレードオフになる:

| 戦略 | キャッシュ効率 | モデルコスト | 総コスト |
|------|-------------|------------|---------|
| 1モデル統一（高コスト） | 最高（プレフィックス共有） | 最高 | 中〜高 |
| 1モデル統一（低コスト） | 最高（プレフィックス共有） | 低 | 最低（成功率低下リスク） |
| タスク別ルーティング | 低（モデル毎に個別キャッシュ） | 低〜中 | 中（バランス型） |
| ルーティング + プレフィックス統一 | 中（モデル跨ぎは別キャッシュ） | 低〜中 | **最適** |

**最適解**: タスク種別ごとにモデルを変えつつ、**同一モデル内ではプレフィックスを統一**する。ルーター自身は低コストモデル（Haiku / Grok Fast）に任せる。

### 7.3 実装パターン

```
ユーザー入力
  └→ ルーター（Haiku 5.5）: タスク種別を判定
      ├→ 設計/アーキテクチャ → Opus 5.5（プレフィックスA）
      ├→ コード実装       → Sonnet 5.5（プレフィックスB）
      ├→ 抽出/分類       → Haiku 5.5（プレフィックスC）
      └→ ファイル検索     → Grok Fast（プレフィックスD）
```

各プレフィックス（システムプロンプト + ツール定義）はモデル単位で固定する。同一モデルへの連続リクエストはTTL内に収まるようバッチ処理する。

## 9. キャッシュ活用チェックリスト

以下の項目をすべて満たせば、入力コストの70〜90%削減が現実的になる。

### 安定プレフィックス
- [ ] システムプロンプトは不変（動的変数を含まない）

### キャッシュ有効化
- [ ] Claude: 固定ブロックに`cache_control: {"type": "ephemeral"}`を付与

- [ ] モデル切替前に`/compact`でコンテキストを整理

### 実測
- [ ] `cache_read_input_tokens`を日次収集
- [ ] キャッシュヒット率（cache_read / total input）が70%以上
- [ ] 想定削減率と実測削減率の乖離を週次レビュー
- [ ] TTL切れによる再書き込みの頻度をモニタリング

## 10. 制約と注意点

| 項目 | 内容 |
|------|------|
| TTLの壁 | 5分以上の間隔が空くとキャッシュが無効化 → 書き込みコスト再発生 |
| モデル単位のキャッシュ | モデルを変えるとキャッシュは別管理（モデル切替時に再書込） |
| プレフィックス変更の影響 | 先頭ブロックを1トークンでも変更すると後方キャッシュも全無効 |
| キャッシュ書き込みの割増 | Claudeは書込時に1.25x〜2xのコスト。過剰な書込は逆効果 |
| プロバイダ間の非互換 | キャッシュの制御方式・TTL・コスト体系はプロバイダごとに異なる |
| ワークロード依存 | 毎回異なるプロンプトを使用するケースでは効果が限定的 |
