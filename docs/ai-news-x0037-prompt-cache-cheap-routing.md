# X-0037: 安定プレフィックスキャッシュ＋安価ルーティング — 統合戦略で入力コストを最大90%削減

**AIニュース提案 X-0037**: プロンプトキャッシング（安定プレフィックス）と安価モデルルーティングの**統合戦略**により、LLM APIの入力トークンコストを最大90%削減可能。キャッシュ読み取り（0.25x）に加え、単純タスクをHaiku / mini等の安価モデル（0.025x〜0.1x）へルーティングする組合せで、品質を維持したままコストを劇的に低減する。キャッシュ書き込み時はClaude APIで1.25x〜2xのプレミアムが発生するため、安定プレフィックスの設計と更新頻度の管理が鍵となる。

観測日: 2026-11-13

## 1. 概要

LLM APIのコスト構造において、**入力トークンが出力トークンを大幅に上回る**（エージェント型ワークロードでは入力:出力 = 5:1〜10:1）のが一般的である。プロンプトキャッシングと安価モデルルーティングは、それぞれ異なるレイヤーでコスト削減を実現するが、**両者を統合することで相乗効果が生まれる**。

### 1.1 2層の削減戦略

```
削減の2層:
  ① プロンプトキャッシング（安定プレフィックスの再利用）
     システムプロンプト・ツール定義・固定指示をキャッシュ → −60〜75%
  
  ② 安価モデルルーティング（タスク難易度に応じたモデル切替）
     単純タスクをHaiku/mini/Grok Fastへ → −75〜97.5%
     ────────────────────────────────────
     統合効果: −70〜95%（タスク構成による）
```

### 1.2 従来のアプローチとの違い

| 観点 | X-0035（個別最適化） | X-0037（統合戦略） |
|------|---------------------|------------------|
| キャッシュ | プロバイダ別の機構解説 | 安定プレフィックスとルーティングの結合設計 |
| ルーティング | モデル別のコスト比較 | キャッシュ状態を考慮したルーティング判断 |
| 実装 | 個別テクニックの列挙 | プレフィックス＋ルーターの統一アーキテクチャ |
| 評価 | キャッシュヒット率 | 総コスト削減率（キャッシュ＋ルーティング） |

### 1.3 なぜ「統合」が重要なのか

キャッシュとルーティングは独立した戦略ではない。**キャッシュは同一プレフィックスの連続利用で最大化され、ルーティングはモデル単位でキャッシュを分断する。** 両者を個別に最適化するとトレードオフが発生するため、統合設計が不可欠。

| 戦略 | キャッシュ効率 | モデルコスト | 総コスト | 適性 |
|------|-------------|------------|---------|------|
| 1モデル統一（高コスト） | 最高（単一プレフィックス） | 最高 | 中〜高 | 品質重視 |
| 1モデル統一（低コスト） | 最高（単一プレフィックス） | 低 | 低（品質リスク） | 単純タスクのみ |
| タスク別ルーティング（無統制） | 低（モデル毎に別キャッシュ） | 低〜中 | 中 | 汎用的 |
| **ルーティング＋プレフィックス統一（本提案）** | **中（モデル跨ぎは別）** | **低〜中** | **最適** | **バランス型** |

## 2. 安定プレフィックス設計 — キャッシュの基盤

### 2.1 プレフィックス構成の黄金則

キャッシュ効率は**プレフィックス一致率 × TTL内再利用頻度**で決まる。以下の配置順が最適:

```
最適なブロック配置（キャッシュ対象大 → 小）:
  [1] ツール定義（不変）           ← 最も安定。セッション間で変化しない
  [2] システムプロンプト（不変）    ← プロジェクト固有。変更頻度: 週次以下
  [3] 固定コンテキスト（不変）      ← 会社概要・過去事例・制約条件
  ─── キャッシュ境界 ───
  [4] 可変指示（動的）             ← キャッシュ対象外
```

### 2.2 プロバイダ別キャッシュ制御

| プロバイダ | キャッシュ方式 | プレフィックスキャッシュ化 | コスト |
|-----------|--------------|------------------------|-------|
| Claude API | `cache_control: {"type": "ephemeral"}` を先頭ブロックに付与 | system, tools, 固定コンテキスト | 書込1.25x（5分TTL） / 読取0.25x |
| Claude API（長期） | `cache_control: {"type": "ephemeral"}` + 1時間TTL相当の間隔設計 | 同上 | 書込2x / 読取0.25x |
| OpenAI API | 自動キャッシュ（先頭1,024トークンブレークポイント） | system, toolsを先頭配置するだけ | 書込1x（無料） / 読取0.5x |
| Grok API | `x-grok-conv-id` / `prompt_cache_key` | conv-idの再利用 | 書込1x / 読取0.5x（目安） |

### 2.3 プレフィックスキャッシュの実装パターン

```javascript
// Claude API: 明示的キャッシュ制御
// tools + system + 固定コンテキストをキャッシュ対象に
const response = await anthropic.messages.create({
  model: "claude-sonnet-5-5",
  tools: [...],           // ← 先頭: キャッシュ境界
  system: [
    {text: "あなたはブース設計...", cache_control: {type: "ephemeral"}}
  ],
  messages: [
    {role: "user", content: [
      {type: "text", text: "会社概要: 株式会社...",
       cache_control: {type: "ephemeral"}},
      {type: "text", text: "実際の指示..."} // ← 動的部分
    ]}
  ]
});

// OpenAI API: 自動キャッシュ（特別なパラメータ不要）
// システムプロンプト + ツール定義を先頭に配置するだけで自動キャッシュ
const response = await openai.chat.completions.create({
  model: "gpt-6-mini",
  messages: [
    {role: "system", content: "あなたはブース設計..."}, // ← 自動キャッシュ
    {role: "user", content: "会社概要: 株式会社..."},   // ← 自動キャッシュ（前方一致）
    {role: "user", content: "実際の指示..."}             // ← 非キャッシュ
  ]
});
```

### 2.4 プレフィックス更新の指針

キャッシュの最大の敵は**プレフィックスの変更**。先頭ブロックを1トークン変更すると、後方キャッシュも含めて全無効になる。

| 変更内容 | 影響範囲 | 推奨運用 |
|---------|---------|---------|
| ツール定義の先頭追加 | 全キャッシュ無効（大損害） | ツール追加は末尾appendのみ |
| ツール定義の末尾追加 | 後方キャッシュは維持 | 許容（ツール数増で書込コスト増加に注意） |
| システムプロンプトの一部変更 | 全キャッシュ無効（中損害） | 変更はバッチ更新（書き込み1回に集約） |
| 固定コンテキストの差し替え | 当該ブロック以降のキャッシュ無効 | 案件単位での切替時に許容 |
| 日付・時刻の追加 | キャッシュ無効（大損害） | 動的部分は末尾のユーザーメッセージへ |

## 3. 履歴管理 — キャッシュ破壊を防ぐ運用

キャッシュが最も破壊されるのは、**プレフィックス変更以外では履歴の肥大化**による。ターンが進んで履歴が増えると、先頭プレフィックスと履歴の結合部でキャッシュが一致しなくなる。

### 3.1 キャッシュ維持のための履歴戦略

| テクニック | 効果 | 実装コスト |
|-----------|------|-----------|
| `/clear` で無関係タスク間をリセット | 履歴がリセットされ、新規プレフィックスでキャッシュ再構築 | 低（コマンド1つ） |
| `/compact` で長セッションを圧縮 | 履歴を要約（150トークン以下に圧縮）し、キャッシュ破壊を防止 | 低（20ターン毎または手動） |
| 未使用MCP / ツールの無効化 | ツール定義サイズを削減 → 書込コスト削減 | 中（settings.jsonの編集） |
| 大きなツール出力（10KB超）をファイル保存に置換 | 履歴の肥大化防止 → キャッシュプレフィックス維持 | 中（ツール設定でファイル参照へ切替） |
| チャンク分割（複数ファイルの一括処理） | 1ファイルずつコンテキストに入れるよりキャッシュ効率向上 | 中（実装パターンの統一） |

### 3.2 自動履歴管理の推奨設定

```json
// ~/.claude/settings.json
{
  "idleCompaction": false,  // 意図しないcompactionを防止
  "automaticContext": {
    "compactThreshold": 20,  // 20ターンごとにcompactを促す
    "maxHistoryMessages": 50  // 最大履歴メッセージ数
  }
}
```

ユーザー入力
  └→ ルーター（Haiku 5.5 / GPT-6 Mini）: タスク種別を判定（〜200t）

**キーポイント**: ルーター自身は安価モデルで動作（コスト無視できるレベル）。各レーンのプレフィックスはモデル単位で固定し、同一モデルへの連続リクエストはTTL内に収める。

## 6. 株式会社オージャストへの適用

### 6.1 ブース提案の定型プレフィックスキャッシュ

オージャストの主力ユースケース「展示会ブース提案のコピー生成」では、以下のように安定プレフィックス＋安価モデルルーティングを適用する:

**現状の問題**:
- 10〜20案のブース提案文を生成するたびに、同じ会社概要・過去事例・制約条件をプロンプトに含めている
- ChatGPT（GPT-6）での生成に統一しているため、高コストモデルに単純なコピー生成が混在
- プロバイダ切替のたびにキャッシュが破棄される

**改善案**:

```
改善前（1案あたり、GPT-6 Luna）:
  会社概要(500t) + 過去事例(800t) + 制約条件(300t) + 企画指示(200t) = 1,800t
  → コスト: 1,800t × $2.50/M = $0.0045/案（通常）
  20案: $0.090

改善後（Claude APIでキャッシュ + Haikuでコピー生成）:
  初回: [会社概要 + 過去事例 + 制約条件] @cache_write(1.25x)
      = 1,600t × $0.75/M × 1.25 = $0.0015
  2〜20回目: [同上] @cache_read(0.25x)
      = 1,600t × $0.19/M = $0.0003/回
  コピー生成: Haiku 5.5（$0.25/M）
      = 200t × $0.06/M = $0.00005/案
  20案: $0.0015 + $0.0003 × 19 + $0.00005 × 20 = $0.0076
  → 削減率: $0.090 → $0.0076（**−91.6%**）
```

## 7. 実装チェックリスト

以下の項目をすべて満たせば、安定プレフィックスキャッシュ＋安価ルーティングによる統合コスト削減が実現できる。

### 安定プレフィックス
- [ ] システムプロンプトは不変（動的変数を含まない）
- [ ] ツール定義は不変（追加は末尾appendのみ）
- [ ] 固定指示（会社概要・過去事例）はプレフィックス内に分離
- [ ] 動的部分（日付・時刻・案件ID）は末尾のユーザーメッセージで渡す
- [ ] プレフィックスのバージョン管理（変更時は書き込み1回に集約）

### キャッシュ有効化
- [ ] Claude: 固定ブロックに`cache_control: {"type": "ephemeral"}`を付与
- [ ] OpenAI: システムプロンプト・ツール定義を先頭に配置（自動キャッシュ）
- [ ] Grok: `x-grok-conv-id`または`prompt_cache_key`を指定
- [ ] バッチ生成はTTL内（5分）に連続実行する設計
- [ ] キャッシュ書込コスト（1.25x〜2x）を考慮した頻度設計

### 履歴管理
- [ ] 無関係タスク間で`/clear`を実行
- [ ] 長セッションでは`/compact`で履歴圧縮（20ターン毎を目標）
- [ ] 大きなツール出力（10KB超）はファイル保存に置換
- [ ] 未使用MCP/ツールは設定から削除（settings.json）
- [ ] `idleCompaction: false`を設定

### 安価ルーティング
- [ ] ルーターに低コストモデル（Haiku / Mini / Grok Fast / DeepSeek）を使用
- [ ] 単純タスク（抽出・分類・検索・翻訳）は低コストモデル専用
- [ ] 同一モデルへのリクエストは集中させてプレフィックスを共有
- [ ] モデル切替前に`/compact`でコンテキストを整理
- [ ] 各モデルのプレフィックスを固定（プレフィックス別管理ファイル）

### 実測とモニタリング
- [ ] `usage.cache_read_input_tokens`を日次収集（Claude API）
- [ ] 各モデルの入力/出力トークン数をルーティングログから集計
- [ ] キャッシュヒット率（cache_read / total input）が70%以上を維持
- [ ] ルーティング成功率（安価モデルで品質基準を満たした割合）を週次レビュー
- [ ] TTL切れによる再書き込みの頻度をモニタリング（目標: 1日1回未満）
- [ ] 想定削減率と実測削減率の乖離を週次レビュー

### コスト目標数値
| 指標 | 目標値 | 計測方法 |
|------|-------|---------|
| キャッシュヒット率 | ≥70% | `cache_read_input_tokens / input_tokens` |
| 安価モデルルーティング率 | ≥60% | `cheap_model_tasks / total_tasks` |
| 総入力コスト削減率 | ≥70% | （削減前 - 削減後） / 削減前 × 100 |
| 品質維持率（再生成率） | ≤5% | `regenerated_count / total_count` |
| 月間APIコスト | $50未満 | API請求ベース |

## 8. 制約と注意点

| 項目 | 内容 | 対策 |
|------|------|------|
| TTLの壁 | 5分以上の間隔が空くとキャッシュ無効化 → 書込コスト再発生 | バッチ生成は連続実行 / 長期間隔なら書込を許容計上 |
| モデル単位のキャッシュ分断 | モデル切替時にキャッシュは別管理 | 同一モデルへのリクエスト集中 / 切替前に`/compact` |
| プレフィックス変更の大損害 | 先頭ブロックを1トークン変更で後方キャッシュも全無効 | 末尾append運用 / 変更はバッチ更新 |
| キャッシュ書き込みの割増 | Claudeは書込時に1.25x〜2xのコスト | 書込回数を最小化 / 書込の価値を検証 |
| 安価モデルの品質限界 | 複雑な設計判断を安価モデルに任せると品質低下 | タスク難易度に応じたルーティング / 品質フィルタの導入 |
| ルーター自身のコスト | ルーター（分類モデル）のコストが積み上がる | Haiku / Miniを使用（無視できるレベル） |
| プロバイダ間の非互換 | キャッシュ制御方式・コスト体系が異なる | プロバイダ単位で設定テンプレート化 |
| ルーティング成功判定の難しさ | 「品質を満たしたか」の自動判定が困難 | ハローチェック（必須項目の有無） / サンプリングレビュー |
