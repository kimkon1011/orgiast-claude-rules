# ドキュメント中心の階層的AI開発（要求→仕様→タスク→検証のトレーサビリティ）— AIニュース提案 X-0039

## 1. 目的と位置づけ（元記事未確認の注記を含む）

本稿は「ドキュメント中心の階層的AI開発」手法について、一般的な階層化手法の整理として記述する。元記事（X-0039のベースとなる外部記事）は未取得であり、本稿は元記事の主張を断定引用せず、筆者が実務で有効と考える階層的トレーサビリティ管理の枠組みを提示するものである。本手法は、AIエージェント（Claude、Codex、安価LLM等）が協調して開発を進める際に、要求から検証までの一貫した追跡を可能にし、品質保証と責務の明確化を目的とする。

## 2. 4階層の定義とID規約

開発プロセスを以下の4階層で構造化する。各階層には一意のIDを付与し、親子関係を明示することでトレーサビリティを確保する。

### 階層定義

| 階層 | 略称 | 説明 |
|------|------|------|
| 要求 | REQ | システムや機能に対する顧客・プロダクトの要求。変更が最も難しい上位層。 |
| 仕様 | SPEC | 要求を実現するための具体的な仕様。技術的制約や設計判断を含む。 |
| 作業 | TASK | 仕様または要求を実装するための具体的な作業単位。1人日未満が目安。 |
| 検証 | TEST | 作業の完了確認または要求の充足確認。自動テストまたは手動テスト手順。 |

### ID形式

- `REQ-<領域>-NNN`（例: `REQ-BOOTH-001`）
- `SPEC-<領域>-NNN`（例: `SPEC-BOOTH-001`）
- `TASK-<領域>-NNN`（例: `TASK-BOOTH-001`）
- `TEST-<領域>-NNN`（例: `TEST-BOOTH-001`）

領域は `BOOTH`（ブース制作）または `SITEUI`（サイトUI）とする。NNNは3桁数字で、領域ごとに連番を付与する。

### 親子関係ルール

- SPEC → REQ（SPECはどのREQに紐づくか）
- TASK → SPEC または REQ（TASKはどのSPECまたはREQを実装するか）
- TEST → TASK または SPEC または REQ（TESTは何を検証するか）

**禁止事項**: 孤立した要素（親を持たないTASK/TEST）を作成しない。各REQは最低1つのTASKと1つのTESTに到達しなければならない。

## 3. トレース表の書式（機械検査の入力）

トレース表はMarkdownの表形式で記述し、機械による検査を前提とする。ヘッダ行は厳密に以下の書式に従う。

```
| ID | 親ID | 成果物パス | 担当 |
```

- **ID**: 4階層のID（REQ/SPEC/TASK/TEST）
- **親ID**: REQ行の場合は `-`。複数ある場合はカンマ区切り。
- **成果物パス**: リポジトリ相対パス。バッククォートで囲まない。
- **担当**: kim（人間）/ Claude / Codex / 安価LLM / 検証 のいずれか。

### 検査コマンド

```bash
node tools/req-trace-check.mjs <mdファイル...>
```

このツールは以下を検出する:

- 孤立TASK/TEST（親なし・親が不在）
- 未カバーREQ（TASK/TESTに到達しない）
- 重複ID
- 参照先パス不在（成果物パスが実際に存在しない）

## 4. エージェント役割分担表

| 役割 | 読むもの | 書くもの | 承認点 | 備考 |
|------|-----------|-----------|---------|-------|
| 監督（Claude） | REQ、SPEC、TASK、HANDOFF、DECISION-TEMPLATE | 仕様書、タスク割当て、レビュー結果 | 全TASKの完了承認 | ファイル渡しでCodexに指示 |
| 実装（Codex、tools/codex-do.mjs） | SPEC、TASK | コード、テスト、成果物パス | 自己レビュー後、監督の承認 | 指示はファイル渡し（標準入力を使用しない） |
| 量産・下書き（安価LLM、tools/llm-ask.mjs） | REQ概要、テンプレート | 下書き文書、テスト案 | 監督の修正承認 | 社外送信不可、課金不可 |
| 検証（別経路） | TASK、TEST、実装物 | 検証報告 | 人の最終承認 | 別経路で起動、tools/pr-land.mjsでの着地前に実施 |

**制約**: 社外送信・削除・課金・権限変更は人の承認後のみ実行可能。

## 5. 適用例A: ブース制作フロー

ブース制作における不具合要望の取込みフローを例示する。

| ID | 親ID | 成果物パス | 担当 |
|----|------|-----------|------|
| REQ-BOOTH-001 | - | tools/booth-feedback-intake.mjs | kim |
| SPEC-BOOTH-001 | REQ-BOOTH-001 | tools/booth-feedback-intake.mjs | Claude |
| TASK-BOOTH-001 | SPEC-BOOTH-001 | tools/booth-feedback-intake.mjs | Codex |
| TEST-BOOTH-001 | TASK-BOOTH-001 | tools/booth-feedback-intake.test.mjs | 検証 |

この例では、ブース制作に関する不具合・改善要望（REQ）を取込むためのフィードバック取込ツールを実装する。仕様（SPEC）は取込フォーマットとバリデーションを定義し、作業（TASK）で実際の実装を行い、テスト（TEST）で動作を確認する。

## 6. 適用例B: サイトUI改善

サイトUI改善におけるドキュメント整備の例を示す。

| ID | 親ID | 成果物パス | 担当 |
|----|------|-----------|------|
| REQ-SITEUI-001 | - | docs/ai-news-x0010-transitions-ui-library.md | kim |
| SPEC-SITEUI-001 | REQ-SITEUI-001 | docs/ai-news-x0018-ui-eval-loop.md | Claude |
| TASK-SITEUI-001 | SPEC-SITEUI-001 | docs/ai-news-x0010-transitions-ui-library.md | Codex |
| TEST-SITEUI-001 | TASK-SITEUI-001 | docs/ai-news-x0018-ui-eval-loop.md | 検証 |

この例では、サイトUIのトランジション管理（REQ）を実現するための評価ループ（SPEC）を定義し、UIライブラリドキュメント（TASK）を更新し、評価ループドキュメント（TEST）で一貫性を検証する。

## 7. 人間コラボを模した受渡し（依頼→レビュー→差し戻し）

以下の番号付き手順で人間とAIの協業を模す。

1. **依頼書（ファイル）**: 監督（Claude）が仕様書ファイルを作成し、実装担当に渡す。依頼書には目的・対象REQ/SPEC/TASK ID・成果物パス・合格条件（実行するテスト）を記述する。

2. **実装担当が実装**: Codex（tools/codex-do.mjs）が仕様書を読込み、指示に従ってコードを実装する。成果物は指定されたパスに書出す。

3. **別エージェントがレビュー**: 検証エージェント（別経路）または監督（Claude）が実装物をレビューする。レビュー結果は {expected, actual, what to fix} 形式で記録する。

4. **差し戻し時**: 問題がある場合、差し戻しは以下の形式で行う。
   ```
   expected: <期待する動作・状態>
   actual: <実際の動作・状態>
   what to fix: <具体的な修正指示>
   ```

5. **再実装**: 修正指示を受けてCodexが再実装を行う。

6. **検証**: 修正後、tools/booth-feedback-intake.test.mjs 等のテストを実行し、期待通りの動作を確認する。

7. **着地**: 検証が通ったら、tools/pr-land.mjs を使用して変更を着地させる。判定は tools/commit-landed.mjs が行う。

**例外処理**: 同じ失敗を2回繰り返した場合、最小断片（最小の変更単位）に絞って再度依頼する。

## 9. 運用上の限界

- **元記事未確認**: 本稿は元記事を未確認のまま一般的な手法を整理したものであり、元記事の主張を正確に反映していない可能性がある。
- **表は手書きで陳腐化しうる**: トレース表は手作業で更新するため、実装と乖離が生じる可能性がある。定期的な検査（tools/req-trace-check.mjs）が必須。
- **検査は構造の整合のみ**: 検査ツールはIDの一貫性やパスの存在を確認するが、内容の正しさやテストの網羅性は保証しない。
- **全自動化は非現実的**: 社外送信・削除・課金・権限変更など、人間の承認が必要な操作は依然として存在する。
- **領域の拡張**: BOOTHとSITEUI以外の領域に拡張する場合は、本稿の規約に従うこと（ID形式の一貫性、親子関係ルールの遵守）。
