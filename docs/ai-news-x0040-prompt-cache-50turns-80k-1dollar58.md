観測日: 2026-11-18

## 1. 課題: 繰り返し問い合わせのコスト

### 1.1 イベント企画の反復作業

展示会イベント企画では、以下のような**同一システムプロンプト＋少量の可変パラメータ**の繰り返しが頻発する:

| シーン | 固定部（システムプロンプト） | 可変部（ユーザーメッセージ） |
|--------|---------------------------|--------------------------|
| 複数顧客の企画案作成 | ブースデザインの制約・予算枠・施工ルール（〜60K Tok） | 顧客名・希望コンセプト・予算（〜20K Tok） |
| 見積もり比較検討 | 見積ルール・単価表・割引条件（〜70K Tok） | 対象アイテム一覧（〜10K Tok） |
| スケジュール調整案 | イベント日程・会場制約・スタッフ情報（〜50K Tok） | 候補日・希望条件（〜30K Tok） |
| 施工手順書生成 | 施工基準・安全規定・チェックリスト（〜65K Tok） | ブース図面・機材リスト（〜15K Tok） |

毎回80K Tokの入力をFableに送ると、1回$0.64（$8.00/1M Tok）。50ターンで**$32.00**。

### 1.2 コスト内訳（キャッシュなし）

| 項目 | 数値 |
|------|------|
| モデル | Fable 5.2（$8.00/1M Tok 入力） |
| 1ターンの入力 | 80K Tok（システムプロンプト60K + 履歴20K） |
| 1ターンの出力 | 200 Tok |
| 1ターンのコスト | 80K × $8.00/1M = $0.64 |
| 50ターンの総コスト | **$32.00** |

## 2. 解決策: プロンプトキャッシュ + 出力短縮

### 2.1 キャッシュ機構

Claude APIのプロンプトキャッシュ（`cache_control: {"type": "ephemeral"}`）は、不変プレフィックスをキャッシュに書き込み、5分TTL内の再送信で読み取り専用料金（0.25x）で再利用する。

| フェーズ | コスト係数 | 80K Tokの実費 |
|----------|-----------|--------------|
| 初回（キャッシュ書き込み） | 1.25x | $0.80 |
| 2回目以降（キャッシュ読み取り） | 0.25x | **$0.016** |
| 出力（200 Tok） | — | $0.015（$75.00/1M Tok 出力） |

### 2.2 50ターンの累計コスト

| ターン | 入力コスト | 出力コスト | 累計 |
|-------|-----------|-----------|------|
| 1（キャッシュ書込） | $0.80 | $0.015 | $0.815 |
| 2〜50（キャッシュ読取） | 49 × $0.016 = $0.784 | 49 × $0.015 = $0.735 | $2.334 |
| **合計** | **$1.584** | **$0.750** | **$2.334** |

出力200 Tokでも$0.75かかる。ここで**出力を短くする**ことでさらに削減:

| 出力長 | 出力コスト（50ターン） | 総コスト |
|--------|---------------------|---------|
| 200 Tok（標準） | $0.75 | **$2.33** |
| 100 Tok（短縮） | $0.375 | **$1.96** |
| 50 Tok（最小） | $0.188 | **$1.77** |
| **20 Tok（ワードのみ）** | **$0.075** | **$1.66** |

出力を20 Tok（キーワードのみの応答）に抑えると、**$1.58**に到達。

### 2.3 実現条件

1. **システムプロンプトを先頭に固定**: 可変パラメータは後続のユーザーメッセージに配置。不変プレフィックスがキャッシュキーになる
2. **5分以内の再送信**: TTL内に次のターンを送る（バースト処理やキュー投入で実現）
3. **出力を短く**: `max_tokens` を20〜50に制限。システムプロンプトに「簡潔に答える。キーワードのみ。」と指示
4. **履歴は最小限**: 過去のやり取りは必要なら外部ファイルに保存し、毎ターン再送しない

### 2.4 出力短縮の実践

```
// ❌ 標準出力（〜200 Tok）
「株式会社〇〇様のブースデザイン案をご提案します。テーマカラーは青系、
3m×3mのブースで、左壁にパネル展示、中央にカウンター、右壁に…
(以下150 Tok続く)」

// ✅ 短縮出力（〜20 Tok）
「青系・3m×3m・左パネル・中央カウンター・右ブランド壁・前面オープン」
```

短縮出力は中間結果として受け取り、人間または後続AIが必要に応じて整形する。

## 3. オージャストでの適用

### 3.1 イベント企画繰り返し問い合わせ

展示会イベント企画では、以下のパターンで同一システムプロンプトを多数の顧客に使い回す:

```typescript
// システムプロンプト（固定）: 60K Tok
const SYSTEM_PROMPT = `
あなたは展示会ブースデザインの専門家です。
以下の制約を守って企画案を出力してください:
- ブースサイズ: 可変（ユーザー入力から取得）
- 予算: 可変（ユーザー入力から取得）
- 施工可能期間: イベント3週間前まで
- 安全基準: ...（詳細ルール）
- 使用可能な素材一覧: ...
- 料金体系: ...
（合計約60,000 Tok）
`;

// バースト実行: 10顧客 × 5ターンずつ = 50ターン
const customers = ['顧客A', '顧客B', /* ... */];
for (const c of customers) {
  for (const query of queries) {
    const response = await anthropic.messages.create({
      model: 'claude-fable-5-2',
      system: [{ text: SYSTEM_PROMPT, cache_control: { type: 'ephemeral' } }],
      messages: [{ role: 'user', content: `${c}の${query}` }],
      max_tokens: 20,  // ← 出力を極限まで短く
    });
    // 5分以内に次のリクエストを送信（バースト実行なら自動）
  }
}
```

## 4. 注意点と対策

| リスク | 内容 | 対策 |
|-------|------|------|
| キャッシュミス | 5分超えるとキャッシュ消失、再度書き込み料金 | ターン間隔を4分以内に。キューでバースト処理 |
| システムプロンプト変更 | 内容を1文字変えるとキャッシュキーが変わる | 変更は一括で行い、変更後は初回書き込みを許容 |
| 出力品質低下 | 20 Tok制限で情報が不足 | 必要に応じて特定ターンだけ通常出力に戻す |
| TTL管理の複雑さ | バースト処理のタイミング設計 | 同じシステムプロンプトの全リクエストを連続投入（5分以内） |
| 履歴の肥大化 | 過去ターンを含めるとキャッシュサイズ増 | 履歴は外部保存し、毎ターンは最小のプロンプトのみ送信 |
