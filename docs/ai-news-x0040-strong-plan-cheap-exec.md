# X-0040: 強AI計画＋安AI実行 — GitHub Improve スタイルのコード改善パイプライン

**AIニュース提案 X-0040**: 強いAI（Fable 5.1）でコードを点検し改善計画を書き、安いAI（Codex / Gemini / Groq）でその計画を実行する「GitHub Improve」スタイルのパイプライン。コードレビューと実装修正の役割をAI間で分割し、品質を維持しながら実行コストを抑制する。オージャストのイベント管理ツールやブース関連自動化開発で役割分担を試す。

観測日: 2026-11-14

---

## 1. 概要

GitHub Copilot の **Improve** 機能は、PRのコード差分を分析し改善提案を自動生成する。本提案はこの思想を Claude Code のワークフローに取り入れ、**計画（高品質・高コスト）と実行（安価・高頻度）をAI間で分割**する。

### 1.1 なぜ「Improve」スタイルか

| 観点 | 従来（全工程を1AI） | X-0040（Improve分割） |
|------|-------------------|---------------------|
| コードレビュー品質 | 安AIは見落としがち | **強AIが確実に検出** |
| 実装コスト | 強AIで全実装は高額 | **安AIで実行して節約** |
| 作業計画の明示性 | 暗黙的な修正 | **計画を文書化→レビュー可能** |
| 再利用性 | 毎回同じ判断を繰り返す | **計画テンプレートが蓄積** |
| 手戻りリスク | 安AIの誤修正に気づきにくい | **強AIの計画がガイドになる** |

### 1.2 従来の委譲パターンとの違い

| パターン | X-0036（Sonnet+Fable advisor） | X-0040（Improve分割） |
|---------|-------------------------------|---------------------|
| トリガー | 判断に迷ったら `/advisor` | **コード変更・PR作成時** |
| 強AIの役割 | 相談相手（回答生成） | **コード点検＋計画作成** |
| 安AIの役割 | 日常作業（一律） | **計画に従った実装** |
| 出力 | アドバイステキスト | **構造化タスク計画＋実装コード** |
| 検証 | なし（Sonnetが最終判断） | **強AIが計画の実行結果を検証** |

## 2. パイプライン設計

### 2.1 全体フロー

```
[コード変更/diff]
       │
       ▼
 ┌─────────────────┐
 │ Phase 1: 強AI   │  Fable 5.1 / Opus 5.5
 │  コード点検     │  effort: high
 │  ────────       │
 │  • 問題点特定   │
 │  • 改善計画生成 │
 │  • タスク分解   │
 └────────┬────────┘
          │ 構造化タスク計画（JSON）
          ▼
 ┌─────────────────┐
 │ Phase 2: 安AI   │  Codex / Gemini / Groq
 │  計画実行       │  effort: medium
 │  ────────       │
 │  • タスク1      │
 │  • タスク2      │
 │  • タスク3      │
 └────────┬────────┘
          │ 実装コード
          ▼
 ┌─────────────────┐
 │ Phase 3: 検証   │  Fable 5.1（計画と結果を照合）
 │  実行結果検証   │  またはテスト自動実行
 │  ────────       │
 │  • 計画充足チェック│
 │  • テスト実行   │
 └────────┬────────┘
          │
          ▼
      [PR作成 / マージ]
```

### 2.2 タスク計画の構造

強AIが生成するタスク計画は以下のJSON形式で、安AIが解釈可能な構造を持つ:

```json
{
  "planId": "improve-20261114-001",
  "target": {
    "files": ["src/booth-planner.ts", "src/estimate-calc.ts"],
    "diffSummary": "見積計算の端数処理漏れ、ブースプランナーのCSS breakpoint不足"
  },
  "tasks": [
    {
      "id": "T1",
      "title": "端数処理の四捨五入ロジック追加",
      "file": "src/estimate-calc.ts",
      "line": 145,
      "description": "税抜価格×1.1の計算結果を Math.round() で整数に",
      "expectedChange": "return Math.round(price * 1.1);",
      "testRequired": true
    },
    {
      "id": "T2",
      "title": "ブースプランナーに768pxブレークポイント追加",
      "file": "src/booth-planner.ts",
      "line": 230,
      "description": "@media (max-width: 768px) のレイアウト定義を追加",
      "expectedChange": "grid-template-columns: 1fr; に切り替え",
      "testRequired": false
    }
  ],
  "verification": [
    "端数計算のテストが通ること",
    "768px以下で1カラム表示になること"
  ],
  "cost": {
    "estimatedTokens": 12000,
    "preferredLane": "codex"
  }
}
```

### 2.3 モデル選定基準

| 役割 | 推奨モデル | effort | 理由 |
|------|-----------|--------|------|
| コード点検（強AI） | Fable 5.1 | high | 見落とし防止、全体俯瞰 |
| タスク計画作成（強AI） | Fable 5.1 | medium | 構造化JSONの品質確保 |
| 実装（安AI） | Codex Sol | medium | 定型的な修正作業 |
| 実装（代替） | Gemini 2.5 Flash | medium | Codex枠切れ時の退避先 |
| 実装（最終退避） | Groq Fast | low | 超単純タスクのみ |
| 検証（強AI） | Fable 5.1 | low | 計画対実装の照合のみ |

## 3. 実装

### 3.1 新規ツール: `tools/code-improve-plan.mjs`

コード改善パイプラインのエントリポイント。以下のインターフェースを持つ:

```
node tools/code-improve-plan.mjs [--diff <diff-text> | --target <file>] [--plan-only] [--dry-run]
```

| オプション | 説明 |
|-----------|------|
| `--diff <text>` | レビュー対象の差分テキスト（省略時はgit diff） |
| `--target <file>` | 単一ファイルを指定 |
| `--plan-only` | 計画生成で停止（Phase 1のみ） |
| `--dry-run` | API呼び出しせず計画案のみ表示 |
| `--verify-only <plan.json>` | 既存計画の実行結果を検証（Phase 3のみ） |

### 3.2 既存ツールとの統合

- **codex-do.mjs** — Phase 2の実装実行に流用。タスク計画の各項目を `codex-do` の個別指示として投入
- **cost-improve-loop.mjs** — 改善サイクルの一部として定期実行可能
- **rescue-review-scan.mjs** — 救済ブランチの改善計画にも適用

### 3.3 処理フロー詳細

```
code-improve-plan.mjs
  │
  ├─ Phase 1: 強AIコード点検
  │   ├─ git diff または指定diffを取得
  │   ├─ Fable 5.1にレビュー指示 + 構造化タスク計画生成
  │   └─ plan.json を出力（--plan-only ならここで停止）
  │
  ├─ Phase 2: タスク実行（plan.json の各タスク）
  │   ├─ T1 → codex-do "task description" --cwd ...
  │   ├─ T2 → codex-do "task description" --cwd ...
  │   └─ 各タスクの成功/失敗を記録
  │
  └─ Phase 3: 検証
      ├─ 全タスクの完了確認
      ├─ テスト実行（node --test）
      └─ 計画充足率をレポート
```

## 6. 注意点と対策

| リスク | 内容 | 対策 |
|-------|------|------|
| 強AI計画の過剰品質 | 細かい問題まで拾ってタスク数爆増 | タスク上限（最大8件）と重要度フィルタ |
| 安AI実行の逸脱 | 計画と異なる実装をしてしまう | 各タスクに expectedChange を記載して照合 |
| 計画作成コスト | Fableの計画作成だけで$4超 | plan-only で確認後に実行（承認ゲート） |
| テスト不足 | 安AIがテストを書かない | testRequired フラグで強制 |
| 過剰な改善サイクル | 毎回改善して安定コードを壊す | diffサイズが50行未満はスキップ |
