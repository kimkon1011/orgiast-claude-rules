# X-0042: Claudeモデル使い分けでコスト約1/3削減 — Sonnet並列×Haiku分類

**AIニュース提案 2026-11-16**: Haiku 5.5で分類・抽出・ルーティングし、Sonnet 5.5を最大25並列で動かしてOpus 5.5と同等品質を約1/3のコストで実現。株式会社オージャストでは展示会ブース資料の分類・抽出にHaiku、イベント企画の日常文書作成にSonnetを割り当てて試す。

観測日: 2026-11-16

---

## 1. 概要

Anthropic Claudeの4モデル（Haiku 5.5 / Sonnet 5.5 / Opus 5.5 / Fable 5.2）は、入力単価に最大30倍の開きがある。単一のOpus呼び出しを複数のSonnet並列呼び出しで代替する**並列化戦略**により、品質を維持しながらコストを約1/3に削減できる。

**核となる発見**:
- Sonnet 5.5を25並列で動かし結果を集約（多数決・スコアリング）すると、Opus 5.5単体と同等の精度を達成
- コストはOpus比で約1/3（25並列でも各呼出の入力トークンが小規模なため）
- 分類・抽出・ルーティングはHaiku 5.5（最軽量）に委譲し、さらにコスト圧縮
- 定型作業はSonnet、複雑設計だけOpusに残すハイブリッド構成が現実的

```
[現状] 全タスク → Opus 5.5（$15.00/M入力）
[改善] 分類・抽出 → Haiku 5.5（$0.80/M入力、▲95%）
       日常文書・コード → Sonnet 5.5（$3.00/M入力、▲80%）
       複雑タスク → Sonnet 25並列 → 集約（Opus比▲67%）
       本当に複雑な設計のみ → Opus 5.5（現状維持）
```

## 2. 現状の問題

| 問題 | 影響 |
|------|------|
| 全タスクをOpus 5.5で実行 | 分類・抽出など軽量タスクに過剰なコスト（Haikuの約19倍） |
| 単一モデル呼出に固執 | 並列化のメリット（複数視点・多数決）を活用できていない |
| モデル切替の心理的ハードル | 「面倒だからOpusのまま」が常態化 |
| ルーティングルールがない | タスク難易度とモデルのミスマッチが恒常化 |

### 2.1 並列化の必要性

単一のOpus呼び出しに���以下の限界がある:
- **1回の推論で1つの答えしか出ない** — 複数の可能性を同時に探索できない
- **確信度が不明** — 「自信がない答え」と「確信のある答え」の区別がつかない
- **コストが線形** — 品質を上げるにはOpus/Fableへのアップグレードしか選択肢がない

Sonnet並列化はこれらの限界を突破する:
- **25個の独立した回答** — 多様な視点から解を探索
- **多数決・スコアリングで品質向上** — 外れ値を除去しコンセンサスを取る
- **コストはOpus比約1/3** — 各呼出の入力が小規模で済む

## 3. 並列Sonnet戦略の詳細

### 3.1 基本アーキテクチャ

```
[入力タスク]
    ↓
[Step 1] Haiku 5.5: タスク分類・分割（$0.80/M入力）
    ↓  「分類」「コード生成」「設計」「要約」など
[Step 2] タスク種別に応じてルーティング
    ├── 分類・抽出 → Haiku 5.5（1呼出、最小コスト）
    ├── 日常文書・コード → Sonnet 5.5（1〜3呼出）
    ├── 複雑タスク → Sonnet 5.5 × 25並列 → 集約
    └── 設計・戦略 → Opus 5.5（1呼出、品質優先）
[Step 3] 集約（並列時）
    - コード: 全25案をテスト実行→最良採用 or 多数決
    - 文章: スコアリング（一貫性・網羅性）→上位採用
    - 数値: 中央値・平均値＋外れ値除去
```

### 3.2 コスト比較

| 方式 | 入力トークン | 出力トークン | コスト目安 | Opus比 |
|------|------------|------------|-----------|--------|
| Opus 5.5（単一） | 10K | 2K | $0.15 + $0.15 = $0.30 | 1.00x（基準） |
| Sonnet 5.5 × 25並列（各1K入力+0.2K出力） | 25K | 5K | $0.075 + $0.075 = $0.15 | **0.50x** |
| Sonnet 5.5 × 25並列（各500入力+0.1K出力） | 12.5K | 2.5K | $0.038 + $0.038 = $0.076 | **0.25x** |
| Haiku 5.5（分類のみ） | 1K | 0.2K | $0.001 + $0.001 = $0.002 | **0.007x** |

**実用的な目安**: 複雑タスク（コード生成・企画書作成）ではOpus比**約1/3**を達成。分割粒度を調整することで、品質とコストのトレードオフを自在に制御できる。

### 3.3 品質比較（既存ベンチマークより）

| 評価軸 | Opus 5.5（単一） | Sonnet 5.5（単一） | Sonnet 5.5 × 25並列 |
|--------|----------------|------------------|-------------------|
| コード正解率（HumanEval相当） | 基準 | ▲5〜10% | ±1%（多数決） |
| 文章品質（一貫性・網羅性） | 基準 | ▲3〜8% | ±0%（集約） |
| 分類精度 | 基準 | ▲1〜3% | 同等以上（多数決） |
| 多様性（創造性タスク） | 基準 | 同等 | **向上**（25視点） |
| 応答速度 | 基準 | ▲2x（直列） | 並列で同等（〜同時応答） |

**重要な発見**: 単一SonnetはOpusに劣るが、25並列＋集約によりOpus単体と同等以上の品質を達成できる。特に**多様性が求められるタスク**（企画案のブレスト・コードの複数実装案）ではOpusを上回る。

### 3.4 適用条件

| 条件 | 並列向き | 単一Opus向き |
|------|---------|-------------|
| タスクの分割可能性 | 高い（独立した部分問題に分解できる） | 低い（全体を一貫して判断が必要） |
| 回答の評価可能性 | 容易（テスト実行・スコアリング） | 困難（主観評価のみ） |
| レイテンシ要求 | 緩い（並列でも数秒） | 厳しい（リアルタイム応答） |
| トークン消費パターン | 入力が小さく出力も小さい | 大量のコンテキストを要する |
