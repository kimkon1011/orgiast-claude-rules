## 概要

LLMの推論（Inference）には多大な計算リソースが消費されるが、その多くは冗長な計算・待機・メモリ非効率による「無駄」である。本稿では、LLM推論を高速化・低コスト化する6つの主要手法 — Prefix Caching, Continuous Batching, PagedAttention, Chunked Prefill, Speculative Decoding, Prefill/Decode Disaggregation — を解説し、オージャストの展示会ブース提案生成への適用可能性を検討する。

## 1. Prefix Caching（KVキャッシュ共有）

### 原理

TransformerのSelf-Attentionでは、各トークンのKey（K）とValue（V）を計算し、以降のトークン生成で再利用する。同じトークンプレフィックス（例: システムプロンプトの冒頭部分）を共有する複数のリクエストがある場合、既に計算されたKV状態をキャッシュから再利用できる。これにより、毎回のprefillフェーズで同じプレフィックスを再計算する必要がなくなる。

### 効果

- 共有プレフィックスが長いほど効果が大きい（数十〜数千トークン）
- Anthropicの実測: キャッシュヒット時、prefill速度が最大75%向上
- プロンプトキャッシュによるコスト削減: 入力トークン単価が約75%オフ（Anthropic APIの場合）

### 実装方式

| 方式 | 説明 | 適用例 |
|------|------|--------|
| APIレベルの自動キャッシュ | Anthropic/Prompt CachingのようにAPI側で自動管理 | Anthropic Claude API |
| 手動キャッシュ管理 | 共有プレフィックスを明示的に分離しキャッシュ制御 | カスタムデプロイ（vLLM等） |
| コンテキストキャッシュ | システムプロンプト＋共通インストラクションを固定 | Gemini API（Context Caching） |

### オージャストでの応用例

展示会ブースのデザイン提案では、毎回の生成に以下の共通プレフィックスが含まれる：
- 自社のブース制作ガイドライン（約300トークン）
- クライアント業界の特性説明（約200トークン）
- 会場特有の制約条件（約150トークン）

これらをプレフィックスキャッシュとして固定することで、新規クライアント提案の初回生成コストを約65%削減できる見込み。

## 2. Continuous Batching（連続バッチ処理）

### 原理

従来のStatic Batchingでは、1バッチ内の全リクエストが完了するまで次のバッチを開始できない。Continuous Batchingは、バッチ内で処理が終了したリクエストを即座に除去し、待機中のリクエストを空いたスロットに挿入する。各イテレーションでバッチ構成が動的に変更される。

### 効果

- GPU利用率: Static Batching比で最大2〜3倍向上
- 全リクエストの応答時間（P99）: 30〜50%短縮
- vLLM / TensorRT-LLM / TGI で標準実装

### 動作イメージ

```
Static Batching:
| Req1 | Req2 | Req3 | → 全完了 → | Req4 | Req5 | ...
                    ↑ Req1だけ早く終わっても待機

Continuous Batching:
| Req1 | Req2 | Req3 | → Req1完了 → | Req4 | Req2 | Req3 | → ...
```

### オージャストでの応用例

複数クライアントのブース提案書を同時生成する際、1社分の提案が先に終われば即座に次の提案生成を開始できる。営業チームの待ち時間が大幅に短縮される。

## 3. PagedAttention（ページング方式のアテンション）

### 原理

従来のアテンション実装では、KVキャッシュを連続したGPUメモリ（VRAM）に格納するため、メモリ断片化と事前割当による無駄が生じる。PagedAttentionは、KVキャッシュを固定サイズの「ブロック」（ページ）に分割し、論理KVブロックを非連続な物理GPUブロックにマッピングする。OSの仮想メモリのページングと同様の概念。

### 効果

- KVキャッシュメモリ使用量: 最大96%削減（vLLMの実測）
- メモリ断片化の劇的削減
- より多くの同時リクエストを同一GPUで処理可能
- vLLMの中核技術として採用

### 従来方式とPagedAttentionの比較

| 項目 | 従来方式 | PagedAttention |
|------|----------|----------------|
| KVキャッシュ格納 | 連続メモリ領域 | 非連続ブロック |
| メモリ割当 | 最大長で事前確保 | 必要量だけ動的確保 |
| メモリ使用効率 | 20〜40% | 80〜96% |
| 同時処理可能数 | 少 | 多（同VRAMで2〜4倍） |

### オージャストでの応用例

AWS/GCPのGPUインスタンス費用が削減可能。現状1GPUで同時処理できる提案書生成数を増やせるため、繁忙期のインスタンス追加費用を抑えられる。

## 4. Chunked Prefill（プリフィルの分割処理）

### 原理

長い入力プロンプトのprefill（入力処理）フェーズでは、全トークンを一度に処理するため長い計算時間がかかる。Chunked Prefillは、長いprefillを小さなチャンクに分割し、デコード（生成）作業とインターリーブ（混在）して処理する。これにより、prefill専用の待機時間が解消される。

### 効果

- 初回トークン出力までの時間（TTFT）: 最大50%改善
- GPUの遊休時間を削減
- 長文プロンプト（数千トークン）での効果が顕著

### 動作イメージ

```
通常:
|-- Prefill (全3000トークン) --|-- Decode Token1 --|-- Decode Token2 --|...

Chunked Prefill:
| Pre-1k | Dec-1 | Pre-1k | Dec-2 | Pre-1k | Dec-3 | Dec-4 | ...
```

### オージャストでの応用例

展示会の詳細条件を含む長いプロンプト（会場図面・制約事項・過去実績等 2,000〜5,000トークン）を扱う提案生成で、初回応答までの待ち時間が短縮される。クライアントとの対話中に即座に提案を表示できる。

## 5. Speculative Decoding（投機的デコード）

### 原理

軽量なドラフトモデル（小規模LLM）が高速に複数のトークンを「予測提案」し、ターゲットモデル（本命の大規模LLM）がそれらを一度に検証・採択する。提案されたトークンが全て採択されれば、1回のターゲットモデル呼び出しで複数トークンを生成できたことになる。

### 効果

- ターゲットモデルの呼び出し回数: 状況により2〜3倍削減
- 生成速度: 1.5〜3倍向上（ドラフトモデルとターゲットモデルの一致率に依存）
- 出力品質はターゲットモデル単体と同等（検証で不採択分は再生成）
- 入力・出力の完全一致保証付き

### ワークフロー

```
ドラフトモデル（軽量）:
[提案] Token A → Token B → Token C → Token D

ターゲットモデル（本命）:
[検証] Token A (OK) → Token B (OK) → Token C (OK) → Token D (NG→再生成)

結果: 1回のターゲット呼出で3トークン確定（本来は3回必要）
```

### オージャストでの応用例

大量のブース提案書をバッチ生成する際、軽量モデル（Gemini Flash等）でドラフトを生成し、Opus/Fableで検証することで、品質を維持しながら生成速度を2〜3倍に向上できる。

## 6. Prefill/Decode Disaggregation（プリフィルとデコードの分離）

### 原理

prefill（入力処理）とデコード（出力生成）は計算特性が大きく異なる：
- **Prefill**: 計算集約型（Compute-bound）、大量の並列行列演算、高いGPU利用率
- **Decode**: メモリ帯域制約型（Memory-bound）、小さな演算を逐次実行、低いGPU利用率

両者を別々のワーカープールに分離し、各々に最適化されたGPUインスタンスで処理。Prefill Workerは高スループットGPU、Decode Workerは低レイテンシGPUに割り当て、中間KVキャッシュを転送する。

### 効果

- GPU全体の利用率: 20〜40%向上
- インスタンスコスト: 状況により30〜50%削減
- 大規模デプロイ（100GPU超）での効果が顕著
- 需要変動に応じて各プールのサイズを独立にスケール可能

### アーキテクチャ

```
                    ┌─────────────────┐
                    │ Prefill Worker   │ ← A100/H100クラスタ
                    │ (高スループット) │
                    └────────┬────────┘
                             │ KV Cache 転送
                    ┌────────▼────────┐
                    │ Decode Worker    │ ← L4/L40クラスタ
                    │ (低レイテンシ)  │
                    └─────────────────┘
```

### オージャストでの応用例

短期的には大規模デプロイではないが、将来的に全社AI基盤を拡大する際の設計指針となる。特に繁忙期（展示会シーズン）のみprefillプールを増強するといった柔軟なスケーリングが可能。

1. **Prefix Caching（Anthropic API）**: ブースデザインガイドラインをシステムプロンプト固定部分に配置し、キャッシュが効く構造に変更。Claude APIのプロンプトキャッシュ機能を有効化。コスト削減見込み: 月額$100〜300程度のAPI費用に対し、入力トークンコスト約75%削減。

2. **Continuous Batching（vLLMデプロイ）**: 自社モデルデプロイ環境（vLLMが稼働していれば）の設定で既定で有効。設定変更のみ。

### Phase 2（1〜4週間）: ミドルウェア変更が必要な手法

3. **PagedAttention（vLLM更新）**: vLLM最新版への更新で自動適用。AWS/GCPのGPUインスタンス費用を30〜50%削減。

4. **Chunked Prefill**: vLLMの `--enable-chunked-prefill` フラグで有効化。長文プロンプト（会場図面等）を扱うケースで効果を計測。

### Phase 3（1〜3ヶ月）: パイプライン設計変更が必要な手法

5. **Speculative Decoding**: ドラフトモデル（Gemini Flash / Groq / DeepSeek）で高速ドラフト生成 → 本命モデル（Opus/Fable）で検証のパイプライン構築。提案書バッチ生成ワークフローへの組み込み。

6. **Prefill/Decode Disaggregation**: 全社AI基盤のGPUプール設計時のアーキテクチャ選択肢として採用判断。
