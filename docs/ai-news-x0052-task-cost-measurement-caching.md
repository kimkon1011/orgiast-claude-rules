# X-0052: タスク完了コスト測定と繰り返しコンテキストのキャッシュ

**AIニュース提案 X-0052**: 各タスクの完了までに要する時間とコストを実測し、推論努力（effort）をタスクに合わせて調整する。繰り返し使用するプロンプトコンテキスト（標準ブース仕様・過去イベントデータ・制作手順書）をキャッシュして毎回フル入力価格を払わない。株式会社オージャストのブース制作・イベント運営業務において、タスク完了までの実コストと時間を測定して継続的に最適化するワークフローを提案する。

観測日: 2026-11-15 | 関連: X-0035, X-0025, X-0045, X-0046, X-0047, X-0023

---

## 1. 概要

### 1.1 問題意識

LLMを業務に組み込む際、以下の2つのコスト漏れが発生している：

1. **全タスク一律の effort 設定**: 単純なコピー生成から複雑な設計判断まで、同じ effort レベル（多くの場合 high/xhigh）で実行している。生成AIアドバイザー不要の作業に過剰な推論リソースを消費。
2. **繰り返しコンテキストの非キャッシュ**: 毎回のプロンプトに標準ブース仕様・会社概要・過去事例・制作手順書を含めているが、これらはタスク間で変化しない。毎回フル入力トークン単価（$3.00〜$15.00/M）を支払っている。

**改善余地**:
- 推論努力の調整で 30〜60% のトークン削減
- キャッシュ利用で入力コストの 75% 削減
- 両者の統合で総コスト 80〜90% 削減

既存の関連提案との関係:

| 提案 | 焦点 | X-0052との関連 |
|------|------|----------------|
| X-0035 | プロバイダ別キャッシュ機構 | **キャッシュ層の基盤技術** |

| X-0045 | モデル使い分け | **effort 調整の上位概念** |

## 2. タスク完了コスト測定

### 2.1 測定対象

LLMタスクを以下の3層で測定する：

```
Layer 1: トークン単位のコスト
  - 入力トークン数（キャッシュヒット/ミス）
  - 出力トークン数
  - モデル単価 → トークンコスト換算

Layer 2: セッション単位のコスト
  - 1タスクあたりのAPI呼び出し回数
  - モデル切替の有無
  - advisor呼び出しの有無と回数

Layer 3: 業務単位のコスト
  - タスク完了までの経過時間
  - 手戻り率（検証→修正→再検証のループ回数）
  - 人によるレビュー時間
  - 総工数（LLM + 人間）
```

### 2.2 測定指標

| 指標 | 定義 | 目標値 |
|------|------|--------|
| cost_per_task | 1タスク完了までのLLM API費用 | 提案タスク: <$0.05 |
| time_to_complete | タスク開始から完了までの経過時間 | 5分以内 |
| token_efficiency | 出力トークン / 総入力トークン | >0.3 |
| cache_hit_ratio | キャッシュヒットトークン / 総入力トークン | >0.7 |
| rework_rate | 修正ループが入ったタスク / 全タスク | <0.2 |
| effort_risk_ratio | 実際に高effortが必要だったタスク / 全タスク | <0.3 |

### 2.3 実測方法

Claude Code/APIの利用時に以下のデータを収集：

1. **使用量ログ**: `~/.claude/cost-*.jsonl` からモデル別・セッション別のトークン使用量を収集
2. **キャッシュ効率**: `tools/cache-warm-audit.mjs` (X-0024) でキャッシュヒット率を分析
3. **effort実測**: 同一タスクを異なるeffortで実行し、出力品質・所要時間を比較
4. **コスト集計**: `tools/claude-cost-reporter.mjs` で日次・週次コストをレポート

```javascript
// 実測コード例: タスク完了コスト計測
async function measureTaskCost(task, { model, effort }) {
  const startTime = Date.now();
  const result = await executeTask(task, { model, effort });
  const elapsedMs = Date.now() - startTime;
  
  // cost-*.jsonl から当該呼び出しのトークン使用量を取得
  const usage = await getUsageSince(startTime.toString());
  
  return {
    task: task.name,
    model,
    effort,
    elapsedMs,
    inputTokens: usage.inputTokens,
    outputTokens: usage.outputTokens,
    cacheHit: usage.cacheReadTokens,
    costUSD: await calcCost(usage),
    quality: await assessQuality(result, task.expectedOutput),
  };
}
```

## 3. 努力調整戦略

### 3.1 effortレベル定義

Claude API/Claude Codeにおけるeffortレベルの実測コスト差（X-0047実測より）:

| effort | Tokens/タスク | 正解率 | コスト比 | 相対 |
|-------|-------------|-------|---------|-----|
| low | ~260,000 | ~70% | 0.8x | 低コスト高速 |
| medium | ~310,000 | ~82% | 1.0x | 基本設定 |
| high | ~420,000 | ~88% | 1.4x | 複雑タスク用 |
| xhigh | ~520,000 | ~91% | 1.7x | クリティカル判断用 |

**出典**: X-0047「同一バッグ直しを5.1と5.2に3回ずつ」の実測データに基づく。

### 3.2 タスク種別×effort マトリックス

| タスク種別 | 推奨effort | 根拠 |
|-----------|-----------|------|
| コピー文案生成（定型） | low〜medium | 80%以上の正解率で実用的 |
| コードのバグ修正（再現手順明確） | medium | 明確な手順があればhigh不要 |
| 企画設計・ブースレイアウト全体判断 | high | 複合的判断が必要 |
| 予算配分・戦略的決定 | xhigh | ミスが許されない領域 |
| CSV・TSVデータ変換 | low | ルーチン作業。effort不要 |
| GASコード書込 | medium〜high | ロジック検証が必要 |

### 3.3 選択的effort適用フロー

```
[決定木]
タスク到着
  ├─ 単純なルーチン作業？ → [effort: low]
  ├─ テンプレート修正・定形作業？ → [effort: medium]
  ├─ 論理的要・コード生成？ → [effort: medium〜high]
  ├─ 戦略判断・予算決定？ → [effort: high〜xhigh]
  └─ 初回の不確定タスク？ → [effort: mediumで試行 → 検証失敗時はhigh]

**principle**: まず低effortで試し、検証で不合格だった項目だけeffortを上げて再実行する（X-0023の失敗時リトライ方式）。

## 4. 繰り返しコンテキストのキャッシュ

### 4.1 キャッシュ対象コンテキスト

株式会社オージャストの繰り返し使用コンテキスト:

| コンテキスト | トークン数 | 更新頻度 | キャッシュ戦略 |
|-------------|-----------|---------|--------------|
| 標準ブース仕様（3パターン） | ~800 | 四半期 | 書込時1.25x → 読取0.25x |
| 会社概要（企業理念・実績） | ~500 | 年1回 | 同上 |
| 展示施工制約（会場別） | ~600 | イベント前 | 案件単位で書込 |
| 品質チェックリスト | ~400 | 不定期 | 長期キッシュ（1h） |
| 過去イベント実績 | ~1,200 | イベント後 | 案件ごとに差替 |
| ブランドボイスガイドライン | ~300 | 半年 | 書込時1.25x|

### 4.2 キャッシュ配置設計

Claude APIのキャッシュ制御（X-0035より）:

```
最適な配置順:
  [tools定義（不変）]                  ← 先頭で最大キャシュ効果
  [systemプロンプト（ブランドボイス）]   ← 半不変
  [固定コンテキスト（標準仕様・制約）]    ← 案件間でキャシュ
  [案件固有コンテキスト（顧客要望）]     ← キャシュ対象外
```

**キャッシュライフタイム管理**:

- **5分TTL（ephemeral）**: 連続したバッチ生成に最適。書き込み1.25x、読み取り0.25x
- **1時間TTL**: 長時間の分析セッション向け。書き込み2.0xだが、読み取り0.25x
- タスク完了後は`/clear`でキャッシュをリセット（古いコンテキストの引きずり防止）

### 4.3 コスト比較：キャッシュ有無

**20案のブースコピー生成（同一コンテキスト使用）**:

| ケース | 入力トークン | 出力トークン | コスト |
|--------|------------|------------|-------|
| キャッシュなし（毎回フル書込） | 1,600t×20=32,000t | 200t×20=4,000t | $0.096|
| キャッシュあり（書込1回＋読取19回） | 1,600t書込 + 1,600t×19読取 | 200t×20=4,000t | $0.026（−73%） |

**計算詳細（Claude Sonnet 5.5単価で）**:
```
キャッシュなし: 32,000t × $3.00/M + 4,000t × $15.00/M = $0.096 + $0.060 = $0.156
キャッシュあり: 1回書込: 1,600t × $3.75/M = $0.006
                19回読取: 30,400t × $0.75/M = $0.023
                出力: 4,000t × $15.00/M = $0.060
                計: $0.089（キャッシュなし比で−43%）
```

## 5. オージャスト実践編

### 5.1 最適化作戦マップ

以下の順序で最適化を段階的に実施：

```
Phase 1: 現状測定（1周目）
  ├─ 現在のタスク種別ごとのコストを計測
  ├─ キャッシュヒット率の現状把握
  └─ 高effort実行の割合を確認

Phase 2: 定期キャッシュ導入
  ├─ 標準ブース仕様・会社概要を固定context化
  ├─ tools定義とsystemを先頭配置に変更
  └─ キャッシュ有効性を実測

Phase 3: effort段階的適用
  ├─ 50%のタスクをeffort medium化
  ├─ 検証残り率を監視
  └─ 品質を維持しつつ段階的に低effortへ

Phase 4: 継続的最適化ループ
  ├─ 週次コストレビュー
  ├─ タスク種別のeffort調整を更新
  └─ 新規繰り返しコンテキストをキャッシュ対象に追加
```

### 5.2 ターゲットタスク

| ブースコピー生成（定型） | ~$0.156 | ~$0.026 | −83% |
| イベント告知文作成 | ~$0.110 | ~$0.019 | −83% |
| 品質チェック自動化 | ~$0.080 | ~$0.015 | −81% |

長期（3〜4週間）で取り組むタスク:

### 5.3 測定環境の構築

1. **既存ツールの流用**:
   - `tools/claude-cost-reporter.mjs` — 日次コスト集計

## 8. 注意点・リスク

| リスク | 影響 | 緩和策 |
|--------|------|--------|
| effort低下による品質劣化 | 手戻り増加 | 検証工程の強化。不合格時のみ高effort再実行（X-0023方式） |
| キャッシュ設計の誤りでTTL切れ多数 | キャッシュ効率低下 | プレフィックス設計の定期的見直し。キャッシュヒット率の監視 |
| 測定自体のコストが増加 | 測定コスト > 削減効果 | 測定は週次集計に限定。軽量なツールを流用 |
| タスク種別分類の精度不足 | effort最適化が逆効果 | まずは3段階（単純／標準／複雑）の粗い分類から開始 |
