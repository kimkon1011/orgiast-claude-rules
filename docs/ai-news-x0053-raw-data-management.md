# X-0053: AI検索は生データ管理と基盤改善

**AIニュース提案 X-0053**: AI検索可視性ツールの乱立と統一基準の不在を受け、第三者ツールに依存せず自社で生データを管理する基盤戦略。エンティティ情報・サイト構造・コンテンツ信頼性を改善し、AI回答の引用元として自社サイトを確立する。

観測日: 2026-11-17

---

## 1. 背景: AI検索可視性ツール194個の現実

### 1.1 市場の実態

過去約2年間で**194個のAI検索可視性（GEO/AEO）ツール**が登場した（Product Hunt・G2・LinkedIn での発表ベース）。しかし:

| 指標 | 値 |
|------|-----|
| 総ツール数 | 約194（直近2年） |
| 個人開発・サイドプロジェクト比率 | **60%以上** |
| 年間廃業率 | 55〜60% |
| トップ10ツールのシェア | 約28%（市場は分散） |
| 2020年以降設立比率 | 84% |

**出典**: Dan Taylor 調査、InternetWarriors.de AIO & GEO Platforms Report 2025

### 1.2 統一基準の不在による問題

AI検索可視性ツールには**統一された測定基準がない**。同じプロンプトでも:

- **モデルごとに回答が変わる**: ChatGPT, Gemini, Perplexity, Claude, Copilot, DeepSeek, Grok で異なる回答
- **同一モデルでも日によって変わる**: モデルアップデートやA/Bテストで引用元が変動
- **ツールごとにスコアリングが異なる**: あるツールでは「表示あり」でも別のツールでは「表示なし」

このため、ツールを乗り換えると比較が困難になり、ノイズの多いデータに振り回されるリスクがある。

### 1.3 ツール依存のリスク

| リスク | 具体例 | 影響 |
|--------|--------|------|
| サービス終了 | 60%廃業率、突然使えなくなる | 蓄積データが消失・移行不能 |
| スコアリング変更 | アルゴリズム変更で過去比較不能 | 改善効果の測定が不可能に |
| コスト高騰 | LLM推論費用・レジプロキシ費用の高さ | 月額$500〜$1,000超も |
| カバレッジ不足 | 全モデル・全プロンプトをカバーできない | 見落としが発生 |

## 2. 解決策: 生データの自社管理

### 2.1 自社管理の3層構造

```
Layer 1: 生データ収集（自社測定）
  └─ AIへの自社名・キーワード質問を定期的に実行し、回答を生データとして保存
Layer 2: 基盤改善（サイト品質）
  └─ エンティティ情報整備・構造化データ・サイト構造の最適化
Layer 3: コンテンツ具体化（引用されやすさ）
  └─ 会社概要・事例・料金を具体的な数字・固有名詞で記述
```

### 2.2 生データ収集の設計

#### 収集すべきデータ

| データ種別 | 内容 | 収集頻度 |
|-----------|------|---------|
| 自社名回答 | 「株式会社オージャストとは？」のAI回答 | 週1回 |
| サービス回答 | 「展示会ブース制作 会社」のAI回答 | 週1回 |
| 競合比較 | 「大阪 展示会ブース 制作 会社 比較」のAI回答 | 隔週 |
| キーワード別 | 主要キーワード20〜30種のAI回答 | 週1回 |
| AI Overviews | Google検索でのAI Overview表示状況 | 日次（自動） |

#### 保存形式

```json
{
  "query": "株式会社オージャストとは？",
  "model": "chatgpt-4o",
  "captured_at": "2026-11-17T10:00:00Z",
  "answer_text": "...",
  "cited_sources": ["orgiast.jp", "rebooth.co.jp"],
  "accuracy_score": 0.85,
  "issues": ["料金記載なし", "事例が古い"]
}
```

### 2.3 既存ツールの活用方針

| 用途 | 推奨ツール | 理由 |
|------|-----------|------|
| 定点観測（自社） | 自社スクリプト | 生データを自社管理、ツール変更の影響を受けない |
| 補完調査（競合） | 無料〜低価格ツール | 方向性の確認に使い、判断の根拠にしない |
| 業界トレンド | Ahrefs Brand Radar / Semrush AIO | 大規模データは既存SEOスイートのAI機能で補完 |

## 3. 基盤改善: エンティティ・構造・信頼性

### 3.1 エンティティ情報整備

AIが正確に引用するためには、**ページの内容が機械可読であること**が不可欠。具体的には:

#### 優先実装項目

| 項目 | 内容 | 優先度 | 備考 |
|------|------|--------|------|
| Organization Schema | 会社名・所在地・代表者・設立年・従業員数 | **P0** | 全ページに共通JSON-LD |
| Service Schema | ブース制作・イベント制作のサービス定義 | **P0** | サービスページに個別 |
| Product Schema | Re:ブース（商標登録第6772061号） | **P1** | 商標情報を含む |
| Event Schema | 実績展示会（出展イベント） | **P1** | 実績ページに |
| FAQ Schema | よくある質問と回答 | **P1** | FAQページに |
| SameAs links | Wikidata・Wikipedia・各種SNS | **P2** | エンティティの信頼性向上 |
| Review Schema | 顧客レビュー・評価 | **P2** | 実績ページに |

#### Wikidata エンティティ登録（推奨）

Wikidata に自社エンティティを登録し、sameAs でサイトとリンクする。これにより:
- ChatGPT や Perplexity が知識ベースから自社情報を引ける
- 複数ソース間の同一性が保証される
- ハルシネーション（社名間違い・所在地間違い）が減少する

### 3.2 サイト構造の最適化

AIクローラーが効率的に情報を取得できる構造にする:

| 施策 | 内容 | 優先度 |
|------|------|--------|
| llms.txt | AIエージェント向けサイトマップ（既存: ✅） | 完了 |
| ai.txt | AI利用許諾（既存: ✅） | 完了 |
| robots.txt | OAI-SearchBot・ClaudeBot・PerplexityBot・Google-Extended を許可 | 確認済み |
| サイトマップ | 全ページを含むXMLサイトマップ | 維持 |
| パンくずリスト | BreadcrumbList 構造化データ | P1 |
| 内部リンク構造 | 孤立ページの解消、関連ページ間のリンク | P1 |

### 3.3 コンテンツ信頼性の改善

AIが引用するかどうかは、**ページの信頼性シグナル**に依存する:

| シグナル | 改善方法 | 効果 |
|---------|---------|------|
| 具体的数値 | 「多くの実績」→「年間100件以上・8社の展示会実績」 | 引用率大幅向上 |
| 固有名詞 | 「大手企業」→「ポルシェジャパン・三井不動産・東京海上日動」 | エンティティ認識 |
| 日付情報 | 「近日開催」→「2026年11月24日〜26日」 | 鮮度判断 |
| 第三者証拠 | 顧客の声・導入社数・受賞歴 | 権威性向上 |
| オリジナルデータ | 自社調査・独自統計・写真 | 唯一性 |

## 4. オージャスト実践計画

### 4.1 フェーズ1: 定点観測基盤（今週〜2週間）

| # | タスク | 詳細 |
|---|--------|------|
| 1 | 自社名・サービス名のAI回答を収集するスクリプト作成 | 主要5モデル（ChatGPT・Gemini・Perplexity・Claude・Grok）に質問 |
| 2 | 回答をスプレッドシートに保存（日時・モデル・全文・引用元） | 生データの蓄積開始 |
| 3 | 週1回の差分チェック | 回答��変化を検知・記録 |
| 4 | 問題点のタスク化 | 「料金が記載されていない」「事例が古い」等を改善タスクに |

### 4.2 フェーズ2: 基盤改善（2〜4週間）

| # | タスク | 詳細 |
|---|--------|------|
| 1 | 全ページに Organization Schema 実装 | 会社情報の統一 |
| 2 | サービスページに Service Schema 実装 | ブース制作・イベント制作 |
| 3 | FAQ Schema 実装 | よくある質問を構造化 |
| 4 | 会社概要ページの具体化 | 設立年・資本金・従業員数・拠点一覧を明記 |
| 5 | 事例ページのストーリー化 | 「課題→解決→結果」形式にリライト |

### 4.3 フェーズ3: コンテンツ具体化（4〜8週間）

| # | タスク | 詳細 |
|---|--------|------|
| 1 | 料金ページの具体化 | スモール/ミドル/カスタムの3段階目安を公開 |

| 4 | Wikidata エンティティ登録 | 自社・Re:ブース・主要サービス |

### 4.4 継続運用

| 頻度 | タスク | 担当 |

## 6. リスクと対策

| リスク | 確度 | 影響 | 対策 |
|--------|------|------|------|
| 自社スクリプトのメンテナンス工数 | 高 | 中 | シンプルな構成（スクレイピング不要・APIのみ） |
| モデル側の仕様変更 | 中 | 中 | モデル別の抽象化レイヤー、変更検知アラート |
| データ量が増えすぎる | 低 | 低 | 週1回のスナップショット、古いデータはアーカイブ |
| AI回答の変動が激しい | 高 | 低 | 傾向を見る（個別の回答ではなく週単位の変化） |
| 料金公開による競合対策 | 中 | 中 | 「目安」と明記、カスタムブースは応相談と併記 |
