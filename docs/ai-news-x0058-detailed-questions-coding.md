# X-0058: GrokとCodexでUXを反復改善する — 細かいUX改善をGrok＋Codexで延々と回す

観測日: 2026-11-18。出典: AIニュース提案 [X-0058]。
目的: Grok（xAI）のUI分析力とCodexの高速実装力を組み合わせ、細かいUX改善を反復的に回し続けるサイクルを構築する。株式会社オージャストでは展示会ブース提案サイトのUXを毎週改善ループで磨く。

## 1. なぜUX改善が停滞するのか

Webサービスや業務アプリのUXは、ローンチ直後に大きく改善され、その後停滞するのが常だ。理由は以下の3つ：

| 停滞の原因 | 詳細 | 影響 |
|-----------|------|------|
| **「小さすぎて優先度が上がらない」** | ボタンの配置・フォントサイズ・エラーメッセージの表現など、1つ1つは数十分で直せるが、優先順位で後回しになる | 小さなストレスが積み重なり、ユーザー離脱率が徐々に上昇 |
| **「直す人が気づかない」** | 開発者は同じ画面を毎日見ているため、違和感に気づきにくい | UXの問題が「仕様」として定着する |
| **「直すための工数確保が難しい」** | 新機能開発にリソースが集中し、改善は「いつかやる」になる | 改善の文化的習慣が根付かない |

これらの問題に共通するのは **「人間の意思決定と工数確保がボトルネック」** という点だ。AIに「気づき」と「修正」を任せれば、このボトルネックは解消できる。

## 2. Grok + Codex UX改善ループの仕組み

### 2.1 基本サイクル

```
[Grok] UIを分析・問題点を指摘
    ↓
[Codex] 指摘された問題をコード修正
    ↓
[検証] 修正後のUIを確認（Playwright / スクリーンショット）
    ↓
[Grok] 修正結果を評価・次の問題を指摘
    ↓
[Codex] 次の問題を修正…
```

このループを**人間が介入せずに延々と回し続ける**ことで、UXが自律的に改善され続ける。

### 2.2 Grokに任せる役割

Grokは以下の分析に優れている：

| 分析領域 | 具体的なタスク | Grokの強み |
|---------|--------------|-----------|
| **視覚的UI分析** | スクリーンショットを見て「フォントが小さい」「コントラストが低い」「余白が不自然」を指摘 | 画像認識＋UI/UX知識の組み合わせ |
| **ユーザビリティ診断** | 操作フローを分析して「このボタンは押せると気づきにくい」「ステップ数が多い」を発見 | 人間の認知モデルに基づく診断 |
| **競合比較** | 競合サービスのUIと比較して不足要素をリストアップ | Web検索＋比較分析 |
| **アクセシビリティ** | 色覚シミュレーション・キーボード操作の観点で問題を検出 | WCAGガイドラインの知識 |

### 2.3 Codexに任せる役割

Codex（またはClaude Code / Cursor）は以下の実装を担当する：

| 実装領域 | 具体的なタスク | 期待される成果 |
|---------|--------------|--------------|
| **CSS調整** | フォントサイズ・余白・カラー・ホバー効果の修正 | 数秒〜数分で反映 |
| **コンポーネント修正** | ボタンの配置・ナビゲーション構造・フォームレイアウトの変更 | 数分〜10分で完了 |
| **アニメーション追加** | マイクロインタラクション・トランジション効果の実装 | 視覚的な質が向上 |
| **レスポンシブ調整** | 特定の画面幅での表示崩れを修正 | デバイス間の一貫性が向上 |

## 3. 実装パターン

### 3.1 スクリーンショット駆動ループ（基本形）

最もシンプルなパターン。1サイクルが完全に自動化される。

```bash
# 1. Grokにスクリーンショットを渡して問題を指摘させる
grok_issues=$(grok "この画面のUI/UXの問題点を5つ挙げ、改善案を具体的に述べてください" --attach screenshot.png)

# 2. 指摘をCodexに渡して修正させる
codex "以下のUI改善を実装してください: $grok_issues" --files src/components/Header.tsx

# 3. テスト実行
npm test
npm run build

# 4. 新しいスクリーンショットを撮影してループ継続
playwright screenshot --url http://localhost:3000 --output screenshot.png
```

### 3.2 分析→優先順位付け→実装（3段階ループ）

1度に多数の問題が見つかった場合、優先順位を付けてから実装する。

| フェーズ | 担当 | 内容 | 時間目安 |
|---------|------|------|---------|
| **分析** | Grok | UI全体を分析し、問題点を列挙（画像＋コード両方から） | 30秒〜2分 |
| **優先順位付け** | Grok | 各問題の「影響度×修正容易度」でスコアリングし、実装順を決定 | 10〜30秒 |
| **実装** | Codex | 優先度順に1つずつ修正。各修正後に自動テスト | 1〜10分/件 |

このパターンでは、「ボタンの色を変えるだけ」のような軽微な修正が大量に溜まっている場合でも、**影響の大きいものから順に**効率的に消化できる。

### 3.3 定時実行（完全無人ループ）

スケジューラーに登録し、毎日決まった時間に自動実行する：

```
毎日 06:00 JST:
  1. 本番サイトのスクリーンショットを取得（トップページ・主要LP・問い合わせフォーム）
  2. Grokに分析させる（前回の改善結果も含めて）
  3. 新たに見つかった問題のみを抽出
  4. Codexで修正
  5. CI通過を確認
  6. PR作成 → 自動レビュー → マージ
  7. 本番デプロイ
  8. 改善レポートを保存（何を・なぜ直したか）
```

この仕組みが動けば、**「起きたらUXが昨日より良くなっている」** 状態が実現する。

## 4. 効果測定

### 4.1 定量指標

| 指標 | 従来（月1回改善） | Grok+Codexループ（週3回） | 想定改善率 |
|-----|-----------------|------------------------|-----------|
| 1サイクルあたりの修正件数 | 3〜5件（人間の作業） | 5〜15件（AI自動） | 3倍 |
| 1件あたりの修正時間 | 30分〜2時間 | 1〜10分 | 90%以上削減 |
| 問題発見から修正までのリードタイム | 2週間〜1ヶ月 | 24時間以内 | 95%以上削減 |
| UX改善の年間実施回数 | 12回（月1） | 156回（週3） | 13倍 |
| 人間の作業時間（月換算） | 8時間 | 30分（レビューのみ） | 94%削減 |

### 4.2 定性効果

- **「気づき」の外部化**: 開発者が主観で決めていたUX判断が、Grokの客観的分析に置き換わる
- **改善の文化化**: 「直すなら今」が習慣になり、小さな問題を放置しなくなる
- **ユーザー体験の漸進的向上**: 大きなリニューアルではなく、毎日の微調整でUXが自然に洗練される
- **開発者の負荷軽減**: 「細かい直し」から解放され、本質的な機能開発に集中できる

## 5. 株式会社オージャストでの適用: ブース提案サイトのUX改善

### 現状の課題

株式会社オージャストの展示会ブース提案サイト（orgiast.jp/booth）には、以下のような細かいUX問題が放置されている：

| 問題 | 発見時期 | 放置期間 | 直す工数 |
|------|---------|---------|---------|
| スマホ表示でCTAボタンが画面端に被る | 2026-09 | 2ヶ月以上 | 15分 |
| 料金表の「税別」表記が小さく見落とす | 2026-08 | 3ヶ月以上 | 5分 |
| フォーム送信後のサンクスページが白紙 | 2026-10 | 1ヶ月以上 | 30分 |
| 事例ギャラリーの画像読み込みが遅い | 2026-09 | 2ヶ月以上 | 1時間 |

これらの問題は、どれも「直すのは数十分だが、優先度が上がらない」タイプだ。Grok＋Codexループで週3回自動改善すれば、**1ヶ月以内にこれらの問題はすべて解消される**。

### 適用計画

#### Phase 1: パイロット（今週）

1. **スクリーンショット取得基盤**: Playwrightでトップページ・料金ページ・お問い合わせフォームのスクリーンショットを毎日自動取得
2. **Grok分析スクリプト**: スクリーンショットをGrokに送り、UX問題点を抽出するCLIツールを作成
3. **Codex修正パイプライン**: Grokの指摘をCodex指示に変換し、修正→テスト→PR作成までを自動化

#### Phase 2: 拡大（来週）

1. **改善対象ページ拡大**: 全LP・ブログ記事・施工事例ページを対象に追加
2. **競合比較ループ追加**: 競合サイトとの差分から「自社に不足しているUX要素」をGrokが自動検出
3. **効果測定ダッシュボード**: 改善回数・ページ表示速度・直帰率の推移を可視化

#### Phase 3: 定着（2週間後）

1. **全社展開**: 他のサービスサイト（イベント企画・映像制作等）にも同ループを展開
2. **知見の蓄積**: 「Grokが指摘した問題のうち、実際に効果があった改善」をナレッジベース化
3. **改善テンプレート化**: 業種・画面タイプ別の「よくあるUX問題と修正パターン」をテンプレート化

### 期待される成果

| 指標 | 現状 | 導入後（1ヶ月見込み） |
|------|------|---------------------|
| 未解決の細かいUX問題 | 10件以上 | 0〜2件 |
| 月間のUX改善実施回数 | 0〜1回 | 12回（週3回） |
| 1件あたりの改善コスト | 30分〜2時間（人間） | 1〜10分（AI自動） |
| サイト滞在時間（改善対象ページ） | 現状値 | +15%〜30% |
| 問い合わせフォーム完了率 | 現状値 | +10%〜20% |

## 6. リスクと対策

| リスク | 対策 |
|--------|------|
| Grokの指摘が的外れで、逆にUXを悪化させる | 各修正に自動テストを必須化。CSSはVisual Regression Testで「変化の検出」ではなく「意図した変化か」を確認。悪化が検出されたら自動ロールバック |
| 毎日の自動修正でデザインの一貫性が失われる | デザイントークン（カラー・フォント・スペーシング）を一元管理し、Grokの指摘もトークン内での調整に制限 |
| 修正の頻度が高すぎてユーザーが戸惑う | 修正は即時反映せず、週2回のリリースにバンドル。ユーザーへの変更通知は月1のまとめレポートのみ |
| 自動修正が本番で問題を起こす | 修正は必ずステージング環境でテストし、CIが通ったものだけを本番反映。問題が起きたら直前の安定版に自動ロールバック |

## 7. 実装のポイント

### 7.1 Grokへの指示テンプレート

```
あなたはUI/UX専門家です。以下のスクリーンショットを分析し、改善すべき点を
リストアップしてください。

【評価基準】
1. 視認性: テキストは読みやすいか、コントラストは十分か
2. 操作性: ボタンやリンクは押しやすいか、フォームは入力しやすいか
3. 一貫性: デザインの統一感はあるか、色使いに一貫性があるか
4. 情報設計: 重要な情報が目立つか、不要な情報が省かれているか
5. レスポンシブ: スマホ・タブレットでの表示は適切か

【出力形式】
各問題を以下のJSON形式で出力してください:
{
  "issues": [
    {
      "severity": "high/medium/low",
      "element": "問題のある要素",
      "problem": "問題の説明",
      "suggestion": "改善案（具体的なコード変更を含む）",
      "effort": "修正にかかる推定時間（分）"
    }
  ]
}

【制約】
- 各ラウンドで最大5件まで。最も影響の大きいものから列挙
- 前回の指摘と重複するものは除外
- 修正が10分以内で完了するものだけを対象
```

### 7.2 Codexへの指示テンプレート

```
以下のUI改善指示に従ってコードを修正してください。

【修正対象】
{ファイルパスのリスト}

【修正内容】
{Grokが出力した改善案}

【制約】
- 各修正は独立したコミットにすること
- 修正後は必ず既存のテストを実行し、すべて通過すること
- デザイントークン（variables.css）の値は変更しないこと
- 変更は最小限に留め、余計なリファクタリングをしない

【確認項目】
1. 修正が正しく適用されたか
2. 既存のテストがすべて通るか
3. 他の画面に悪影響がないか
```
