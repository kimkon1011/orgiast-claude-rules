# X-0058: Voder（VeriLoop-Governed Recurrence）— Rust検証層を持つAIコーディングハーネス

**AIニュース提案 X-0058**: 提案生成と変更承認を分離するVeriLoop-Governed Recurrence (VGR) アーキテクチャ。LLMが変更を提案し、SHA-256でファイルパス・元内容・置換バイトに束縛、隔離サンドボックスで検証、Rustガバナンス層が評価しPASSなら書き込みFAILなら証拠を返す。DeepSWE v1.1で85.20%（426/500）、Terminal-Bench 2.0で76.40%のエージェントシステムスコア。オージャストでは自社サイトコードにVoderの検証適用ワークフローを試す。

観測日: 2026-11-15

---

## 1. 概要

**Voder** はVeriLoopチームが開発する、**VeriLoop-Governed Recurrence (VGR)** を中核としたコーディングエージェントである（GitHub: [brucewang123456789/Voder](https://github.com/brucewang123456789/Voder)、Apache-2.0ライセンス）。従来のAIコーディングエージェント（Claude Code、Codex、CodeCursor等）がLLMに「生成→適用」を一任するのに対し、Voderは**提案生成と変更承認を独立した層で分離**する点が最大の特徴。

### 従来のAIコーディングエージェントとの違い

| 観点 | 従来エージェント | Voder（VGR） |
|------|--------------|-------------|
| 変更の承認 | LLMがそのまま適用 | Rustガバナンス層が独立検証・承認 |
| 変更の同一性 | ファイルパスのみ参照 | SHA-256でパス・元内容・置換バイトを束縛 |
| 検証環境 | 作業ツリー上で直接 | 隔離サンドボックス＋独立チェックアウト |
| 証跡 | Gitログに依存 | 追記専用ハッシュ連鎖ジャーナル（監査可能） |
| 再実行耐性 | ワークスペース変更で誤判定 | メタ監査（最終コミット前にもう一度検証） |

## 2. VGRの動作フロー

```
LLMが変更を提案
  └── ファイルパス・元内容SHA-256・置換バイトに束縛
        ↓
Rust Coreが候補を受け付け
  ├── リソース会計（トークン消費・時間制約）
  └── 隔離サンドボックスへ転送
        ↓
隔離環境でバリデータを実行
  ├── 独立チェックアウト＋フレッシュなピンバリデータ
  ├── PASS → 証拠を発行
  └── FAIL → 証拠と共に却下・修正を要求
        ↓
Rust Governance Layerが最終評価
  ├── 証拠の真正性を確認（署名・ハッシュ）
  ├── メタ監査：ワークスペース変更なしを再確認
  └── PASS → 書き込み実行、FAIL → 修正ループへ
        ↓
追記専用ハッシュ連鎖ジャーナルに記録
```

### 2.1 候補同一性（Candidate Identity）

各変更提案は以下の3点で束縛される：

```json
{
  "targetPath": "src/components/Pricing.tsx",
  "originalContentHash": "sha256:e3b0c44298fc1c149afbf4c8996fb924...",
  "replacementBytes": "base64:VXBkYXRlZCBwcmljaW5nIGNvbXBvbmVudA=="
}
```

これにより「検証通過した別の変更」が異なるファイルに適用される攻撃（クロスファイル認可バイパス）を防止する。

### 2.2 隔離検証と証拠発行

- 独立したチェックアウト上で `npm test` / `go test` / ESLint 等を実行
- バリデータはピン固定（実行時の最新版は使わない）
- 検証結果は署名付きで証拠として発行

### 2.3 メタ監査（Meta-Audit）

最終コミット前に以下を再確認：
- コンテキストの変更（他セクションの同時編集）
- ハード義務事項（.gitignore ルール、禁止パターン）
- フレッシュなバリデータの再実行

## 3. ベンチマーク結果

VoderのVGRアーキテクチャを適用したエージェントシステム（VeriLoop Coder-E1プロトタイプ）の評価：

| ベンチマーク | スコア | 備考 |
|----------|------|------|
| SWE-bench Verified | **85.20%**（426/500） | 単一パッチコード品質、手書きバリデータ |
| SWE-bench Pro | **62.38%**（456/731） | より難易度の高い実世界タスク |
| Terminal-Bench 2.0 | **76.40%** | CLI/端末操作タスク |
| DeepSWE | **33.63%** | デバッグ・修正タスク |

**参考**: 2026年10月時点のDeepSWE v1.1リーダーボードでは、Muse Wonder Preview（Meta）が78.8%、Gemini 4 Argonが77.9%、DeepSeek V4.1 Flash（1017更新版）が77.0%と僅差の上位争い。VGRの検証ループをDeepSeek V4.1 Flashと組み合わせた場合、単体モデルスコアをさらに上回る可能性がある。

### 3.1 モデル単体 vs エージェントシステム

Voderの評価は「エージェントシステム全体」の結果であり、モデル単体のベンチマーク（LM Harness等）とは測定対象が異なる。VGRは制御ループの品質を測っており、同じモデルでもVGRの設定（検証項目・隔離度合い・再試行回数）によってスコアが変動する。

## 4. オージャストでの適用シーン

### 4.1 自社サイトコードへのVGR検証導入

提案の核心：**オージャストの自社サイトコード（tetsuko.co.jp等）に対するAI変更提案を、VoderのVGR検証層を通して適用する**。

| ステップ | 内容 | 従来のリスク | VGR適用後 |
|---------|------|------------|----------|
| 1 | LLMが変更を提案 | 誤ったコードがそのまま書かれる | 隔離検証で事前発見 |
| 2 | テスト・リント自動実行 | LLMが「テスト通った」と嘘をつく可能性 | 独立チェックアウトで実実行 |
| 3 | 書込み | 検証結果が別の変更に使い回される | SHA-256束縛で防止 |
| 4 | マージ | 検証後〜マージ前に他変更が混入 | メタ監査で検出 |

### 4.2 想定適用範囲

| 対象 | 優先度 | VGRの価値 |
|------|-------|----------|
| tetsuko.co.jp 価格表示ロジック | 高 | 金額誤差の防止（PASS後のメタ監査） |
| 受注フォームの入力検証 | 高 | 隔離検証でSQLインジェクション等を事前検出 |
| 在庫管理API | 中 | 変更前後の一貫性チェック |
| バッチ処理スクリプト | 中 | リソース会計で処理時間の逸脱を防止 |
| 静的サイト生成 | 低 | エラーなく生成されたことをRust層が確認 |

### 4.3 導入のハードル

| 課題 | 影響 | 対策 |
|------|------|------|
| Voderはプレリリース段階 | 本番投入は慎重に | 開発環境で並行評価。検証だけ先行導入 |
| Rustランタイムのインストール | 環境構築に時間 | `.claude/setup` にスクリプト化（既存コードベースで実績） |
| テストスイートの充実度 | 検証品質はテストに依存 | まずクリティカルパスのテストを優先。VGRはテスト不在のプロジェクトでは効果半減 |
| 既存のCI/CDとの統合 | 二重検証のリスク | VGRはGitフック＋Actionsの補完と位置づける |

## 5. Voder vs 現行ツールチェーン

### 5.1 既存の検証機構との比較

| 機構 | 検証のタイミング | 検証者 | 変更束縛 | 隔離度 |
|------|---------------|-------|---------|-------|
| **GitHub Actions CI** | PRマージ前 | CIランナー | なし（PR全体） | 中（コンテナ分離） |
| **husky + lint-staged** | コミット前 | ローカル | あり（ステージ） | 低（同一環境） |
| **Code Review** | PR作成後 | 人間 | なし | - |
| **Voder VGR** | 書込み直前 | Rust層（独立） | SHA-256 + メタ監査 | 高（隔離サンドボックス） |

### 5.2 適用判断マトリクス

```
変更の影響度（大） × 変更頻度（高） = VGRの価値（最大）

       変更頻度 高
        │
  影響度大┼─────┼─────→ VGR優先導入
        │     │
        └─────┼─────→ CIで十分
        変更頻度 低
```

## 6. 想定される初期実装ステップ

1. **環境構築**: Voderリポジトリをクローンし、Rustツールチェーンをインストール
   ```bash
   git clone https://github.com/brucewang123456789/Voder.git
   cd Voder && cargo build --release
   ```
2. **最小検証**: 自社サイトの1ファイルに対して「コメント追加」の提案をVGRに流し、PASS/FAILを確認
3. **テストスイートの充実**: 価格計算・受付フォームのAPI に対してテストを追加
4. **CI連携**: VGR の検証結果を PR コメントとして投稿（GitHub Checks API）
5. **段階的適用**: 影響度の高いコード（価格・在庫）から順にVGR通過をマージ条件に
6. **評価と共有**: 1ヶ月間のインシデント件数・誤検知率を計測し、チームで知見を共有

## 7. 制約とオープンな課題

| 制約 | 内容 |
|------|------|
| **未実証のASI安全性** | Voder論文自体が「ASIリスク低減を実証していない」と明記 |
| **ガバナンスシステムの自己変更** | 「ガバナンス層自身の変更」は同一の保証ができない（オープンな研究課題） |
| **VS Code拡張のプレリリース** | フルエージェントツールチェーンは非公開部分あり |
| **検証コスト** | 隔離サンドボックス＋二重実行でトークン消費が2〜3倍に。低リスク変更にはオーバーヘッド |
| 開発工数が課題 | Go / Rust / TypeScript のテスト環境が必要。現状のNode.jsのみでは一部検証項目が不足 |

## 8. 結論

Voder/VGRは、**「AIにコード変更を任せたいが、誤った変更がそのまま書かれるリスクを許容できない」** というジレンマに1つの解答を与える。検証（証拠）と承認（書込み）を独立させたアーキテクチャは、従来のCIやCode Reviewを補完する新しいレイヤとなる。

オージャストのような中規模なWebサイト運営では、影響度の高い価格表示・受注処理系から段階的に導入を始め、検証済みAI変更の業務適用を積み上げれば、従来の人間レビューとCIだけではカバーできなかった隙間を埋められる可能性がある。

ただし、現時点ではプレリリース段階であり、本番投入は検証環境での十分な評価を要する。まずは開発環境でVGRのPASS/FAIL挙動を体感し、自社のテストスイートとVGR設定の相性を見極めることから始めるべきである。
