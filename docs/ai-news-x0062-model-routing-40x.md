# X-0062: 複雑度別モデルルーティングでコスト40倍差活用

> AIニュース提案 2026-11-17
> 対象: タスク複雑度に応じて Haiku / Sonnet / Opus をルーティングし、コスト40倍の差を活用する戦略
> 基: [X-0054 3AI分業＋暗黙キャッシュ95%オフ](ai-news-x0054-3ai-cache-90percent.md) / [X-0030 Claudeモデルコスト削減](ai-news-x0030-claude-model-cost-reduction.md)

## 概要

Claude モデルファミリー（Haiku 5.5 / Sonnet 5.5 / Opus 5.5）は入力トークン単価で最大 **40倍** の開きがある。全タスクを最強モデルで処理するのではなく、タスクの複雑度に応じて適切なモデルにルーティングすることで、品質を維持したままコストを劇的に削減できる。

本提案では、**ルーティングの自動化パターン**と、**ミッドセッション切替の落とし穴**、**株式会社オージャストの展示会ブース制作への適用シナリオ**を具体的に示す。

### コスト比較（10K入力 + 2K出力トークン想定）

| モデル | 入力単価 (/1M) | 出力単価 (/1M) | 1リクエスト単価 | Haiku比 |
|--------|---------------|----------------|----------------|---------|
| Haiku 5.5 | $0.10 | $0.50 | $0.002 | 1x |
| Sonnet 5.5 | $2.00 | $10.00 | $0.04 | 20x |
| Opus 5.5 | $4.00 | $20.00 | $0.08 | 40x |

たった1リクエストでも40倍の差。月間10万リクエストなら **Haiku $200 / Sonnet $4,000 / Opus $8,000** と、年間では $96,000（約1,400万円）もの差になる。

## 2. ルーティング方式

### 2.1 決定論的ルーティング（推奨）

タスクの種類やファイルの種類など、**プログラムで判定可能な属性**でモデルを割り当てる。

```javascript
// 擬似コード: 拡張子＋ファイルサイズでルーティング
function routeTask(filePath, taskType) {
  if (taskType === 'classify' || taskType === 'extract') return 'haiku';
  if (filePath.endsWith('.test.ts')) return 'haiku';  // 単体テスト生成
  if (filePath.endsWith('.ts') && fileSize < 200) return 'sonnet';  // 通常コード
  if (taskType === 'architecture' || taskType === 'refactor') return 'opus';
  return 'sonnet';  // デフォルト
}
```

**メリット**: 判定コストゼロ、再現性100%、キャッシュが安定する。
**向くケース**: 決まったファイル種別の処理、バッチジョブ、CIパイプライン。

### 2.2 分類モデルによるルーティング

Haiku 5.5 自体に「このタスクはどのモデルが適切か」を分類させる。コストは $0.002 未満。

```
プロンプト例:
「以下のタスク記述を L1（Haiku向け）/ L2（Sonnet向け）/ L3（Opus向け）に分類してください。
タスク: {タスク記述}
分類:」
```

**メリット**: 柔軟性が高い、未知のタスクにも対応。
**注意点**: 分類ミスによる品質低下を検知するフォールバック機構（後述）とセットで使う。

### 2.3 エスカレーションパターン（決定論的チェック＋フォールバック）

最も実用的なパターン。**安いモデルで試し、決定論的チェックに失敗したら上位モデルへエスカレーション**する。

```
Haiku → 決定論的チェック（スキーマ検証・構文解析・正規表現マッチ）
  ├── 合格 → 完了
  └── 不合格 → Sonnet → チェック
                    ├── 合格 → 完了
                    └── 不合格 → Opus（最終手段）
```

**チェックの例**:
- JSON/TSの構文パースが通るか
- 必須フィールドが存在するか
- テストがgreenになるか
- ファイルサイズが閾値以内か

**実装のコツ**: チェックは**人間の判断ではなくプログラム**で行う。人間が確認する段階までエスカレーションしない。

## 3. ミッドセッション切替の注意点

### 3.1 KVキャッシュの非互換問題

同じコンテキストを異なるモデルで使い回すと、**KVキャッシュの再利用が壊れる**。Claude のプロンプトキャッシュはモデル固有であり、Haiku で書き込んだキャッシュを Sonnet で読み込むことはできない。

**ダメなパターン**:
```
1. Haikuで「問題を分類」→ コンテキストに分類結果が残る
2. 同じコンテキストで「分類結果に基づきコードを書いて」→ Sonnetに切替
3. キャッシュミス → コンテキスト再書き込み → コスト増 + レイテンシ増
```

### 3.2 ステートレスサブタスク分離の原則

各ティアは**独立したサブタスク**として分離し、コンテキストを共有しない。

**よいパターン**:
```
[Dispatcher]
  ├── Haiku（独立コンテキスト）: 問題分類 → 結果をファイルに保存
  ├── Sonnet（独立コンテキスト）: ファイルを読んでコード作成
  └── Opus（独立コンテキスト）: ファイルを読んでアーキテクチャレビュー
```

**実装の工夫**:
- 各モデルの入出力は**ファイルまたは標準化されたデータ構造**で受け渡す
- 中間結果はファイルシステムやDBに保存し、次のモデルが読み込む
- サブタスクは冪等に設計し、再実行可能にする

## 5. 実装手順

### Step 1: ルーティング判定関数の作成

```javascript
// tools/model-router.mjs
export function selectModel(task) {
  const { type, complexity, fileType } = task;

  // 決定論的ルーティング（拡張子・タスク種別ベース）
  if (type === 'classify' || type === 'extract') return 'haiku';
  if (type === 'test') return fileType === 'e2e' ? 'sonnet' : 'haiku';
  if (type === 'implement') return complexity > 7 ? 'opus' : 'sonnet';
  if (type === 'review') return complexity > 8 ? 'opus' : 'sonnet';
  if (type === 'design') return 'opus';

  return 'sonnet'; // デフォルト
}
```

### Step 2: エスカレーション機構の組み込み

```javascript
// tools/execute-with-escalation.mjs
export async function executeWithEscalation(task, initialModel) {
  const models = [initialModel, 'sonnet', 'opus'];
  for (const model of models) {
    const result = await llmCall(model, task.prompt);
    if (await deterministicCheck(task, result)) {
      return { model, result };
    }
  }
  throw new Error('全モデルで不合格');
}
```

## 6. コスト測定計画

### 6.1 測定方法

1. **現状把握**: 現行のモデル使用量を1週間ロギング（モデル別・タスク別トークン数）
2. **ルーティング適用**: 決定論的ルーティングを実装し、同じワークロードで1週間運用
3. **比較**: トークンコスト・品質（エラー率・修正率）・レイテンシの3軸で比較

### 6.2 成功基準

| 指標 | 目標 |
|------|------|
| コスト削減率 | 全Sonnet比 50%以上削減 |
| 品質維持 | エラー率・修正率の増加 5%未満 |
| レイテンシ増加 | 平均20%未満（Haikuの高速性で相殺） |

## 7. 制約とリスク

| リスク | 影響 | 対策 |
|--------|------|------|
| 分類ミスによる品質低下 | Haikuに難しいタスクが割り当てられる | 決定論的チェック＋エスカレーションで担保 |
| KVキャッシュの非互換 | キャッシュヒット率低下 | ステートレスサブタスク分離で回避 |
| ルーティングのオーバーヘッド | 判定ロジック自体のコスト | 決定論的ルーティングならほぼゼロ |
| モデル間の出力形式の違い | 後段処理でパースエラー | 標準化されたスキーマで受け渡し |
