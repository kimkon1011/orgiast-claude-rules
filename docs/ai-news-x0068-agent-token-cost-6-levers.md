# X-0068: 6レバーでエージェントトークンコストを削減 — マルチエージェント構成のコスト最適化戦略

観測日: 2026-11-17。出典: AIニュース提案 [X-0068]。
本稿は、マルチエージェントシステムにおけるトークン消費の増大（1エージェント約4倍、チーム15倍）に対し、6つのレバーでコストを削減する手法を解説する。12エージェントの例では38Mトークン/日から9Mトークン/日へ削減可能。株式会社オージャストではブース制作の固定ガイドラインと過去事例をプロンプト先頭に置いてキャッシュし、簡単なデザイン案生成を小モデルにルーティングしてコスト測定を試す。

---

## マルチエージェントのコスト課題

単一のLLM呼び出しと比較して、エージェントシステムは以下の要因でトークン消費が増大する:

| 要因 | 倍率 | 内訳 |
|------|------|------|
| エージェントループ（思考・観測・行動） | 約4x | 各ステップで全コンテキストを再読込 |
| チーム協調（複数エージェントの直列・並列） | 約15x | エージェント間のメッセージ中継・状態共有 |
| ツール呼び出しと結果の埋め込み | 約2〜5x | ツール出力を毎ターンコンテキストに追加 |
| サブエージェントの起動と結果集約 | 約3〜8x | 子エージェントの独立したコンテキスト消費 |

**具体例**: 12エージェントの構成では、最適化なしで1日あたり約38Mトークンを消費する。6レバーを適用することで約9Mトークン/日（約76%削減）が可能。

---

## レバー1: プロンプトキャッシュの最大化 — 不変部分を先頭に固定

エージェントシステムでは、システムプロンプト・ツール定義・固定ガイドラインが毎ターン同じ形で読み込まれる。これをプロンプトの先頭に固定し、キャッシュを効かせる。

### キャッシュの価格差（Claude Sonnet 例）

| 状態 | 料金（/百万トークン） | 倍率 |
|------|---------------------|------|
| 通常入力 | $3.00 | 1x（基準） |
| キャッシュ書き込み | $1.50 | 0.5x |
| **キャッシュヒット** | **$0.30** | **0.1x** |

キャッシュヒット時の入力コストは通常の**約10分の1**になる。12エージェント構成のプロンプト先頭60%がキャッシュ可能だと仮定すると、入力コストは約46%削減される。

### キャッシュヒット率80%を目標とする設計

```
適用前: [タスク指示（毎回変化）] | [システムプロンプト] | [ツール定義]
        → 先頭が毎回異なるためキャッシュ全体が無効

適用後: [システムプロンプト] | [ツール定義] | [固定ガイドライン] | [タスク指示]
        → 先頭の60〜70%がキャッシュ対象
```

**目標**: キャッシュヒット率80%。プロンプトの先頭から連続した同一トークン列を最大化する。

### キャッシュ維持の実践

- 5分以内に次のターンを回す（キャッシュ有効期限内）
- バッチ処理は連続実行し、休憩を挟まない
- 固定部と可変部を明確に分離する

## レバー2: 簡単なステップを小モデルにルーティング

エージェントの全ステップを高価なモデル（Fable / Opus）で実行する��要はない。判断基準を設定し、難易度に応じてモデルを切り替える。

### ルーティング基準の例

| ステップの種類 | 推奨モデル | コスト比 | 適用条件 |
|--------------|-----------|---------|---------|
| 戦略的意思決定・設計 | Fable 5.2 / Opus | 1x（基準） | 判断ミスが全体に影響する |
| 分類・抽出・要約 | Gemini Flash / Groq | 0.02〜0.05x | 構造化された出力形式 |
| 単純なテキスト変換 | DeepSeek / Haiku | 0.01〜0.03x | フォーマット変換・翻訳 |
| 検索・データ取得 | コード（LLM不要） | 0x | APIコールで完結する処理 |

### オージャストでの適用例: ブースデザイン案生成

```
[Fable 5.2] ブースの全体コンセプト・デザイン方針の決定
     ↓（方針をテキストで引き継ぎ）
[Haiku] 方針に基づく3パターンの簡易デザイン案生成
     ↓
[Fable 5.2] 生成案のレビュー・最終決定
```

簡単なデザイン案生成を小モデルに委譲することで、コストを約60〜80%削減できる。

## レバー3: ツール数を3〜6に制限

エージェントに与えるツールの数は、コンテキスト長と思考の分岐に直接影響する。ツール定義はコンテキストの先頭に位置するため、数が多いほどキャッシュ対象範囲が増える一方、エージェントの選択負荷が上がる。

### ツール数の影響

| ツール数 | コンテキスト消費 | エージェントの選択精度 | 推奨 |
|---------|----------------|---------------------|------|
| 1〜2 | 少 | 高いが機能不足 | 単機能タスクのみ |
| **3〜6** | **適切** | **高い** | **推奨範囲** |
| 7〜15 | 多い | 低下傾向 | 機能分割を検討 |
| 16+ | 非常に多い | 選択ミス増加 | サブエージェント化 |

### 実践: ツール設計の原則

1. **機能別にグループ化**: 読み取り系・書き込み系・検索系に分類し、タスクに必要なグループだけを渡す
2. **サブエージェントに委譲**: 7種類以上のツールが必要な処理は、サブエージェント化して専用コンテキストで処理
3. **ツール説明は30語以内**: 長い説明はコンテキストを消費し、モデルの選択精度を下げる
4. **動的ツールローディング**: フェーズごとに必要なツールセットを切り替える

## レバー4: ターン数とトークンキャップの設定

エージェントが無限ループに陥るのを防ぎ、コストの上限を設定する。

### 推奨キャップ値

| パラメータ | 推奨値 | 根拠 |
|-----------|--------|------|
| 最大ターン数 | **30** | 複雑なタスクでも30ターン以内に収束しない場合は設計見直し |
| コンテキスト上限 | **400Kトークン** | 400Kを超えるとKVキャッシュ再計算がコスト増の主因に |
| 出力上限/ターン | **2,000トークン** | 長い出力は次ターンの入力増加を招く |

### ターン数とコストの関係

```
ターン数増加によるコスト増:
1-10ターン: 緩やかな増加（コンテキストがまだ小さい）
11-20ターン: 加速（会話履歴の蓄積が顕著に）
21-30ターン: 急増（KVキャッシュ再計算が支配的に）
31+ ターン: 爆発的（400K超のコンテキスト再処理）
```

**教訓**: 30ターンを超えるエージェントは設計を見直す。長期的な処理はサブタスクに分割し、各サブタスクを独立した30ターン以内のエージェントで処理する。

## レバー5: バッチ処理で夜間実行（50%オフ）

即時応答が不要な処理は、バッチAPIを利用して深夜に実行する。Anthropic APIのバッチ処理は**50%割引**で提供される。

### バッチ処理の適用判断

| 処理の種類 | 即時性 | バッチ適性 |
|-----------|--------|-----------|
| ユーザーとの対話 | 必要 | ✗ 不向き |
| 内部処理（分類・抽出・集計） | 不要 | ✓ 最適 |
| レポート生成 | 翌朝までに | ✓ 最適 |
| テスト実行・検証 | 開発中は即時 | 本番CIはバッチ検討 |
| キャッシュウォーミング | 不要 | ✓ 最適 |

### コスト比較（月間100万トークンの処理）

| 実行方式 | 単価 | 月額 |
|---------|------|------|
| リアルタイム（通常料金） | $3.00/Mtok | $3.00 |
| バッチ（50%オフ） | $1.50/Mtok | $1.50 |
| バッチ＋キャッシュヒット | $0.15/Mtok | $0.15 |

### バッチ設計のポイント

- キューイングシステムで処理を蓄積し、深夜に一括投入
- キャッシュウォーミングはバッチ処理の最初に実行
- 同じプロンプトパターンは同じバッチ内にまとめて投入
- バッチ結果は非同期で受け取り、エラー処理を実装

## レバー6: エージェント間通信の圧縮と構造化

マルチエージェントシステムでは、エージェント間のメッセージ中継が最大のコスト要因になる。各エージェントがフルコンテキストを次のエージェントに渡すと、チーム全体のトークン消費が爆発的に増加する。

### 通信パターンとコスト

| パターン | 説明 | トークン消費 |
|---------|------|------------|
| フルコンテキストパススルー | 全履歴を次のエージェントに渡す | 15x（基準） |
| **構造化サマリー** | 結論・判断根拠だけをJSONで渡す | **3〜5x** |
| 結果だけ渡す | 最終成果物だけを渡す | 1〜2x |

### 構造化サマリーの設計

```
// 悪い例: フルコンテキストのパススルー
"あなたは前のエージェントの会話をすべて引き継ぎます。[50ターン分の会話履歴]"

// 良い例: 構造化サマリー
{
  "agent": "design-analyzer",
  "task": "ブース設計図の分析",
  "findings": ["通路幅2.5m必要", "照明数12基推奨"],
  "decisions": {"material": "アルミフレーム", "budget_used": "65%"},
  "next_actions": ["デザイン案生成に進む"],
  "excluded": ["分析過程の詳細ログ", "試行錯誤の記録"]
}
```

### チーム構成のコスト最適化

| 構成 | トークン消費 | 品質 | 推奨状況 |
|------|------------|------|---------|
| 単一エージェント | 1x | ベースライン | 単純タスク |
| supervisor + worker（密結合） | 8〜12x | 高い | 高品質が必要な複雑タスク |
| supervisor + worker（疎結合） | 3〜5x | 高い | **推奨: コストと品質のバランス** |
| ピアツーピア（全員が全員と通信） | 15x+ | やや高い | 避ける |

**疎結合のポイント**: supervisorはworkerに「何をすべきか」だけを渡し、workerは「結果」だけを返す。中間状態や試行錯誤は各workerのコンテキスト内に閉じる。

## 6レバー統合: 12エージェント構成のコスト試算

### 前提
- モデル: Claude Sonnet（入力$3/Mtok、出力$15/Mtok）
- 1エージェントあたり: 平均入力5,000 tok、出力1,000 tok
- 12エージェント、1日あたりのタスク数: 20

### 最適化前: 38Mトークン/日

| 項目 | トークン数/日 | コスト/日 |
|------|-------------|----------|
| エージェントループ（4x） | 20M | $60.00 |
| チーム協調（15x） | 15M | $45.00 |
| ツール結果埋め込み | 3M | $9.00 |
| **合計** | **38M** | **$114.00** |

### 最適化後: 9Mトークン/日（約76%削減）

| レバー | 削減効果 | 適用後のトークン/日 | コスト/日 |
|-------|---------|-------------------|----------|
| 1. プロンプトキャッシュ | 入力46%減 | 20.5M | $61.50 |
| 2. 小モデルルーティング | 全体40%減 | 12.3M | $36.90 |
| 3. ツール制限（3〜6） | コンテキスト20%減 | 9.8M | $29.52 |
| 4. ターン/トークンキャップ | 超過防止 | 9.8M（安定） | $29.52 |
| 5. バッチ処理（50%オフ） | 該当処理50%減 | 9.8M（うち30%バッチ） | $25.09 |
| 6. 通信圧縮 | チーム協調70%減 | **9.0M** | **$23.04** |

**月間削減額**: ($114.00 - $23.04) × 30日 = **約$2,729/月**

## オージャストでの適用: ブース制作AIアシスタント

### 現在の構成（最適化前）

```
[Fable 5.2] 顧客ヒアリング内容の分析
[Fable 5.2] ブースコンセプトの立案
[Fable 5.2] デザイン案の生成
[Fable 5.2] デザイン案のレビュー・修正
[Fable 5.2] 見積もりの計算
[Fable 5.2] 提案書の作成
```

全工程をFable 5.2で実行しており、1案件あたり約200Kトークン（約$4.80）を消費している。

### 最適化後の構成（6レバー適用）

```
レバー1: [固定ガイドライン+過去事例をプロンプト先頭にキャッシュ]
レバー2: [Fable 5.2] 顧客ヒアリング分析 → [Haiku] デザイン案生成 → [Fable 5.2] レビュー
レバー3: ツールを「事例検索」「デザイン生成」「見積計算」の3つに制限
レバー4: 各エージェントの最大ターン数を20に制限
レバー5: 提案書の一括生成は夜間バッチで実行
レバー6: 各工程は「決定事項のみ」を次の工程にJSONで渡す
```

**試算**: 1案件あたり約50Kトークン（約$1.20）、**約75%削減**。月間50案件で約$180/月の削減が見込める。

### 導入フロー

```
1. 現在のブース制作AIのプロンプト構造を分析
2. 固定ガイドラインと過去事例を文書化し、プロンプト先頭に配置
3. デザイン案生成をHaikuに委譲するルーティング基準を定義
4. 各エージェントのツールセットを3〜6に制限
5. ターン数・トークンキャップを設定
6. 夜間バッチ処理の対象を選定
7. エージェント間の通信フォーマットをJSONサマリーに統一
8. 1案件の実測コストを最適化前後で比較
```
