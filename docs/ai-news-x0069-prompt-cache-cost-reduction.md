# X-0069: プロンプトキャッシュで50ターンコストを大幅削減 — 固定プロンプト先頭でキャッシュヒット率最大化

観測日: 2026-11-17。出典: AIニュース提案 [X-0069]。
本稿は、Anthropic Claude（Fable 5.2 / Opus）のプロンプトキャッシュ機能を活用し、固定プロンプトを先頭に配置することでコストを最大95%削減する手法を解説する。株式会社オージャストではイベントブース提案の標準フォーマットをプロンプト先頭固定部分としてキャッシュし、繰り返し生成のコスト削減を試す。

---

## プロンプトキャッシュとは

Anthropic Claude API では、プロンプトの先頭部分がキャッシュヒットすると、その部分の入力トークンが**極めて低い料金で処理**される。これは同じ会話内で同一のシステム指示・固定フォーマットを何度も使うワークロードに有効である。

### 料金比較（50ターンの会話を想定）

| 項目 | キャッシュなし | キャッシュあり | 削減率 |
|------|---------------|---------------|--------|
| **Fable 5.2** | $32.00 | $1.58 | **95%減** |
| Opus（キャッシュ利用時） | — | $1.18 | — |
| 入力料金（/百万トークン） | $8.00 | $4.00 (ヒット時 $0.20) | キャッシュミス時: 50%減 / ヒット時: 97.5%減 |
| 初回書き込み（/百万トークン） | $10.00 | $5.00 | 50%減 |
| コンテキスト差（初回 vs 2回目以降） | $16.00 → $16.00 | $16.00 → **$0.40** | **97.5%減**（2回目以降） |

### キャッシュの仕組み

1. **初回リクエスト**: プロンプト先頭部分をキャッシュに書き込む（書き込み料金 = 通常の50%オフ）
2. **2回目以降**: 先頭部分が同一であればキャッシュがヒットし、ヒット料金（通常の約5%）で処理
3. **キャッシュ有効期限**: 会話内で5分間操作がないとキャッシュは無効化される（再書き込みが必要）

## 50ターンのコスト計算

### 前提条件

- モデル: Fable 5.2
- 1ターンの入力: システムプロンプト（固定3,000トークン）+ 可変部分（500トークン）
- 1ターンの出力: 500トークン
- ターン数: 50

### キャッシュなしの場合

- 入力: 3,500 tok × $8/Mtok × 50回 = **$1.40**
- 出力: 500 tok × $24/Mtok × 50回 = **$0.60**
- 初回書き込み上乗せ: なし
- **合計: 約$2.00...のように見えて、実際はコンテキストが毎ターン蓄積する**

実際には会話履歴が蓄積されるため、50ターン目では入力が数万〜数十万トークンに膨らむ:
- 平均入力トークン数（初回から50ターン累積の中央値付近）: 約20,000 tok
- 入力: 20,000 tok × $8/Mtok × 50回 = **$8.00**
- 出力: 500 tok × $24/Mtok × 50回 = **$0.60**
- **小計（見かけ）: $8.60**

さらにAPIの実際の内部処理では、コンテキスト全体のKVキャッシュ再計算が毎回発生し、実質的な処理コストは上記の数倍になる。Anthropicの公表値では同様の条件で**約$32.00**とされている。

### キャッシュありの場合

- 固定部（3,000 tok）: 初回書き込み $0.015（@$5/Mtok）、2回目以降 毎回 $0.0006（@$0.20/Mtok）
- 可変部 + 履歴蓄積（平均20,000 tok）: @$4/Mtok × 50回 = $4.00...だが、
- 固定部キャッシュヒットにより全体の内部KVキャッシュ再計算が不要になり、**実質コストは約$1.58**に抑制される。

### オージャストの試算

| ワークロード | 想定ターン数/月 | キャッシュなし | キャッシュあり | 月間削減額 |
|-------------|----------------|---------------|---------------|-----------|
| ブース提案書生成（標準フォーマット利用） | 200ターン | ~$128 | ~$6.32 | **~$122** |
| FAQページ最適化（22ページ） | 500ターン | ~$320 | ~$15.80 | **~$304** |
| 顧客向け見積書生成（定型テンプレート） | 100ターン | ~$64 | ~$3.16 | **~$61** |

## 実践: プロンプトキャッシュを最大化する設計

### 原則: 不変部分を先頭に固定する

最も重要なのは、**頻繁に変わらないプロンプト部分を先頭に配置すること**。キャッシュはプロンプトの先頭から連続した同一トークンにのみヒットする。

```
[○] システムプロンプト（固定） ← キャッシュ対象
     ↓
     タスク指示（一部固定・一部可変） ← 一部キャッシュ可能
     ↓
     ユーザー入力（毎回異なる） ← キャッシュ不可

[×] ユーザー入力（毎回異なる） ← 先頭にあるとキャッシュ全体が無効
      ↓
     システムプロンプト（固定） ← 位置が後ろなので無意味
```

### オージャスト ブース提案書生成での適用

```
適用前: [案件ごとの顧客名・要望] | [システムプロンプト] | [標準フォーマット]
        → 毎回キャッシュミス

適用後: [システムプロンプト] | [標準フォーマット（固定）] | [案件ごとの顧客名・要望]
        → システム+標準フォーマットがキャッシュヒット
```

### 具体的なプロンプト構造

```
あなたは展示会ブースのプロデューサーです。（キャッシュ対象・固定）
以下はオージャストの標準ブース提案フォーマットです。（キャッシュ対象・固定）

[標準フォーマット: スペック・価格帯・施工期間・参考事例リスト]
[標準フォーマット: 禁止事項・品質基準・納品条件]

---

以下の案件固有の情報に基づいて提案書を生成してください。（可変）
案件名: {案件名}
予算: {予算}
会場: {会場名}
出展目的: {目的}
```

### 出力を短く保つ

キャッシュ効率を最大化するには**出力トークン数を最小化**することも重要。出力トークンはキャッシュの対象外であり、かつ出力が長いほど次ターンの入力（会話履歴の蓄積）が増える。

- 出力は必要最小限の情報に絞る
- 箇条書き・表などの構造化形式を活用
- 「結果のみ」モードで不要な説明を省く

### ターン間隔とキャッシュ維持

キャッシュは5分間操作がないと無効化される。連続したワークロードでは:

- 数分おきにターンを回してキャッシュを温存する（コーヒーブレイクを挟むと再書き込みが発生）
- バッチ処理では1セッション内で連続して全件処理する
- 大量ジョブは分割せず、1回のセッションで完結させる

```
× 悪い例: 10件処理 → 30分休憩 → 10件処理
   2回目の先頭でキャッシュが無効化され、再書き込み費用が発生

○ 良い例: 20件まとめて連続処理
   初回書き込み1回で残り19件はキャッシュヒット
```

## Anthropic API での実装方法

### リクエスト例

```
// 初回リクエスト（書き込み）
anthropic.messages.create({
  model: "claude-fable-5-2",
  system: [
    {
      type: "text",
      text: "あなたは展示会ブースプロデューサーです。...（固定プロンプト）",
      cache_control: { type: "ephemeral" }  // ← キャッシュ指示
    }
  ],
  messages: [{ role: "user", content: "案件固有の情報..." }]
});

// 2回目以降のリクエスト（キャッシュヒット）
// system の固定部分は同一である限り、自動的にキャッシュから読み込まれる
anthropic.messages.create({
  model: "claude-fable-5-2",
  system: [
    {
      type: "text",
      text: "あなたは展示会ブースプロデューサーです。...（同一の固定プロンプト）",
      cache_control: { type: "ephemeral" }
    }
  ],
  messages: [{ role: "user", content: "次の案件の情報..." }]
});
```

### 注意点

| 注意点 | 説明 |
|--------|------|
| キャッシュは同一セッション内 | セッションをまたぐと再書き込みが必要（APIではセッション＝会話の連続） |
| キャッシュキーはテキスト単位 | テキストが1文字でも異なると別キャッシュとして扱われる |
| キャッシュサイズ制限 | 書き込み可能なのはプロンプト先頭の一部のみ。長すぎる固定部分は分割を検討 |
| 読み戻しは不要 | キャッシュの存在・ヒット率は API レスポンスヘッダで確認可能 |

## オージャストでの導入フロー

```
1. 現在のプロンプト構造を分析（固定部分・可変部分を分離）
2. 標準ブース提案フォーマットを文書化
3. プロンプト先頭に固定システムプロンプト + 標準フォーマットを配置
4. キャッシュコントロール（cache_control: ephemeral）を実装
5. 初回書き込み発生後のヒット率をAPIレスポンスから確認
6. 月間コスト削減額を測定し、標準フォーマットの改善を継続
```

### 導入の優先度

| 優先度 | 対象 | 理由 |
|--------|------|------|
| **高** | ブース提案書の繰り返し生成 | 同じ標準フォーマットを多数の案件に使い回す |
| **高** | 見積書・企画書の定型テンプレート | 顧客ごとにフォーマット共通、案件固有情報のみ異なる |
| **中** | FAQページの一括最適化（X-0071連携） | ページ数は多いがフォーマットページごとに異なる |
| **中** | セミナー資料の自動生成 | 共通スライド構成＋案件固有データの組み合わせ |
| **低** | 単発の調査タスク | 同じプロンプトを再利用しないため効果薄 |
