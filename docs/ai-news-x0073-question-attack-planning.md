# X-0073: 質問攻め計画でAIコーディングを20倍速

観測日: 2026-11-18。出典: AIニュース提案 [X-0073]。
目的: 100以上の質問で要件を完全に引き出し、細分化されたタスクでAIコーディングを高速化する手法を確立し、展示会ブースサイトの事例ギャラリーや見積機能の実装に適用する。

## 1. 質問攻め計画とは

AIコーディングにおいて、実装着手前に**徹底的な質問**で要件を引き出すことで、手戻りを劇的に減らし全体速度を向上させる手法。以下のプロンプトが核となる：

```
I want to build out {機能詳細}.
Ask as many questions you need of me to fully understand every detail
of what I want to build out. Then take everything you learn,
and create super focused and detailed Linear issues. Then begin work.
```

### 1.1 なぜ20倍速くなるのか

従来の「〜を作って」という1行指示では、以下の問題が発生する：

| 問題 | 影響 |
|------|------|
| 前提の不一致 | AIが想定した要件と実際の要件がズレている |
| 曖昧な仕様 | 「こんな感じ」が通じず、数回の試行錯誤が必要 |
| タスクの粒揃い | 大きすぎるタスクを1回で片付けようとして失敗 |
| 手戻りの連鎖 | 前提のズレが後続タスク全体に波及 |

質問攻め計画では、実装前に**100以上の質問**で要件を完全に引き出し、**40以上の細分化タスク**を生成する。これにより：

- 着手後は「次のタスク」を実行するだけで迷わない
- 前提のズレが事前に解消されている
- 各タスクが小さく確実に完了できるサイズになっている
- 途中で「やっぱりこうだった」の修正が激減する

結果として、全体の実装時間が約1/20に短縮される（情報元の実測値）。

## 2. 3ステップのワークフロー

### Step 1: 質問ラウンド（要件引き出し）

AIが100以上の質問を投げ、開発者が回答する。質問の種類：

| カテゴリ | 質問例 | 目的 |
|----------|--------|------|
| **ユーザー** | 誰が使う？ どんな権限が必要？ | ペルソナ・認証設計 |
| **データ** | どんなデータを表示？ どこから取得？ | データモデル・API設計 |
| **UI** | どんな画面がある？ モバイル対応は？ | 画面遷移・レスポンシブ設計 |
| **ふるまい** | クリックしたらどうなる？ エラー時の挙動は？ | インタラクション設計 |
| **制約** | 予算・期間・技術縛りは？ | 実装制約の明確化 |
| **既存** | 再利用できるコードは？ 移行計画は？ | 既存資産の活用 |

#### 実用的な質問スニペット

```markdown
## プロジェクト質問テンプレート

### ユーザー関連
- この機能を使うのは誰ですか？（エンドユーザー、管理者、両方）
- 認証は必要ですか？（ログイン/SNS連携/なし）
- 権限レベルはいくつ必要ですか？

### データ関連
- データの保存先は？（DB/ファイル/外部API）
- 1回の操作で扱うデータ量は？
- データの更新頻度は？

### UI関連
- 対応画面サイズは？（デスクトップのみ/タブレット/スマホ）
- カラースキームやデザインシステムは指定ありますか？
- アニメーションやトランジションは必要ですか？

### ふるまい関連
- エラー時のユーザー体験は？（トースト/モーダル/リダイレクト）
- ローディング中の表示は？
- オフライン対応は必要ですか？

### 制約関連
- 使用するフレームワーク/ライブラリの指定は？
- ブラウザ対応範囲は？（最新のみ/IE11含む）
- パフォーマンス目標は？（読み込み◯秒以内など）

### 既存関連
- 再利用可能なコードベースはありますか？
- APIの仕様書やモックはありますか？
- 移行すべき既存データはありますか？
```

### Step 2: タスク分解（Linear Issue生成）

質問で得た情報をもとに、超詳細なLinear Issue（タスク）を生成。各Issueは：

- **1つのファイルまたは1つの関数**に相当する粒度
- **完了条件**が明記されている
- **依存関係**が整理されている
- **見積もり時間**が付与されている

タスクの例：

```
Task: 事例ギャラリーのカードコンポーネント作成
- ファイル: components/CaseCard.tsx
- 受け取るprops: { title, thumbnail, category, link }
- 完了条件: Cardが正しくレンダリングされ、Storybookで全バリアント確認
- 依存: なし（独立して作業可能）
- 見積もり: 30分
```

### Step 3: 「next thing」で進行

タスクリストができたら、以下のルールでひたすら消化する：

1. **最も依存の少ないタスク**から着手
2. 1タスク完了したら「next thing」と指示
3. AIが自律的に次のタスクを選び実行
4. 行き詰まったら「next thing」で再起動
5. 全タスク完了で終了

この方式の利点：
- 都度「次は何をしよう」と考える必要がない
- AIが文脈を保ったまま連続作業できる
- 中断・再開が容易（タスクリストがあればどこからでも再開可能）
- 進捗が「◯/40タスク完了」と可視化される

## 3. 展示会ブースサイト事例ギャラリーへの適用例

### 3.1 プロンプト例

```
I want to build out a case study gallery for an exhibition booth company's website.
Ask as many questions you need of me to fully understand every detail
of what I want to build out. Then take everything you learn,
and create super focused and detailed Linear issues. Then begin work.
```

### 3.2 想定される質問と回答

| AIの質問 | 回答例 |
|---------|--------|
| ギャラリーに表示する事例はどこから取得しますか？ | WordPressのカスタム投稿タイプ「case_study」のREST API |
| 1ページあたりの表示件数は？ | 12件（3列×4行）、無限スクロール or 「もっと見る」ボタン |
| フィルター機能は必要ですか？ | 業種カテゴリ・ブースサイズ・予算帯の3軸フィルター |
| スマホ対応は？ | レスポンシブ必須、スマホは1列表示 |
| 画像の扱いは？ | サムネイル（400×300）とフルサイズの2段階。lightbox表示 |
| 事例詳細ページは別途必要？ | モーダル内で完結させる。URLは/#/case/{slug}で直リン可能に |
| 検索機能は？ | キーワード検索（タイトル・説明文） |
| ソート順は？ | 新しい順（デフォルト）、おすすめ順（管理画面で設定） |
| 表示速度の目標は？ | Lighthouse 90以上。画像はWebP + lazy loading |

### 3.3 生成されるタスク例（実装指示書）


## 5. 実装テンプレート

### 5.1 質問攻めプロンプトテンプレート

```markdown
I want to build out {機能名} for {プロジェクト名}.

{機能の簡潔な説明（1〜2文）}

Ask as many questions you need of me to fully understand every detail
of what I want to build out. Then take everything you learn,
and create super focused and detailed Linear issues. Then begin work.
```

### 5.2 回答の準備

質問攻めの効果を最大化するには、回答側が事前に以下の情報を整理しておく：

```markdown
## 事前準備シート
- 機能名: 
- 対象ユーザー: 
- 既存のコードベース: 
- 使用技術スタック: 
- 参考資料URL: 
- 制約・期限: 
- 決定済みの事項（変更不可）: 
- 検討中の事項（変更可）: 
- 優先度の高い要件トップ3: 
```

### 5.3 「next thing」運用ルール

タスク消化中は以下のルールに従う：

1. **着手前に現状確認**: `git status` で変更差分を確認
2. **1タスク=1コミット**: `git add <該当ファイル> && git commit -m "feat(x0073): タスク名"`
3. **完了したら報告**: `✅ task-004 完了（CaseCard.tsx, 全バリアント確認済み）`
4. **次のタスク**: AIが自動選択 or 「next thing」と指示
5. **行き詰まり**: 15分以上かかりそうなら「next thing」とだけ入力（AIが戦術変更）
6. **全タスク完了**: 「すべて完了しました。タスク一覧: ◯/◯」を確認して終了

## 6. 期待される効果

| 指標 | 従来方式 | 質問攻め計画 |
|------|---------|-------------|
| 実装着手までの準備時間 | 5〜10分（曖昧なまま開始） | 30〜60分（質問回答） |
| 着手後の手戻り率 | 40〜60% | 5〜15% |
| 1機能あたりの修正回数 | 5〜10回 | 1〜3回 |
| 全体実装時間（事例ギャラリー想定） | 3〜5日 | 3〜6時間 |
| タスク管理の透明性 | 低い（頭の中） | 高い（40+タスクで可視化） |
| 中断後の再開コスト | 高い（文脈再構築） | 低い（タスク一覧があれば即再開） |

> **注記**: 上記の数値は情報元の報告に基づく期待値。オージャストの実プロジェクトでの実測値が得られ次第更新する。

## 7. 導入ステップ

1. **最初のプロジェクト選定**: 事例ギャラリー機能を最初の適用対象とし、質問攻め計画を実践
2. **質問リストの改善**: 実際のQAからノウハウを蓄積し、プロジェクト種別ごとの質問テンプレートを洗練
3. **「next thing」の自動化**: Claude CodeのWorkflow機能と組み合わせ、タスク消化を半自動化
4. **効果測定**: 従来方式との比較（実装時間・手戻り回数・品質）を計測し、20倍高速化を検証
5. **横展開**: 展示会ブースサイトの他の機能（見積・お問い合わせ・管理画面）にも順次適用
6. **社内ナレッジ化**: 成功パターンをSkillsとして保存し、再利用可能にする

## 8. 注意点と制約

- **質問に答える人の負荷**: 100以上の質問に答えるには30〜60分程度の集中した時間が必要。開発者にまとまった時間を確保してもらう必要がある。
- **全ての質問に答えられなくても良い**: 「未定」「検討中」と回答しても問題ない。その場合はAIが適切なデフォルト値を提案し、タスクに「確認事項」としてマークする。
- **大規模プロジェクトでは分割**: 1回の質問攻めでカバーできる範囲には限界がある。大きすぎる機能は複数のサブ機能に分割してから各サブ機能に質問攻めを適用する。
- **手法自体の改善**: 実施後の振り返りで「この質問は不要だった」「この質問が不足していた」を記録し、次回の質問テンプレートに反映する。
