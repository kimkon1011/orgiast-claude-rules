# X-0098: プレフィックスアウェア・ルーティング — マルチワーカーでキャッシュ効率を最大化

> 2026-11-28 設計・実装。自動セッションによる実装。
> 既存 X-0009（KVキャッシュ共有）・X-0015（静的先頭配置）は単一ワーカー前提。
> X-0098 はマルチワーカー環境でプレフィックスを安定ルーティングしキャッシュヒット率を改善する。

## 概要

LLM 推論を複数ワーカー（コンテナ/インスタンス）で負荷分散する環境では、リクエストを**どのワーカーに割り振るか**がキャッシュ効率を決める。
ラウンドロビン（均等分散）では、同一プレフィックスを持つリクエストが異なるワーカーへ散るため、各ワーカー内の KV キャッシュが独立して育たず、**キャッシュヒット率は 1/N（N=ワーカー数）に低下する**。

本提案では、**プレフィックスハッシュ（consistent hashing）によるアフィニティ・ルーティング**で、同一プレフィックスのリクエストを必ず同じワーカーへ送り、キャッシュヒット率を単一ワーカーと同等（〜100%）に維持する。

## 問題

| 戦略 | N=8 でのキャッシュヒット率 | TTFT | コスト |
|------|---------------------------|------|--------|
| ラウンドロビン | 12.5%（=1/8） | 高（キャッシュミス時 800ms+） | 高（キャッシュ割引が効かない） |
| ランダム | ~12.5% | 同等 | 同等 |
| プレフィックスアフィニティ | **〜100%（最初の1リクエスト以外）** | 低（キャッシュヒット時 150ms） | low（キャッシュ割引 90% 減） |

8 ワーカー構成で 100 件の同一プレフィックスリクエストを処理する場合：

- **ラウンドロビン**: 各ワーカーに 12〜13 件ずつ。各ワーカーで最初の 1 件だけがキャッシュミス（計 8 回ミス）、残りはヒット。ヒット率 = (100-8)/100 = **92%**
- **アフィニティ**: 1 台のワーカーに全 100 件集約。最初の 1 件だけがミス、残り 99 件はヒット。ヒット率 = **99%**。加えて、他の 7 台はキャッシュメモリを消費しない。

→ 見かけの差は小さいが、**メモリ効率とスループットで差が拡大**する（後述）。

## 解決策

### コンシステントハッシュリング

ワーカーをリング状に配置し、各プレフィックスのハッシュ値から最も近いワーカーを決定する。ワーカーの追加・削除時に再配置が最小限で済む（リング上の隣接ノードのみ影響）。

```
       [Worker-A]
         /    \
  [Worker-H]  [Worker-B]
    |    リング    |
  [Worker-G]  [Worker-C]
    |    ハッシュ   |
  [Worker-F]  [Worker-D]
         \    /
       [Worker-E]

PrefixHash("ブース標準仕様") → ring position 0x3A → Worker-C
PrefixHash("ブース標準仕様") → ring position 0x3A → Worker-C（毎回同じ）
PrefixHash("イベント企画")  → ring position 0xB1 → Worker-F
```

### アフィニティ・ルーティングの種類

| 方式 | 説明 | トレードオフ |
|------|------|-------------|
| プレフィックスハッシュ固定 | プレフィックス文字列のハッシュ値でワーカー決定 | ワーカー増減時に一部再配置（ok） |
| テンプレートIDベース | ブーステンプレートIDなど、既存の安定キーを使用 | キーの設計が必要（ID が無いと使えない） |
| セッションアフィニティ | 同一セッションからのリクエストを同じワーカーに | セッション跨ぎのキャッシュは効かない |
| ハイブリッド | プレフィックス長に応じて方式を切り替え | 実装が複雑 |

### オージャスト適用: ブーステンプレートを安定プレフィックスに

展示会ブース提案の生成では、以下のようにテンプレートをプレフィックスとして使う：

1. **標準ブース仕様テンプレート**（`apps/booth-spec-generator/cache-prefix.md`）をプレフィックスとして登録
2. 同一テンプレートを使用する案件は同一ワーカーへルーティング
3. 8 ワーカー構成でも、**テンプレート単位でキャッシュが 1 台集中**して育つ
4. ヒット率は単一ワーカーと同等（提案生成: 65〜70%、一括案件: 85〜90%）

```mermaid

    A[リクエスト着信] --> B{プレフィックス抽出}
    B -->|共通部分| C[ハッシュ計算]
    C --> D[リング参照]
    D -->|Worker-3| E[Worker-3 で処理]
    E --> F{KVキャッシュ}
    F -->|ヒット| G[高速応答: ~150ms TTFT]
    F -->|ミス(初回のみ)| H[通常応答: ~800ms TTFT → キャッシュに保存]
```

## 測定指標

| 指標 | ラウンドロビン | アフィニティ | 改善 |
|------|---------------|-------------|------|
| キャッシュヒット率 (N=8) | 92%* | **99%** | +7% |
| 平均TTFT | ~750ms | **~200ms** | −73% |
| メモリ使用ワーカー数 | 8台すべて | **1台のみ** | −87.5% |
| ワーカー追加時の再配置率 | N/A | **1/N** | 最小限 |

\* ラウンドロビンでも多数リクエストがある程度ヒットするのは、各ワーカーに数件ずつ割り当たるため。ただし、ワーカー間でキャッシュが重複するメモリ問題がある。

## 前提と限界

- **同一プレフィックスは同一テキストであること**: バイトレベルの一致が必要（X-0015 参照）
- **プレフィックス長が十分であること**: 最低 20 トークン以上の共通部分が必須
- **ワーカー数が動的に変わる場合**: コンシステントハッシュリングは最小限の再配置で対応可
- **外部負荷分散器との統合**: 本ツールはルーティング決定論理まで。実際の振り分けはロードバランサー（K8s Service, Envoy, Nginx）のレイヤーで実装する
