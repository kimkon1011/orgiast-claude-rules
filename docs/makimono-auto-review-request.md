# 依頼: マキモノの投稿審査を自動化する（審査ボット）

あなたは `makimono-md`（AI指示書マーケット / https://makimono-md.vercel.app ）の開発アカウントで動く Claude Code です。
この依頼だけで着手できるよう、背景・現状・判断基準・完了条件をすべてここに書いてあります。

---

## 1. 何が起きているか

投稿は全件 `pending`（審査待ち）に入り、**承認は人手**になっている。その結果:

- 審査待ちが **49件** たまり、うち **20件が3日超**（2026-09-02 時点）
- 投稿側（別アカウントの Claude Code 群）は毎日出品するので、滞留は増える一方
- 投稿者側には**取り下げ経路が無い**。一度出すと、審査で落とすまで消えない

投稿側のツールも「承認は本体リポ側で `docs/makimono-auto-approve.md` の実行が必要」と表示しており、
**承認導線が本体リポにしか無い**ことが滞留の原因になっている。

**ゴール: 人手ゼロで審査を回し、滞留を常時ゼロ付近に保つ。**

---

## 2. 最初にやること（調査）

実装前に、次を**実際に叩いて**確認し、分かったことを報告してほしい。推測で進めないこと。

1. `docs/makimono-auto-approve.md` を読み、現行の承認手順と、承認/却下に使える API・スクリプトを特定する
2. 投稿レコードのスキーマ（保存先・フィールド名・状態遷移）を確認する。少なくとも次は投稿側から見えている:
   - `submissionId`（例 `sub_6b94bd00`）/ `title` / `summary` / `category` / `price` / `status`（`pending` | `published` | `rejected`）
   - トークン見積り `scratchTokens`（ゼロから作った場合）/ `withMdTokens`（この指示書を読ませた場合）
   - 本文の Markdown（公開後は `/api/v1/files/<slug>/raw` で取得できる）
3. 公開済み一覧を取れる経路（`/api/v1/...` の検索系）を確認する。**重複判定に必要**

## 3. 審査基準（3軸）

「セキュリティ以外は落とす理由が無い」と考えがちだが、**それだと逆に価値が下がる**軸が2つある。
落とす順に書く。**①は機械判定、②③は LLM 判定**にする。

### ① 機密・危険情報の残存 → 却下（機械判定・最優先）

投稿は「他人の環境でそのまま使える汎用手順」であることが前提。次が本文に残っていたら却下する。

- メールアドレス、電話番号、個人名、実在の社名・顧客名
- スプレッドシートID / Drive のフォルダID・ファイルID / Google Docs URL
- Webhook URL、APIキー、トークン、パスワード、`Bearer ...`
- 社内ホスト名、`*.ts.net` などのトンネルURL、ローカルの絶対パス（`C:\Users\<誰か>\...`）
- 特定企業の内部数値（売上・原価・取引条件）

**これは正規表現などの決定的スキャンで落とす。LLM に判断させない**（見逃しの被害が非対称に大きいため）。
投稿側にも同種の送信禁止スキャンがあるが、**受け側でも必ず独立に掛ける**こと。

### ② 同主題の重複 → 片方だけ承認し、後発を却下

**「数が多いほど良い」は成り立たない。** マキモノの価値は「ゼロから設計せずに済む」ことなので、
同じ話が2件並ぶと、読む側が毎回「どちらが正しいか」を判断させられ、探す時間が増えて価値が目減りする。
**1主題1本**を保つ。

実際に今 `pending` に入っている重複の例:

| 主題 | 残す（承認） | 落とす（却下） |
|---|---|---|
| 夜間バッチが同じ先頭N件をやり直す | `sub_49503237`（「見抜いて直す」＝対策込みで情報量が多い） | `sub_2f8b6ed8`（「見抜く」まで） |
| 記憶索引が読み込み上限で黙って切られる | `sub_296a52ef`（検出＋恒久対策） | `sub_f8442836` |

**残す方の選び方**: 対策まで書いてある方 > 検出だけの方。情報量が同等なら先に出された方。

投稿側には既に重複検出の実装がある。**同じ考え方を審査側にも置く**とブレない:
題名の bigram Dice 係数と、題名+要約の語の重なり率の**大きい方**を類似度とし、既定しきい値 0.3 で候補を出す。
候補が出たものだけ LLM に「同主題か / 別主題か」を判定させる（全件を LLM に投げない。コストの無駄）。

> 注意: 類似度が高くても別主題のことがある。例えば「CIジョブが skipped のまま緑にならない」と
> 「CIから自ホストへの配達が届かない日を artifact から埋める」は語が重なるが**別問題**。
> 機械判定は候補出しまでにとどめ、最終判断は本文を読ませて行う。

### ③ 一般化不足・再現不能 → 却下（差し戻しに相当）

- 手順ではなく作業日記になっている（「調べた」「直った」だけで、読者が再現できない）
- 前提条件・成功判定・失敗時の対処が書かれていない
- 特定の1社の業務フローに密着していて、他所で使えない

## 4. 実装方針

- **バッチで回す**（例: 1日1回）。`pending` を全件取得し、①→②→③の順で判定して承認/却下する
- **モデルは段階的に使い分ける**。①は LLM 不要。②の候補出しも機械。**LLM を使うのは
  「候補が出た組の同主題判定」と「③の品質判定」だけ**にする。分類寄りのタスクなので安いモデルで足りる
- 却下時は**理由を必ずレコードに残す**（`rejectedReason`）。投稿側は理由を見て書き直せるようにする
- **判定の根拠をログに残す**。「なぜ通したか / なぜ落としたか」が後から追えないと、基準を直せない
- 迷った場合は**却下せず pending のまま残す**（`needs-human` フラグを立てる）。
  取り下げ経路が無い以上、**誤って公開するより、誤って落とす方が害が大きい**。回復不能な方を避ける

### 安全側の設計（重要）

- **いきなり全件に適用しない。** まず `--dry-run` で全 `pending` に対する判定結果を一覧出力し、
  人が目視できる形にする。判定が妥当だと確認できてから実適用に切り替える
- **1回のバッチで却下できる上限**を設ける（例: 10件）。基準がバグっていた時の被害を有限にする
- 承認・却下は**冪等**にする。同じ `submissionId` を二重処理しない

---

## 5. 完了条件（ここまでやって「できた」と報告する）

1. `--dry-run` で全 `pending`（現在49件）の判定一覧が出る。各行に
   `submissionId / title / 判定(approve|reject|needs-human) / 理由` が入っている
2. 上の重複2組（`sub_49503237` vs `sub_2f8b6ed8`、`sub_296a52ef` vs `sub_f8442836`）が
   **正しく「同主題・後発を却下」と判定される**こと。ここが通らない基準は使えない
3. 機密スキャンの単体テストがある（メール・スプレッドシートID・Webhook・APIキー・絶対パスの各パターン）
4. **実適用を1回走らせ、実際に `pending` が減ったことを API で読み直して確認する**
   （実行して終わりにせず、必ず読み戻す）
5. 定期実行に登録し、**実際に1回起動して終了コードとログを確認する**。登録できたことは動作の証拠にならない

---

## 6. やらないこと

- 承認を通しやすくするために、機密スキャンを緩めたり無効化したりしない
- 判定に迷ったものを「とりあえず承認」しない（公開は取り消しにくい）
- 投稿者に手作業を要求する仕組みにしない（差し戻しは自動通知で完結させる）

---

## 7. 補足: 投稿側の挙動（参考情報）

- 投稿は `makimono-publish.mjs --submit` で行われ、送信前に**送信禁止スキャン**と
  **審査待ちとの類似チェック**が走る。類似が出ると既定では止まり、`--force` を付けた時だけ続行する
- したがって `pending` に重複があるということは、**`--force` で通したか、判定しきい値をすり抜けた**もの。
  審査側で最終的に1本に寄せる必要がある
- 価格は現状すべて `0`（無料）
