## 1. 目的とスコープ

### 1.1 目的

オージャスト社の AI エージェントに対して評価駆動開発（Eval-Driven Development, EDD）を適用し、改善の前後を定量的に比較できる仕組みを確立する。

### 1.2 評価対象エージェント

現在の評価対象は**ブース制作の顧客問い合わせ対応エージェント**（以下「本エージェント」）。これはオージャスト社の制作現場に寄せられる顧客からの問い合わせ（Discord / メール / チャット経由）に自動応答するシステム。

将来的には以下のエージェントにも拡大を検討する:
- TETSUKO サイト問い合わせ対応
- 社内向け IT 依頼登録エージェント
- 営業案件管理エージェント

### 1.3 成功定義

1. 評価データセットが 20 件以上揃っている
2. 評価を自動実行するスクリプトが存在する
3. 改善前後でスコアの差分が測定できている
4. プロンプト変更のたびに全評価が再実行されている

## 2. 評価データの定義

### 2.1 評価項目（評価軸）

各評価例に対して以下の項目を評価する:

| # | 項目 | 評価方法 | 重み |
|---|------|---------|------|
| 1 | **適切な routing** | 問い合わせを適切な部署/担当に振れたか（正解の振り先と一致） | 3 |
| 2 | **情報充足度** | 顧客が求める情報を過不足なく提供できたか | 2 |
| 3 | **トーン・倫理** | 丁寧かつ倫理的に問題ない応答か | 2 |
| 4 | **余計な処理をしない** | 依頼されていない処理（登録・発注等）を勝手に行っていないか | 3 |
| 5 | **既存の良い動作を維持** | 以前できていた正しい動作を壊していないか | 2 |

> **重み**: 各評価項目の重み（1〜3、大きいほど重要）。合計点 = Σ(スコア × 重み) / Σ(重み) で正規化。最大値 1.0、最小値 0.0。

### 2.2 評価方法

各評価例は以下の構造を持つ:

```json
{
  "id": "EVAL-001",
  "title": "見積もり依頼（初回接触）",
  "category": "見積もり依頼",
  "input": {
    "user_message": "サンプルスタジオ様より、ブース制作の見積もりをお願いします。規模は3m×3mです。",
    "context": {
      "sender": "sample@example.com",
      "channel": "email"
    }
  },
  "expected": {
    "routing": "sales",
    "info_completeness": 0.9,
    "tone_ethics": 1.0,
    "forbidden_action": 0.0,
    "scores": {
      "routing": 1.0,
      "info_sufficiency": 1.0,
      "tone_ethics": 1.0,
      "no_overaction": 1.0
    }
  },
  "rationale": "初回の見積もり依頼は営業チームへ振る。必要情報（サイズ）が揃っている。",
  "tags": ["見積もり", "初回", "営業"]
}
```

### 2.3 スコアリングの種類

1. **分類評価**: routing の正誤（正解の部署と一致するか = 1.0/0.0）
2. **人手評価**: 情報充足度・トーンは人間が 0.0 / 0.5 / 1.0 で評価（後述の自動化候補）
3. **禁止動作検出**: 禁止処理を実行したか = 0.0（実行した）/ 1.0（実行していない）

### 2.4 評価の自動化ロードマップ

| フェーズ | 内容 | 時期（目安） |
|---------|------|------------|
| Phase 0 | **手動作成・手動評価**: 本ドキュメントの評価データを人間が作成。評価も人間が実行。 | 現在 |
| Phase 1 | **自動評価スクリプト**: エージェントを呼び出し、routing の正誤を自動判定。人間評価項目は保留。 | 次フェーズ |
| Phase 2 | **LLM-as-Judge**: 情報充足度・トーンの一部を LLM 評価に置き換え。 | 将来 |
| Phase 3 | **継続的評価**: プロンプト変更のたびに CI で全評価を自動実行。 | 将来 |

## 3. フォルダ構成

```
eval-driven/
├── index.md                    # この設計書
├── eval-set/                   # 評価データセット
│   ├── initial-evaluations.tsv # TSV版（人間編集・確認用）
│   └── initial-evaluations.json # JSON版（機械処理用、tsvから生成）
├── results/                    # 評価結果
│   └── .gitkeep
├── schema/                     # 評価データのスキーマ定義
│   └── .gitkeep
└── scripts/                    # 評価実行スクリプト（将来）
    └── .gitkeep
```

### 3.1 データ形式の使い分け

- **TSV**: 人間が見て編集しやすい。Excel/Google Sheets で直接開ける。各行が1評価例。
- **JSON**: 機械処理用。スクリプトが直接読む。スキーマでバリデーション可能。

両方置き、JSON を正本として管理する（編集は TSV を経由し、変換スクリプトで JSON を再生成）。

## 4. EDD 実装開始条件（AIコーディング開始ゲート相当）

Claude（人間の実装者）は、以下の条件がすべて満たされるまで**評価自動実行のコードを書いてはならない**。
条件を満たす前に実装を求められた場合は未充足項目を提示し、ドキュメント編集を優先する。

### 共通・必須

- [ ] `eval-driven/index.md` がユーザー承認済み
- [ ] `eval-driven/eval-set/initial-evaluations.tsv` に実在の過去問い合わせに基づく評価例が 20 件以上ある

- [ ] 評価例のカテゴリが最低 3 種類（見積もり依頼 / 仕様質問 / クレーム）をカバーしている

### 自動評価スクリプト（Phase 1）の開始条件

- [ ] 上記「共通・必須」がすべて完了

### プロンプト改善（改善サイクル）の開始条件

## 5. 用語

| 用語 | 定義 |
|------|------|
| EDD | Eval-Driven Development（評価駆動開発）。実装前に評価データを定義し、変更前後を比較しながら改善する方法。 |
| 評価例 | 1件の入力＋期待される出力＋評価スコアのセット。評価データセットの最小単位。 |
| 評価データセット | 複数の評価例を集めたもの。エージェントの性能を測るためのテストスイート。 |
| ベースライン | 改善前のエージェントで評価データセットを実行したスコア。 |
| 回帰 | 改善後に以前できていた動作ができなくなること（既存の良い動作を壊す）。 |
| routing | 問い合わせを適切な部署・担当者に振り分ける処理。 |
| LLM-as-Judge | LLM 自身に評価をさせて人手を省く手法。 |
