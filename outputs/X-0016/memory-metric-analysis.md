# KVキャッシュのメモリ定量分析（X-0016 差分）

> 元ニュースの数値: **32層GQA・ヘッド次元128・BF16** の構成で、
> **8192トークン1シーケンス = 1GiB のKVキャッシュ**、**独立した16シーケンス = 16GiB**。
> プレフィックスキャッシュは一致するプレフィックス部分のKVを共有する。
> 2026-11-09 自動セッションで検算・定量化。

## 1. 1GiB / 16GiB の検算

KVキャッシュのバイト数は次式で表せる。

```
KV bytes = L層 × h_kv(KVヘッド数) × d(ヘッド次元) × 2(KとV) × 2(BF16=2バイト) × Tトークン
```

与えられた条件（L=32, d=128, BF16, T=8192）で 1GiB になるのは **h_kv = 8 のとき**:

```
32 × 8 × 128 × 4 × 8192 = 1,073,741,824 bytes = 1,024 MiB = 1 GiB   ✓
```

- KVヘッド8本は GQA の代表的な構成（例: Llama-3 8B 相当）で、元ニュースの数値と整合する。
- **16シーケンスがプレフィックスを一切共有しない場合**: 16 × 1GiB = **16GiB** ✓

## 2. プレフィックス共有時のメモリ削減

16シーケンス（各8192トークン）がプレフィックス **P トークン**を完全一致で共有するとき、
メモリは「共有1部＋非共有16部」になる。

```
total[GiB] = P/8192 + 16 × (8192 − P)/8192
```

| 共有プレフィックスP | 共有分 | 非共有分（16本） | 合計 | 16GiB比 |
|---|---:|---:|---:|---:|
| 0（独立） | 0 | 16 GiB | **16.00 GiB** | 100%（基準） |
| 2,048 | 0.25 GiB | 12.00 GiB | **12.25 GiB** | −23.4% |
| 4,096 | 0.50 GiB | 8.00 GiB | **8.50 GiB** | −46.9% |
| 6,144 | 0.75 GiB | 4.00 GiB | **4.75 GiB** | −70.3% |
| 8,192（全一致） | 1.00 GiB | 0 | **1.00 GiB** | **−93.75%** |

→ プレフィックスが長いほど効果が線形に増し、**全一致なら16GiB → 1GiB（16分の1）**。

## 3. 「メモリ効率を意識した生成」の意味

- サーバーサイドのバッチ推論（vLLM / SGLang の **RadixAttention / 自動プレフィックスキャッシュ**）では、
  共有KVは実際に GPU メモリ上で1部に集約される → 同じメモリでより多くの同時シーケンス・長い出力が回せる。
- API レベルのプロンプトキャッシュ（Anthropic / OpenRouter）では、キャッシュはプロバイダー側で保持され、
  ユーザーへの効果は **prefill 計算の省略（TTFT短縮）＋ cached トークンの割引課金（約10%）** として現れる
  （X-0009 で実測シミュレーション済み: TTFT −82.8〜85.0%、コスト −60〜68.6%）。
- ユーザー側が取れる操作は「**共通プレフィックスを固定する・類似リクエストを連続実行する・
  TTL 内（既定5分）にまとめる・cache_creation / cache_read トークンを測定する**」4点で、
  これが「メモリ効率を意識した生成」の実践になる。

## 4. オージャスト適用の定量想定

展示会ブース提案の類似案件（共通デザインガイドライン＋展示会ルール＋会社概要を先頭に固定）:

- 想定: 16案件 × 8,192トークン文脈、うち共通プレフィックス 2,048トークン
  → KVメモリ 16GiB → **12.25GiB（−23.4%）**、加えて X-0009 のゲートウェイで
  2件目以降 TTFT −80%級・入力コスト −60%級。
- 共通部を充実させる（4,096トークン化 → −46.9%）ほど利益が大きい。
  共通プレフィックスの自然な候補: 小間規格（2.7m×6m・[[reference-koma-unit-definition]]）、
  使用構造材・照明・床材の標準仕様、安全・搬入出ルール、会社プロフィール。

## 5. 実測時の確認項目（次回、実 API で）

- `usage.cache_read_input_tokens`（Anthropic） / `usage.cached_tokens`（OpenRouter）が 2件目以降 0 でないこと
- 2件目以降の TTFT（streaming 最初の content token 到達）が初回より短いこと
- 同じ内容でもプロンプト末尾に1バイトでも差分があるとキャッシュが効かないこと（先頭一致が前提）
