# AIニュース提案 [X-0039]: ドキュメント中心の階層的AI開発 — 要求トレーサビリティを実現する多層エージェント設計

観測日: 2026-11-17
出典: IBM Think / Google Cloud Architecture / ACM DocEng 2026 / arXiv:2503.15736 (SPD-RAG) / LangGraph / ＠IT / renue
ライセンス: 各出典のライセンスに準拠

## 概要

2026年、AIエージェントによるソフトウェア開発は「単一エージェントに全部やらせる」フェーズから、**階層的タスク分解 × ドキュメント中心設計**のフェーズへ移行している。複雑な要求を上位エージェントが分解し、下位の専門エージェントに委任、各エージェントは必要最小限のドキュメントだけを読んで実行する——このアーキテクチャが、大規模開発のトレーサビリティ・品質・コストのすべてを改善する。

本提案の核となる概念:

| 概念 | 説明 |
|------|------|
| 階層的作業設計 | 複雑タスクを木構造のサブタスクに分解し、各階層が担当範囲を委任・監督 |
| 要求トレーサビリティ | 各成果物がどの要求／設計書のどの項目から生まれたかが追跡可能 |
| ドキュメント=コード | 要求仕様・設計書・タスクリストをAIエージェントの直接入力として使う |
| コンテキスト分離 | 各エージェントは自分のタスクに関係するドキュメントサブグラフだけを読む |

## ドキュメント中心階層型アーキテクチャ

### 3層構造（IBM階層型AIエージェントモデル）

IBM が提唱する階層型AIエージェントアーキテクチャは、3層で構成される:

```
┌─────────────────────────────────┐
│  上層: 戦略立案・タスク分解      │  ← オーケストレーター
│  ─ 要求分析、タスクグラフ構築    │     （Opus/Fable クラス）
│    トレーサビリティマップ管理     │
├─────────────────────────────────┤
│  中層: 戦術的意思決定・調整      │  ← ドメインスペシャリスト
│  ─ ドキュメント生成、品質検証    │     （Sonnet クラス）
│    サブタスク割り当て、進捗監視   │
├─────────────────────────────────┤
│  下層: 個別タスク実行            │  ← ワーカーエージェント
│  ─ コード実装、テスト実行、       │     （Codex / Haiku クラス）
│    ファイル編集、データ処理       │
└─────────────────────────────────┘
```

**利点**: 各層が分離されることで、上位の戦略的判断を下位の実装詳細が汚染しない。上位は要求全体の一貫性を保ち、下位は実装に集中できる。

### ドキュメント DAG（Context Hierarchy System）

Context Hierarchy System（cavekit / Blueprint）は、プロジェクト知識を**有向非巡回グラフ（DAG）** として整理する:

```
refs/ ─→ blueprints/ ─→ plans/ ─→ impl/
(要求)    (設計)         (実装計画)   (実装コード)
```

各ドキュメントは「どの上位ドキュメントのどの要件を満たすか」を明示するリンクを持つ。エージェントはルートから入り、自分のタスクに関係するサブグラフだけをトラバースする。これにより:

- エージェントのコンテキストが肥大化しない
- 変更があったドキュメントだけを差分読込可能
- 親の意思決定（なぜこの仕様なのか）が下位のどの実装に影響するか追跡可能

### SPD-RAG: 文書単位サブエージェント

SPD-RAG（arXiv:2503.15736）は、クロスドキュメントQAのために設計された階層的マルチエージェントフレームワーク:

- **各文書に専用サブエージェントを割り当て**（文書単位の集中検索）
- **コーディネーター**がタスクをディスパッチし、部分回答を集約
- **Map-Reduce合成層**で大規模コーパスをスケーラブルに処理

LOONGベンチマークで Avg Score 58.1（通常RAGの33.0を大幅に上回る）、APIコストはフルコンテキストベースラインの**38%**。

### Dash: ハイパーメディアワークスペース（ACM DocEng 2026）

Dash は、AIエージェントを**キャンバス上の第一級ドキュメント**として操作する新しいパラダイム:

- エージェントとドキュメントが双方向リンクで接続
- Ollama経由のローカルモデルで完全オンデバイス動作
- HIPAA/法務/防衛/金融向けの強固なセキュリティモデル

ドキュメント間の双方向リンクがエージェントの意思決定根拠のトレーサビリティを担保する点が特徴。

## 2026年のマルチエージェントパターン

### 階層的分解（マトリョーシカ）パターン

親エージェントが複雑なタスクをサブタスクに分割し、適切な専門エージェントに委任する。親は一部タスクのみ委任し、結果を待って推論を継続（同期/非同期の混在）。

Google Cloud はこれを **「マルチエージェント階層型タスク分解パターン」** として公式ドキュメント化（2026年5月最終更新）。特に「曖昧で自由度の高い問題」に適するとされる。

### InfiAgentの3レベル階層

InfiAgent（arXiv, 2026年1月）はエージェントを木構造に組織化:

| レベル | 役割 | 責務 |
|--------|------|------|
| Level 3 | Alpha orchestrator | タスク分解・全体戦略 |
| Level 2 | Domain specialists | Coder, Data Collection, QA など専門分野 |
| Level 1 | Atomic tool executors | ファイル編集、API呼び出し、テスト実行 など単一操作 |

**External Attention Pipeline**: エージェントがドキュメント情報を必要とするとき、一時的に分離されたLLMプロセスを起動して問い合わせる。メインエージェントのコンテキストをリーンに保つ設計。

### LangGraph Supervisorモデル

LangGraph の Supervisor（監督者）パターンでは:

- **システムプロンプトを「職務記述書」として設計**
- 監督者は各ワーカーの出力をレビューし、品質基準を満たさなければ差し戻す
- ワーカーは単一責任原則で設計（1ワーカー1責務）

状態管理の単純化、拡張性・保守性の向上がメリット。特に「ドキュメント→コード」の変換チェーン（requirements→design→tasklist→implementation→test）に適する。

### オージャストでの適用シナリオ

#### シナリオ1: ブース制作フローのAIエージェント化

```
要求書（クライアントヒアリングシート）
    ↓ 上層エージェント: 要求分析・タスク分解
設計書（ブース設計図・仕様書）
    ↓ 中層エージェント: 見積・素材手配・工程表
実装指示（各工程の作業指示書）
    ↓ 下層エージェント: 各部品の発注・制作管理・納品書生成
```

各段階のドキュメントがトレーサビリティリンクを持ち、「クライアントのどの要望→設計→工程」が追跡可能。変更要求が来たときの影響範囲を自動特定できる。

#### シナリオ2: サイトUI改善の要求→実装パイプライン

```
仕様ドキュメント（要件定義・ワイヤーフレーム）
    ↓ 階層的タスク分解（コンポーネント単位・修正単位に分割）
設計ドキュメント（技術設計・API仕様）
    ↓ 各ドキュメントに紐付くタスクリスト
Codex / 下位エージェントによる実装
    ↓ 各タスク完了後、親エージェントがレグレッションチェック
```

オージャストのkaden-call-app等で実践されている「requirements.html→design.html→tasklist.md→Codex実装」のフローが、このパターンに合致する。各ファイルの要求トレーサビリティを強化することで、変更影響の自動分析や並行作業の衝突検出が可能になる。

#### シナリオ3: 社内自動化のマルチエージェント化

- **GAS管理エージェント**: Driveコマンドキューの各命令を独立エージェントとして実行
- **メール処理エージェント**: メール分類・返信案作成・送信を階層的分業
- **データ同期エージェント**: supabase←→sheetsの双方向同期をドキュメント定義で管理

上位エージェントが各々の進捗を監視し、異常があれば人間にエスカレーション。
