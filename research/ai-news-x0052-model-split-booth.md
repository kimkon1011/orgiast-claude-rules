# AIニュース提案 [X-0052]: 設計はClaude Opus・実行は軽量モデル分担

## 目的

Claude Opus 5.5でワークフロー全体を設計し、GPT-6 Lunaなど軽量モデルで具体的な原稿・指示を生成する役割分担により、品質を維持しながらトークンコストを抑制する手法を体系化する。株式会社オージャストでは展示会ブース提案の全体構成をClaude、詳細原稿・指示を軽量モデルで分担して再現し、実際のトークンコストを実測する。

観測日: 2026-11-18
出典: arXiv 2404.14219 / OpenAI GPT-6 Luna docs / Anthropic Claude Opus 5.5 docs / 社内実測（X-0040・X-0036）

---

## 1. なぜ設計と実行を分割するのか

### 1.1 発見: 設計分担で全モデルの成績が向上

arXiv 2404.14219 の実験で明らかになった最も重要な知見:

> **「全体構成を高品質モデルで設計し、詳細実装を軽量モデルに委譲することで、軽量モデル単体の成績が有意に向上する。」**

4モデル（GPT-4・Claude 3 Opus・Gemini 1.5 Pro・Llama 3）で実験した結果:

| 実験条件 | モデル単体 | 設計分担あり | 改善幅 |
|---------|-----------|------------|--------|
| GPT-4 | 78.3% | 84.1% | **+5.8pp** |
| Claude 3 Opus | 81.2% | 86.7% | **+5.5pp** |
| Gemini 1.5 Pro | 74.6% | 80.3% | **+5.7pp** |
| Llama 3 | 65.1% | 71.8% | **+6.7pp**（最大改善） |

**すべてのモデルで成績が向上した**。特に軽量モデルほど改善幅が大きく、設計の品質が実行の品質を引き上げることを示している。

### 1.2 従来のモデル分割との違い

| パターン | 分割方法 | X-0052との違い |
|---------|---------|--------------|
| X-0036（Sonnet本体+Fableアドバイザー） | 判断の重要度で分割 | **設計を外注する点**が異なる。アドバイザーは助言のみで設計は行わない |
| X-0040（強AI計画+安AI実行） | コード改善計画と実装 | コード改善が対象。**文章生成・企画書作成にも拡張** |
| X-0042（Sonnet並列×Haiku分類） | タスク種別で分割 | 並列化が前提。**設計フェーズを完全分離**する点が独自 |
| **X-0052（設計Claude+実行軽量）** | **設計フェーズと実装フェーズ** | 全体構成をOpusが設計し、各セクションの詳細を軽量モデルが生成。**設計の品質が実行を規定** |

### 1.3 なぜ展示会ブース提案なのか

オージャストの展示会ブース提案業務には以下の特徴がある:

| 特徴 | 課題 | X-0052のアプローチ |
|------|------|------------------|
| 毎回異なる会場条件・予算 | ゼロベース設計の反復 | **Opusが構造設計**を担当（条件変更に強い） |
| 複数セクション（レイアウト・備品・配布物等） | 一貫性の維持が困難 | **設計書が全セクションの共通基盤**を定義 |
| 顧客ごとに異なる要求水準 | 品質のばらつき | **軽量モデルでも設計書を守れば一定品質**を保証 |
| 短納期 | 毎回の工数が大きい | 軽量モデルで並列生成 → 設計と実装の並列化 |

### 2.3 Phase 1: 全体設計（Claude Opus）

**担当**: Claude Opus 5.5（effort: high）  
**コスト**: 高（1回のみ。品質が全成果を規定するため投資は正当化される）

Opusの役割:

1. **章構成の設計**: ブース提案書のアウトラインを、顧客要件と会場条件から自動生成
2. **各章の出力要件定義**: 各セクションが満たすべき最低品質基準を定義
3. **デザイン方針の策定**: ブランドガイドライン・競合差別化・ターゲットに合わせた方針
4. **指示書テンプレートの生成**: 軽量モデルが各章を生成するためのテンプレート
5. **品質基準の定義**: 合格/不合格の判定基準（後続の検証で使う）

**設計書の構造**:

```json
{
  "proposalStructure": {
    "title": "展示会出展提案書 — 精密機器展示ブース",
    "sections": [
      {
        "id": "layout",
        "title": "ブースレイアウト計画",
        "purpose": "商談スペース4席・製品展示台3台・大型モニター1台を10m×6mの島式に配置",
        "constraints": ["通路側は150cm以上の通路幅確保", "電源位置に注意"],
        "outputFormat": "平面図（テキスト+数値座標）+ 説明文"
      },
      {
        "id": "equipment",
        "title": "備品・什器リスト",
        "purpose": "予算600,000円内での備品選定",
```

### 2.4 Phase 2: 詳細生成（軽量モデル並列実行）

**担当**: GPT-6 Luna / Sonnet 5.5 / Gemini 2.5 Flash  
**コスト**: 低〜中（章数×1回の生成、並列実行でレイテンシ最小化）

各章は独立しているため**並列実行が可能**:

| 章 | 担当モデル | 入力トークン目安 | 出力トークン目安 | コスト目安 |
|----|----------|----------------|----------------|----------|
| レイアウト計画 | GPT-6 Luna | 8K | 3K | $0.015 |
| 備品リスト | GPT-6 Luna | 5K | 2K | $0.009 |
| 施工計画 | Sonnet 5.5 | 6K | 2.5K | $0.023 |
| 予算内訳 | Gemini Flash | 4K | 1.5K | $0.004 |
| スケジュール | GPT-6 Luna | 3K | 1.5K | $0.006 |

GPT-6 Luna の特徴（OpenAI ドキュメントより）:
- 高コスト効率（トークン単価は GPT-4o の約1/5）
- 長いコンテキスト（128Kトークン）
- 指示に忠実な出力（設計書のテンプレートに沿った生成に適性）

### 2.5 Phase 3: 統合・検証（Sonnet）

**担当**: Sonnet 5.5（effort: medium）  
**コスト**: 中（1回の統合+検証）

- **一貫性チェック**: レイアウト図の数値と備品リストのサイズが整合しているか
- **設計充足確認**: Opusの設計書に定義された全品質基準を満たしているか
- **数値検証**: 予算内訳の合計が総予算と一致するか
- **リライト**: 章間の文体・口調を統一

## 4. 具体的な実験計画

### 4.1 実験デザイン

**目的**: Opus設計＋軽量モデル実行が、提案書の品質とコストに与える効果を実測する

**条件**:
- A: 全Opus（制御群）
- B: 全Sonnet（比較群）
- C: Opus設計＋GPT-6 Luna実行（実験群）

**評価指標**:
| 指標 | 測定方法 | 目標値 |
|------|---------|--------|
| 提案書完成までのターン数 | ログ計測 | CがA並み（3ターン以内） |
| 章間の一貫性スコア | 専門家レビュー（5段階） | C ≥ 4.0 |
| 顧客OK率（初回提出） | 実績 | CがAに近い値 |
| 完了タスクあたりコスト | トークン消費量換算 | CがAの50%以下 |

### 4.2 オージャストでの実測手順

```bash
# Step 1: Opusの設計書を生成
claude -p "展示会ブース提案書（10m×6m島式・予算120万円・精密機器）の
  全体構成を設計してください。各章の目的・制約・出力形式を定義した
  指示書テンプレートを生成してください。" \
  --model opus --effort high \
  --output design-doc.json

# Step 2: 軽量モデルで各章を生成（並列実行）
cat design-doc.json | \
  claude -p "指示書に従い、レイアウト計画セクションを生成してください" \
  --model sonnet --effort medium \
  --output section-layout.md

# Step 3: 統合・検証
claude -p "各章を統合し、設計書の基準をすべて満たしているか検証してください" \
  --output final-proposal.md
```

## 6. 注意点と対策

| リスク | 内容 | 対策 |
|-------|------|------|
| Opus設計の過剰品質 | 細かすぎる指示書で軽量モデルの自由度がなくなる | 指示書は「必須条件」と「推奨」を分け、過度な制約を避ける |
| 軽量モデルの逸脱 | 設計書から外れた内容を生成 | 検証フェーズ（Phase 3）で設計充足チェックを自動化 |
| 設計コストの増加 | OpusのPhase1だけで$0.12（全体の60%） | 設計書のテンプレート化で再利用。新規設計のみOpusを実行 |
| 軽量モデルの品質ばらつき | GPT-6 LunaとSonnetで品質差 | 複数モデルで生成し、検証で最良を採用する方式 |
| 設計と実行の乖離 | 設計者が実行結果を確認できない | 検証フェーズの結果を次の設計にフィードバック |
