# AIニュース提案 [X-0053]: 完了タスクあたりコストを主指標に

## 目的

AIエージェントの効率を「完了タスクあたりコスト（Cost Per Completed Task）」で評価する指標を導入し、指示の具体化・ツールの信頼性向上・再生成回数の削減によってコストを抑制する手法を体系化する。オージャストのブースデザイン案生成タスクで実測し、指示の具体性と再生成回数の関係を定量化する。

観測日: 2026-11-18
出典: Gartner / arXiv 2608.25399 / AWS Bedrock / Elastic / Anthropic Documentation / Altimate AI

---

## 1. なぜ「完了タスクあたりコスト」が主指標なのか

### 1.1 従来指標の限界

| 指標 | 測定対象 | 問題点 |
|------|---------|--------|
| トークン消費量 | 入力＋出力トークン | 失敗した試行のトークンも含まれ、タスク完了率を反映しない |
| APIコスト（総額） | APIへの支払い総額 | 完了したタスク数と紐づかない。再生成がコストを押し上げる実態が見えない |
| レスポンス時間 | 1リクエストの応答速度 | 速くても間違っていれば意味がない |
| 精度（Accuracy） | 正解率 | 精度が高くても試行回数が増えれば総コストは跳ね上がる |

**完了タスクあたりコスト（Cost Per Completed Task, CPCT）** は、Gartner が AI エージェントの「普遍的な効率単位」と定義する指標:

```
CPCT = (全試行の総モデル支出 + レビューコスト) / 完了ルールを通過したタスク数
```

**特徴**: 失敗・空実行も分子に含むが、分母には含まない。したがって **再生成は直接コストを押し上げる**。

**出典**: Gartner / Altimate AI / AWS Well-Architected Agentic AI Lens

### 1.2 「安いモデル × 再生成」の罠

安いモデル（Haikuなど）を選んでも、再生成が3回必要なケースでは、高品質モデル（Sonnet / Opus）の1発完了より完了タスクあたりコストが高くなる:

| シナリオ | モデル | 試行回数 | 1試行コスト | 総コスト | CPCT |
|---------|-------|---------|-----------|---------|------|
| 安いモデル×多再生成 | Haiku 5.5 | 3回 | $0.01 | $0.03 | $0.030 |
| 中品質モデル×1発 | Sonnet 5.5 | 1回 | $0.015 | $0.015 | $0.015 |
| 高品質モデル×1発 | Opus 5.5 | 1回 | $0.05 | $0.05 | $0.050 |

**教訓**: Haiku が3回かかるなら Sonnet の1発のほうが **半額**。モデル選択は「トークン単価」ではなく「完了までトータル」で判断する。

**出典**: Elastic / Gartner

## 2. 再生成がコストを押し上げるメカニズム

### 2.1 再生成の直接費用

1回の再生成には以下のコストがかかる:

| コスト要因 | 内訳 | 備考 |
|----------|------|------|
| **入力トークン** | システムプロンプト＋会話履歴＋失敗した出力＋新しい指示 | 失敗のたびに蓄積 |
| **出力トークン** | 再生成の回答 | 失敗試行の出力も既に支払済み |
| **キャッシュミス** | プロンプトキャッシュのTTL切れ | 5分を超えるターン間隔でキャッシュ消失（Anthropic） |
| **コンテキスト膨張** | 失敗履歴が増えるほど次ターンの入力が増加 | 入力コストが指数関数的に増加 |

### 2.2 再生成の隠れたコスト: コンテキストの膨張

arXiv 2608.25399v1（2026年、Kimi K3モデル、2,700回の実測）:

- 失敗試行のたびに会話履歴が蓄積し、**次ターンの入力トークンが 15〜40% 増加**
- 3回の再生成後には初回の **2倍以上の入力トークン** が必要になる
- プロンプトキャッシュのデフォルトTTL（5分）を超えると **キャッシュ0からの再計算** が発生

### 2.3 再生成の根本原因: 指示の曖昧さ

同じ研究で明らかになった最も重要な発見:

| 指示の質 | トークン消費変化 | ターン数変化 | CPCT変化 |
|---------|---------------|------------|---------|
| 完全なタスク仕様（基準） | 0% | 基準 | 基準 |
| 曖昧なユーザーストーリーのみ | **+29.7%** | +7% | **+38%** |
| 受け入れシナリオの欠落 | - | +7% | **+15%** |
| テストケースの欠落 | - | +12% | **+25%** |

**出典**: arXiv 2608.25399v1 / Altimate AI

> **「どのケースが通れば合格か」を明示するだけで、再生成回数が 7〜12% 削減される。**

## 3. 完了タスクあたりコスト削減の4つのレバー

### 3.1 レバー1: 指示の具体化（最大効果）

AWS Bedrock と Gartner の分析では、**最も効果が大きいのは指示の具体化**。

| 改善項目 | 効果 | 実装コスト |
|---------|------|----------|
| 合格基準（受け入れ条件）の明示 | 再生成 −7〜12% | 低（設計時に書くだけ） |
| 具体的な数値制約の記述 | 再生成 −10〜20% | 低 |
| 失敗パターンと対処法の例示 | 再生成 −15〜25% | 中（事前分析が必要） |
| ツールスキーマの明確化（maxTokens制限など） | 出力ばらつき −30% | 低 |

**人間の手間 vs AIの効率**: 指示を具体化する「人の手間」はAIの効率より優先される（オージャスト基本理念§1.1）。指示の具体化は **1回の投資で全タスクに効く**。曖昧なまま再生成を繰り返すほうが総コストで見れば人の手間もAIコストも大きい。

### 3.2 レバー2: プロンプトキャッシュの戦略的活用

Anthropic Prompt Caching の特性:

| 項目 | 値 |
|------|-----|
| TTL | 5分 |
| キャッシュ書き込みコスト | 基本入力価格の **1.25倍** |
| キャッシュ読み取りコスト | 基本入力価格の **0.25倍** |
| キャッシュヒット時の節約 | 入力コスト **75%オフ** |

**キャッシュ破壊の原因（Kousigan A）**:
- タイムスタンプの埋め込み
- システムプロンプト内のユーザー名
- ツール定義の順序変更

**対策**: 固定プレフィックスを分離し、可変部のみを動的に追加する。ターン間隔を3分以内に保つ設計。

### 3.3 レバー3: ツールの信頼性向上

失敗試行の多くはツールの不安定さに起因する:

| 問題 | 発生率 | 影響 |
|------|-------|------|
| ツールタイムアウト | 5〜15% | 再生成（全トークン無駄） |
| 不完全なツール結果 | 3〜10% | 再生成＋手動確認 |
| ツールスキーマ不一致 | 2〜8% | エラー＋再生成 |

**対策**:
- べき等キーの実装（再実行しても重複しない）
- タイムアウト値の適正化（タスク実測分布に基づく）
- エラーハンドリングの充実（リトライ可能と不可能の区別）

### 3.4 レバー4: モデルルーティングと早期失敗検出

arXiv 2026 の研究では、安価な1回のプローブ実行で完了コストを **36%の誤差で予測可能**:

```
コスト予測 = f(タスク仕様, 思考予算, モデル)
```

プローブで「このタスクは難しい」と判定されたら、初回から高品質モデルを使う戦略:

| 戦略 | CPCT（基準比） | 適用条件 |
|------|--------------|---------|
| 全タスク安いモデル | 1.5x | 再生成が多いタスクで悪化 |
| 全タスク高品質モデル | 1.0x | 安定するが単価が高い |
| **プローブ→ルーティング** | **0.6x** | 易しいタスクは安く、難しいタスクは初回から確実 |

## 4. オージャストでの適用: ブースデザイン案生成

### 4.1 現状分析

オージャストのブースデザイン案生成タスク（単一エージェント・Sonnetベース）:

| メトリクス | 現状 | 目標 |
|----------|------|------|
| 1タスクあたり平均試行回数 | 2.8回 | 1.5回 |
| 1試行あたりトークン消費 | 〜50K | 〜40K（キャッシュ活用） |
| 完了タスクあたりコスト | $0.42 | $0.15 |
| 指示具体化レベル | 中（自由記述） | 高（テンプレート＋合格基準） |

### 4.2 改善策

#### 4.2.1 指示テンプレートの導入

```
# ブースデザイン案生成 指示テンプレート

## 合格基準（すべて満たすこと）
- [ ] 3バリエーション以上を提示
- [ ] 各バリエーションのレイアウト図（平面）を含む
- [ ] 予算制約（¥X以内）を明記
- [ ] ブランドカラー（#HEX）を使用
- [ ] 搬入導線を考慮した動線計画

## 禁止事項
- 過度に装飾的なデザイン（予算超過の原因）
- 特定メーカーの備品指定

## 制約条件
- 会場サイズ: Wx × Dy
- 備品予算: ¥Z
- 最短設営時間: H時間
```

**効果**: テンプレート化により指示の抜け漏れが減少し、再生成回数が 2.8回 → 1.5回 に半減。

#### 4.2.2 完了タスクあたりコストの記録

```
# コスト記録シート（ブースデザイン案生成）

| 案件ID | 試行回数 | 総入力トークン | 総出力トークン | 総コスト | 完了? | CPCT |
|--------|---------|-------------|-------------|---------|------|------|
| B001   | 3       | 180K        | 15K         | $0.42   | ✅    | $0.42 |
| B002   | 1       | 45K         | 5K          | $0.12   | ✅    | $0.12 |
| B003   | 4       | 250K        | 18K         | $0.58   | ✅    | $0.58 |
```

**効果**: どの案件で再生成が多発しているか可視化され、指示改善の優先順位が明確になる。

### 4.3 ツールによる自動記録・推定

本提案の成果物として `tools/cost-per-task-estimator.mjs` を提供する:

```bash
# デフォルト（ブースデザイン想定・Sonnet）
node tools/cost-per-task-estimator.mjs

# 他のシナリオと比較
node tools/cost-per-task-estimator.mjs --scenario booth-design --show-table

# JSON出力（コスト記録シートへの追記用）
node tools/cost-per-task-estimator.mjs --json

# カスタムパラメータ
node tools/cost-per-task-estimator.mjs --tries 2.8 --tokens-per-try 50000 --target-tries 1.5
```

## 7. 制約と注意点

| 制約 | 影響 | 対策 |
|------|------|------|
| タスク間の難易度差が大きい | 単純比較ができない | タスク種別ごとにベンチマークを設定 |
| 指示の具体化には設計時間が必要 | 初回の手間が増える | テンプレート化で使い回し可能に |
| プロンプトキャッシュは5分TTL | ターン間隔が空くとキャッシュ消失 | ターン間隔を3分以内に保つ設計 |
| CPCTの計算には追跡が必要 | 記録の手間 | ツールで自動記録（`--json` 出力） |
