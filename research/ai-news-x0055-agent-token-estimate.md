# AIニュース提案 [X-0055]: エージェントのトークン消費を4-15倍と見積もる

## 目的

AIエージェント（単一・チーム）のトークン消費量がチャット比で4〜15倍になることを実データで示し、オージャストのイベント関連マルチエージェント利用（デザイン生成・スケジュール・見積）でトークンを適切に見積もり、再読み込みを減らすプロンプト設計手法を提供する。

観測日: 2026-11-18
出典: Anthropic Engineering Blog / CloudZero / AI Agents Choice / Microsoft Research / Provn / unerr.dev / arXiv

---

## 1. エージェントのトークン消費: チャット比4〜15倍

### 1.1 Anthropic 公式発表（2025年6月）

Anthropic のエンジニアリングブログ「How we built our multi-agent research system」では以下の数値が公表されている:

| モード | チャット比トークン消費 | 備考 |
|--------|---------------------|------|
| 標準チャット | 1x（基準） | 1ターンの会話 |
| **単一エージェント** | **〜4x** | ツール呼び出し・履歴保持を含む |
| **マルチエージェントシステム** | **〜15x** | オーケストレーター＋サブエージェント構成 |

トークン消費量だけで **パフォーマンス分散の80%** を説明できる（BrowseComp評価）。マルチエージェントシステム（Opus 4 lead + Sonnet 4 subagents）は単一Opus 4エージェントより **90.2%高いパフォーマンス** を示したが、トークン消費は15倍に跳ね上がる。

**出典**: https://www.anthropic.com/research/multi-agent-research-system

### 1.2 実測データ（Sverklo / Reveneau / arXiv 2026）

| 研究 | 測定内容 | トークン消費 | チャット比換算 |
|------|---------|------------|-------------|
| Sverklo（47セッション・312タスク） | プライベートリポジトリでの平均 | 22,840入力トークン/タスク | 〜3x |
| Reveneau（JWT認証追加） | 小規模Node.jsタスク | 15,600トークン/タスク | 〜4x |
| Reveneau（PostgreSQLマイグレーション） | 中規模タスク（エラー訂正含む） | 40,700トークン/タスク | 〜10x |
| arXiv（SWE-bench Verified, 8モデル） | エージェントコーディングタスク | チャット比 **〜1,000x** | 〜1,000x |
| arXiv（同タスクの実行間分散） | 同一タスクの実行間変動 | **最大30倍の差** | — |

エージェントコーディングタスク（SWE-bench）は特殊で、ファイル読み取り・grep・テスト実行が繰り返されるためチャット比が極端に大きい。一般的な知識作業エージェントでは4〜15倍が妥当な範囲。

### 1.3 入力トークンが支配的

| 内訳 | 割合 | 備考 |
|------|------|------|
| grep結果 | **41%** | 最大のコスト要因 |
| ファイル読み取り（再読込含む） | **28%** | 既読ファイルの再読み込みが無駄 |
| 会話履歴 | **18%** | セッションが長いほど増加 |
| glob結果 | **7%** | — |
| システム＋ツール定義 | **6%** | 固定部 |

**出典**: Sverklo (2026) / unerr.dev

## 2. なぜ4-15倍になるのか

### 2.1 単一エージェント（〜4x）の内訳

| 要因 | チャット | エージェント | 倍率 |
|------|---------|------------|------|
| システムプロンプト | 数百トークン | 数千〜数万トークン（ツール定義含む） | 10〜50x |
| 1ターンの出力 | 数百トークン | 数十〜数百トークン（ツール呼び出し） | 0.5〜1x |
| ターン数 | 1〜3 | 5〜50+ | 5〜50x |
| 履歴の蓄積 | 低い | 非常に高い（全ツール結果を保持） | 10〜100x |
| **総トークン** | **低** | **チャットの〜4x** | **〜4x** |

### 2.2 マルチエージェント（〜15x）の追加要因

| 要因 | 説明 | 影響 |
|------|------|------|
| オーケストレーターのオーバーヘッド | サブエージェントへの指示・結果集約 | 2〜3x |
| サブエージェント間のコンテキスト共有 | 各エージェントが同じ履歴を保持 | 2〜3x |
| 並列エージェントの台数 | 3〜5台のサブエージェント | 3〜5x |
| 結果の検証と統合 | 各エージェントの出力を検証・マージ | 1.5〜2x |
| **マルチエージェント合計** | | **〜15x** |

### 2.3 再読み込みの無駄（〜30%）

Microsoft Research の TokenEconomizer は、エージェントのツール呼び出しの **約30%が既存の情報の再取得** であると報告している:

- 同じファイルの再読み取り
- 同じgrepクエリの再実行
- 同じツール結果の再解釈

**対策**: ツール呼び出し後のチェックポイント要約、セマンティックツール検索、スライス読み取り

**出典**: https://www.microsoft.com/en-us/research/blog/tokeneconomizer-learning-from-experience-to-make-ai-coding-agents-more-efficient/

## 3. オージャストでの適用: イベント関連マルチエージェント

### 3.1 典型的なユースケース

オージャストのイベント業務では以下の3エージェントを並行稼働することがある:

| エージェント | 役割 | トークン消費見積もり |
|------------|------|-------------------|
| **デザイン生成エージェント** | ブースデザインのバリエーション生成（画像生成指示・レイアウト案） | 〜4x（単一エージェント） |
| **スケジュールエージェント** | 出展スケジュール管理・搬入出計画・人員配置 | 〜3x（定型タスク） |
| **見積エージェント** | 見積書作成・単価照会・予算管理 | 〜4x（データ照会多） |
| **統合（マルチエージェント）** | 上記3つの統合 | **〜15x** |

### 3.2 トークン消費見積もり早見表

| シナリオ | 1タスクあたり推定トークン | チャット比 | コスト目安（Sonnet） |
|---------|----------------------|----------|-------------------|
| 単純な質問（チャット） | 〜1K | 1x | $0.001〜0.003 |
| 定型データ入力 | 〜5K | 〜2x | $0.005〜0.01 |
| 単一エージェント（デザイン生成） | 〜50K | 〜4x | $0.05〜0.15 |
| マルチエージェント（3台並列） | 〜500K | 〜15x | $0.50〜1.50 |
| フルイベント企画（10ターン×3エージェント） | 〜2M | 〜50x | $2.00〜6.00 |

### 3.3 プロンプト設計: 再読み込みを減らす

以下の設計でマルチエージェントのトークン消費を適切に見積もり、再読み込みを削減する:

#### 3.3.1 固定プレフィックスの階層化

```
[Layer 1: 不変システムプロンプト]        ← キャッシュ対象
  役割定義・ブランドガイドライン・品質基準

[Layer 2: 共有コンテキスト]              ← キャッシュ対象
  会場情報・過去事例・制約条件・料金テーブル

[Layer 3: エージェント固有の指示]         ← サブエージェント間で差別化
  デザイン生成用指示 / スケジュール用指示 / 見積用指示

[Layer 4: 現在のターンの可変情報]         ← 毎回変化
  クライアント名・予算・日付・ターゲット
```

**効果**: 初回以降のターンでLayer 1〜3がキャッシュヒットし、入力コストが75%オフ（Anthropic Prompt Caching）。

#### 3.3.2 チェックポイント要約

ツール呼び出しのたびにエージェントが状態を要約し、次のターンでは要約のみを引き継ぐ:

```
# 悪い例: ツール結果を丸ごと引き継ぐ
[前ターンのgrep結果: 200行]
[前ターンのファイル読み取り: 500行]

# 良い例: 要約だけ引き継ぐ
[要約: 見積書#123の金額は¥500,000。前回の指示で¥450,000に修正済み]
```

**効果**: 履歴トークンを **60〜80%削減**（Provn / unerr.dev）。

#### 3.3.3 セマンティックツール検索

全ツール定義を毎回送る代わりに、現在のタスクに必要なツールだけを動的に選択:

```
# 悪い例: 全23ツールの定義を毎ターン送信（〜15Kトークン）
# 良い例: 必要な3ツールだけ送信（〜2Kトークン）
```

**効果**: システムプロンプトのツール定義部分を **87%削減**。

#### 3.3.4 モデルルーティング

タスク難易度に応じてモデルを切り替え:

| タスク | モデル | コスト比（Opus基準） |
|-------|-------|-------------------|
| 定型データ入力・分類 | Haiku 5.5 | 0.03x |
| スケジュール調整・一覧化 | Sonnet 5.5 | 0.10x |
| デザイン生成・見積書作成 | Opus 5.5 / Fable 5.1 | 1.0x |
| 全体統合・判断 | Fable 5.1 | 1.5x |

## 4. 実装: トークン消費推定ツール

本提案の成果物として `tools/agent-token-estimator.mjs` を実装する:

### 4.1 機能

- シナリオベースのトークン消費推定（チャット / 単一エージェント / マルチエージェント）
- モデル別コスト計算（Haiku / Sonnet / Opus / Fable）
- キャッシュあり・なしの比較
- プロンプト設計の改善提案
- JSON / テーブル形式の出力

### 4.2 使い方

```bash
# デフォルト（単一エージェント・Sonnet）
node tools/agent-token-estimator.mjs

# マルチエージェント・Opus・JSON出力
node tools/agent-token-estimator.mjs --mode multi --model opus --json

# カスタムパラメータ
node tools/agent-token-estimator.mjs --turns 20 --input-tokens 50000 --agents 3
```

## 7. 制約と注意点

| 制約 | 影響 | 対策 |
|------|------|------|
| 同一タスクでも実行間で最大30倍の分散 | 見積もりが不正確になる可能性 | 複数回の実測で平均を取る |
| エージェントの種類によって倍率が異なる | コーディングエージェントは特に高消費 | タスク種別ごとの見積もり係数を用意 |
| プロンプトキャッシュの効果はTTL依存 | 5分を超えるとキャッシュ消失 | ターン間隔を3分以内に保つ設計 |
| モデルごとにトークン単価が異なる | 同じトークン数でもコストが数倍異なる | モデル別のコスト計算をツールに組み込む |
