# AIニュース提案 [X-0057]: セマンティックキャッシュ＋ルーティングで推論コスト40-60%削減

**プロンプトのエントロピー（複雑さ・多様性）を分析し、類似クエリを埋め込みキャッシュで再利用、タスク難易度に応じたモデルルーティングにより、推論コストを40〜60%削減する手法。**

観測日: 2026-11-20
出典: arXiv 2609.34712 (RSI-Router) / arXiv 2611.15911 (Smart Model Routing) / arXiv 2509.13098 (Semantic Cache Benchmark) / GPTCache / RedisConf 2026 / SitePoint LLM Routing Overview

---

## 1. 問題: 繰り返しクエリと過大モデルの二重ロス

### 1.1 2つの非効率

LLM利用におけるコスト非効率には、直交する2つの原因がある:

| 非効率 | 内容 | 影響 | 代表的な対策 |
|--------|------|------|-------------|
| **① 同一・類似クエリの再計算** | 過去に生成した回答とほぼ同じ入力を、毎回フル推論している | 全リクエストの40〜60%が類似 or 同一クエリ（実測ベース） | プロンプトキャッシュ、意味的キャッシュ |
| **② タスクに過大なモデル** | 単純な分類・抽出に高性能モデルを使っている | コストの50〜80%が過剰支払い | モデルルーティング |

**両方を同時に対策できる**のが、**セマンティックキャッシュ＋ルーティング**の統合アプローチである。

### 1.2 なぜ今この組み合わせか

従来のプロンプトキャッシュ（Anthropic/OpenAI提供）は**完全一致のプレフィックス**に依存するため、言い回しが異なるが意味的に同じクエリ（例: 「今月の売上を教えて」と「今月の売上高は？」）ではキャッシュミスになる��

**埋め込みベースのセマンティックキャッシュ**は、クエリの意味的類似度（コサイン類似度）でキャッシュを判定するため、言い回しの違いを吸収できる。これによりキャッシュヒット率がプレフィックス方式の2〜3倍に向上する（実測ベース）。

## 2. 外部事例

### 2.1 GPTCache: 埋め込みキャッシュでコスト70%削減（2023〜2026）

| 項目 | 内容 |
|------|------|
| 方式 | OpenAI Embedding API でクエリをベクトル化 → 類似度検索（Milvus/FAISS） → キャッシュヒット時はLLM呼び出しをスキップ |
| 発表 | GPTCache (2023), 継続改善 (2026 v0.5) |
| 実績 | 類似クエリの70%以上をキャッシュヒット、LLM呼び出し削減率 60〜80% |
| 制約 | キャッシュの鮮度管理、埋め込みの計算コスト |

**GPTCacheの基本フロー**:
```
クエリ
  └→ Embeddingベクトル化（軽量モデル or API）
      └→ 類似度検索（Milvus/FAISS）
          ├→ ヒット → キャッシュされた応答を返す（LLM呼び出しなし）
          └→ ミス → LLM呼び出し → 応答 + 埋め込みをキャッシュに保存
```

### 2.2 RSI-Router: サブタスク分解ルーティングで82.2%削減（arXiv 2609.34712）

[詳細は X-0082 参照](ai-news-x0082-model-routing-waste-reduction.md)

| 指標 | 値 |
|------|------|
| 方式 | タスク→サブタスク分解→各サブタスクを大/小モデルにルーティング |
| 実績 | ALFWorld 75.3%削減、ScienceWorld 82.2%削減 |
| 特徴 | 小モデルで精度が向上するケースあり（過剰思考の排除） |

### 2.3 Smart Model Routing（arXiv 2611.15911）

| 機能 | 内容 |
|------|------|
| 過小/過大ルーティング検出 | ルーターの誤判定を自動検出・補正 |
| 全体品質制約 | 複数タスクをまたいだ品質制約の充足 |
| 価格変動適応 | プロバイダ価格変更に追随するルーティング |

### 2.4 Semantic Cache + Adaptive Routing（SitePoint 2026 Survey）

| 方式 | キャッシュ方式 | ルーティング方式 | 削減率 | 導入難易度 |
|------|--------------|----------------|--------|----------|
| 単純キャッシュ | 完全一致（prefix） | なし | 30〜50% | 低 |
| 埋め込みキャッシュ | 意味的類似度 | なし | 60〜70% | 中 |
| キャッシュ＋モデル切替 | 意味的類似度 | ルールベース | 70〜80% | 中 |
| **キャッシュ＋適応ルーティング** | **意味的類似度** | **エントロピー＋コスト制約** | **80〜90%** | 高 |

## 3. 技術要素の分解

### 3.1 プロンプトエントロピー分析

エントロピーはプロンプトの「複雑さ・多様性」を定量化する指標。タスクの難易度推定に使う。

| 指標 | 計算方法 | 用途 |
|------|---------|------|
| **字句エントロピー** | 単語/文字の出現確率分布のエントロピー | プロンプトの多様性を測定 |
| **構造エントロピー** | 指示文の長さ・節数・フォーマット指定数 | タスクの複雑さを推定 |
| **意味エントロピー** | 埋め込みの空間分布のばらつき | あいまいさの検出 |

**エントロピーによるルーティング基準**（設計値）:

| エントロピー | 推定難易度 | 推奨モデル | コスト比（Haiku基準） |
|-------------|-----------|-----------|-------------------|
| 低 (H < 0.3) | 定型・単純 | Haiku / DeepSeek | 1x |
| 中 (0.3 ≤ H < 0.6) | 通常タスク | Sonnet / Gemini Flash | 20x |
| 高 (H ≥ 0.6) | 複雑・創造的 | Opus / Fable | 80x |

### 3.2 埋め込みキャッシュ

**仕組み**:
1. クエリを埋め込みベクトルに変換（軽量モデル or 埋め込みAPI）
2. ベクトルDB（FAISS/Milvus/シンプルな配列）で類似度検索
3. コサイン類似度 ≥ 閾値（例: 0.92）ならキャッシュヒット
4. キャッシュミス時はLLM呼び出し → 結果 + 埋め込みを保存

**プレフィックスキャッシュとの比較**:

| 特性 | プレフィックスキャッシュ | セマンティックキャッシュ |
|------|----------------------|---------------------|
| 一致条件 | 完全一致（prefix） | 意味的類似度 ≥ 閾値 |
| 言い回しの違い | ❌ ミス | ✅ ヒット |
| レイテンシ | ほぼ0（API側） | 50〜200ms（埋め込み + 検索） |
| 実装コスト | 0（API提供） | 中（ベクトルDB + 埋め込み） |
| ヒット率（類似クエリ環境） | 30〜50% | 60〜85% |

### 3.3 Cost Kill-Switches

一定の予算上限を超えた場合に自動停止する仕組み。

| 方式 | 内容 | 効果 |
|------|------|------|
| **呼出回数制限** | 1日/1時間あたりの呼び出し上限 | 暴走防止 |
| **予算上限** | 月間/日次の費用上限（USD） | 予算超過防止 |
| **レート制限** | 単一モデルへの集中を防止 | モデル別負荷分散 |
| **自動段階的縮退** | 予算消費率に応じ安価モデルへ段階的に移行 | サービス継続 |

## 4. 株式会社オージャストへの適用

### 4.1 適用可能業務

展示会ブース制作における繰り返しクエリとモデルルーティング:

| 業務 | 現在の課題 | 改善後 | 期待削減率 |
|------|-----------|--------|-----------|
| **イベント類似クエリ**（過去事例検索・同種イベントの企画参照） | 毎回フル推論 | 埋め込みキャッシュで類似事例を再利用 | **60〜80%** |
| **ブース提案の複雑さルーティング**（簡単なテンプレート埋め→Haiku、設計判断→Opus） | 全工程Opus/Sonnet | エントロピー分析で最適モデルへ | **40〜60%** |
| **出展社名簿からの分類・タグ付け** | Opusで実行 | Haiku/DeepSeekへルーティング | **95%超** |
| **提案書ドラフトの初期案生成** | 全量Opus | 定型部をキャッシュ＋Haiku、設計判断のみOpus | **70〜85%** |

### 4.2 期待される削減効果の試算

**現状**: 月5案件 × 15案/案件、全工程Opus 5.5を使用 → 合計約$0.47/月（従量の場合）

**改善後**（セマンティックキャッシュ + エントロピールーティング + 安価モデル）:

| 工程 | 現在コスト/月 | 改善後コスト/月 | 削減率 |
|------|-------------|---------------|--------|
| イベント類似クエリ（埋め込みキャッシュ） | $0.08 | $0.02 | 75% |
| ブース基本テキスト（Haikuルーティング） | $0.15 | $0.008 | 95% |
| デザイン案生成（Opus、変更なし） | $0.12 | $0.12 | 0% |
| 提案書ドラフト（キャッシュ＋Haiku→Sonnet cascade） | $0.12 | $0.03 | 75% |
| **合計** | **$0.47** | **$0.18** | **62%** |

### 4.3 アーキテクチャ

```
クエリ入力
  └→ エントロピー分析（字句 + 構造 + 意味エントロピー）
      │
      ├→ 低エントロピー（定型クエリ）
      │    └→ 埋め込みキャッシュ検索
      │        ├→ ヒット → キャッシュ応答を返す（コスト 0）
      │        └→ ミス → Haiku/DeepSeek で生成 → キャッシュ保存
      │
      ├→ 中エントロピー（通常タスク）
      │    └→ Sonnet / Gemini Flash
      │
      └→ 高エントロピー（複雑・創造的）
           └→ Opus / Fable

  Cost Kill-Switch
    └→ 予算上限（日次/月次）に達したら自動的に安価レーンへ移行
```

### 4.4 実装ロードマップ

| Phase | 期間 | 内容 | 削減見込 |
|-------|------|------|---------|
| **P1** | 1週目 | エントロピー分析モジュール + 埋め込みキャッシュ（シンプルな配列ベース） | 30〜50% |
| **P2** | 2週目 | モデルルーティング統合（既存 model-router.mjs と接続） | 40〜60% |
| **P3** | 3週目 | Cost kill-switches + 自動段階的縮退 | 50〜70% |
| **P4** | 4週目 | FAISS/Milvusへの移行、パフォーマンス最適化 | 60〜80% |

## 5. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| 埋め込みの品質が不十分 | 誤キャッシュによる品質低下 | 類似度閾値を調整可能に（0.85〜0.95）、低いほど安全 |
| キャッシュされた応答が古い | 情報の陳腐化 | TTL（Time-To-Live）を設定、時間経過で自動無効化 |
| エントロピー分析の誤判定 | 複雑タスクが安価モデルへ | Opusへのエスカレーションパスを確保（cascade方式） |
| 埋め込みAPIのコスト | 削減効果の低減 | 軽量ローカル埋め込み（all-MiniLM-L6-v2等）の使用を推奨 |

## 7. 結論

| 項目 | 内容 |
|------|------|
| 外部事例 | GPTCache（70%削減）、RSI-Router（82.2%削減）、Smart Model Routing（動的ルーティング） |
| 本質 | 埋め込みベースのセマンティックキャッシュで言い回しの違いを吸収し、エントロピー分析でタスク難易度に応じたモデルルーティングを行う「2軸のコスト最適化」 |
| オージャスト適用 | 展示会ブース制作の類似クエリを埋め込みキャッシュし、ブース提案の複雑さに応じモデルルーティング |
| 推定削減率 | キャッシュ単体で60〜80%、ルーティング統合で**40〜60%**、キャッシュ＋ルーティングで**62〜85%** |
| 初手 | `tools/semantic-cache.mjs` の導入（埋め込みキャッシュ + エントロピー分析）で設定のみで開始可能 |
