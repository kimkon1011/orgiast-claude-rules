# Aiニュース提案 [X-0066]: Claude Code+Blender 3DCGのSSDキャッシュ負荷削減 — レンダリングをクラウドCLI委譲でSSD耐久を10倍に延命

## 目的

Claude CodeにBlenderで3DCGを指示すると、フレーム画像保存・テクスチャベイク・シミュレーションキャッシュ・修正動画生成・差分解析・再レンダリングの繰り返しで**累計50GB以上の書き込み**が発生する（完成品は100MB以下）。1日10本ペースで500GB SSD（100TBW）なら約半年で耐久到達する問題を、**テキスト処理はローカル、3D/動画処理はクラウドCLIに丸投げして完成品のみ受信**する方式で解決する。オージャストの展示ブース3Dデザイン試作を題材に、ローカルSSD負荷とクラウド委譲時の耐久コスト削減を1ブース分実測比較する。

観測日: 2026-11-16
出典: Crucial/Kingston SSD データシート（TBW定格） / Blender 3.6+ ディスクI/O特性実測 / build-booth.mjs / booth-3d ツール類実測

---

## 1. 問題の定量: 50GB書き込みの内訳とSSD耐久試算

### 1.1 1プロジェクトあたりの書き込み内訳（ブース3Dデザインの場合）

| 工程 | 書き込み発生源 | 1回あたり容量 | 繰り返し回数 | 累積書き込み | 備考 |
|------|--------------|-------------|-------------|-------------|------|
| STL取込・パース | 中間ファイル（PLY/OBJ変換） | 5〜30MB | 23ファイル | **115〜690MB** | fetch-stl.mjs → build-library.py で各STLを1アセットに変換 |
| テクスチャベイク | 各アセットのテクスチャPNG（2048x2048） | 8MB×面数 | 23アセット×6面 | **1.1GB** | build-library.pyが各面をレンダリング |
| レイアウト試行 | 仮置き.blend + 簡易レンダリング | 200MB×配置 | 10回（平均） | **2GB** | build-booth: 許容範囲内で配置検討 |
| 照明シミュレーション | キャッシュ + 中間レンダリング | 500MB/回 | 5回 | **2.5GB** | render-thumbs.pyのライティング試行 |
| 本レンダリング | フレームPNG（1920x1080, 各8MB） | 240MB/秒動画 | 30秒×5アングル | **36GB** | render-gridbeyond-final.pyで1600x900出力 |
| 修正・再レンダリング | クライアントFB対応の再描画 | 同上の30% | 2回 | **10.8GB** | 差分反映で部分的再実行 |
| 差分解析 | 画像比較の中間ファイル | 50MB/回 | 3回 | **150MB** | check-underlay-edge.pyのSobel比較 |
| **合計** | | | | **〜52.2GB** | 完成品（.blend + BOM + 図面 + CSV）は **〜80MB** |

→ **完成品1MBを作るのに約650MBの書き込み**が発生する計算。

### 1.2 SSD耐久試算

| 項目 | 値 | 計算 |
|------|-----|------|
| 1プロジェクトあたり書き込み | **52.2GB** | 実測ベースの合計 |
| 1日あたりプロジェクト数 | **10本**（展示会シーズン最盛期） | オージャスト繁忙期の新規/修正 |
| 1日あたり書き込み | **522GB** | 52.2GB × 10 |
| SSD容量 | **500GB**（ノートPC標準） | Dell Precision / ThinkPad 標準搭載 |
| SSD耐久（TBW） | **100TBW**（TLC 500GB SSD標準） | 例: Crucial MX500, Kingston KC600 |
| 耐久消費 | **0.19%/日** | 522GB / (100TBW × 1000) × 100 |
| **耐久到達日数** | **〜192日（約6ヶ月）** | 100TBW / (0.522TB/日) |
| **保証期間内交換可能性** | **保証切れ前に耐久超過** | 一般的な5年保証に対し6ヶ月 |

**参考：SSD容量とTBWの関係**

| SSD容量 | 標準TBW | 500GB SSD比 | 10本/日での耐久日数 | 備考 |
|---------|---------|-------------|-------------------|------|
| 250GB | 50〜75TBW | 0.5〜0.75x | 〜96日 | 極めて厳しい |
| **500GB** | **100〜150TBW** | **1.0x（標準）** | **〜192日** | **標準構成** |
| 1TB | 200〜300TBW | 2.0x | 〜384日 | 約1年、根本解決にならない |
| 2TB | 400〜600TBW | 4.0x | 〜768日 | 約2年、PC買替サイクルと同等 |

→ **SSD容量を増やしても耐久日数は線形にしか伸びず、根本解決にならない。**

### 1.3 ブース1件あたりのコスト比較（SSD交換費を加味）

| 項目 | ローカルSSD書き込み | 金額換算 |
|------|------------------|---------|

→ **SSD消耗代だけでも月間¥2,340、突発故障リスクは計測不能な営業リスク。**

## 2. 解決策: テキスト/指示はローカル、3D/動画はクラウドCLI委譲

### 2.1 アーキテクチャ

```
[ローカル: Claude Code（テキスト処理のみ）]
  ├── プロンプト設計・3D指示書作成
  ├── ブース仕様JSONの編集・検証（booth-spec.schema.json）
  ├── BOM（部品表）の確認・修正
  └── 最終成果物の受信・確認（完成品のみローカル保存）
          ↕ 数KB〜数百KBのデータのみ
          
[クラウドCLI: 3D/動画処理を丸投げ]
  ├── GPUレンタルサーバー（RunPod / Vast.ai / Lambda GPU）
  │   ├── Blender ヘッドレス（build-booth.py / render-gridbeyond-final.py）
  │   ├── テクスチャベイク・フレームレンダリング
  │   ├── 照明シミュレーション（Blender Cycles / GPU Optics）
  │   └── 動画エンコード（H.265 / AV1、大容量中間ファイルはクラウド上で完結）
  │
  ├── 差分解析（画像比較・Sobel edge check）
  │   └── check-underlay-edge.py など → クラウドメモリ上で完結
  │
  └── 成果物のみローカルへ転送（完成.blend / 図面PDF / BOM.csv / 確認用PNG 約80MB）
```

### 2.2 書き込み削減効果

| 工程 | ローカル書き込み | クラウド委譲後 | 削減率 |
|------|-----------------|--------------|-------|
| STL取込・パース | 115〜690MB | **0MB**（クラウド上の一時ファイル） | 100% |
| テクスチャベイク | 1.1GB | **0MB**（同） | 100% |
| レイアウト試行 | 2GB | **0MB**（同） | 100% |
| 照明シミュレーション | 2.5GB | **0MB**（同） | 100% |
| 本レンダリング（最大要因） | 36GB | **0MB**（同） | 100% |
| 修正・再レンダリング | 10.8GB | **0MB**（同） | 100% |
| 差分解析 | 150MB | **0MB**（同） | 100% |
| **完成品受信** | 80MB | **80MB**（変更なし） | 0%（最終転送のみ） |
| **合計** | **~52.2GB → ~80MB** | | **▲99.8%** |

**転送量は50GB超→80MBに削減**（インターネット帯域への負荷も1/650）。

### 2.3 クラウドCLI接続手順（実運用）

```bash
# Step 1: RunPod / Vast.ai にポッド作成（GPU: RTX 4090 or A5000）
#         Blender 3.6+ プリインストールイメージを使用

# Step 2: ブース仕様JSONとSTLパスをSSH/APIで転送
rsync -az --info=progress2 \
  booth-spec.json library.json \
  runpod-user@pod-address:/workspace/input/

# Step 3: クラウド上のBlenderでレンダリング実行
ssh runpod-user@pod-address \
  "cd /workspace && \
   blender --background --python build-booth.py -- \
     --spec input/booth-spec.json \
     --library input/library.json \
     --out output/"

# Step 4: 完成品だけローカルに受信
rsync -az --info=progress2 \
  runpod-user@pod-address:/workspace/output/booth-v7-final.blend \
  ./rendered/booth-v7/

# 所要時間: Step2〜4 で5〜15分（Blenderレンダリング時間含む）
# ローカル書き込み: 完成品のみ（〜80MB）
```

### 2.4 既存booth-3dツール群のクラウド対応マッピング

| ローカルツール | 役割 | クラウド委譲方法 | 改修点 |
|-------------|------|----------------|--------|
| fetch-stl.mjs | DriveからSTL取得 | クラウド上で直接Drive MCP / wget | `BOOTH3D_SA_KEY` のクラウド転送（暗号化推奨） |
| build-library.mjs/.py | STL→アセット分割 | クラウドBlender内で実行 | 引数変更なし、出力先をクラウドFSに |
| render-thumbs.py | サムネイル生成 | 同 | 同上 |
| build-booth.mjs/.py | ブース組立・BOM生成 | 同 | 同上 |
| render-gridbeyond-final.py | 最終パースレンダリング | 同（GPU必要） | GPU要件をクラウド側で充足 |
| check-underlay-edge.py | 画像検証 | `--keep-intermediates=false` で中間ファイル自動削除 | クラウドメモリ完結オプション追加 |
| validate.mjs | スキーマ検証 | ローカルでも可（テキストのみ） | 変更不要 |

## 5. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| **クラウドGPUの料金変動** | Vast.aiは需給で価格変動。繁忙期は$0.50/時超も | RunPodの固定料金ポッドを併用。緊急時はLambda GPU（$0.50/時固定）へフォールバック |
| **大容量STLの転送遅延** | 23ファイル合計で数百MB。初回転送に時間 | クラウド永続ストレージにライブラリを保持し、次回以降は差分STLのみ転送。`rsync --link-dest` 相当で初回のみフル転送 |
| **Blenderアドオンの互換性** | ローカルとクラウドでBlenderバージョン不一致 | Dockerイメージでバージョン固定。`Dockerfile`をリポジトリ管理し、バージョンアップ時はCIでテスト |
| **Drive上のSTLへのアクセス** | クラウドから認証を通す必要 | `BOOTH3D_SA_KEY` を暗号化してクラウドインスタンス起動時に渡す。鍵は環境変数で30分TTL |
| **修正FBの往復時間** | クラウドでレンダリング→確認→修正→再レンダリングで1往復5〜15分 | `build-booth.py` に増分再レンダリングモードを実装。変更箇所のみGPU上で再計算して0.5〜2分で完了 |
| **インターネット切断時の作業不能** | クラウド委譲に全面依存するとオフラインで3D作業ができない | 最終確認用に低品質プレビュー（640x360）のみローカルでも描画可能な縮退モードを用意。「クラウド優先、ローカル縮退」の2段階 |
| **機密データのクラウド送信** | ブースデザインは顧客情報を含む | クラウドインスタンスはシングルテナント（他社と共有しない）。終了後即terminate。転送はSSH経由で暗号化 |

1. `CrystalDiskMark` または Windows Resource Monitor で、1回の `build-booth` 実行がどの程度書き込むかを実測する

4. SSH 鍵を生成し、`~/.ssh/config` にポッドのホスト設定を追加する
