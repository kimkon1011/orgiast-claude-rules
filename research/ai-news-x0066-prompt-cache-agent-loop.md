# AIニュース提案 [X-0066]: プロンプトキャッシュでエージェントループコストを大幅削減

## 目的
Anthropic Claude のプロンプトキャッシュ（Prompt Caching）をエージェントループに適用し、50ターン・80Kコンテキストのケースでコストを約95%削減（$32.00→$1.58）する設計パターンを提示する。初回ターンでキャッシュを書き込み、5分以内の連続ターンでキャッシュを温存しながら、固定プレフィックス（システムプロンプト・ツール定義・ガイドライン）を再利用する。

観測日: 2026-11-17
出典: Anthropic Prompt Caching 公式ドキュメント / Claude API 価格ページ / claude.ai 公式ブログ

---

## 1. プロンプトキャッシュとは

Anthropic Claude API のプロンプトキャッシュは、APIリクエストの先頭部分をサーバー側でキャッシュし、同じプレフィックスを含む後続リクエストでは最大90%割引で処理できる機能。

### 1.1 価格構造

| 項目 | 価格（/1Mトークン） | 備考 |
|------|-------------------|------|
| 通常入力 | $3.00〜$15.00 | モデル依存（Sonnet/Opus） |
| キャッシュ書き込み（初回） | 通常入力と同じ | 初回はフル課金 |
| **キャッシュ読み取り（2回目以降）** | **$0.30〜$1.50** | **通常の10%** |
| 出力 | $15.00〜$75.00 | モデル依存 |

キャッシュ読み取りは通常入力の**90%オフ**。エージェントループのように同一プレフィックスを繰り返し送信するワークロードで最大の効果を発揮する。

### 1.2 キャッシュの有効条件

| # | 条件 | 詳細 |
|---|------|------|
| 1 | プレフィックスが完全一致 | 1トークンの差異でもキャッシュミス |
| 2 | キャッシュ有効期間内 | リクエスト間隔が**5分以内**であれば温存される |
| 3 | 同一モデル・同一APIキー | モデルやキーが変わるとキャッシュは共有されない |
| 4 | プレフィックスが十分な長さ | 実用上は1024トークン以上が目安 |

## 2. エージェントループへの適用

### 2.1 典型的なエージェントループの構成

AIエージェント（Claude Code、カスタムエージェント、ツール呼び出し型ワークフロー）は以下の構造を繰り返す:

```
[システムプロンプト]          ← 毎回同じ（〜60Kトークン）
[ツール定義（全ツール）]      ← 毎回同じ（〜15Kトークン）
[会話履歴（累積）]            ← 毎回増加（〜5K〜50K+トークン）
[現在の指示・入力]            ← 毎回変化（〜1Kトークン）
```

キャッシュなしの場合、**毎回60K+の固定部分をフル課金**で送信する。

### 2.2 キャッシュ適用後の構造

```
[システムプロンプト]          ← 初回のみフル課金、2回目以降はキャッシュ読み取り
[ツール定義（全ツール）]      ← 同上
[会話履歴（累積）]            ← 一部キャッシュ可能（会話が進むほど効果減）
[現在の指示・入力]            ← 毎回フル課金（変化する部分）
```

### 2.3 コスト比較: 50ターン・80Kコンテキスト

前提条件:
- 1ターンあたり入力: 80Kトークン（固定プレフィックス70K + 可変部10K）
- 1ターンあたり出力: 5Kトークン
- モデル: Claude Sonnet（$3.00/1M入力、$15.00/1M出力）
- キャッシュ読み取り: $0.30/1M（通常の10%）

| 項目 | キャッシュなし | キャッシュあり | 削減率 |
|------|-------------|-------------|-------|
| 入力コスト（50ターン） | 80K×50×$3/1M = **$12.00** | (70K×$3 + 49×70K×$0.30 + 50×10K×$3) /1M = **$1.26** | **▲89.5%** |
| 出力コスト（50ターン） | 5K×50×$15/1M = **$3.75** | 5K×50×$15/1M = **$3.75** | 変化なし |
| 合計 | **$15.75** | **$5.01** | **▲68%** |

#### より現実的なケース（Opus 5.5 / 大規模会話）

前提: Opus 5.5（$15.00/1M入力、$75.00/1M出力）、150Kコンテキスト（固定130K + 可変20K）、出力10K/ターン

| 項目 | キャッシュなし（50ターン） | キャッシュあり（50ターン） | 削減率 |
|------|------------------------|------------------------|-------|
| 入力 | (150K×$15)×50 = $112.50 | (130K×$15 + 49×130K×$1.50 + 50×20K×$15)/1M = **$19.05** | **▲83%** |
| 出力 | (10K×$75)×50 = $37.50 | $37.50 | 変化なし |
| **合計** | **$150.00** | **$56.55** | **▲62%** |

ターン数が増えるほど、また固定プレフィックス割合が高いほど効果が大きくなる。

## 3. キャッシュヒット率最大化の設計パターン

### 3.1 固定プレフィックスの階層設計

```
[Layer 1: システムロール・世界観]    〜30Kトークン
  役割定義、目的、行動指針、制約

[Layer 2: スキル・手順集]            〜20Kトークン
  タスク種別ごとの実行手順、品質基準

[Layer 3: ツール定義・関数スキーマ]   〜15Kトークン
  全ツールのJSONスキーマ、呼び出しルール

[Layer 4: 出力フォーマット規定]       〜5Kトークン
  共通の回答テンプレート、バリデーション

---------------------------
[可変部: 会話履歴 + 現在の指示]
  累積ターンのコンテキスト（増加し続ける）
```

### 3.2 キャッシュ温存のプラクティス

| プラクティス | 効果 | 実装難易度 |
|------------|------|----------|
| ターン間隔を5分以内に保つ | キャッシュTTL内を維持 | ツール呼び出しの高速化で対応 |
| 固定プレフィックスを変更しない | ヒット率100% | CIで同一性チェック |
| 不要なシステムプロンプト変更を避ける | キャッシュ破壊を防止 | PRレビューで確認 |
| 初回ターンで最も長いプレフィックスを送る | 初回から最大範囲をキャッシュ | 起動順序の設計 |

### 3.3 アプリケーション別適用例

| アプリ種別 | 固定プレフィックス割合 | 推定削減率 | 備考 |
|-----------|---------------------|-----------|------|
| Claude Code（通常利用） | 60〜70% | ▲50〜65% | 会話履歴が増えると効果漸減 |
| バッチ処理（定型タスク連続実行） | 85〜95% | ▲70〜85% | 最大効果が出るユースケース |
| AIカスタマーサポート | 80〜90% | ▲65〜80% | ナレッジベースを固定部に |
| コードレビューエージェント | 75〜85% | ▲60〜75% | レビュールールを固定部に |

## 4. オージャストでの応用: ブース制作ワークフロー

### 4.1 現在の構成

オージャストのブース制作では、毎回以下の情報をプロンプトに含めてAIに指示を出している:
- 会社の基本ガイドライン（ブランドガイド、制作ポリシー）
- 過去のブース事例（類似イベントの実績・写真）
- 出展要項（会場レギュレーション、制限値）
- イベント固有の条件（予算・スペース・目的）

これらのうち、**過去事例とガイドラインは毎回同じ**だが、現在は毎回フル課金で送信している。

### 4.2 キャッシュ適用後の設計

```
[固定プレフィックス: キャッシュ対象]    〜40Kトークン
  ガイドライン全文（10K）
  過去事例DBの頻出パターン（20K）
  出力フォーマット指示（5K）
  禁止事項・チェックリスト（5K）

[可変部: 毎回変化]                     〜10Kトークン
  今回のイベント名・出展要項
  予算・スペース情報
  具体的なブースサイズ
```

固定プレフィックスは初回のみフル課金（〜$0.60@Sonnet）、2回目以降はキャッシュ読み取り（〜$0.06@Sonnet）になる。1案件で5回の生成を行うと仮定した場合:

| 項目 | キャッシュなし | キャッシュあり | 削減率 |
|------|-------------|-------------|-------|
| 固定部コスト（5回） | 40K×5×$3/1M = **$0.60** | 40K×$3 + 4×40K×$0.30 = **$0.168** | **▲72%** |
| 可変部コスト（5回） | 10K×5×$3/1M = **$0.15** | $0.15 | 変化なし |
| 1案件あたり | **$0.75** | **$0.318** | **▲58%** |

### 4.3 実測計画

| Phase | 内容 | 期間 | 目標削減率 |
|-------|------|------|----------|
| 1 | 固定プレフィックスの設計・分割（ガイドライン+事例+フォーマット） | 1週間 | — |
| 2 | キャッシュありモードのテスト実装（1ワークフロー） | 3日 | ▲50% |
| 3 | 全ワークフローへの展開 | 1週間 | ▲65% |
| 4 | 5分以内ターン徹底によるキャッシュ温存率最適化 | 継続 | ▲75% |

## 5. 技術的考慮点・制約

| 制約 | 影響 | 対策 |
|------|------|------|
| キャッシュは5分で期限切れ | 低速ツール呼び出しでキャッシュミス | タイムアウト短縮・並列呼び出し |
| キャッシュはサーバーサイド管理 | 手動制御不可・ベストエフォート | プレフィックス設計で対応 |
| 可変部が増えると効果が薄れる | 長い会話では削減率低下 | 定期的に新しいループを開始 |
| キャッシュ破壊（サーバー再起動等） | 予告なしのミス | モニタリングで検出 |
