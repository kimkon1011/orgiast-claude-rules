## 2. 本提案の核：プロンプト設計パターンでキャッシュを「確実にヒットさせる」

### 2.1 問題: 暗黙的キャッシュのヒット条件

Gemini 4 の暗黙的キャッシュ（implicit caching）には**明示的なAPI（ContextCache.create）が不要**な一方、**サーバー側が自動判定する**ため、ヒット条件を設計でコントロールする必要がある。

暗黙的キャッシュがヒットする条件（Gemini 4仕様から推定）:
1. **同一APIキー・同一モデル**で同一プレフィックスを送信
2. プレフィックスが**十分な長さ**（実測ベースで4096トークン以上が目安）
3. プレフィックスが**完全一致**（1トークンでも異なるとキャッシュミス）
4. キャッシュTTL内（Gemini 4は明示的キャッシュ非対応＝暗黙的キャッシュのTTLはプロバイダ管理）

### 2.2 解決: 4096+トークン固定プレフィックス設計

以下の**4層構造**で4096トークン以上の固定プレフィックスを構築する:

```
[Layer 1: 世界観定義] 〜800トークン
  - あなたは〜です（システムロール）
  - このプロジェクトの目的は〜
  - 対象業界・ブランド・価値観

[Layer 2: 禁止事項] 〜600トークン
  - 絶対にしてはいけないこと
  - 禁止フォーマット・禁止表現
  - 守るべきガイドライン

[Layer 3: スキル集] 〜2000トークン
  - 各タスク種別の実行手順
  - 使用可能なツール・関数定義
  - 依存関係・入出力フォーマット

[Layer 4: 出力フォーマット] 〜1000トークン
  - 共通のJSONスキーマ・テンプレート
  - 必須フィールド・バリデーションルール
  - 品質基準・チェックリスト

---------------------------
[可変部: 当日データ]
  - 本日の案件一覧
  - 分析対象データ
  - 具体的な指示内容
```

**合計: 固定プレフィックス 〜4400トークン（≧4096）＋可変部**

これを守って複数回連続投入すると、2回目以降は全入力トークンのうち約4400トークンが**キャッシュヒット（95%オフ）**になる。

## 3. 思考レベル切替＋タスク難易度マトリクス

### 3.1 タスク種別と思考レベル・コストの対応

X-0068 の思考レベル定義を踏まえ、タスク種別と思考レベル・実効コストを対応付ける:

| タスク種別 | 難易度 | 思考レベル | 出力/思考トークン倍率 | 実効出力コスト（/M換算） | キャッシュ有効性 |
|-----------|-------|-----------|-------------------|----------------------|----------------|
| **単純整形**（フォーマット変換・日付整形） | 低 | **low** | 0.5x | ~$3.75 | プレフィックス〜4400T（最大95% off） |
| **要約**（テキスト要約・分類・抽出） | 中 | **medium** | 1.0x（標準） | ~$7.50 | 同 |
| **コーディング**（定型コード生成・設定ファイル） | 高 | **high** | 2.0x | ~$15.00 | 同 |
| **設計**（企画構成・アーキテクチャ） | 最高 | **xhigh** | 3.0x | ~$22.50+ | 同 |

**コスト最適化ルール**:
- プレフィックスキャッシュは入力のみ（出力コストには無関係）
- 思考レベルは**出力トークン消費量**に影響（high/xhighは思考トークン増）
- キャッシュ割引 + 思考レベル最適化の**相乗効果**:
  - 単純整形（low + キャッシュ）: 入力95% off + 出力最小化 → 通常比 **▲90〜97%**
  - 要約（medium + キャッシュ）: 入力95% off + 標準出力 → 通常比 **▲60〜80%**
  - コーディング（high + キャッシュ）: 入力95% off + 思考トークン増 → **▲30〜50%**（思考トークンで相殺）

### 3.2 ルーティングテーブル（実務用）

## 7. リスクと対策

|--------|------|------|
| **暗黙的キャッシュのヒット条件が不透明**（Googleがアルゴリズムを開示していない） | キャッシュヒット率が想定を下回り、削減効果が▲95%に届かない | まず実測。ヒット率80%でも▲60%は達成可能（シミュレーション済み）。最悪ケースでも通常料金に戻るだけ（損しない） |
| **Grok Bot の収集品質が不十分**（supergrok定額枠でのレート制限や検索精度） | Hydrogen に渡す生データの品質が低く、出力が使えない | Grok Bot の収集後、Carbon で軽くフィルタリング（スポット¥0.02/回）。または収集をX API経由に切り替え |
| **Batch API の完了時間が読めない**（非同期処理） | 週末イベント中に結果が返ってこない | 優先度の高い投稿はリアルタイム（標準課金）、事後分析のみ Batch に振り分け |
| **Hydrogen の日本語品質が低い**（特に展示会専門用語） | SNS投稿・企画書の品質が実用に耐えない | 最終出力のみ Claude Sonnet で校正検証（▲$0.01/回）。下書きは Hydrogen、仕上げは Claude の分業 |
| **固定プレフィックスが4000トークンを超えない**（設計不足） | キャッシュヒットの確率が下がる | スキル集や出力フォーマットを追加で拡張。最低でも3000トークンは確保する |
| **同一APIキーのレート制限** | 連続投入で429エラー | リクエスト間隔を200ms以上空ける。複数キーに分散可能 |
