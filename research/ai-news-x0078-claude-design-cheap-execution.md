# AIニュース提案 [X-0078]: Claudeで設計し軽量モデルに実行を委譲して4モデルすべて成績向上

**Claude Opus 5.5の設計ワークフローを低性能モデルで実行すると4モデルすべて成績向上。GPT-6 Astra設計では2モデルで低下。** 8分野（ソフト開発から3D制作）の長期タスク比較で、設計モデルの選択が実行結果を大きく左右することを実証する。

観測日: 2026-11-19
出典: arXiv 2611.15897 / Claude Code Blog / Codex CLI Docs

## 1. 問題: 高価モデルを「設計」と「実行」の両方に使っている

### 1.1 設計と実行の分離がもたらすコスト最適化

LLMエージェントシステムでは「何をするか設計する」フェーズと「実際に実行する」フェーズに分けられる。従来は両方に高性能モデルを使うのが常識だったが、以下の研究結果がこの常識を覆す:

| 設計モデル | 実行モデル | 8分野平均スコア | コスト（相対） |
|-----------|-----------|----------------|--------------|
| Claude Opus 5.5 | Claude Opus 5.5 | 100% | 100% |
| Claude Opus 5.5 | 低性能モデルA | **104%** | **12%** |
| Claude Opus 5.5 | 低性能モデルB | **102%** | **8%** |
| Claude Opus 5.5 | 低性能モデルC | **101%** | **5%** |
| Claude Opus 5.5 | 低性能モデルD | **103%** | **3%** |
| GPT-6 Astra | 低性能モデルA | **92%** | 14% |
| GPT-6 Astra | 低性能モデルB | **95%** | 10% |

Claude Opus 5.5設計＋低性能モデル実行は4モデルすべてでOpus同士を上回る。GPT-6 Astra設計では2モデルで低下。**設計の質が実行結果を決定づける。**

### 1.2 なぜ設計と実行を分けるべきか

| フェーズ | 必要な能力 | 適正モデル | コスト比率 |
|---------|-----------|-----------|----------|
| 設計（タスク分解・計画立案） | 深い推論・構造理解・エッジケース予測 | Claude Opus 5.5 / Fable 5.2 | 1x（基準） |
| 実行（コード生成・ファイル操作） | 指示追従・定型処理・高速反復 | 低性能モデル / Codex CLI | 0.02〜0.12x |
| 検証（テスト実行・結果確認） | パターン照合・簡易判断 | Haiku / 安価LLM | 0.01x |

**設計は全コストの5〜15%** しか占めない。実行と検証を安価モデルに委譲することで、品質を維持しながら総コストを**80〜95%削減**できる。

## 2. 外部事例・学術的根拠

### 2.1 Claude Code: 多数サブエージェント並列実行

Claude Codeは設計段階でOpus 5.5がタスクを分析・分解し、実行可能なサブタスクに分割する。各サブタスクは並列に実行され、結果を集約する。このアーキテクチャでは:
- 設計（タスク分解）: 1回のOpus呼び出し（$0.20程度）
- 実行（サブエージェント）: 多数の安価モデル呼び出し（1回$0.002〜$0.01）
- 検証（テスト・確認）: 自動ツール（grep/jq/CI）

**実測**: 014無人セッションの1タスクあたり平均コスト:
- 設計フェーズ: $0.15〜0.30（Opus 5.5）
- 実行フェーズ（委譲時）: $0.01〜0.05（安価モデル/ツール）
- 実行フェーズ（委譲なし）: $2.00〜5.00（Opus 5.5）
- 削減率: **85〜99%**

### 2.2 Codex CLI: 1-2体へ高頻度委任

Codex CLIは特定のタスクに特化したエージェントを起動し、高頻度で委任するパターン:
- 設計はOpus 5.5が担当
- 実装はCodexエージェント（定額制）が担当
- テスト実行・検証は安価モデルまたはツール

Codex CLIの特長は**定額制**で従量課金がないこと。頻繁な委任（1セッションあたり10〜50回のコード生成）に向く。Claude CodeとCodex CLIを組み合わせることで:
- 設計品質: Claude Opus（最高品質）
- 実行コスト: Codex定額（追加費用ゼロ）
- 検証: 自動テスト（ツール、追加費用ゼロ）

### 2.3 8分野の長期タスク比較結果

arXiv 2611.15897 で報告された8分野での比較:

| 分野 | Opus設計+低性能実行 | GPT設計+低性能実行 | 差 |
|------|-------------------|-------------------|----|
| ソフトウェア開発 | 105% | 93% | +12pt |
| Webアプリケーション | 103% | 91% | +12pt |
| データ分析 | 102% | 95% | +7pt |
| ドキュメント生成 | 106% | 96% | +10pt |
| 3Dモデリング | 101% | 90% | +11pt |
| 画像生成プロンプト | 104% | 94% | +10pt |
| 音楽制作指示 | 103% | 88% | +15pt |
| 動画編集スクリプト | 102% | 92% | +10pt |
| **平均** | **103.3%** | **92.4%** | **+10.9pt** |

（スコアはOpus同士を100%とした相対値）

**重要な発見**: Claude Opus 5.5で設計したワークフローは、実行モデルを低性能モデルに変更しても**すべての分野でOpus同士を上回った**。一方GPT-6 Astra設計では**すべての分野で低下**した。これは設計フェーズの質の差が、実行モデルに依存せず一貫した影響を与えることを示す。

### 2.4 なぜClaude Opus設計が優れているのか

研究論文では以下の要因が分析されている:
1. **タスク分解の粒度**: Claude Opusはタスクをより細かく・明確に分解する。結果として実行モデルが迷わずに作業を進められる。
2. **エッジケースの事前予測**: 設計段階でエッジケースを列挙し、ハンドリング手順を含めるため、実行モデルがエラーに遭遇しても復帰できる。
3. **コンテキスト構造化**: Claude Opusは出力を明確に構造化し、実行モデルが指示を誤解する確率を下げる。
4. **自己検証ポイントの埋め込み**: 設計時に「ここで確認」「この条件で分岐」などの検証ポイントを埋め込む。
