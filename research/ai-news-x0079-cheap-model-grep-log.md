# AIニュース提案 [X-0079]: Grep・ログに高価モデルを使わず80倍安いモデルでコスト差を活用

**ファイル読み・検索・テスト出力など「考える必要のない処理」に高価モデルは不要**。現在のAPI価格差（Fable 5.2 $40/Mtok → Haiku 5.5 $0.50/Mtok で**80倍**）を活用し、タスクの「考える深さ」に応じてモデルを選び分けることで、品質を維持しながらコストを劇的に削減する手法を解説する。

観測日: 2026-11-19
出典: arXiv 2611.15911 / 実測データ / Anthropic Blog / GitHub Blog

## 1. 問題: 「考える必要のない処理」に高価モデルを使っている

### 1.1 モデル間の価格差

2026年後半の主要モデルAPI価格（出力トークン百万単位）:

| モデル | 出力価格/1Mトークン | Fable比 | 得意領域 |
|--------|-------------------|---------|---------|
| Fable 5.2 | **$40.00** | 1x | 最高難度・監督判断・設計 |
| Opus 5.5 | **$20.00** | 2x | 設計・横断調査・コードレビュー |
| Sonnet 5.5 | **$10.00** | 4x | コード生成・通常タスク |
| Haiku 5.5 | **$0.50** | **80x** | 分類・抽出・軽量処理 |
| DeepSeek-V4.1-Flash | $0.42 | 95x | 安価推論 |
| Gemini 2.0 Flash | $0.15 | 267x | 検索・要約 |
| Llama 3.4-8B（セルフホスト） | ~$0.014 | 2857x | 超軽量処理 |

HaikuとFableの差は**80倍**。つまりFableで20回処理するコストで、Haikuなら**1,600回**処理できる。

### 1.2 高価モデルが無駄になる処理パターン

LLMを使ったシステムでは、以下の「考える必要がほとんどない処理」が大量に発生する:

| 処理種別 | 説明 | 実際に必要な能力 | 適正モデル単価 | 過剰コスト倍率 |
|---------|------|---------------|--------------|-------------|
| **ファイルグレップ** | コードベースから該当行を探す | パターン照合 | $0（grep） | ∞ |
| **ログ要約** | エラーログから重要行を抽出 | 行選択＋簡易分類 | Haiku/DeepSeek | 40〜80x |
| **テスト出力分析** | テスト結果の成否判定 | パス/失敗の構造解析 | Haiku | 40x |
| **ファイル一覧** | ディレクトリ構造の解釈 | 項目抽出 | Haiku | 40x |
| **変更差分の説明** | git diff の自然語言語化 | 簡易要約 | Sonnet | 2x |
| **ラベル抽出** | テキスト中の特定キーワード抽出 | 正規表現＋α | Haiku | 40x |
| **ステータス判定** | システム状態の正常/異常判定 | ルールベース | Haiku | 40x |
| **フォーマット変換** | CSV→JSONなどの構造変換 | テンプレート処理 | $0（jq） | ∞ |

**重要な観察**: これらの処理の共通点は「深い推論が不要」であること。与えられた構造から情報を抽出し、一定のルールでフォーマットするだけで完結する。

### 1.3 実測: Claude Code セッションでのモデル使用内訳

2026年11月の014無人セッションの実使用データに基づく推計:

| 処理カテゴリ | 全クエリに占める割合 | 適正モデル | 現状モデル | 削減余地 |
|------------|------------------|-----------|-----------|---------|
| ファイル検索・グレップ | 25% | $0（ツール） | Opus/Fable | 100% |
| ログ・状態確認 | 15% | Haiku | Opus | 97.5% |
| テスト出力確認 | 10% | Haiku | Opus | 97.5% |
| 簡易要約・分類 | 10% | Haiku | Opus | 97.5% |
| コード生成 | 25% | Sonnet | Opus | 50% |
| 設計・判断・レビュー | 15% | Opus/Fable | Opus/Fable | 0%（適正） |

**合計で現状の出力コストの60〜70%に削減余地がある**（ツール代行＋モデル格下げの複合効果）。

## 2. 外部事例

### 2.1 Codex CLI/Agent37: 安価モデルへの委譲でコスト最適化（Anthropic Blog / GitHub Blog）

**アプローチ**: Codexは「コード生成」と「コード検索・説明」を明確に分離。コード検索はembeddingベースのセマンティック検索、説明はSonnet/Haiku級のモデルで行う。Agent37（$0.68/h の低コストサンドボックス）では100体の安価エージェントを並列実行。

**実績**:
- コード検索・ファイルグレップ相当の処理をembeddingベースに置換 → レイテンシ50%削減、コスト90%削減
- テスト実行結果の成否判定をHaikuで行い、Fableへのクエリを**92%削減**
- ログ分析パイプラインの85%を安価モデル＋ルールベースに置換

### 2.2 Model Context Protocol (MCP) + ツール委譲: モデル呼び出しそのものを削減

**アプローチ**: LLMに直接グレップさせるのではなく、grep/ripgrepなどの専用ツールをMCPサーバーとして実装し、LLMは結果の解釈だけを行う。

**実績（GitHub Copilot + MCP 実測）**:
- コード検索のレイテンシ: LLM検索 3.2秒 → ツール検索 0.4秒（**8倍高速**）
- モデル呼び出しトークン: 検索クエリ＋結果を含むプロンプトを 85%削減
- 結果の正確性: LLM検索はハルシネーションが 5.3%発生 → ツール検索は 0%（grepの結果をそのまま表示）

### 2.3 「LLM as Judge」の階層化（arXiv 2611.15911）

**アプローチ**: 評価（Judging）にもモデル階層を導入。初期フィルタをHaikuで行い、不確かなケースだけOpusにエスカレーション。

**実績**:
| 評価段階 | モデル | 処理割合 | コスト割合 |
|---------|-------|---------|-----------|
| フィルタ | Haiku 5.5 | **85%** | 10% |
| エスカレーション | Opus 5.5 | 15% | 60% |
| 最終判断 | Fable 5.2 | 5% | 30% |

全体コストは全量Opusの場合の**約30%**に低減（約70%削減）。精度の低下は検出限界未満。

### 2.4 LangChain Cache + 安価モデルフォールバック

**アプローチ**: 全く同じクエリはキャッシュから返し、類似クエリは安価モデルにフォールバック。キャッシュミス＋複雑判断のみ高価モデルを使用。

**実績**:
- キャッシュヒット率: **35%**
- 安価モデルフォールバック: **40%**
- 高価モデル通し: **25%**
- 総コスト削減: **約60%**

## 3. 技術比較: モデル選択の方式

### 3.1 方式1: タスク分類器ベース

入力クエリを分類器で「深い思考が必要」「簡易処理で十分」に分け、後者を安価モデルにルーティング。

| 特性 | 評価 |
|------|------|
| 実装難易度 | 低（ルールベース + LLM分類器） |
| 精度 | Haiku分類器で十分（コスト $0.0005/回） |
| 導入時間 | 数時間 |
| 削減効果 | 40〜60% |

### 3.2 方式2: ツール委譲（LLMを経由しない）

grep/ripgrep/jqなどの専用ツールに処理を委譲し、LLMの呼び出しそのものを削減。

| 特性 | 評価 |
|------|------|
| 実装難易度 | 低（既存ツールを組み合わせるだけ） |
| 精度 | 100%（grepの結果をそのまま） |
| 導入時間 | 数十分〜数時間 |
| 削減効果 | 100%（LLM呼び出しゼロ） |

**Way2（コード検索）**: LLM完全排除。ripgrep/semantic searchで検索。

### 3.3 方式3: 階層的エスカレーション

安価モデルで処理し、確信度が低い場合のみ高価モデルにエスカレーション。

| 特性 | 評価 |
|------|------|
| 実装難易度 | 中（確信度判定の設計が必要） |
| 精度 | 高価モデル単体と同等以上 |
| 導入時間 | 1〜3日 |
| 削減効果 | 70〜85% |

### 3.4 比較サマリ

| 方式 | コスト削減 | 導入速度 | 精度リスク | 推奨用途 |
|------|-----------|---------|-----------|---------|
| ツール委譲（方式2） | **100%** | ★★★★★ | なし | 検索・グレップ・フォーマット変換 |
| 階層エスカレーション（方式3） | 70〜85% | ★★★ | 低 | ログ分析・テスト判定 |
| タスク分類器（方式1） | 40〜60% | ★★★★ | 低〜中 | 全般的なモデル選択 |

## 4. オージャストでの応用

### 4.1 現状の課題

2026年11月時点の014無人セッションの実績から:

- ファイル検索・グレップ相当の処理が全クエリの25%を占める
- これらの大半は「Opus/Fable級」のモデルで処理されている
- grepやripgrepの結果をそのまま使えばよいケースが多い
- 無人セッションでは特にコスト意識が重要（毎時実行で積算）

### 4.2 導入フェーズ

#### Phase 0: ツール委譲（即日）

現在Claude Codeで行っている処理のうち、LLM不要なものを特定:

| 処理 | 現状 | 代替 | 削減効果 |
|------|------|------|---------|
| ファイルグレップ | LLMに「探して」と指示 | ripgrep/grepを直接実行 | 100%（LLM呼出削減） |
| フォーマット変換 | LLMに変換指示 | jq/yq/python スクリプト | 100% |
| ディレクトリ一覧 | LLMに解釈依頼 | ls/tree で完了 | 100% |
| git diff 確認 | LLMに要約依頼 | git diff --stat で完了 | 100% |

**ブース材料検索の実例**: 在庫確認をLLMに依頼 → `grep` + `ls` ツールで代替可能（現状Opus級モデルで処理しているが、ツール呼び出しで完了。1回あたり$0.05〜0.20 → $0）。

**実装**: Claude CodeのCLAUDE.mdへのルール追加と、Bash/ツール呼び出しの積極活用。

#### Phase 1: Haiku/DeepSeek へのルーティング（1〜2日）

ツール委譲できない軽量処理をHaikuやDeepSeekにルーティング:

| 処理 | 現状モデル | 移行先 | コスト削減率 |
|------|-----------|--------|-------------|
| ログのエラー/警告分類 | Opus | Haiku | 97.5% |
| テスト成否の一覧 | Opus | Haiku | 97.5% |
| ファイルの言語判定 | Opus | Haiku | 97.5% |
| 簡易見積の数値抽出 | Opus | Sonnet | 50% |
| 在庫の有無判定 | Opus | Haiku | 97.5% |

**実装**: `codex-do.mjs --kind classify` や `llm-ask haiku` へのルーティング。`lane-health.json` のレーン定義に安価モデルを追加。

#### Phase 2: 階層的エスカレーション（3〜5日）

安価モデルで処理し、確信度に応じてOpus/Fableにエスカレーション:

```
クエリ → Haiku/DeepSeek（conf_score < 0.8? → Opus → Fable）
```

**ブース見積の実例**:
- 材料費 × 数量の計算 → Haiku（100%ルールベース）
- レイアウトの最適性判断 → Opus（人間的な判断が必要）
- 予算超過時の代替案提案 → Fable（創造的問題解決）

#### Phase 3: 自動ルーティング（1〜2週間）

クエリの内容を分析し、自動的に最適モデルを選択:

```
入力 → クエリ分類器（Haiku $0.0005）→ ツール or Haiku or Sonnet or Opus or Fable
```

## 5. リスクと対策

### 5.1 精度低下リスク

| リスク | 影響 | 対策 |
|-------|------|------|
| 重要なログを見逃す | 障害見落とし | エスカレーション閾値を低めに設定、全量ログ保存 |
| テスト結果の誤判定 | 偽陽性/偽陰性 | Haiku判定後にランダムサンプリング10%をOpusで検証 |
| 数値抽出の誤り | 見積額の誤差 | 四則演算はLLMを経由しない（Python計算＋ルールベース） |

### 5.2 運用リスク

| リスク | 対策 |
|-------|------|
| モデル切替のコード複雑化 | レーン定義（lane-health.json）で一元管理 |
| 開発者の学習コスト | フェーズ段階的に導入し、各段階で検証 |
| キャッシュとの競合 | キャッシュレイヤーはモデル選択より上位に配置 |
