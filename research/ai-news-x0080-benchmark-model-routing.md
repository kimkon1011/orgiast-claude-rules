# AIニュース提案 [X-0080]: 再現ベンチマークでモデルルーティング最適化

**元の状態から異なるモデルやスキル定義でエージェントタスクセットを再実行し、評価・ベンチマーク結果に基づいて最適なモデルルーティング構成を決定する手法**を解説。RADW-Bench（ETA 2026）、RECE（NeurIPS 2026）、RSI-Router再現評価の実績を踏まえ、オージャストの過去ブース提案生成タスクを複数LLMで再実行してコストとスタイル適合を比較する適用計画を提示する。

観測日: 2026-11-19
出典: arXiv 2606.07972, 2611.03429, 2609.34712, 2611.15911 / Stanford DSP / RECE NeurIPS

---

## 1. 問題: ルーティング最適化にエビデンスが足りない

### 1.1 ルーティング導入の壁

X-0082で示したように、モデルルーティングは理論上50〜80%のコスト削減が可能だが、実際に導入するには以下の問いに答えなければならない:

| 問い | リスク | エビデンス不足の結果 |
|------|--------|---------------------|
| 「どのタスクを安価モデルに回してよいか」 | 安価モデルに回したタスクの品質低下 | 全タスクを高価モデルに維持＝削減ゼロ |
| 「どのモデルがどのタスクに向いているか」 | 誤ったルーティングによる品質劣化 | ルーティングの信頼喪失、導入断念 |
| 「ルーティングの効果はどの程度か」 | 導入判断の不確かさ | 経営判断の遅延、機会損失 |
| 「時間とともに最適構成はどう変わるか」 | 陳腐化したルーティング | 削減効果の漸減、気付いた頃には逆効果 |

**答えは「実際に計測する」の一言に尽きる。** しかし、手作業での評価は:
- 主観的で再現性がない
- タスク間の比較ができない
- コストと品質のトレードオフが定量化できない
- モデル更新のたびに再評価が必要だが、その労力が確保できない

### 1.2 再現ベンチマークの必要性

再現可能なベンチマーク（reproducible benchmark）は、**同一のタスクセットを異なる条件下で反復実行し、結果を定量比較する仕組み**。これにより:

- **客観的なエビデンス**: モデルAよりモデルBが〇〇%優れている、という主張にデータが伴う
- **継続的改善**: 新しいモデルが出たら同じタスクセットで再実行し、ルーティングを更新
- **コスト対品質の定量トレードオフ**: 削減率と品質スコアの関係をグラフ化
- **チーム全体の共通認識**: 「このタスクはSonnetで十分」といった知見が属人化しない

## 2. 外部事例: 再現ベンチマークによるモデルルーティング最適化

### 2.1 RADW-Bench: 最適モデル選択のベンチマーク（arXiv 2606.07972）

**概要**: 27の現実世界タスクを8つのLLMで実行し、コスト・精度・レイテンシを体系的に測定・評価するベンチマークフレームワーク。

**方法論**:
1. 固定タスクセット（コード生成・テキスト要約・分類・推論など27種）を定義
2. 各タスクを複数モデル（GPT、Claude、Gemini、Llamaなど8種）で実行
3. 各モデルの出力を自動評価（ルーブリック＋LLM-as-Judge）
4. コスト対精度のパレート最適フロンティアを計算

**主要な発見**:

| タスク種別 | 最適モデル | 高価モデル比のコスト | 精度差 |
|-----------|-----------|-------------------|--------|
| コード生成（簡単） | Sonnet 5.5 | Fable比 **75%減** | +2%（小モデルの方が高精度） |
| テキスト要約（短い） | Haiku 5.5 | Opus比 **97.5%減** | -3%（誤差範囲） |
| 分類（2クラス） | Haiku 5.5 | Opus比 **97.5%減** | ±0%（同等） |
| 複雑推論 | Fable 5.2 | —（適正） | 基準 |
| クリエイティブ生成（長文） | Opus 5.5 | Fable比 **50%減** | -1%（ほぼ同等） |

**再現性の担保方法**:
- 固定シードによる出力の決定論的制御
- 評価ルーブリックの事前公開
- テストデータセットの固定
- 自動評価パイプラインのコード公開

**オージャストへの示唆**: 同様の固定タスクセットを自社のブース提案業務から収集し、同一条件で複数LLMを実行することで、**タスクごとの最適モデルをエビデンスベースで決定**できる。初回のセットアップ工数は大きいが、一度作れば新しいモデルが出るたびに再実行してルーティングを更新できる。

### 2.2 RECE: エージェントコスト対効果ベンチマーク（NeurIPS 2026）

**概要**: Stanford DSPが提案する、エージェントタスクの**再現可能評価フレームワーク**。コスト・成功率・レイテンシの3軸を同時計測。

**方法論の特徴**:
1. **標準化されたタスクフォーマット**: 入力・期待出力・評価基準を統一
2. **コストトラッキング**: API呼び出しごとのトークン消費と価格を記録
3. **複数実行による分散の測定**: 同一タスクを複数回実行し、出力のばらつきを計測
4. **回帰テスト**: モデル更新後も同じ結果が出るか自動チェック

**RECEの4段階評価プロセス**:

```
Phase 1: ベースライン計測
  └→ 現在のモデル（例: Opus）で全タスクを実行し、品質・コスト・所要時間のベースラインを取得
    
Phase 2: 代替モデル実行
  └→ 候補モデル（Sonnet・Haiku・DeepSeek）で全タスクを再実行
    
Phase 3: 比較分析
  └→ モデル間のコスト差・品質差・ばらつきを定量比較
  └→ タスクごとに「この品質差ならこのコスト削減を許容できる」の閾値を決定
    
Phase 4: ルーティング決定
  └→ Phase 3のデータに基づき、タスク種別ごとの最適モデルを決定
  └→ ルーティングルールとしてコードに埋め込む
```

**再現性の鍵**: Phase 1〜4を通じて使用する**タスク定義・評価スクリプト・出力ログ**をバージョン管理し、誰でもいつでも再実行できる状態にする。

### 2.3 RSI-Router再現評価（arXiv 2609.34712）

RSI-Routerの画期的な点は、**サブタスク分解によるルーティング**だが、その有効性を実証するために彼ら自身が再現ベンチマークを実施している:

**RSI-Routerの評価方法論**:
1. タスクセット: ALFWorld（テキストゲーム）、ScienceWorld（科学教育）、WebShop（模擬EC）、SWE-bench（ソフトウェア工学）、Terminal-Bench（ターミナル操作）
2. 各タスクを複数のルーティング戦略で実行（大モデルのみ・小モデルのみ・RSI-Router・ランダムルーティング）
3. **6世代**の進化的最適化でルーティングポリシーを進化
4. 各世代のコスト・精度を比較し、最適ポリシーを選択

**結果**: タスクによっては大モデル単体よりRSI-Router（小モデル＋ルーティング）の方が高精度。

この評価方法論が示すのは:
- ルーティング最適化には**反復的な測定と調整のサイクル**が不可欠
- 1回の測定で最適構成は見つからない
- ルーティングポリシー自体も改善の対象

### 2.4 軽量評価フレームワーク（arXiv 2611.03429）

**概要**: LLMアプリケーションの評価を**5分で開始可能**にする軽量フレームワーク。

**特徴**:
1. 最小構成: 評価データセット（20〜50サンプル）＋評価スクリプト（50行）
2. 自動評価: LLM-as-Judge（判定役のLLMが出力を採点）
3. コスト自動記録: APIラッパーがトークン消費を記録
4. 視覚化: コスト対品質の散布図を自動生成

**評価データセットの最小サイズ**:

| 目的 | 推奨サンプル数 | 信頼区間 |
|------|--------------|---------|
| 大まかな比較（どちらが良いか） | 20〜30 | ±15% |
| 実用レベルの判断（最適モデル決定） | 50〜100 | ±8% |
| 統計的有意差検出 | 200+ | ±4% |

Reference: RADW-bench の実測値から推定

### 2.5 Stanford DSP Benchmark (NeurIPS 2026 Workshop)

エージェントタスクの評価における重要な知見:
- **決定論的実行（固定シード）と非決定論的実行（可変シード）の両方を計測**することで、モデルの本質的な能力とばらつきを分離
- **コストを固定した場合の品質比較**が実務上有用（予算制約下での最適モデル選択）

## 3. 再現ベンチマークの構築方式比較

| 方式 | 概要 | 再現性 | セットアップ工数 | 自動化の容易さ |
|------|------|--------|----------------|--------------|
| **固定タスクセット + 手動レビュー** | 事前定義した入力を複数モデルで実行し、人間が評価 | 低（評価者によるばらつき） | 低（数時間） | 低 |
| **固定タスクセット + LLM-as-Judge** | LLMに出力を自動採点させる | 中程度（判定LLMのバイアス） | 中（1〜2日） | 中 |
| **決定論的評価パイプライン** | 固定シード・固定プロンプト・固定評価基準で完全自動実行 | 高（コードで完全再現可能） | 中（2〜3日） | 高 |
| **継続的ベンチマークCI** | PRごとにタスクセットを自動実行し、品質回帰を検出 | 最高（常に最新状態で評価） | 高（1〜2週間） | 最高 |

### 3.1 推奨: 段階的導入

オージャストの規模とリソースを考慮した現実的な導入経路:

| Phase | 方式 | 期間 | 得られるもの |
|-------|------|------|------------|
| **P0: 即時** | 手動サンプリング（過去提案書から5〜10件選び、主観評価） | 即日 | 第一印象の把握 |
| **P1: Quick Benchmark** | 20タスク + LLM-as-Judge自動評価 + コスト記録 | 1〜3日 | タスクごとの最適モデル推定 |
| **P2: Reproducible Benchmark** | 50タスク + 固定シード + 自動評価パイプライン + バージョン管理 | 1〜2週間 | 再現可能なエビデンス |
| **P3: Continuous Benchmark CI** | P2 + CI連携 + モデル更新時自動再実行 + 回帰検出 | 2〜4週間 | 陳腐化しないルーティング |

## 4. オージャストでの適用: ブース提案再現ベンチマーク

### 4.1 適用可能タスクの収集

株式会社オージャストでは、過去のブース提案生成タスクを収集し、複数LLMで再実行することで最適ルーティング構成を決定する。

#### 想定タスクセット（収集対象）

| # | タスク種別 | 具体例 | 収集ソース | 難易度 |
|---|-----------|--------|-----------|--------|
| 1 | **ブース基本説明文生成** | 出展社名・小間番号・出展趣旨から3行の説明文 | 過去提案書・見積 | 低 |
| 2 | **イベント企画（定型）** | 過去の同種イベントの企画書をテンプレートに沿って生成 | 案件アーカイブ | 低〜中 |
| 3 | **ブースコンセプトライティング** | クライアントの業種・目的からコンセプト文を生成 | 提案書 | 中 |
| 4 | **見積明細の説明文生成** | 各費目の簡潔な説明書き | 見積書 | 低 |
| 5 | **クライアント提案書（簡易）** | 小規模ブースの簡易提案書（ページ構成含む） | 過去提案書 | 中 |
| 6 | **デザイン意図説明文** | デザイン案に付随する意図説明 | デザイン提案書 | 中〜高 |
| 7 | **競合出展社分析** | 同展示会の出展社リストからの競合分析 | リサーチ資料 | 高 |
| 8 | **展示会レポート要約** | 展示会参加レポートの要約 | 社内報告書 | 中 |

#### 収集方針

- **出典の明記**: 各タスクに元となった案件ID・提案書名を記録
- **個人情報の除去**: クライアント名・担当者名は匿名化またはダミーに置換
- **バリエーションの確保**: 同一タスク種別でも複数のバリエーション（小規模〜大規模、業種違い）を含める
- **評価基準の定義**: タスクごとに「何をもって良い出力とするか」の評価ルーブリックを事前定義

### 4.2 評価モデル候補

| モデル | 出力価格/1Mトークン | 用途想定 |
|--------|-------------------|---------|
| Opus 5.5 | $20 | 現行基準（ベースライン） |
| Sonnet 5.5 | $10 | コスト削減候補（第1候補） |
| Haiku 5.5 | $0.50 | 大幅削減候補（定型タスク向け） |
| DeepSeek-V4.1-Flash | $0.42 | 追加削減候補（コスト優先タスク） |

### 4.3 評価指標

| 指標 | 測定方法 | 重要度 |
|------|---------|--------|
| **コスト** | API出力トークン数 × モデル単価 | 必須 |
| **品質（自動評価）** | LLM-as-Judge（Opusを評価者として使用、基準出力との一致度） | 必須 |
| **品質（人手評価）** | チームメンバーによるブラインド比較（月1回サンプリング） | 推奨 |
| **スタイル適合度** | オージャストのトーン・表現ルールへの準拠度（評価ルーブリックで測定） | 推奨 |
| **レイテンシ** | 出力完了までの実時間 | 任意 |
| **出力のばらつき** | 同一入力に対する出力の分散（5回実行の標準偏差） | 任意 |

### 4.4 評価プロセス（RECE 4段階に準拠）

#### Phase 1: ベースライン計測（現状把握）

**目的**: 現在のOpusでの出力品質・コストのベースラインを取得する。

```
タスク数: 最低20（推奨50）
実行回数: 各タスク1回（ばらつきはPhase 2で計測）
評価者: Opus自身（LLM-as-Judge）
出力: タスクごとの品質スコア（1-5）× コスト（トークン数 × 価格）
```

期待アウトプット:
- 全タスクの品質スコア分布（平均・分散）
- 全タスクのコスト分布
- コスト対品質のベースライン散布図

#### Phase 2: 候補モデル実行（比較測定）

**目的**: 全候補モデルで同一タスクセットを実行し、Phase 1 のベースラインと比較する。

```
モデル: Sonnet・Haiku・DeepSeek（OpusはPhase 1の結果を流用）
実行回数: 各モデル×各タスク3回（出力のばらつき計測のため）
評価者: Opus（一貫した評価のため、全モデルの出力を同じ評価者で判定）
評価基準: 
  - 絶対品質（1-5スケール）
  - ベースライン比（Opusの出力と比べてどうか）
  - スタイル適合度（オージャストのトーンに合っているか）
```

期待アウトプット:
- モデル×タスクのコスト対品質比較マトリックス
- タスク種別ごとの「最適モデル」ランキング
- 「この品質差ならこのコスト削減を許容できる」の閾値決定のためのデータ

#### Phase 3: ルーティング決定（最適構成の特定）

**目的**: Phase 2のデータから、タスク種別ごとの最適ルーティング構成を決定する。

**判断基準**:

```
条件1: 品質低下が許容範囲（例: 0.5ポイント未満） → 最も安いモデルを割り当て
条件2: 品質低下があるが許容範囲内（例: 0.5-1.0ポイント） → コスト削減率と相談
条件3: 品質低下が許容範囲外 → Opusを維持（またはFableにアップグレード）
```

期待アウトプット:
- タスク種別ごとのルーティング定義（コード化可能なルール）
- 期待削減率の計算（Phase 1の総コスト対比）
- リスク評価（許容できない品質低下が発生する可能性とその影響）

#### Phase 4: 実運用＋監視（継続的最適化）

**目的**: 決定したルーティングを実運用に適用し、効果を継続監視する。

| 項目 | 頻度 | 方法 |
|------|------|------|
| 品質モニタリング | 週1回サンプリング | LLM-as-Judge自動評価 |
| コスト削減効果測定 | 日次 | APIログ集計 |
| モデル更新検知 | 随時 | Anthropic/各社リリース通知 |
| ルーティング再調整 | モデル更新時 | Phase 1〜3を簡略版で再実行 |
| 四半期フル棚卸し | 3ヶ月ごと | Phase 1〜3をフル再実行 |

### 4.5 期待効果

| 指標 | 現状 | 目標 |
|------|------|------|
| ブース基本説明文生成コスト | Opus: $20/1Mトークン | Haiku: $0.50（**97.5%減**） |
| 定型イベント企画コスト | Opus: $20/1Mトークン | Sonnet: $10（**50%減**） |
| 全ブース関連タスク平均コスト | Opus: $20/1Mトークン | 混在: ~$3（**85%減**） |
| ルーティング導入判断のエビデンス | なし（勘） | 定量データあり |

## 5. ルーティング最適化の自動化: ベンチマーク駆動型ルーティング

### 5.1 概念: ベンチマーク→ルーティングのフィードバックループ

```
タスクセット（固定） → 複数モデルで実行 → 評価・比較
                                              ↓
                                  最適ルーティング決定
                                              ↓
                                  ルール/コードに反映
                                              ↓
                                  実運用で監視 -----→ モデル更新検知 → 再実行
```

### 5.2 コード化可能なルーティングルールの例

```python
# benchmark-result-driven-routing.py（コンセプトコード）
# X-0080 再現ベンチマーク結果に基づくモデルルーティング

TASK_ROUTING = {
    "booth_basic_description": {
        "model": "haiku-5.5",        # コスト97.5%減・品質±3%
        "cost_per_1m_tokens": 0.50,
        "fallback": "sonnet-5.5",    # Haiku失敗時のフォールバック
        "benchmark_evidence": "X-0080-benchmark-20261119",  # 証拠となるベンチマークID
        "quality_score": 4.2,        # ベンチマーク測定値（5段階）
        "cost_reduction": "97.5%",   # Opus比
    },
    "event_plan_standard": {
        "model": "sonnet-5.5",       # コスト50%減・品質±5%
        "cost_per_1m_tokens": 10,
        "fallback": "opus-5.5",
        "benchmark_evidence": "X-0080-benchmark-20261119",
        "quality_score": 4.0,
        "cost_reduction": "50%",
    },
    "client_proposal_complex": {
        "model": "opus-5.5",         # 品質維持優先
        "cost_per_1m_tokens": 20,
        "fallback": "fable-5.2",
        "benchmark_evidence": "X-0080-benchmark-20261119",

    },
    # ... 全タスク種別に展開
}
```

### 5.3 継続的改善のトリガー

| トリガー | アクション | 緊急度 |
|---------|-----------|--------|
| 新モデルリリース | 全タスクセットで再実行（Phase 1〜3） | 高（リリース後1週間以内） |
| 品質モニタリングで低下検出 | 該当タスク種別の詳細分析 | 中 |
| 新タスク種別の追加 | 新タスクのベースライン計測＋ルーティング決定 | 中 |
| 四半期フルレビュー | 全タスクセット再実行＋ルーティング見直し | 低（定期） |

## 6. リスクと対策

| リスク | 影響 | 確率 | 対策 |
|--------|------|------|------|
| ベンチマークタスクセットが実務を代表しない | ルーティングが実務で最適にならない | 中 | 定期的なタスクセット見直し、実務タスクの都度追加 |
| LLM-as-Judgeの判定バイアス | 評価結果が偏る | 高 | 月1回の人間レビューと相関確認、複数判定LLMの利用 |
| 評価コストが削減効果を上回る | ベンチマーク自体のコストがペイしない | 低 | 評価はHaiku（$0.50/M）で実行、週次サンプリング |
| モデルの出力ばらつきが大きく評価が安定しない | 信頼できる比較ができない | 中 | 複数回実行（3回以上）で平均値と分散を同時評価 |
| 新しいタスクが増え続けてメンテナンス不能 | ベンチマークが陳腐化 | 中 | 全タスクではなく「代表タスク」20種を維持し、新タスクは都度追加 |

### 6.1 LLM-as-Judgeのバイアス対策

LLM-as-Judge（LLM自身に出力を評価させる手法）には以下のバイアスが知られている:

| バイアス | 影響 | 対策 |
|---------|------|------|
| 自己優先バイアス（自身の出力を高評価） | Opus評価者がHaikuを不当に低評価 | 匿名化した出力をランダム順で評価、複数の判定モデルでクロスチェック |
| 位置バイアス（先に提示された出力を高評価） | 比較評価の順序による影響 | 出力の提示順をランダム化、複数順序で評価して平均 |
| 長さバイアス（長い出力を高評価） | 冗長な出力が不当に高評価 | トークン数による正規化、簡潔さを評価基準に追加 |
| フォーマットバイアス（箇条書き等を高評価） | 特定の書式が不当に有利 | 評価前に書式を統一、内容ベースの評価に集中 |
