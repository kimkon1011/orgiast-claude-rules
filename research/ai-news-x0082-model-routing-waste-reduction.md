# AIニュース提案 [X-0082]: 過大モデルへの無駄をルーティングで削減

**プロンプトをタスクに適したサイズのモデルに振り分けるルーティング**により、品質を維持しながら推論コストを50〜80%以上削減する手法を解説。RSI-Router（82.2%削減）、LangChain Switchyard（74%削減）、RouteLLM、LiteLLMなどの実績を踏まえ、オージャストのブース制作業務への適用を提案する。

観測日: 2026-11-19
出典: arXiv 2609.34712, 2611.15911, 2611.13209 / LangChain Blog / LiteLLM Docs / SitePoint

---

## 1. 問題: 過大モデルへの支払い過多

### 1.1 現状のモデル価格差

2026年後半の主要モデルAPI価格（出力トークン百万単位）:

| モデル | 出力価格/1Mトークン | 用途適性 |
|--------|-------------------|---------|
| Fable 5.2 | $40 | 最高難度・監督判断 |
| Opus 5.5 | $20 | 設計・横断調査・レビュー |
| Sonnet 5.5 | $10 | コード生成・通常タスク |
| Haiku 5.5 | $0.50 | 分類・抽出・軽量処理 |
| DeepSeek-V4.1-Flash | $0.42 | 安価推論 |
| Qwen3.5-9B (セルフホスト) | ~$0.014 | 超軽量処理 |

HaikuはFableの**80分の1**、Opusの**40分の1**の価格。にもかかわらず、多くのシステムは全クエリを同一（多くの場合は高性能）モデルに送っている。

### 1.2 無駄の構造

展示会ブース制作業務で考えた場合:

| タスク | 必要な能力 | 適切なモデル | 過大モデルを使った場合の超過コスト |
|--------|-----------|-------------|-------------------------------|
| ブース基本テキスト生成 | 低 | Haiku/DeepSeek | Opus比 40倍 |
| 出展者名簿からの分類 | 低 | Haiku | Opus比 40倍 |
| 在庫確認 | 低 | Haiku | Opus比 40倍 |
| 簡易見積 | 中 | Sonnet | Fable比 4倍 |
| デザインコンセプト設計 | 高 | Opus/Fable | —（適正） |
| クライアント重要判断 | 最高 | Fable | —（適正） |

日常業務の70〜80%は低〜中難度であり、高性能モデルを使い続けると**本来不要なコストの40〜80%**を支払っている計算になる。

## 2. 外部事例

### 2.1 RSI-Router: サブタスクレベルで82.2%削減（arXiv 2609.34712）

**アプローチ**: タスクを**サブタスク**に分解し、各サブタスクを大モデル（DeepSeek-V4.1-Flash）か小モデル（Qwen3.5-9B）にルーティング。進化的アルゴリズムで6世代にわたりルーティングポリシーを最適化。

**実績（大モデル単体との比較）**:

| ベンチマーク | コスト削減 | 精度変化 |
|------------|----------|---------|
| ALFWorld | **75.3%** | 90.62% → **98.44%**（+8.6%） |
| ScienceWorld | **82.2%** | 維持または向上 |
| WebShop | **74.7%** | 維持または向上 |
| SWE-bench Verified | **8.1%** | 維持 |
| Terminal-Bench 2.0 | **18.0%** | 維持または向上 |

**重要な発見**: **小モデルを使うとむしろ精度が向上する**タスクが存在する。単純なタスクでは大モデルの「過剰思考」がノイズになる場合がある。

### 2.2 LangChain Switchyard: 74%コスト削減

**構成**: Opus 4.8（高性能）× Nemotron 3.5 Lightning（低コスト）の2段階ルーティング。

**テスト**: 145のマルチステップエージェントタスクで計測。

| 指標 | 値 |
|------|------|
| 安価モデルが処理した呼び出し | 全呼び出しの**93%** |
| 安価モデルへの支出割合 | 総支出の**10.4%** |
| 総コスト削減 | **74%** |
| 精度低下 | わずか**6ポイント** |

**Minimum Offload Formula**（最低委譲条件）:

```
委譲条件: judge_cost / (expensive_cost - cheap_cost) < 1
```

つまり、判定（judge）のコストが、大モデルと小モデルの価格差より小さければ委譲する価値がある。実際にはこの式が満たされるケースがほとんどであり、ルーティングはほぼ常に経済的に成立する。

### 2.3 RouteLLM (lmsys, オープンソース)

シンプルな2モデル間ルーティング。コスト閾値を設定し、安価モデルの回答信頼度が閾値を下回った場合のみ高価モデルにエスカレーションする方式。コスト対品質のトレードオフを1パラメータで制御可能。

### 2.4 LiteLLM + OCI Gateway: 19%コスト削減（トレーニング時間0.18秒）

Oracle Cloudの実装例では、**220KBの軽量分類器**（トレーニング時間0.18秒）をゲートウェイに組み込み、リクエストごとに最適なルートを予測。3層の判断:
1. ルールベース（事実・固定ルール）
2. 学習済みルーター（埋め込みベースの軽量分類）
3. ビジネスルール（アカウント別ポリシー）

**結果**: 推論モデル常時使用比で **84%の良好回答率を維持しつつ19%のコスト削減**。

### 2.5 Smart Model Routing（arXiv 2611.15911）

実運用での課題に対応:
- **過小/過大ルーティング**の検出と補正
- **全体品質制約**（aggregate quality constraint）の充足
- **マルチプロバイダ価格変動**への適応
- **Tier障害時のフォールバック**（高価モデルへ一時切替）

## 3. ルーティングの方式比較

| 方式 | 概要 | メリット | デメリット | 代表事例 |
|------|------|---------|-----------|---------|
| **Pre-generation分類** | 呼び出し前にクエリを分類し適切なモデルへ | 最小レイテンシ・無駄な推論ゼロ | 分類器の精度が品質を決める | LiteLLM classifier |
| **Cascade（段階的）** | 安価モデル→品質判定→高価モデルへ昇格 | 必要な時だけ高価モデルを使う | 判定のレイテンシ・品質判定自体のコスト | RouteLLM, FrugalGPT |
| **サブタスク分解** | タスクを分解し各サブタスクを個別ルーティング | 粒度が細かく最大効率 | 分解オーバーヘッド | RSI-Router |
| **本文ベースルーティング** | リクエスト本文の内容に基づき振り分け | 柔軟性が高い | 実装が複雑 | Praxis (X-0084参照) |
| **エージェントルーティング** | スキル定義に基づきエージェントを選択 | 機能単位の最適化 | 設計コスト | LangChain Switchyard |

### 3.1 実装難易度別の推奨方式

| 段階 | 方式 | 見込み削減 | 実装工数 | 適用例（オージャスト） |
|------|------|-----------|---------|---------------------|
| 初級 | 手動切り替え（コード分岐） | 20〜40% | 数時間 | 定型テキスト生成→Haiku |
| 中級 | Cascade（RouteLLM等） | 40〜60% | 数日 | 見積→Sonnet、設計→Opus |
| 上級 | サブタスクルーター（RSI等） | 60〜80% | 数週 | ブース提案全体の自動分解・振り分け |

## 4. オージャストへの適用

### 4.1 適用可能業務と期待効果

| 業務 | 現在の想定モデル | ルーティング後 | 期待削減率 |
|------|----------------|--------------|-----------|
| **ブース基本テキスト生成**（出展社名・小間番号・基本情報） | Opus/Sonnet | Haiku/DeepSeek | **80〜95%** |
| **イベント企画（定型）**（過去事例の再利用） | Opus | Sonnet/DeepSeek | **50〜75%** |
| **デザイン案生成** | Opus/Fable | Opus（変更なし） | 0%（適正） |
| **在庫確認・簡易問合せ** | Opus | Haiku | **95%超** |
| **クライアント提案書（複雑）** | Fable | Fable（変更なし） | 0%（適正） |
| **分類・タグ付け**（出展企業リスト、ブース種別） | Opus | Haiku/DeepSeek | **95%超** |
| **料金計算** | Sonnet/Opus | Sonnet→Haiku cascade | **80〜90%** |

### 4.2 想定アーキテクチャ

```
クライアント（Slackコマンド / Web / GAS）
  └→ ルーター（軽量分類器 < 1MB）
      ├→ 「定型テキスト生成」→ Haiku 5.5 / DeepSeek ($0.50/M)
      │    出力: ブース基本説明文・出展社プロフィール
      ├→ 「通常生成」→ Sonnet 5.5 ($10/M)
      │    出力: 見積案・スケジュール案・簡易提案
      └→ 「複雑生成」→ Opus 5.5 / Fable 5.2 ($20-40/M)
           出力: デザインコンセプト・競合分析・高難度提案
      
      品質モニター
        └→ ルーターの判定精度を継続測定・フィードバック
```

ルーター自体はHaikuか軽量埋め込み分類器で稼働させ、ルーターの運用コストを全体の1%未満に抑える。

### 4.3 フェーズ別導入計画

| Phase | 内容 | 期間 | 削減見込み |
|-------|------|------|-----------|
| **P1** | 手動ルーティング: コード上でタスク種別によりモデルを切り替え（if/switch文） | 1週間 | 30〜50% |
| **P2** | Cascade導入: まずHaiki→NGならSonnet→NGならOpus | 2週間 | 50〜70% |
| **P3** | 分類器ルーター: LiteLLM等でリクエスト内容に基づく自動振り分け | 1ヶ月 | 60〜80% |
| **P4** | サブタスク分解ルーター: 複合タスクを分解し各サブタスクを最適ルートへ | 2ヶ月 | 70〜85% |

## 5. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| ルーターの誤分類による品質低下 | クライアント提案の質低下 | Cascade方式で高価モデルへのエスカレーションパスを確保 |
| 分類器のメンテナンスコスト | 運用負荷 | 教師データを実績から自動収集（正解ラベルは後続の人間レビューから取得） |
| 安価モデルの出力ばらつき | ブランドイメージ低下 | 社外向け最終確認は人間（またはOpus）のレビューを必須に |
| ルーター自体のコスト | 削減効果の低減 | ルーターはHaikuかルールベースで運用コスト0.1%未満に |

## 6. キャッシュとの併用効果

本提案（X-0082）とプロンプトキャッシュ（X-0084）は独立した削減軸であり、**組み合わせるとさらに効果が増幅**する。

| 施策 | 単独効果 | 併用時の相乗効果 |
|------|---------|----------------|
| モデルルーティングのみ | 50〜80%削減 | — |
| プロンプトキャッシュのみ | 40〜70%削減 | — |
| 両方の併用 | — | **70〜95%削減**（総支出） |

具体的な併用イメージ:
- キャッシュヒットした定型クエリ: コストほぼゼロ（キャッシュから応答）
- キャッシュミスした定型タスク: Haiku/DeepSeekへルーティング
- 複雑タスク: Opus/Fableへ直接（キャッシュヒット率も高い）
