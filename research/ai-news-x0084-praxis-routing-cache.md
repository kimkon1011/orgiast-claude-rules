# AIニュース提案 [X-0084]: プロンプトキャッシュとルーティングでトークン支出40-70%削減

**Praxis（Red Hat EnMaaS）** でルーティンcoding/evaluationトラフィックを外部APIから自己ホストオープンウェイトへルーティング。30日で1兆トークン超処理、利用が商業フロンティア70/30からオープン30/70へシフト。プロンプトキャッシュとルーティングによりトークン支出を従来フロンティア比40-70%削減。

観測日: 2026-11-19
出典: Red Hat 公式ブログ (2026-11-09) / Praxis GitHub / CNCF Sandbox Proposal #506

---

## 1. 外部事例: Red Hat EnMaaS（Praxis + llm-d）

### 1.1 全体像

Red Hat（IBM子会社）は2026年11月、内部MaaS（Model-as-a-Service）パイロット「**EnMaaS**（Engineering Model-as-a-Service）」の成果を公開した。2つのCNCFサンドボックスプロジェクトを組み合わせた構成:

| コンポーネント | 役割 | 言語 | CNCF寄贈時期 |
|--------------|------|------|------------|
| **Praxis** | AIゲートウェイ（ルーティング・ポリシー・プロトコル変換） | Rust | 2026年9月 |
| **llm-d** | K8sネイティブ分散推論フレームワーク（vLLM + KVキャッシュ階層化） | Go/Rust | 2026年3月 |
| vLLM | ランタイムスケジューリング・複数ポッド連携・KVキャッシュ管理 | Python | — |

### 1.2 実績

**30日間での計測結果**:

| 指標 | 値 |
|------|------|
| 処理トークン数 | **1兆トークン超**（単一30日ウィンドウ） |
| 利用技術者数 | 数千人のRed Hatエンジニア |
| 利用比率変化 | フロンティア70% / オープン30% → **フロンティア30% / オープン70%** |
| トークン支出削減 | **従来フロンティア比 40〜70%** |
| ライセンス | Apache 2.0（OSS） |

### 1.3 アーキテクチャ

```
開発者
  └→ Praxis（AIゲートウェイ・Rust）
      ├→ ルーティング（リクエスト本文ベース / モデル名 / MCPツール名）
      ├→ API翻訳（OpenAI ↔ Anthropic ↔ Chat Completions）
      ├→ ガードレール（コンテンツフィルタ・レート制限）
      ├→ トークン会計（ユーザー別・チーム別・モデル別）
      └→ ext_proc ↔ llm-d（分散推論）
           ├→ vLLM + プリフィル/デコード分離
           ├→ KVキャッシュ階層化（GPU/CPU/NVMe）
           └→ Endpoint Picker（EPP）: 推論対応ルーティング
```

Praxisはリクエスト本文の内容に基づくルーティング（body-based routing）を実行するため、従来のURLベースルーティング（Envoyなど）より精密な振り分けが可能。プロトコル変換機能により、OpenAI API形式のクライアントからAnthropic APIへ、またはその逆の透過的な通信を実現する。

### 1.4 なぜこの事例が重要なのか

**従来のコスト削減アプローチ**は「より安いAPIを使う」だったが、EnMaaSは**自己ホスト型オープンモデルへの全面移行**を実現した点が新しい。

| アプローチ | 削減率 | 前提条件 | 制約 |
|-----------|-------|---------|------|
| APIルーティング（従来） | 20〜50% | プロバイダ間の価格差 | API依存継続 |
| プロンプトキャッシュ（従来） | 60〜90% | 同一プレフィックスの連続利用 | 5分TTL制約 |
| **自己ホスト移行（本件）** | **40〜70%** | GPUインフラ（初期投資） | メンテナンス負荷 |
| キャッシュ＋自己ホスト（統合） | **70〜95%** | 両方の実装 | 複合運用コスト |

## 2. 技術要素の分解

### 2.1 Praxis: AIゲートウェイ

Praxisは従来のAPIゲートウェイ（Kong, Envoy）と異なり、**AIペイロード向け**にゼロから設計されている。

| 機能 | 詳細 |
|------|------|
| Body-based routing | プロンプト内容に基づくルーティング（例: コード生成はCodex用OpenAI Responsesへ、質問はClaude用Anthropic Messagesへ） |
| Provider translation | OpenAI ↔ Anthropic ↔ Chat Completions 間のプロトコル変換 |
| Content guardrails | 機密情報検出・プロンプトインジェクション対策 |
| Token accounting | ユーザー/チーム/モデル別のトークン消費・コスト集計 |
| Rate limiting / quota | モデル別レート制限・割当管理 |
| MCP / A2A routing | Model Context Protocol / Agent-to-Agent ルーティング |
| Observability | Prometheus / OpenTelemetry 対応 |

### 2.2 llm-d: K8sネイティブ推論

llm-dはKubernetes上で大規模LLM推論を効率的に運用するためのフレームワーク。

| 機能 | 効果 |
|------|------|
| Prefill/Decode disaggregation | プリフィル（計算集中）とデコード（メモリ集中）を別Podで実行 → リソース最適化 |
| KV-cache tiering | GPU → CPU → NVMe の階層化キャッシュ → コスト最適 |
| Endpoint Picker (EPP) | 推論対応ルーティング（Praxisのext_proc経由で連携） |
| MoE expert parallelism | Mixture-of-Expertsモデルの専門家並列化 |
| GPU idle reduction | リクエスト集中によるGPU稼働率向上 |

### 2.3 プロンプトキャッシュ（補完的技術）

Praxis単体ではプロバイダ側のプロンプトキャッシュ機構は持たないが、**llm-dのKV-cache階層化**が推論時のキャッシュ効果を提供する。APIレイヤーでは上下流のキャッシュが別途有効:

| レイヤー | キャッシュ方式 | 効果 | 実装者 |
|---------|--------------|------|-------|
| APIゲートウェイ | Praxisでのルーティングキャッシュ | ルーティング判断の高速化 | Red Hat |
| 推論基盤 | llm-d KV-cache tiering | 推論時のキャッシュヒット率向上 | Red Hat |
| APIプロバイダ | Anthropic prompt caching / OpenAI auto-cache | 入力トークンコスト削減 | Anthropic/OpenAI |
| アプリケーション | 固定プレフィックス設計＋安価ルーティング | 総コスト最適化 | ユーザー |

## 3. 株式会社オージャストへの適用

### 3.1 現状の課題

オージャストの展示会ブース制作フローでは、以下の繰り返しプロンプトが発生:

| 工程 | 現在の課題 | トークン消費（推定） |
|------|-----------|-------------------|
| 仕様テンプレート生成 | 案件ごとに同じテンプレート構造をプロンプト | 〜4Kt/案 |
| イベント進行台本 | 毎回同じイベントフォーマットを記載 | 〜3Kt/台本 |
| ブースコピー案（10〜20案） | 会社概要・過去事例を毎回含める | 〜2Kt/案 |
| 提案書ドラフト | 簡単なテンプレート埋めを高コストモデルで実行 | 〜5Kt/ドラフト |
| 施工計画書の初期案 | 安全基準＋共通手順を毎回含める | 〜4Kt/計画書 |

**現状の推計月間コスト**:
- ブース提案: 月5案件 × 15案 × $0.0045/案 = $0.34
- 台本作成: 月10件 × $0.008 = $0.08
- 提案書ドラフト: 月8件 × $0.006 = $0.05
- **合計: 約$0.47/月**（従量利用の場合）

### 3.2 改善案: 2層の削減戦略

#### 層1: 固定プレフィックスキャッシュ（Anthropic/OpenAI API）

```
改善前（GPT-6 Luna、全工程同じモデル）:
  会社概要(500t) + 過去事例(800t) + 制約条件(300t) + 企画指示(200t) = 1,800t/案
  20案: $0.090 → 企画判断 + 最終選定: $0.020 → 合計: $0.110/案件

改善後（キャッシュ＋安価ルーティング）:
  Step1: 固定プレフィックス書込（初回のみ）: 1,600t = $0.0015
  Step2: 企画方針判断（Sonnet）: 読取 $0.0010 + 出力
  Step3: コピー生成 × 20案（Haiku）: $0.0063
  Step4: 品質フィルタ × 20案（Haiku）: $0.0003
  Step5: 最終選定（Sonnet）: $0.0030
  → 合計: $0.019/案件（**−83%**）
```

#### 層2: 自己ホストオープンモデルへのルーティング（Praxis型）

**中長期的には**、以下のルーティング構成でコスト削減:

```
[ルーティング構成]
  定型作業（仕様テンプレート埋め・キャプション生成）
    └→ 自己ホストオープンウェイト（DeepSeek-Coder, Qwen, GLM）
       ├→ ハードウェア: ラップトップ1台（24GB VRAM）+ API経由
       ├→ ルーター: Gemini Flash（Praxis相当のbody-based routing）
       └→ 検証ゲート: Sonnet / Haiku（品質確認のみ）

  設計判断（3Dブース構想・企画方針）
    └→ Frontier（Sonnet / Opus / GPT-6 Luna）
       ├→ 品質が命
       └→ 案件あたり1〜2回のみ

  バッチ生成（過去事例を基にした大量バリエーション）
    └→ Batch API（24時間待機可、50%オフ）
```

### 3.3 過去案件でのコスト試算

2026年11月時点で、オージャストが過去3ヶ月に対応した展示会案件（推定15案件）を対象に試算:

| シナリオ | 案件あたり | 3ヶ月合計 | 削減率 |
|---------|-----------|----------|-------|
| **現状**（すべてGPT-6 Luna） | $0.110 | $1.65 | — |
| **改善案A**（キャッシュ＋Haikuルーティング） | $0.019 | $0.29 | **−83%** |
| **改善案B**（キャッシュ＋自己ホストオープンルーティング） | $0.008 | $0.12 | **−93%** |
| **改善案C**（キャッシュ＋オープンルーティング＋Batch API） | $0.005 | $0.08 | **−95%** |

### 3.4 実装ロードマップ

| Phase | 期間 | 内容 | 投資額 | 削減見込 |
|-------|------|------|--------|---------|
| P1: キャッシュ基盤 | 1週目 | 固定プレフィックスの分離、キャッシュ制御の実装 | 0（設定変更のみ） | −60% |
| P2: ルーティング | 2〜3週目 | タスク別モデル振り分け（Haiku/DeepSeek/Gemini Flash） | 0（APIキー追加のみ） | −75% |
| P3: 自己ホスト検討 | 4週目〜 | GPU環境の評価、Praxis相当のゲートウェイ構成の検討 | 要検討 | −40〜70%（自己ホスト分） |
| P4: 統合・モニタリング | 5〜8週目 | 全工程の最適化、実績数値の収集 | 0（既存ツール） | −80〜95% |

### 3.5 実測計画

過去案件でのトークン支出を以下の手順で計測:

| # | 手順 | 手法 |
|---|------|------|
| 1 | 現状のAPI使用量の棚卸し | ChatGPT/Grok/Claude APIの利用履歴から集計 |
| 2 | 代表的なプロンプトのトークン数測定 | tiktoken/claude-tokenizerで実測 |
| 3 | キャッシュ適用時のコストシミュレーション | 同一プレフィックスの再利用回数から計算 |
| 4 | ルーティング品質検証 | サンプル10件を各モデルで生成し一致率を比較 |
| 5 | 月間コストベースライン確立 | 3ヶ月平均API費用をベースライン化 |

## 4. 制約と注意点

| 項目 | 内容 | 対策 |
|------|------|------|
| GPU初期投資 | 自己ホストにはGPU搭載マシンが必要 | PraxisはAPIゲートウェイのみでも利用可能（APIルーティング範囲で効果） |
| オープンモデルの品質 | コード生成では遜色ないが、日本語クリエイティブは要注意 | 検証ゲート（Sonnet/Haiku）で品質確認 |
| Praxis導入工数 | Rustベース、K8s前提のため初期設定に習熟が必要 | まずはAPIルーティング（Gemini Flash分類器）から段階的に導入 |
| キャッシュTTL | 5分以内の連続利用が必要 | バッチ生成は連続実行で設計 |
| オープンモデルの日本語対応 | DeepSeek/Qwenは良だが、GLMは英語バイアスあり | 事前評価（サンプル10件の品質チェック）を必須 |

## 5. 結論

| 項目 | 内容 |
|------|------|
| 外部事例 | Red Hat EnMaaS（Praxis + llm-d）で1兆トークン超処理・40-70%削減・オープン70%へシフト |
| 本質 | ルーティン作業を自己ホストオープンウェイトに、設計判断をフロンティアに振り分ける「賢いルーティング」 |
| オージャスト適用 | 展示会ブース制作の繰り返しプロンプト（仕様テンプレート・台本）をキャッシュし、提案書ドラフトをオープンモデルへルーティング |
| 推定削減率 | キャッシュ＋安価ルーティングで**−83%**、自己ホストまで含めると**−95%** |
| 初手 | 固定プレフィックスの分離と`cache_control: ephemeral`の設定のみで開始可能（投資$0） |
