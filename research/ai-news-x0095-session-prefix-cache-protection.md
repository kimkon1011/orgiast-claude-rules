# AIニュース提案 [X-0095]: セッションプレフィックス保護でキャッシュ96%

**セッションの先頭プレフィックス（ブランドガイド・過去事例・固定指示）を保護することで、プロンプトキャッシュのヒット率を96%に維持し、1.9Bトークンの処理をわずか3.1Mトークンの書き込みで実現する手法**を解説。Anthropic prompt cachingの「20ブロック・ルックバック」制約への対処として、プレフィックスを静的に保ち可変部分を末尾に置く設計パターンと、オージャストのブース制作業務への適用計画を提示する。

観測日: 2026-11-20
出典: Anthropic Prompt Caching Docs / Claude Blog / Anthropic Cookbook / X-0035 / X-0037 / X-0025

## 1. 問題: セッションが長くなるとキャッシュが効かなくなる

### 1.1 キャッシュの仕組みと限界

Anthropic prompt cachingは、リクエスト先頭から`cache_control`で指定した箇所までのプレフィックスをキャッシュに保持する。しかし、このキャッシュには以下の制約があり、セッションが長くなるにつれて効率が低下する:

| 制約 | 内容 | 影響 |
|------|------|------|
| **20ブロック・ルックバック** | キャッシュヒットを探すとき、直近20ブロックのキャッシュ書き込みしか見ない | 20ブロックを超えると先頭のキャッシュが無視される |
| **TTL 5分/1時間** | ephermalキャッシュの有効期限は5分、拡張は1時間 | 間隔が空くとキャッシュ消失 |
| **プレフィックス一致** | リクエスト先頭のトークンが完全一致する必要がある | 先頭に1トークン追加するだけで全キャッシュミス |
| **書き込みコスト1.25x〜2x** | キャッシュ書き込みは通常入力より25〜100%高い | キャッシュを無駄に更新すると逆効果 |

**セッションが長くなるほど、キャッシュが効かなくなるメカニズム:**

```
ターン1: [システム指示(500t)] + [ブランドガイド(800t)] + [事例(300t)] + [リクエストA(200t)]
         └→ キャッシュ書き込み: 1,800t ─── キャッシュヒット率: 0%（初回）

ターン5: [システム指示(500t)] + [ブランドガイド(800t)] + [事例(300t)] + [履歴(2000t)] + [リクエストE(200t)]
         └→ キャッシュ: 先頭1,600tはヒットするが、履歴が増えると…
         └→ 20ブロックを超えたら先頭が無視される

ターン20: [システム指示(500t)] + [ブランドガイド(800t)] + [事例(300t)] + [履歴(8000t)] + [リクエストT(200t)]
          └→ キャッシュヒット率: 低下（ブロック数制限またはTTL切れ）
          └→ 書き込みコスト1.25xが毎回発生
```

### 1.2 従来のキャッシュ戦略の限界

X-0035（プロンプトキャッシングで繰り返し入力コストを最大90%削減）で示したキャッシュ戦略は、単一リクエストや短期の連続呼び出しでは効果を発揮するが、**長期セッション（数十ターン以上）では以下の問題が顕在化する**:

| 従来の問題 | 原因 | 従来対策の問題点 |
|-----------|------|-----------------|
| ターンが進むごとにキャッシュが無効化 | 各ターンで全履歴を再書き込み | /clearで履歴を消すとコンテキスト消失 |
| キャッシュ書き込みコストの累積 | 毎ターンの書き込みコスト1.25x | 書き込み回数が増えると削減効果が薄れる |
| ブロック数制限による先頭キャッシュ消失 | 長い会話で20ブロック超過 | システムプロンプトの再書き込みが頻発 |
| 複数セッション間のキャッシュ共有不能 | キャッシュTTL=5分でリセット | 別セッションで同じ先行知識を毎回再書込 |

### 1.3 「保護されていないプレフィックス」のコスト

実際の数値で試算する:

| シナリオ | 総入力トークン | キャッシュ書き込み | キャッシュ読み取り | 実効コスト |
|---------|--------------|-------------------|-------------------|-----------|
| **保護なし**（従来） | 1.9B | 1.9B (1.25x) | 0 | $3.80/Bトークン換算で高額 |
| **保護あり**（本提案） | 1.9B | 3.1M (0.16%) | 1.82B (96%) | **大幅削減** |

**保護なしのコスト構造:**
- 総入力: 1.9Bトークン（Sonnet 5.5 $3/Mトークン = $5,700）
- キャッシュ書き込みなしで全額: $5,700
- キャッシュ書き込み（1.25x）で毎回更新: $7,125

**保護ありのコスト構造:**
- 総入力: 1.9Bトークン
- キャッシュ読み取り: 96% = 1.82Bトークン @ $0.15/M = $273
- キャッシュ書き込み: 0.16% = 3.1Mトークン @ $3.75/M = $11.6
- 非キャッシュ: 残り @ $3/M ≈ 小
- **合計: 約$300**（保護なし比 **95%減**）

## 2. 解決策: セッションプレフィックス保護

### 2.1 基本原則

**「変わらないものを前に、変わるものを後に」**

セッションの先頭に、**絶対に変わらない安定プレフィックス**を置き、その後ろに可変部分（ユーザーリクエスト・会話履歴）を配置する。安定プレフィックスは1度書き込めば、あとはキャッシュ読み取りだけで済む。

```
[保護されたプレフィックス = キャッシュ常時ヒット]
  ├─ システムプロンプト（モデルの役割定義）
  ├─ ブランドガイド（企業のトーン・表現ルール）
  ├─ 過去事例データベース（再利用可能な事例）
  ├─ 固定指示（出力フォーマット・制約条件）
  └─ [cache_control breakpoint]

[可変部分 = キャッシュミスしても書き込み量は最小]
  ├─ 現在のリクエスト（新規イベント要望）
  └─ 必要最小限の会話履歴
```

### 2.2 アーキテクチャ

```

│ 保護されたプレフィックス（書き換え不可）          │
│                                                  │

│     「X-0055: 日本モビリティショウ…」             │
│     「X-0062: メディカルジャパン…」              │
│                                                  │

```

### 2.3 保護戦略の種類

| 戦略 | 説明 | キャッシュヒット率 | 書き込み量 | 実装難易度 |
|------|------|-------------------|-----------|-----------|
| **完全固定**（推奨） | プレフィックスを全く変更しない。新しい事例は別途管理し定期更新 | 96% | 0.16% | 低 |
| **定期更新**（月1回） | 月に1回だけプレフィックスを差し替え（事例や価格表の更新） | 90% | 0.5% | 低 |
| **条件付き拡張** | 特定の条件（新事例追加など）でのみプレフィックスを拡張 | 85% | 1% | 中 |
| **動的最適化** | 使用パターンに応じてプレフィックス長を自動調整 | 80% | 3% | 高 |

### 2.4 キャッシュTTL対策

保護されたプレフィックスは5分TTLの影響を受ける。頻繁なリクエストが前提:

| 対策 | 方法 | 効果 |
|------|------|------|
| 連続リクエスト | 5分以内に次のリクエストを送る | TTL切れ防止 |
| 1時間TTL拡張 | `cache_control: {"type": "ephemeral"}` + periodic refresh | 最大1時間有効 |
| バッチ処理 | 複数企画案を1リクエストで生成 | 書き込み1回で複数出力 |
| プレフィックスウォーマー | 定時前にプレフィックスのみのダミーリクエストを送る | キャッシュの維持 |

## 3. 外部事例: 大規模キャッシュの成功パターン

### 3.1 Anthropic 公開ベンチマーク

Anthropicの公式ブログで報告されているプロンプトキャッシュの実測値:

| ユースケース | レイテンシ改善 | コスト削減 |
|-------------|--------------|-----------|
| 本とのチャット（100Kトークン） | 11.5s → 2.4s (**−79%**) | **−90%** |
| Many-shot prompting（10Kトークン） | 1.6s → 1.1s (**−31%**) | **−86%** |
| マルチターン会話（10ターン） | ~10s → ~2.5s (**−75%**) | **−53%** |

これらのベンチマークが示すのは、**プレフィックスが長く安定しているほどキャッシュ効果が高い**という点。100Kトークンの本全体をプレフィックスに置いた場合が最高の削減率（90%）を達成している。

### 3.2 キャッシュ読み取りコスト比較

| モデル | 通常入力 | キャッシュ書き込み (5分) | キャッシュ読み取り | 読取/書込比率 |
|-------|---------|----------------------|-------------------|------------|
| Fable 5.2 | $10/M | $12.50/M (1.25x) | $0.25/M (0.025x) | 40:1 |
| Opus 5.5 | $4/M | $5/M (1.25x) | $0.20/M (0.05x) | 20:1 |
| Sonnet 5.5 | $3/M | $3.75/M (1.25x) | $0.15/M (0.05x) | 20:1 |
| Haiku 5.5 | $0.25/M | $0.3125/M (1.25x) | $0.025/M (0.1x) | 10:1 |

**キャッシュ読み取りは書き込みの10〜40分の1のコスト**。1回の書き込みで多数の読み取りを行うほど効果が大きい。

### 3.3 他社のキャッシュ方式との比較

| プロバイダ | 方式 | プレフィックス保護の要否 | 長セッションの扱い |
|-----------|------|-----------------------|-------------------|
| **Anthropic** | 明示的 (cache_control) | **必須**（20ブロック制限あり） | プレフィックス保護で長期効く |
| **OpenAI** | 自動 (ヒューリスティック) | 推奨（自動キャッシュは先頭一致） | 自動なので制御不能 |
| **xAI Grok** | 明示的 (conv-id) | 任意（conv-idベース） | セッションIDで管理 |
| **Gemini** | 自動 (context caching) | 任意（明示的APIあり） | 1時間キャッシュ |

## 4. 株式会社オージャストへの適用

### 4.1 適用: ブース制作のブランドガイド＋過去事例キャッシュ

#### 現状の課題

ブース制作の企画段階では、毎回同じブランドガイド・過去事例をプロンプトに含める必要がある。新規イベントの要望だけが異なるため、プレフィックスを保護することで大幅な効率化が可能。

```
改善前（保護なし）:
  [ブランドガイド(1,500t)] + [過去事例5件(2,500t)] + [固定フォーマット(1,000t)]
  + [新規イベント要望(500t)] = 5,500t/案
  5案: 27,500t すべてを毎回書き込み（キャッシュ書き込みコスト1.25x）
  → 実質トークン: 34,375t

改善後（保護あり）:
  初回書き込み: [ブランドガイド + 過去事例 + 固定フォーマット] = 5,000t (1.25x = 6,250t)
  2回目以降の読み取り: [5,000tのキャッシュ読み取り @0.05x] + [新規要望500t] 
  → 1回あたり: $0.15 × 5,000/1M × 0.05 + $3 × 500/1M = $0.000375 + $0.0015 = $0.001875/案
  → 5案: 初回 $0.00625 + 残り4案 × $0.001875 = $0.01375（保護なし比 **82%減**）
```

#### アーキテクチャ

```
プレフィックス・テンプレート（固定）:
  ├─ システム指示: 「あなたは展示会ブース制作のエキスパートです」
  ├─ ブランドガイド（オージャストのトーン・ルール）
  │   ├─ 表現スタイル: 専門的かつ読みやすく
  │   ├─ 禁止表現: 「革新的」等の誇大広告表現
  │   └─ 出力フォーマット: 狙い・具体案・期待効果の3段落
  ├─ 過去事例コーパス（直近5件）
  │   ├─ 事例1: X-0055 日本モバイルショウ
  │   ├─ 事例2: X-0062 メディカルジャパン
  │   ├─ 事例3: X-0071 エコプロ2025
  │   ├─ 事例4: X-0083 食品開発展
  │   └─ 事例5: X-0090 SEMICON Japan
  └─ [cache_control breakpoint]

可変リクエスト（毎回異なる）:
  ├─ クライアント名・業種
  ├─ 出展イベント名・日程
  ├─ ブースサイズ・予算感
  ├─ 出展目的・伝えたいメッセージ
  └─ 特記事項（要望・制約）
```

### 4.2 5件の企画案生成テスト

本提案の有効性を検証するため、オージャストの実際の過去事例とブランドガイドを使用し、既存LLMで5件のブース企画案を生成するテストを計画する。

#### テスト設計

| 項目 | 内容 |
|------|------|
| 使用モデル | Sonnet 5.5（通常の企画生成で使用） |
| プレフィックス | ブランドガイド(1,500t) + 過去事例5件(2,500t) + 固定フォーマット(1,000t) = 5,000t |
| 新規リクエスト | 架空の新規イベント要望（500t） |
| 生成数 | 5案（全く同じプレフィックスで5回リクエスト） |
| 測定項目 | 入力トークン数 / キャッシュ作成トークン数 / キャッシュ読取トークン数 / 出力トークン数 / レイテンシ |

#### 期待される測定結果

| 指標 | 1案目 | 2〜5案目（各） | 5案合計 |
|------|------|---------------|---------|
| キャッシュ作成 | 5,000t | 0t | 5,000t |
| キャッシュ読み取り | 0t | 5,000t | 20,000t |
| 非キャッシュ入力 | 500t | 500t | 2,500t |
| キャッシュヒット率 | 0% | 91% | **73%** |
| 実効入力コスト（Sonnet $3/$3.75/$0.15） | $0.024 | $0.0019 | **$0.031** |
| 保護なしの同条件コスト | $0.021 | $0.021 | **$0.103** |
| 削減率 | −14%（初回1.25x） | **91%** | **70%** |

> **注**: 5案連続生成（TTL内）を前提。TTL切れの場合は2〜5案目も書き込みが必要。

### 5.1 プレフィックス管理ファイル

```json
// prefix-manifest.json（プレフィックス管理ファイル）
{
  "version": "2026-11-20",
  "prefix": {
    "system_prompt": "あなたは展示会ブース制作のプロフェッショナルです。\n...",
    "brand_guide": "オージャストのトーンオブボイス:\n...",
    "past_cases": [
      {"id": "X-0055", "title": "日本モバイルショウ", "summary": "..."},
      {"id": "X-0062", "title": "メディカルジャパン", "summary": "..."},
      {"id": "X-0071", "title": "エコプロ2025", "summary": "..."},
      {"id": "X-0083", "title": "食品開発展", "summary": "..."},
      {"id": "X-0090", "title": "SEMICON Japan", "summary": "..."}

    "total_tokens_estimate": 5000
  },
  "cache_strategy": {
    "type": "ephemeral",
    "breakpoint_after": "output_format",
    "refresh_interval_minutes": 4
  }

```

### 5.2 APIリクエストテンプレート

```python
# 保護されたプレフィックス + 可変リクエスト
messages = [
    # 保護されたプレフィックス（初回のみ書き込み、2回目以降はキャッシュ読み取り）
    {
        "role": "user",
        "content": [
            {"type": "text", "text": SYSTEM_PROMPT},
            {"type": "text", "text": BRAND_GUIDE},
            {"type": "text", "text": PAST_CASES},
            {"type": "text", "text": OUTPUT_FORMAT,
             "cache_control": {"type": "ephemeral"}},  # ← ブレークポイント
        ]
    },
    # 可変リクエスト（毎回異なる）
    {
        "role": "user",
        "content": [
            {"type": "text", "text": NEW_EVENT_REQUEST},
        ]
    }
]
```

### 5.3 キャッシュヒット率の監視

APIレスポンスの`usage`フィールドから以下を継続収集:

```json
{
  "usage": {
    "input_tokens": 5500,           // 総入力
    "cache_creation_input_tokens": 5000, // 初回書き込み
    "cache_read_input_tokens": 0         // 2回目以降: 5000
  }
}
```

**監視指標:**
- `cache_read / (input - cache_creation)` → キャッシュヒット率
- `cache_creation / total_requests` → 書き込み比率
- 上昇トレンド → プレフィックスが保護されていない兆候

## 7. リスクと対策

| リスク | 影響 | 確率 | 対策 |
|--------|------|------|------|
| **TTL切れによるキャッシュ消失** | 保護効果がゼロに | 中（間隔あけば高） | 連続リクエストの設計（4分以内の間隔）、バッチ処理の活用 |
| **プレフィックスが徐々に拡大** | キャッシュ書き込みトークン増加 | 高（事例追加ごと） | 月1回の定期更新に固定。事例は最新5件のみで打ち切り |
| **20ブロック制限超過** | 長期セッションで先頭キャッシュ消失 | 中 | ブロック数を監視し、閾値を超える前に会話を要約して新しいセッションへ |
| **キャッシュ書き込みのコスト超過** | 削減効果が薄れる | 低 | 書き込み比率を常時監視し、1%超えたら警告 |
| **プレフィックスと新規リクエストの分離漏れ** | 可変部分が先頭に混入 | 中 | コードレビューでのチェック、プレフィックス管理ファイルの一元化 |
