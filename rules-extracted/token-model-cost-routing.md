### 実測A/B（合成データ、2026-07。本番未反映）

- **生成タスク（返信メール下書き）**: Sonnet=綺麗な本文を$0.005〜0.007/30sで安定生成。**Kimi K3/K2.6 は本文が空**（max_tokens全部を内部推論に消費、finish_reason=length）。→ **文章生成にKimiは不可が確定**。Kimiは推論モデルなので単純生成でも思考に全トークンを燃やす。
- **推論タスク（議事録6軸採点JSON）**:
  - Sonnet4.6 = ✅妥当JSON total=28 改善5件 **$0.025 / 30s**
  - Opus5 = ✅やや上質（次回日程＋顧客側期限の二重締切テクニック）total=33 **$0.049 / 36s**
  - Kimi K2.6 = ✅妥当JSON total=23 改善5件（品質は十分）だが **$0.020 / 278s（4.6分・推論3866tok）**
- **Kimiの最終判定（標準枠に入れない）**: 品質OK・コスト最安（Sonnet比2割安）だが **1件278秒＝Sonnetの9倍遅い**。serverless関数（Vercel `maxDuration=300`）やcronの逐次ループでは1件でタイムアウト枠をほぼ使い切りアーキテクチャが破綻する。2割の節約に9倍の遅延＋別API/別キー/reasoning_tokenの不確実性は割に合わない。→ **推論の実用本命はSonnet、最高価値判断のみOpus5**。Kimiは「レイテンシが完全に無関係なオフライン大量推論（ローカルスクリプト／長時間GHA／キューワーカー）」限定の実験枠に留める。
- **教訓**: Kimiの推論特性は「生成の敵、推論では品質は出るが激遅」。¥150k/月の主レバーはKimiではなく「Opus5の半額化＋Sonnet default＋Fable5不使用」。安さに飛びつく前にレイテンシとアーキ適合を実測する。

### Kimi K3（2026-07-31 追検証）— 推論オフにすれば実用圏だが優位性は薄い

K3は $3/$15（Sonnetと同単価・1M context・cache-hit $0.30）。**必ず `reasoning_effort:"none"`（または `thinking:{type:"disabled"}`）を付けて呼ぶこと**。付けないと内部推論に大量トークンを燃やし **1件99秒・Sonnetの3〜10倍コスト**になる（デフォルトは推論ON）。実測で推論を切れるパラメータ確認済み: `reasoning_effort:"none"`/`thinking:{type:"disabled"}` で reasoning_tokens=0。

推論オフK3 vs Sonnet4.6（合成A/B）:
- 生成: K3 ✅335字 $0.0050/11.3s ↔ Sonnet ✅283字 $0.0047/6.0s
- 推論: K3 ✅total=24 $0.0125/29.0s ↔ Sonnet ✅total=17 $0.0184/23.2s
- → **品質パリティ・コストほぼパリティ（時に安い）・レイテンシ1.3〜1.9倍**。cache読みは両者$0.30で同額、1M文脈もSonnetにあるため**per-token優位性は無い**。

**K3の位置づけ（結論）**: 効率面でSonnetを上回らないので **default はSonnet据え置き**。K3-nothink の唯一の実利は**別課金プール（Moonshot前払い、Claude Teamクレジットと別勘定）** な点。Claude Teamシートのクレジット上限がその月の律速になっている時に限り、**レイテンシ1.5倍を許容できるオフライン/バッチの生成・推論を K3-nothink に逃がして Claude 側の消費を圧縮**する「オーバーフロー弁」として使える。対話・顧客向け・低レイテンシ経路には使わない。絶対の節約ではなく予算プールの付け替えである点に注意（per-token単価はSonnetと同じ）。

## 1.13 トークン効率を意識する（出力・入力キャッシュ・サブエージェント）

長いセッション・大型プロジェクトでは、累積トークンが応答速度と月次クレジットを直撃する。全プロジェクト共通 で守る。

### A. 出力は最小限（Caveman 風）

- 前置き禁止: 「了解しました、〇〇します」「以下のような感じになります」型の枕詞は書かない
- 完了報告は 1〜3 行: ファイルパス + 何を変えたか、で十分。差分の全文再掲はしない
- markdown 装飾は意味があるときだけ。`###` 連発、絵文字過多、表で済むものを箇条書きで水増し、等を避ける
- ※ コード本体は圧縮できないので、コード出力中心のタスクでは効果限定

### B. 入力（プロンプトキャッシュ）を壊さない

Claude のプロンプトキャッシュは 5 分 TTL。これを意識した書き分け:

- CLAUDE.md には恒久ルールだけ（社名・運用方針・URL 形式など月単位で変わらないもの）
- 現状の状態（実行中タスク、今日の数字、進行中の障害）は CLAUDE.md に書かない → 毎回キャッシュを壊す
- CLAUDE.md の上部ほど変更しない: ファイルの頭は最も静的なルールにする
- 同一セッション内でモデル切替を頻繁にしない（cache 境界が壊れる）

### C. モデルルーティング

- 単純編集 / grep / 置換 / 確認系 → Sonnet または Haiku で十分
- 設計 / コードベース横断調査 / 複数仮説の検証 / リファクタリング戦略 → Opus
- 迷ったら Auto（cache 境界を保つようルーティングされる）
- `/fast` で切替できるが、B の cache 原則からセッション中の切替はコスト得しないケースも多い
- ⚠️ Fable 5 / Mythos は**監督（メインループ）でのみ可**、かつ `tools/fable-policy.json` の `planIncluded: true`（＝自分のアカウントで定額内と実測済み）の時だけ（§1.16 / 2026-09-03改定）。実装・量産・分類・サブエージェント指定 `model:"fable"` は引き続き禁止（単価が Opus の2倍・専用の週間上限を別に持つ）。

### D. サブエージェント分離（重い探索は委譲）

- 「`src/auth` 配下を全部読んでクラス図」型の 重いファイル探索 は Agent ツール (subagent_type=Explore / general-purpose) に委譲する
- 委譲時のモデルは省略（親継承）か `model:"sonnet"`。**`model:"fable"` は指定しない**（単価が Opus の2倍。2026-09-03改定後も `model-agent-guard.mjs` が PreToolUse で deny する）
- subagent には「結果を 200 字以内で報告」「コード本体は含めない」と明示すると、親に戻ってくる量がさらに減る
- 結果: 親コンテキストにサマリだけ残り、cache hit 率が保たれる

Why: Qiita「GitHub Copilot 料金改定対策のトークン削減手法」(2026-06 / shinkai_) を Claude Code 文脈に翻訳。Copilot だけでなく Claude でも prompt cache TTL 5 分・出力トークン課金などの構造は同じ。元記事: https://qiita.com/shinkai_/items/626dfa7857f2d554784e

## 1.16 Fable は「定額内なら監督用のみ」可（2026-09-03 改定・旧: 全用途禁止）

Fable は**監督（設計・タスク分解・指示・レビュー・検証＝メインループ）に限り使ってよい**。ただし自分のアカウントで定額内と確認できている場合のみで、判定の単一の設定源は `tools/fable-policy.json` の `planIncluded`（`false` のアカウントは従来どおり全用途禁止＝安全側の既定）。**サブエージェント指定 (`model: "fable"`) / 実装 / 量産 / 分類は引き続き禁止**。

Why（旧ルールの前提が誤りだった）: 旧「別課金枠だから全用途禁止」（2026-07-13）は 2026-09-03 の実測で覆った。支出レポート（claude.ai/analytics → Export spend report、2026-09-01..09-02）で `claude-fable-5-1` は 13 req・出力 51,036 tok で **net $0.00 / gross $0.00**。当月累計支出の正体は `claude-sonnet-5` $8.64 + `claude-opus-5` $2.77 の上限超過分で、Fable とは無関係だった。usage credits 課金の機能はプランに残枠があっても credits から引かれるため、**$0.00 は定額内の証明になる**。それでも実装・量産に使わないのは課金の問題ではなく、**単価が Opus の2倍（$10/$50 vs $5/$25 per MTok）で専用の週間上限を別に持つ**ため（§1.18 の委譲原則は不変）。

⚠️ **専用のレート制限バーがあることは「定額内」の証明にならない**（fast mode も credits 課金なのに専用プールを持つ）。証拠は支出レポートの金額だけ。プラン変更・seat tier 変更時は Export spend report（MTD）で `model` が fable の行の `total_net_spend_usd` を再確認し、0 でなければ `planIncluded` を false に戻す（データは1日遅れ）。

代替:
- 生成品質重視 → Opus 4.7 / 4.8
- 速度・単純タスク → Sonnet / Haiku
- コーディング → §1.17 に従い Codex

過去メモリのスコープを「サブエージェント限定」から「全用途」に拡張したのが本ルール（2026-06-06 kim 指示）。

## 1.17 コーディングは Codex を主に使う（Claude Code は指揮官）

新規のコード実装タスクは Codex CLI を通じて Claude Code の Bash tool から呼び出して実装する。Claude Code は「指揮官」役に徹する:

- 全体設計・タスク分解・要件整理
- コードレビュー・diff の判定・受け入れ / 差し戻し
- commit / PR / デプロイのオーケストレーション（§1.3 の GAS clasp フロー等と併用）

Codex に渡す情報:
- 明確なタスク指示: 何を作るか、期待入出力、テスト条件、コーディング規約
- 参照ファイルパス / 既存コード抜粋（Codex は Claude Code の context を継承しないため必要）
- 本 ONBOARDING の関連セクション（Codex は CLAUDE.md を自動読み込みしないので、守らせたいルールは呼び出し時に明示）

### 渡し方（2026-08-26 の実害を受けた絶対ルール）

**指示は必ずファイルで渡す。argv で渡さない。TTY を渡さない。上限時間を必ず付ける。**

```
node ~/orgiast-claude-rules/tools/codex-do.mjs --prompt-file <指示ファイル> --cwd <対象パス> --timeout 1800
```

直に叩く場合のみ:

```
wsl -d Ubuntu --cd "<path>" -- timeout 1800 codex exec -s workspace-write - < prompt.md
```

**何が起きたか（2026-08-26）**: Codex への委譲が **丸1日 hang** し、翌日まで気付けなかった。
同型の hang が他に2本（1日 / 19時間）過去セッションから生き残っていた＝**前から起きていたのに
誰も気付いていなかった**。死因は Codex 側ではなく呼び出し方で、3つ同時に起きていた。

1. **argv で渡すとシェルがプロンプトを実行する**。`bash -lc 'codex exec "$(cat prompt.md)"'` の形で
   渡したところ、プロンプト中のバッククォート（`` `scripts/xxx.mjs` `` `` `booth_customer_aliases` `` 等）が
   **コマンド置換として実行**された。Codex に実際に届いたのは「新規ファイル　を1つだけ作成する」＝
   **作るべきファイル名が消えた**指示で、さらに参照用に名前を書いただけの既存スクリプトが**起動**し、
   その出力 `◇ injected env (30) from .env.local` が**プロンプト本文に混入**していた。
   ログには `bash: command substitution: syntax error` / `bash: line 1: booth_customer_aliases: command not found` が並ぶ。
   `"$(cat f)"` は理屈上は再展開されないが、`wsl` → `bash -lc` と層が重なると**実際に展開された**。
   理屈で安全と判断せず、**シェルを1層も通さない経路**にすること。
2. **TTY 付きで起動すると stdin 待ちで永久に眠る**。`ps` の `stat` が **`Ssl+`**（`+` = TTY の
   フォアグラウンド）で、`Reading additional input from stdin...` を出したまま `1-00:57` 経過していた。
3. **`| tail -N` でパイプするとバッファされ**、完了まで1行も出ない。hang と実行中の区別がつかなくなる。
   背景実行してログファイルを直接読むこと。

**返ってこない時の診断**:

```
wsl -d Ubuntu -- bash -lc "ps -eo pid,etime,stat,args | grep '[c]odex'"
```

`stat` に `+` が付いていて `etime` が長ければ TTY 待ちの hang。古いものは kill してよい。

**機械的強制**: PreToolUse の `pretooluse-codex-invocation` が、argv 渡し・`bash -lc` 経由・
`| tail`・`--timeout` 無しを検出して警告する（ブロックはしない）。hook の欠落は SessionStart の
`hook-selfcheck` が自動修復する。

**生成物は必ずレビューする**。今回も Codex は指示した「必須ヘッダから外す」をやらず、定数配列に
残したままフォールバックを書いて**死にコード**にしていた（「Codex はスコープ外も書き換える／
半端に直す」と同型）。

Why: Codex は並列コード生成が得意で、大量実装・A/B 比較・OpenAI 系推論モデル特性が必要なタスクに向く。Claude Code のオーケストレーション能力（MCP・hook・memory・徹底自動化ルール群）と組み合わせるのが最適。ただし verify は Claude Code 側の責務（§1.2 の根本診断原則を Codex 出力にも適用）。

適用外（Claude Code が自分で書いてよいケース）:
- ごく短い編集（数行修正、typo、リネーム、import 追加）
- Codex 呼び出しのオーバーヘッドが本体作業より重いとき
- 設計試行錯誤中で毎回コードを書き直すフェーズ（設計固まってから Codex 一発生成）
- 既存 Claude Code スキル（`/gas-project-setup` 等）がカバーしている定型作業

呼び出し方の推奨:
Bash tool から `codex exec` サブコマンド（あるいはインストール環境に応じたエントリポイント）を叩き、prompt / cwd / 参照ファイルを明示的に渡す。出力を Claude Code が Read → 差分レビュー → 必要なら再 prompt で修正、というループが標準。§1.10 に従い Codex CLI 未インストール環境では Claude が自分で `winget install` 等で導入する。

## 1.17.1 費用対効果ファースト — 追加費用ゼロの経路を先に必ず検討する（絶対ルール、2026-07-13 新設）

あらゆる実行判断の前に「同品質を、追加費用ゼロ（または定額枠内）で出せる経路があるか」を必ず先に確認する。これを飛ばして従量課金の経路を勝手に選ぶことを恒久禁止する。

実行前の必須チェック（コーディング・分析・大量処理すべて）:

```
[必須] 従量課金トークンを使う作業を始める前に毎回:
  1. 定額枠内の代替があるか?
     - コーディング → Codex（ChatGPT 定額枠、§1.17 の主経路）
     - 定型処理・集計 → ローカルスクリプト（Python/Node、トークン消費ゼロ）
     - 既存の自動化（weekly-bot / GAS / 既存アプリ）で済まないか
  2. 「ツールが未導入だから従量経路で」は理由にならない
     → §1.10 と同じ: まず自分で install する。認証だけ user に 1 回依頼
  3. 従量課金しか無い場合はモデルを最小化（§1.13C / §1.18: 分類=Haiku、量産=Sonnet、Opus は品質差の実測がある時だけ）
  4. 大量トークン消費が見込まれる判断（サブエージェント多並列、Opus 長時間、外部API課金）は
     着手前に「費用見込み 1 行」を添えて提示する。勝手に始めない
```

やってはいけない（過去事例 2026-07-13）:
- 経営司令室の実装で、Codex CLI が未導入という理由だけで従量課金の Sonnet サブエージェント＋Opus 検収を勝手に選択した。本来は `npm i -g @openai/codex`（1分）→ login 依頼（user 1クリック）で ChatGPT 定額枠内・同等以上の品質で実装できた。kim「費用対効果の事を第一に考えていない。費用を使わずに効果的な方法があるのに、それを実行せずに、かってに費用がかかってクオリティが低い行動をしている。これは重大な問題です。今後二度と起こらないように」
- 実装・量産・分類を Fable で挽くのも同型の違反（§1.16。課金ゼロでも単価は Opus の2倍で、Codex/Sonnet/Haiku に流すべき仕事を高い枠で使っている）。「動くから」「速いから」は費用を無視する理由にならない

判断の優先順位（上から順に検討）:

| 優先 | 経路 | 費用 |
|---|---|---|
| 1 | 既存の自動化・ローカルスクリプト・既存成果物の再利用 | ゼロ |
| 2 | Codex（コード実装）/ 定額枠内のツール | 定額内 |
| 3 | Haiku（分類・抽出・軽処理） | 最小従量 |
| 4 | Sonnet（量産・ドラフト・調査） | 低従量 |
| 5 | Opus（品質差が実測されたタスクのみ） | 高従量・要正当化 |
| 禁止 | 実装・量産・分類・サブエージェントへの Fable 指定（§1.16） | Opus の2倍単価 |

## 1.18 Opus vs Sonnet の default は Sonnet（品質差が無いタスクは全部 Sonnet）

コスト意識として Sonnet を default モデル とする。Opus は「Sonnet では品質が明らかに落ちる」と実測で判明したタスクにだけ使う。

判定プロトコル:
1. 新規タスクは まず Sonnet で実行 する
2. 結果を評価: 論理の飛躍・誤り・指示の取りこぼし・コードの粗さがあるか
3. 品質差が体感で分からない / 目的達成に支障なし → 以後も Sonnet 継続
4. 明らかに劣化していると分かったら Opus に切替、そのタスク種別を記録して次回同種は最初から Opus

Sonnet で十分な例:
- 数行〜数十行のコード編集
- 単純な grep / ファイル探索（+ subagent 委譲）
- markdown / 設定 / JSON の追記・整形
- 定型フォーマットの生成
- テストコード生成
- コミットメッセージ / PR 説明 / commit 前レビュー
- ONBOARDING / CLAUDE.md 等ドキュメント編集

Opus が要るケース（実測で判明したもの）:
- 複雑なリファクタリング設計（アーキテクチャ変更、依存グラフ再構成）
- 未知の失敗の根本原因分析（複数仮説を並行検証、複数証拠を突き合わせ）
- 大規模コードベース横断の一貫性保証
- 微妙な API 設計判断（backward compat / naming 整合 / 命名衝突検出）
- 経営意思決定の材料整理（複数シート横断、傾向抽出、示唆生成）

Why: Opus は Sonnet に比べ output token 単価が数倍。多くのタスクで品質差は体感できないため、default を Sonnet にする方がクレジット消費が数倍圧縮される。§1.13 C 「モデルルーティング」を強化した位置づけ。Claude 4.6 世代以降、Sonnet の実力が Opus と大差なくなっているケースも増えている。

How to apply:
- `/model sonnet` で明示指定、または Auto 使用時も監視して Opus に自動昇格したら「本当に必要か？」を自問する
- subagent 呼び出しでも `model:"sonnet"` を明示（未指定だと親モデル継承）
- 疑わしいときは Sonnet を先、Opus は「品質不足を確認してから」の 2 段階運用
