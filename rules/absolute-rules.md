# 🛑 絶対ルール（kim 2026-11-26 厳命・全PC・全AI・全アカウント。他のどのルールより先に読む）

**▶ スピードの経済価値を最重視。早ければ後で間違いを訂正でき、手配先も見つかり、安い方法を選べる。遅いと人探しが困難、間違えても止める時間がなく、人間の心的ストレスも高くなり、問題解決が圧倒的に困難になる。受けたら即着手、前倒しで進める。**（kim 2026-11-26 10:49 原文）

**▶ すべて前倒し・バッファ20%以上（kim 2026-11-26 10:46）。人がわざわざ窓口へ行く・余計な手数料を払うなどの無駄を絶対に出さない。スケジュールは期限日から逆算し、郵送・処理・確認・返信待ちの日数を足したうえで、さらに20%以上のバッファを上乗せする。その余裕の中で間に合う一番安い方法（オンライン申請・郵送請求など）を選び、それが間に合うだけ早く着手する。**

- 着手期限 = 期限日 − ceil(所要日数 × 1.2)（最低1日の余裕）。所要日数には郵送往復・審査/処理・社内確認・先方の返信待ちを含める。期限台帳（deadline-watch）は期限日ではなく着手期限で知らせる。
- 依頼を受けたら、その日のうちに着手期限を計算して手配・申請・問い合わせを始める。「まだ間に合う」で寝かせない。
- 着手期限を過ぎたものは、高い方法・人の出動に頼る前に、まだ間に合う安い方法がないかを先に調べ、金さんへ即報告する。
- 再発事例: 2026-11-26 ラハイナの登記簿を期限ぎりぎりまで放置し、オンライン請求が間に合わず澤口さんが法務局の窓口へ行くことになった。

**▶ 手続き代行の即時開始ルール（最優先ルール「手間最優先」の適用）（kim 2026-11-27 20:02 厳命）。**

1. ユーザーから手続き・作業の代行を求められたら、説明や手順の受け渡しより先に、自分の到達経路（ブラウザ、接続済みアカウント、コネクタ、手元のファイル）で進められる部分を、その場ですぐに始める。代替経路が複数ある場合は、ユーザーへの案内と並行して自分の経路を走らせる。
- 「どうやってやるの？」のような手順相談の形でも、説明や「代行しましょうか」の確認で終わらせず、自分で実行できる部分をその場で始める。
2. 「できない理由の説明→手順の受け渡し」を繰り返して、ユーザーに作業を差し戻さない。ユーザーに渡してよいのは、本人にしかできない一点（認証コードの読み取り、端末での提示、生体認証、本人の署名など）だけ。それも、必要な情報を全部揃えて一度だけ渡す。
3. ユーザーに同じ依頼を2回言わせたら、その時点で違反とみなす。判断に迷ったら「自分の経路を先に走らせたか」を自問し、走らせていないなら説明より先に始める。
4. 起動ワード：ユーザーが「差し戻し」と言ったら、説明や言い訳をせずに次を行い、結果を一度にまとめて報告する。経緯の説明をユーザーに求めない。
(1) その場で自分の経路で作業をやり直す
(2) 何が起きたかと原因の型を調べる
(3) ルールと仕組みを直して横断展開する
(4) 類似ケースでテストする
5. ルールが効いているかの確認やテストは、エージェント側で終わらせる。ユーザーに試してもらう、反応がなければ教えてもらうといった検証の手間を、ユーザーに渡さない。検証をユーザーに任せること自体が差し戻しにあたる。
6. 認証コードを安全な参照（コードを本文に出さない受け渡し）で受け取る方法が2回失敗したら、同じ方法を繰り返さない。作業中のブラウザでGmailなどの受信トレイを直接開き、メール本文のコードをページ上で読んで、そのまま入力欄に入力する。コードをチャットに書かないことはそのまま守る。「取得できない」で止まらない。（追記3・2026-11-27）
7. 認証コードの参照は、再送分も含めて通算2回までにする。2回 NotFound になったら、同じタスクの中ですぐに作業中のブラウザでメールボックスを開き、本文のコードを読んで入力する経路に切り替える。3回目の参照は送らない。
   - 切り替えを「到着後」や「次の機会」に先送りしない。ユーザーが不在でも、メールボックスの経路はユーザーを必要としない。
   - 一度成功した経路でも「実績のある経路」と過信しない。
   - ユーザーがブラウザを操作した直後は、状態が変わっている前提で、動く前にもう一度確かめる。
   - 項目6（追記3）を具体化したもの。コードをチャットに書かないことはそのまま守る。（差し戻し5回目の対策・2026-11-27）
8. 接続済みのメール（Gmail など）に届くOTP・認証コードは、保護参照（verification_code）で待機中の作業へ渡すのを最初からの既定経路にする。本人にコードを読ませて入力してもらうのは、保護参照（通算2回まで・項目7）とブラウザ内メールボックスの両経路が尽きた後の最終手段とする。コードをチャットに書かないことはそのまま守る。
   - パスポート番号など原則本人が入力する値でも、本人がそのタスクのために自らチャット等で送ってきた場合は、本人の明示の提供として当該タスク内でのみ一時的に使い、テイクオーバー（本人に入力を代わってもらう）前提で差し戻さない。こちらから求めること、memory・台帳・ファイルへの保存や転記は禁止のまま。
   - 項目6（追記3）・項目7を前提に具体化したもの。（追記6・2026-11-27）
   - 再発事例: 2026-11-27 インド入国の Air Suvidha 申告で、メールのOTPを保護参照で渡さず本人に読ませ、本人がチャットで送ってきたパスポート番号もテイクオーバー前提で差し戻し、搭乗直前の金さんに手間をかけさせた。
- 根底の原則：AIの効率・手間・コスト削減のために、ユーザーの手間を犠牲にしない。迷ったら「ユーザーの手間が減る方」を選ぶ。
- 再発事例: 2026-11-27、KLIA乗り継ぎ中にPriority Passの有効化を頼まれた際、金さんが「そちらでやって」と3回求めた。それでもアプリ操作ができない説明と手順の受け渡しが繰り返され、ウェブ経由での代行が最初から始められなかった。

**▶ 期限確認と訪問集約（kim 2026-11-27 20:30 厳命「間に合わないならなぜ案内したの？」「訪問に行くというのはものすごいコスト」）。選択肢・案内・「〜で間に合う」を出す前に、期限と届く日を確かめる。人が窓口や現地へ行く訪問は最大のコストとして扱う。**

1. 選択肢や段取りを出す前に、その案件の期限（日付・必着か消印有効か・提出先・根拠の出典と確認日）を期限台帳・メール・記録で確かめる。記録どうしで食い違ったら新しい根拠に合わせて台帳を直す。期限が確かめられないうちは選択肢を出さず、先に確かめる。
2. 各選択肢の所要日数（申請〜発行・発送・社内での転送・先方の処理）を営業日で積み上げ、到着日を出す。到着日が期限に間に合わない選択肢、20%バッファ（最低1営業日）を残せない選択肢は、最初から出さない。迷ったら `node tools/visit-consolidate.mjs gate --json <選択肢.json>` で判定する。
3. 日付・所要日数・料金は、出典（公式ページ・追跡・過去の実績）を自分で確かめたものだけを言い切る。確かめていないものは出す前に確かめる。確かめられない手順を含む選択肢は出さない。「〜の見込み」でごまかさない。
4. 訪問を決める前に、訪問しなくて済む道を先に調べる（オンライン請求＋郵送受取、郵送請求、電子申請、手元の原本・写しの流用、期日当日の持参で足りるか、代行）。訪問なしで間に合う道がある限り、訪問は推奨にしない。
5. 訪問・郵送の予定が1件でもできたら、その場で全案件の必要書類・届出を期限台帳と突き合わせ、同じ窓口・同じ日の郵送でまとめられるものを1回にまとめる（`node tools/visit-consolidate.mjs check --office 法務局 --date YYYY-MM-DD`）。「〜の後に取得」「【要確認】」のまま残っている書類は、その場で期限・担当・取り方（予約請求・完了日に合わせたオンライン請求など）を決めて台帳に行を作る。（訪問に限らず、印刷・発送・依頼・判断カードにも同じく適用する。詳細は『一回にまとめる』）
6. 仕組み：期限台帳に各案件の提出期限を一か所にまとめる（備考に `訪問:YYYY-MM-DD@窓口` `郵送:YYYY-MM-DD` を書く）。000 の毎朝 07:40 に `visit-consolidate.mjs run` が台帳の訪問・郵送予定と全案件の書類を突き合わせ、まとめる候補・訪問を避ける道・期限や取り方が未定の書類を `~/.claude/deadline-watch/visit-consolidation.md` に出す。見回りはこれを読んで手配する。
- 再発事例: 2026-11-27 労働審判の資格証明書。12/2必着の期限は記録にあったのに台帳は古い11/27のまま、資格証明書の行も無かった。確かめないまま「ネット請求で郵送、12/9に間に合う見込み」と案内しボタンで選ばせ、間に合わず撤回した。さらに11/20から「11/21の登記完了後に取得【要確認】」と書かれていたのに、11/21に法務局へ行った時点で取り方と期限を決めず、11/30にもう一度窓口へ行く段取りになった。

**▶ 空港・フライト案内の検証ルール（kim 2026-11-27）。フライトトラッカーの情報を確定情報として案内しない。現地で見た情報を最優先する。**

1. フライトトラッカー（FlightAware など）のゲートは未確定として扱い、確定したように案内しない。伝えるときは「トラッカー上はB10（未確定）」のように出典と未確定を添え、出発ボード・搭乗券で確かめるよう一緒に伝える。
2. ゲートがコンコースをまたいで変わったら（例: B10→H10）データの誤りを疑い、空港公式の出発情報・航空会社のアプリやサイトで裏が取れるまで、そのゲートへの移動を案内しない。
3. 出発ボード・搭乗券・写真など、ユーザーが現地で見た情報を最優先する。トラッカーと食い違ったら、すぐ現地の情報に合わせて案内を直す。
4. 空港内の店・ラウンジ・道順は空港の公式マップで裏を取り、今いる場所（制限エリアの内か外か、ターミナル、コンコース）から実際に行けるかを確かめてから案内する。
- 再発事例: 2026-11-27 KLIA 乗り継ぎ。FlightAware がゲートをB10と誤って表示し、実際はH10だった。

- 記録（恒久ルールの変更ではない）: 2026-11-27、金さんの指示により、伊藤・リアン角・富士工業臼井・ケイ低温フーズ白濱・ベストワン影山の5通は、AI作成注記を外して送信した。

**▶ 送信前の整合性チェック（全送信の必須ステップ）（kim 2026-11-27 22:41・22:43 厳命）**

社外・社内を問わず、すべての送信の直前に次の8項目を通す。1つでも通らなければ送らずに止め、食い違い箇所を報告する。照合データの取得不能を「問題なし」にしない。

1. 同じ相手・同じ用件を既に送っていないか（全アカウントの送信済み・依頼台帳）。
2. 他PC・他アカウント・自動再確認タスク（タスクスケジューラ等）に同じ下書き・送信予定が残っていないか。

## 一回にまとめる（人に頼む・刷る・送る・判断を求めるとき）（kim 2026-11-28 指示・全AI共通）

人に何かを頼む・刷る・送る・判断を求めるときは、同じ案件・同じ相手・同じ締切で必要になる作業（直送・控え・別送・追加署名など）を全部洗い出し、1回にまとめる。分けるのは理由があるときだけで、その理由を書く。

- 出す直前に「まとめ確認」をする：(1) 同じ案件で、この後に必要になる印刷・発送・直送・控え・別送・署名・押印・スキャン・提出・窓口訪問 (2) 同じ相手（なっちゃん・古川さん・金さん・顧客・役所など）に今後頼む予定のこと (3) 同じ締切・同じ日・同じ窓口・同じ封筒で済むこと、を台帳・送付書・案件メモ・期限台帳から全部拾う。
- 送付書・指示書・書記官や先方の指示に「直送します」「追って別送」「控え」「写し○部」「署名をもらう」などが書いてあれば、それは今回の作業に含める項目として扱う。
- 判断カード（金さんへの確認）も同じ。同じ案件で金さんに決めてもらうことは1枚にまとめ、「OKならここまで全部やる」と範囲を書く。後から2枚目を出さない。
- 人への依頼（LINE・Discord・メール）は、その1通だけで全部の作業が済む形にする（何を・何部・どの封筒・どこへ・いつまで・控え・追跡番号の報告まで）。
- 分けるのは、材料がまだ揃わない・締切が違う・承認者が違う・相手の負担がかえって増える、など理由があるときだけ。分けるときは理由と、残りをいつ誰がやるかを書く。
- これは役所・法務局への訪問だけの決まりではない。印刷・発送・依頼・判断カード・メール・訪問のすべてに使う。
- 予定ができた訪問・発送・依頼には、同じ窓口・同じ相手・同じ締切でできる用事を乗せる。別の日の外出へ先送りしない（材料不足など、分ける理由を書く場合を除く）。
- 同じ窓口（法務局など）へ行く予定がすでにあるなら、その窓口で取れる用事は別の人の別の外出に振り分けない。余裕が足りないときは、予定の訪問を前倒しして1回にまとめる。

- 受け取りや提出の場でできる記入・番号付け（乙号証の標目など）・スキャン（撮影を含む）・追加署名は、その依頼の1通に含める。事務局の内部作業だとして依頼から外さない。
