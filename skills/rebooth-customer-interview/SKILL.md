# Reブース お客様インタビュー記事 ＋ 掲載打診

目的: 「展示会ブースでゴミを出さない文化」をひろめるため、お客様の声（インタビュー記事）を武器にする。
Reブース案件は **振り返りミーティングのたびに** 記事1本＋打診メール1通を作り、kim の OK 後に送る。

監督（Fable/Opus）は設計・事実確認・レビュー・検証。記事本文とメール本文の起案は Sonnet サブエージェント
（`Agent` model:"sonnet"。プロンプトに「書いて／作って／追加して」を入れると実装ガードに止まるので「起案して保存」と書く）。

## 0. 見本の型を取る

- 見本: https://rebooth.co.jp/reviews/1309/（W2株式会社様）。WebFetch が落ちるときは `curl -sL` で HTML を落としてタグを剥がす。
- 型: H1=お客様の言葉のキャッチ → 社名／担当者・肩書き／[写真] → 前書き（150〜200字）→ Q&A 7〜8問（質問=Re:ブース、回答=お客様）→ [写真]×2 → 関連実績1行。本文 1,800〜2,600 字。
- 見本の質問順: 事業内容 → 依頼の経緯 → 社内外の反応 → 期待した効果 → 成果 → 社内の変化 → 依頼してよかった点 → 今後の期待。
  文字起こしに無い項目は **質問を立てない**（埋めるために作文しない）。

## 1. 一次ソースを特定する（case-consult-sources スキルの順で。既定アカウントの検索だけで「無い」と結論しない）

1. 振り返りミーティングの文字起こし: tldv `search-meetings`（onlyParticipated=false、期間指定）→ Tactiq `search_meetings`（participants に顧客名）→ Drive（Meet 文字起こし Doc）。
   - Tactiq の `get_transcript` は話者名＋秒が付くので検証表に使いやすい。tldv は会議ノートのメールが seisaku-team@ に届く。
   - 会議名は「○○様振り返りMTG」「M:○○様」「反省会」などで揺れる。顧客名で引けないときは期間で全件出して目視する。
2. 担当者名・メール・敬称: `node tools/gmail-search.mjs --query "<顧客名> <担当者名>"`（seisaku-team@ を DWD で検索）。署名から肩書きを取る。
3. 展示会名・会期・会場: 案件フォルダの実施計画書／見積書のタイトル（例 `2601007MED_株式会社メディカルアーツ様 _第9回 メディカル ジャパン 東京`）、主催者からの請求メール、顧客のメルマガ。
4. 見つからないものは「未確認」と書き、照会した経路を列挙する。

## 2. 検証済み引用ブリーフを監督が作る（捏造防止の要）

- 文字起こしから **お客様の発言だけ** を [開始秒-終了秒] 付きで抜き出し、ブリーフ（`brief-<顧客>.md`）に並べる。言い回しの整理は可、意味・数字は変えない。
- オージャスト側の発言（減額再利用、保管、CO2試算 など）は別枠にして「編集部注・質問文にだけ使う」と明記する。
- 記事に使ってよい確定事実（社名・担当者・肩書き・展示会名・会期・会場・小間数・ブースの特徴・振り返り日）を列挙する。
- 数字は文字起こしにあるものだけ（例: リード約350件→商談約10件）。オージャスト側が画面共有した試算値（例: CO2 77%削減）は「オージャスト提示の試算を見て」と前置きしないと使えない。
- お客様が再利用・ゴミ削減に触れていない場合は、Re:ブース側の質問文・前書き・編集部注で説明し、お客様の発言には混ぜない。打診メールで「再利用について一言いただけないか」と添える。

## 3. 記事と打診メールを Sonnet で起案する

- Agent(model:"sonnet", general-purpose) にブリーフと見本テキストのパスを渡す。出力は `article-<顧客>.md`（先頭 `# 見出し`、写真位置は `[写真: 案]`、各回答段落末尾に `<!-- src: 秒-秒 -->`）と `mail-<顧客>.txt`（1行目 `Subject: `、3行目以降本文）。
- 監督レビュー: 各 `<!-- src -->` をブリーフと突き合わせ、根拠のない文は削る。検証表（引用／出典秒／判定）を REPORT に残す。
- 打診メールの骨子（この順）: お打合せのお礼 → サンプル記事リンク「このように掲載されますが、お願いできますでしょうか」（見本 URL 併記）→ 「展示会ブースでゴミを出さない文化をひろめていくため、お客様の声が武器になります」→ 修正・NG箇所は遠慮なく → 社名・お名前・肩書き・写真の掲載可否 → 期限は設けない。400〜650字。

## 4. Google ドキュメント化と共有（Claude Docs・artifact は使わない）

- `node tools/gdoc-create.mjs --file article-<顧客>.md --subject seisaku-team@orgiast.jp --parent <案件の制作フォルダID> --force-new`
  （所有者 seisaku-team@。`<!-- src -->` コメントは Doc に残らないよう、Doc 化前に外した版を渡す。検証用の版は手元に残す）
- お客様が開けるように「リンクを知っている全員が閲覧可」にする: Drive API `permissions.create` に `{type:'anyone', role:'reader'}`（`tools/lib/drive-auth.mjs` の `getDriveToken({impersonate:'seisaku-team@orgiast.jp'})` で実行）。drive-share.mjs は user/group 専用なので使わない。
- read-back: 本文エクスポートで見出しが一致することを確認する。URL は `docs.google.com/a/orgiast.jp/document/d/<ID>/edit`（kim 向け）と素の `docs.google.com/document/d/<ID>/edit`（お客様向け）を分けて書く。

## 5. 下書きは seisaku-team@ の Gmail に作る（送信は kim の OK 後）

- `node tools/gmail-draft.mjs --to <顧客メール> [--cc <同席者>] --subject "<件名>" --body-file mail-<顧客>.txt`（DWD 経路。kim@ 名義の Gmail MCP は使わない）。
- 作成前に `node tools/gmail-search.mjs --query "<顧客メール> インタビュー OR 掲載"` で同じ趣旨の既送信・矛盾がないか見る。
- **夜間・無人では送らない**。kim が「送って」と返したら `node tools/gmail-draft.mjs --send <draftId>`。送ったら本文全文をチャットに再掲する。

## 6. 報告

- `node tools/notify-kim.mjs --kim-action-required "<本文>"` で DM。本文: 記事 Doc リンク（アカウント併記）／下書きの宛先・件名／「OK なら『送って』と返信」。
- 【kim 確認用の全文】（メール全文・記事要旨・引用検証表・未確認事項）を REPORT.md 等に残し、遡らせない。

## 禁止

- 文字起こしにない発言・数字を書く。お客様の感想を推測で補う。
- kim の承認前に外部へ送る。Claude Docs / artifact に記事を置く。
- サブエージェントに Fable を指定する。
