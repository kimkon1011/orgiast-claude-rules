# 要件を凍結してから実装する

## Phase 0 — 凍結原則

**要件が固まるまでコードを1行も書かない。ファイルを作らない。Codex に委譲しない。**

例外は、要件を固めるための読み取り専用の調査だけ。既存コードの確認、Web 検索、既存資産の有無確認は実施してよい。最初に `rg -n "<機能名|業務語>" .` と `rg --files` で類似実装を探し、車輪の再発明を避ける。指示書の再利用が見込める場合は `node ~/orgiast-claude-rules/tools/makimono-search.mjs "<キーワード>"` も検討する。

## Phase 1 — 一問一答ヒアリング

1. 1ターンにつき質問は1つだけ出す。複数の論点を一度に聞かない。
2. 選択式を優先し、`AskUserQuestion` が使えるなら使う。使えない環境では本文に番号付き選択肢を書き、1つ選んでもらう。
3. 各質問に「既定値（推奨）」を必ず添え、分からなければそれを選べば進める状態にする。
4. 次の質問バンクを上から確認し、すでに確定している項目は聞かずに飛ばす。
   1. 何を達成したいか（目的を1文で）
   2. 誰が使うか（kim 本人 / 社内スタッフ / 顧客 / 無人ジョブ）
   3. 入力は何で、どこから来るか（ファイル / API / 手入力 / 既存シート）
   4. 出力は何で、どこへ出るか（画面 / md / Discord / Gmail 下書き / DB）
   5. 実行環境と制約（どのPC / OS / 定期実行か / 認証の有無）
   6. 成功条件（第三者が見て真偽を判定できる客観的な1文）
   7. 非目標（今回やらないこと）
5. 成功条件が観測対象・期待値・判定方法を含まず曖昧なら、客観的な1文になるまでその項目を聞き直す。
6. 各回答の後に、ここまでの回答を箇条書きの「確定事項」として本文に書き出し、認識ズレがないか見せてから次の1問へ進む。
7. 残った未確定事項が実装内容を変える分岐に影響しなくなった時点で打ち切る。目安は5〜9問。10問を超えたら実装分岐に直結する質問だけに絞り、残りは既定値を採用して手順書の「前提」に明記する。

## Phase 2 — 3案 + 推奨案

必ず構造の違う3案を出す。「同じ実装の小・中・大」にはせず、たとえば「既存に乗せる / 新規に作る / 手作業のまま自動化しない」のように方式を変える。次の列を持つ表で比較する。

| 案 | 概要 | 工数感 | リスク | 拡張性 | 運用コスト | user の手作業回数 |
|---|---|---|---|---|---|---|
| A |  |  | 起きたら何が壊れるか |  |  | 0回など数字で記載 |
| B |  |  | 起きたら何が壊れるか |  |  | 数字で記載 |
| C |  |  | 起きたら何が壊れるか |  |  | 数字で記載 |

user の手作業回数は初期設定時と通常運用1回あたりを区別できる場合は両方を数字で書く。表の後に推奨案を1つ選び、「なぜそれか」を3行以内で書く。選ばなかった2案も、却下理由を各1行で書く。

## Phase 3 — 実装手順書を md で出力

リポジトリ内の作業は `docs/plans/<slug>.md`、リポジトリ外のローカル運用は `~/.claude/plans/<slug>.md` に、次の固定テンプレで出力する。

```md
# <タイトル>
## 1. 目的 / 成功条件（客観的に判定できる形で）
## 2. スコープ外（今回やらないこと）
## 3. 前提・確定事項（Phase 1 の結果）
## 4. 採用案と却下案（Phase 2 の結果）
## 5. 実装手順（番号付き。各ステップに「完了条件」を必ず付ける）
## 6. 検証方法（実行するコマンドと、期待する出力をそのまま書く）
## 7. ロールバック手順
## 8. 残TODO / 次回への引き継ぎ
```

セクション5は番号付き手順にし、各ステップへ「完了条件: ...」を付ける。セクション6には `node --test ...`、`npm run typecheck`、`curl ...` など実際に打つコマンドと期待する終了コード・出力・値をそのまま書く。「動作確認する」だけの行は禁止する。

出力後は md のパスを提示して承認を求める。承認を得るまで Phase 4 に進まず、コードや設定ファイルを変更しない。

Codexへ渡す指示ファイルは`protocols/HANDOFF.md`の見出しを使う。

## Phase 4 — 承認後

承認を得たら実装に入る。実装中に要件が変わった場合は、正本である実装手順書を先に更新し、変更点の承認を得てからコードを変更する。完了判定はセクション6に記載した検証コマンドを実際に実行し、期待結果と一致したかで行う。

## 移植性

この skill は Claude Code 専用の道具に依存させない。`AskUserQuestion` などは使える場合だけ使い、使えない環境では本文の選択肢で代替する。Antigravity 等の他エージェントでも、本文の4フェーズをそのままプロンプトとして貼れば同じ流れを再現できるようにする。
